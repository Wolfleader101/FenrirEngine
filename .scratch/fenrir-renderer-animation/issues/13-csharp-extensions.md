## Comments

Built 2026-10-30 on `claude/vibrant-bassi-1f0d60` (ticket 12, PR #248, not merged yet), as a stacked PR. Decisions to review:

- **Hosting through the App.** A scripting extension reaches FenrirSkeleton through the App, not its owner, so `Skeletons` gained static `HostAnimate`, `HostModifier`, `HostLate`, `HostPassEnd` and `RemoveHosted(App&, …)`, finding the install through a private app resource. Hosted work runs after the owner's at an equal order whichever was added first (a tie-break in the stage list), so "C++ first" holds even for C++ work added after the script loaded. `HostPassEnd` runs when each pass returns (frame and tick), outside the pipeline: the extension plays the stage changes back there, so `Detach` and `SpawnModel` from a stage system run after the pass. FenrirSkeleton must be installed before Scripting for its stages to be placed (logged once at Info if not); AnimationDemo does so through a new `DemoConfig::installPackages` hook in the scaffold, which keeps the owners and destroys them after Scripting and before its own packages.
- **`ChangeBuffer::RecordCall`** (FenrirScripting, beyond "generators only"): a public way to run a package's own structural function at playback. The skeleton extension's `Detach` and `SpawnModel` and the renderer's `SpawnModel` use it. `Detach` returns what it can tell at once (`NotAttached`, `InvalidParent` for a dead parent) and `Detached` when recorded; a refusal at playback changes nothing and is logged.
- **The renderer's C# `SpawnModel`** now records `SkinnedMesh` with its skeleton remapped to the recorded owner, and at playback gives the recorded entities their `SkeletonPose`s and bone attachments through the skinning source's `SpawnSkeletons` (FenrirRendererScripting still knows nothing of FenrirSkeleton). It spawns through a new `Fenrir::SpawnModelNodes`, `SpawnModel` returning every node's entity, so the nodes can be followed into the recorded tree.
- **Edit tokens.** The extension holds the running `Modify` group's context and a token advanced as each group starts and ends; a `PoseEdit`'s calls reopen the C++ edit for that call. A kept token, or `Edit` outside `Modify`, writes nothing and warns once.
- **Bindings, no generator change.** Natives taking an entity or handle pointer before an `int` bone mark it `@param[in]`, so the generator does not read the pair as a span. Inside the `Fenrir.Skeleton` namespace `Skeleton` is the namespace, so FenrirAssets's binding names the marker `AssetHandle<global::Fenrir.Assets.Skeleton>`. `BoneName`'s buffer is a private fixed buffer behind a hand-written `Set` (refusing over 255 bytes or a zero, logged through `Log.Error`) and `Get`. `ClipEventId` is an immutable struct with a hand-written `Of`. `MaskScope` is mirrored in `Fenrir.Animation`, where the mask natives take it.
- **FenrirAssets's C# markers** `Skeleton`, `Clip` and `BoneMask` work with `Assets.Load`, `Unload` and `IsValid` too (the kind-generic natives' dispatch gained them), so a clip loads by label, `walk_loop.glb#Clip0`.
- **Scenes 8 and 9** are C# (`examples/AnimationDemo/scripts/`); C++ gives each its floor and sun. The fixture assemblies name entities by id through `Entity`'s internal constructor, and the skeleton fixture calls the pose edit's internal natives to keep a token, so `Fenrir.Scripting` and `Fenrir.Skeleton` grant them `InternalsVisibleTo`.

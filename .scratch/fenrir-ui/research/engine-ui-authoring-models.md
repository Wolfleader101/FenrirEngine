# How game engines and UI middleware author and render gameplay UI

Research note, 2026-11-10. Question: how do current engines and game-UI middleware let an ordinary software developer (web, desktop, mobile background) author gameplay UI that feels modern, and what do their rendering contracts hand the renderer? Seven systems are compared on six facets (authoring, layout, styling, data flow and events, rendering contract, scripting fit). Every claim cites a primary source: official documentation or source code. Where a page could not be reached or does not say, this note says so rather than guessing.

## Summary

1. Every retained system here is the same machine: a tree of elements, a layout pass, a style-resolution pass, a paint pass that emits batched triangles under a scissor or stencil stack, and a text path that shapes and rasterises glyphs into an atlas. They differ in which parts are exposed to the developer and in which language.
2. Three of the seven adopted web vocabulary on purpose: Unity UI Toolkit (UXML/USS/flexbox via Yoga), RmlUi (RML/RCSS, its own CSS2-based layout) and Gameface (real HTML/CSS/JS on V8, flex-only layout). Noesis adopted WPF (XAML, Measure/Arrange, styles, templates, bindings). Unreal and Godot kept engine-native models (Slate slots and UMG anchors; Control anchors and Containers plus Theme resources).
3. Unity's stated reason for UI Toolkit is separation of structure, style and logic "similar to how you might with HTML, CSS, and JavaScript" for collaboration, reuse and faster iteration, in a retained-mode tree; the compare page still lists uGUI as the default runtime recommendation and UI Toolkit as the alternative for multi-resolution, textureless, data-bound UI.
4. Layout engines: Yoga flexbox (Unity, and Gameface's compatibility mode), WPF Measure/Arrange (Noesis), Slate prepass/arrange with desired sizes (Unreal), anchors+Containers (Godot), own CSS block/inline/flex/table engine (RmlUi), flexbox-like fit/grow/fixed/percent (Clay). Units are pixels everywhere, with a scale factor layered on top: Unity PanelSettings scale modes, Unreal's DPI curve, Godot's stretch modes, RmlUi's `dp` ratio, Noesis's Viewbox.
5. Styling ranges from stylesheets with selectors, variables and transitions (USS, RCSS, Gameface CSS) through XAML styles/templates/triggers (Noesis) to typed style assets (Unreal FSlateStyleSet, CommonUI style assets) and theme resources keyed by control type (Godot Theme). Hot reload is documented for Noesis (XAML, textures, fonts), RmlUi (`ReloadStyleSheet`) and Unity (UI Builder live authoring); Godot's theme editor previews live but needs a reload for scene changes.
6. Data flow: observable bindings exist in Unity (`DataBinding`, four modes, `INotifyBindablePropertyChanged`), Noesis (WPF `Binding`, `INotifyPropertyChanged`), Unreal's Viewmodel plugin (FieldNotify), RmlUi (data models dirtied by name) and Gameface (`data-bind-*`, `SynchronizeModels`). Unreal's classic `TAttribute` bindings poll every frame and Epic says never to use them raw.
7. Events bubble in every retained system; Unity, Noesis and RmlUi also run a capture/trickle-down (Noesis: tunnelling "preview") phase. Gamepad focus navigation is first class in Unity (navigation events, focus ring), Unreal (FNavigationConfig, CommonUI action routing to the topmost active tree), Godot (focus neighbours, `ui_*` actions), Noesis (`KeyboardNavigation.DirectionalNavigation`) and RmlUi (`nav-*` properties). Dear ImGui has gamepad nav but says it is not designed for game UI and has no accessibility.
8. Rendering contracts split into two families. "Give me triangles": Slate batches `FSlateDrawElement`s into `FSlateVertex` arrays per shader type; Unity's `UIRenderDevice` allocates vertex pages and kicks ranges with material, texture-slot and stencil state; RmlUi's `RenderInterface` compiles indexed `Vertex{position, premultiplied colour, tex_coord}`; Dear ImGui and Clay emit command lists. "Implement my device": Noesis `RenderDevice` (a fixed set of shader permutations, `Batch` with stencil ref and uniforms, offscreen pass) and Gameface's `renoir::RendererBackend` (resources, pipeline states, `ExecuteRendering` of recorded command buffers). Godot keeps commands server-side and batches them in its own renderer.
9. Text: HarfBuzz shaping appears in Unity's Advanced Text Generator (HarfBuzz, ICU, FreeType), Slate's `FSlateTextShaper` (FreeType + HarfBuzz), Godot's TextServerAdvanced (ICU/HarfBuzz/Graphite, BiDi) and Gameface (HarfBuzz for GPOS kerning, ICU for complex text). Glyphs land in atlases: SDF in Unity, Noesis 3.0 and Gameface; Slate has grayscale, colour, SDF and MSDF font shaders; Godot offers bitmap, MSDF and LCD modes; RmlUi's default FreeType engine returns textured meshes.
10. Scripting fit: Unity is managed throughout (C# over a native renderer/layout core via bindings); Noesis is native with a P/Invoke C# SDK whose `RenderDevice` can be subclassed in C#; Godot's C# talks to the C++ core through interop calls with marshalling cost; Unreal exposes Slate to Blueprints via UMG `UWidget` wrappers; RmlUi is C++ with a Lua plugin; Gameface is JS-first with C++ binding. A C#-optional engine would keep layout, style resolution, painting and text shaping native and expose a tree, a binding surface and a plain-data draw list.

## 1. Unity UI Toolkit

### a. Authoring model

UI Toolkit is Unity's "latest UI system, designed for optimized performance across platforms and inspired by standard web technologies"; structure is authored "with either UXML or C#", style "with USS", and the UI Builder is "a visual authoring tool to create and edit UI Toolkit assets such as UXML and USS files" ([UI Toolkit overview](https://docs.unity.com/en-us/engine/current/manual/uitoolkits/uielements)). The best-practice guide states the goal: "you can separate the structure, style, and behavior of your UI, similar to how you might with HTML, CSS, and JavaScript", with UXML "a markup language inspired by HTML and XML that defines UI structure and reusable templates", and "While you can build UI in C#, using UXML is recommended"; benefits listed are "Better collaboration", "Reusability" and "Faster iteration ... with global style management and live authoring capabilities" ([Introduction to UI Toolkit](https://docs.unity.com/en-us/engine/6000.7/manual/best-practice-guides/bpg-uiad-index/introduction-to-ui-toolkit)). The same page states the mode: "UI Toolkit operates in a retained mode architecture, which means the UI builds a hierarchical structure and maintains it in memory ... You declare the UI structure once, UI Toolkit takes care of rendering and updates based on the changes to the tree."

A reusable widget is a `partial class` deriving from `VisualElement` marked `[UxmlElement]`, with a parameterless constructor, either "UXML-first" (the control's children are declared in a `.uxml` and the file is used as a template) or "element-first" (the constructor calls `asset.CloneTree(this)`); other documents instantiate it with `<ui:Template name="CardElement" src="CardElement.uxml"/>` plus `<ui:Instance template="CardElement"/>`, or from C# with `VisualTreeAsset.Instantiate()` and `Q<CardElement>()`. The recommended split is "UXML for structure, USS for appearance, and C# for logic" ([Encapsulate UXML documents with logic](https://docs.unity.com/en-us/engine/6000.6/manual/uitoolkits/uielements/uie-structure-ui/uie-encapsulate-uxml-with-logic)). UI Builder "lets you visually create and edit UI assets, such as UI Documents (.uxml), and StyleSheets (.uss)" ([UI Builder](https://docs.unity.com/en-us/engine/current/manual/uitoolkits/uielements/uibuilder)). A 2022 Unity blog post adds that "UI Builder is not meant for event management, nor is the UXML document": behaviour lives in C# ([UI Toolkit at runtime: Get the breakdown](https://unity.com/blog/engine-platform/ui-toolkit-at-runtime-get-the-breakdown)).

Why Unity moved from uGUI: the compare page lists what only UI Toolkit offers at runtime ("data binding system, UI transition animations, textureless elements, advanced flexible layout, global style management, dynamic texture atlas, UI anti-aliasing, right-to-left language and emoji, SVG support"), what only uGUI offers ("in-scene authoring, serialized events, integration with Animation Clips and Timeline"), and still recommends uGUI as the runtime default with UI Toolkit as the "alternative" for "a screen overlay UI that runs on a wide variety of screen resolutions", for projects with many interfaces, "Textureless UI rendering", world-space UI and custom shaders; for the editor it recommends UI Toolkit for "Better reusability and decoupling", "Visual tools for authoring UI" and "Better scalability for code maintenance and performance" ([Comparison of UI systems in Unity](https://docs.unity.com/en-us/engine/current/manual/uitoolkits/ui-system-compare)). The blog post frames the runtime motive as workflow: artists edit UXML/USS while C# handles logic, which "improves collaboration between artists and developers", and a scene needs "one UXML file linked to a UI Document" instead of "a single Canvas with dozens of GameObjects" ([blog](https://unity.com/blog/engine-platform/ui-toolkit-at-runtime-get-the-breakdown)).

### b. Layout

"UI Toolkit's layout engine uses the layout principles of Yoga, which implements a subset of Flexbox"; "UI Toolkit supports most properties in Flexbox". Defaults differ from browsers: the default `flex-direction` is `column` ("A container distributes its children vertically"), `flex-basis` defaults to `auto`, and `left/top/right/bottom` are offsets from the parent's edges (setting both `left` and `right` overrides `width`) ([Layout engine](https://docs.unity.com/en-us/engine/current/manual/uitoolkits/uielements/uie-uss/properties/uie-layout-engine)). Yoga itself "is an embeddable layout system used in popular UI frameworks like React Native", whose "only responsibility is determining the size and position of boxes"; it "is not a UI framework, and does not do any drawing itself" ([About Yoga](https://www.yogalayout.dev/docs/about-yoga)). In the C# reference source the layout bindings carry `[NativeHeader("External/Yoga/LayoutNative.h")]` and expose `extern` `CalculateLayout` and `MeasureNode` plus grid-track helpers, so the flexbox solver (and a CSS-grid track sizer) runs natively ([LayoutNative.bindings.cs](https://github.com/Unity-Technologies/UnityCsReference/blob/master/Modules/UIElements/Core/Layout/Native/LayoutNative.bindings.cs)); `LayoutNode.CalculateLayout` is documented as "Performs the flexbox layout calculation" and `Measure` is "used by higher-level track sizing, such as CSS Grid" ([LayoutNode.cs](https://github.com/Unity-Technologies/UnityCsReference/blob/master/Modules/UIElements/Core/Layout/LayoutNode.cs)).

Units and scaling: a `PanelSettings` asset chooses `Scale Mode`: "Constant Pixel Size" (a `Scale` multiplier), "Constant Physical Size" ("Reference DPI ... The UI scales when the actual screen DPI differs", with a "Fallback DPI") or "Scale with Screen Size" ("Reference Resolution" plus "Screen Match Mode": Match Width or Height with a blend value, Shrink, or Expand) ([Panel Settings](https://docs.unity.com/en-us/engine/current/manual/uitoolkits/uielements/uie-support-for-runtime-ui/uie-render-runtime-ui/uie-runtime-panel-settings)). Lengths in the docs are in px and percent; the layout page's examples use `100px`-style values ([Layout engine](https://docs.unity.com/en-us/engine/current/manual/uitoolkits/uielements/uie-uss/properties/uie-layout-engine)).

### c. Styling

USS "is inspired by Cascading Style Sheets (CSS) from HTML"; "USS syntax is the same as CSS syntax, but USS includes overrides and customizations to work better with Unity" ([USS](https://docs.unity.com/en-us/engine/current/manual/uitoolkits/uielements/uie-uss)). Selectors: type, name, class, universal, descendant, child, multiple (compound) selectors, selector lists and pseudo-classes; they are "analogous, but not identical, to simple selectors in CSS" ([USS selectors](https://docs.unity.com/en-us/engine/current/manual/uitoolkits/uielements/uie-uss/selectors)). Pseudo-classes are `:hover`, `:active`, `:inactive`, `:focus`, `:disabled`, `:enabled`, `:checked`, `:root`; `:selected` is not supported ("Use `:checked` instead"), and pseudo-classes chain (`Toggle:checked:hover`) ([USS pseudo-classes](https://docs.unity.com/en-us/engine/6000.6/manual/uitoolkits/uielements/uie-uss/selectors/pseudo-classes)). Variables: "To create a USS variable, prefix its name with a double-hyphen (`--`)", use `var()`, with an optional fallback ("The UI system uses the default value when it cannot resolve the variable"); USS "doesn't support the `var()` function inside of other functions" and "doesn't support mathematical operations on variables" ([Create USS variables](https://docs.unity.com/en-us/engine/6000.0/manual/uitoolkits/uielements/uie-uss/variables/custom-properties)). Transitions mirror CSS (`transition-property/duration/timing-function/delay`), with fully animatable, discrete and non-animatable properties, a fast path for colour properties, and a recommendation to animate transform properties (`scale`, `rotate`, `translate`) because others "can trigger layout recalculations"; the page does not mention keyframe animations ([USS transitions](https://docs.unity.com/en-us/engine/current/manual/uitoolkits/uielements/uie-uss/properties/uie-transitions)). Hot reload: the best-practice guide lists "live authoring capabilities", and the reference source has `ILiveReloadSystem.cs` and `ILiveReloadAssetTracker.cs` in the core module ([Modules/UIElements/Core listing](https://github.com/Unity-Technologies/UnityCsReference/tree/master/Modules/UIElements/Core)).

### d. Data flow and events

Runtime data binding "binds properties of any plain C# object to UI Toolkit controls"; for serialised editor data Unity recommends `SerializedObject` binding instead ([Runtime data binding](https://docs.unity.com/en-us/engine/current/manual/uitoolkits/uielements/uie-data-binding/uie-runtime-binding)). `DataBinding.bindingMode` is one of `TwoWay` (default: "Changes are replicated from the data source to the UI and from the UI to the data source"), `ToTarget`, `ToSource` and `ToTargetOnce` ("replicated from the data source to the UI only once, unless it's marked as dirty"); `updateTrigger` chooses every frame, on change detection ("or every frame if change detection isn't possible"), or when `MarkDirty` is called ([Define binding mode and update trigger](https://docs.unity.com/en-us/engine/6000.7/manual/uitoolkits/uielements/uie-data-binding/uie-runtime-binding/mode-update)). The reference source's `Bindings` directory and `BindableElement.cs` hold the implementation ([Modules/UIElements/Core listing](https://github.com/Unity-Technologies/UnityCsReference/tree/master/Modules/UIElements/Core)).

Events: "The event system listens for events that come from the operating system or scripts, then uses the EventDispatcher to dispatch those events to visual elements." Propagation has a trickle-down phase ("The path starts at the root of the visual element tree and descends towards the target") and a bubble-up phase; "Every element in the propagation path, including the target, receives the event twice", and callbacks registered with `TrickleDown.TrickleDown` run before the default bubble-up ones. Pointer targets use `PickingMode.Position` by default, and `VisualElement.ContainsPoint()` can be overridden for custom shapes ([Dispatch events](https://docs.unity.com/en-us/engine/current/manual/uitoolkits/uielements/uie-events/dispatching)).

Focus and gamepad: `focusable`, `tabIndex`, `delegatesFocus`, `Focus()`/`Blur()`; "Each panel has a focus ring" implemented by `IFocusRing`, which "walks the visual tree depth-first" by default, and a `FocusController` that queues focus changes until "the current event callback has finished executing" ([Focus system](https://docs.unity3d.com/6000.2/Documentation/Manual/UIE-focus-order.html)). `NavigationMoveEvent` (with `direction` and an analog `move` vector), `NavigationSubmitEvent` and `NavigationCancelEvent` "occur at runtime when the user presses the D-pad, moves a joystick, or presses the Escape, Enter or arrow keys" and "aren't limited to a specific input device"; a control that handles one "cancels the event, preventing it from entering the bubble-up phase" ([Navigation events](https://docs.unity.com/en-us/engine/6000.6/manual/uitoolkits/uielements/uie-events/reference/uie-navigation-events)).

Input routing: "When you enter Play mode, UI Toolkit creates a default event system that is not part of any scene"; it "can receive events from both input systems" (legacy Input Manager axes or the Input System package's `UI/Point`, `UI/Click`, `UI/ScrollWheel` and navigation actions). With a uGUI `EventSystem` present, UI Toolkit creates a `PanelRaycaster` and `PanelEventHandler` per panel and "relies on these components to handle input events"; "A pointer event propagates through the panels until a panel responds to it" ([Runtime UI event system](https://docs.unity.com/en-us/engine/6000.5/manual/uitoolkits/uielements/uie-support-for-runtime-ui/uie-render-runtime-ui/uie-runtime-event-system)). The pages read do not document a dedicated "is the pointer over UI" query for gameplay; this note does not claim one.

### e. Rendering contract

Rendering is "a rendering system built directly on top of Unity's graphics device layer" ([overview](https://docs.unity.com/en-us/engine/current/manual/uitoolkits/uielements)). Custom geometry: "Visual content is generated by using the Painter2D object, or manually by allocating a mesh using the MeshGenerationContext.Allocate method and then filling the vertices and indices"; `Allocate(vertexCount, indexCount, texture)` returns a `MeshWriteData` filled with `SetAllVertices`/`SetAllIndices`, and "UI Toolkit might store the texture in an internal atlas"; other members are `DrawText`, `DrawVectorImage`, `DrawMesh`, `AllocateTempMesh` and job-system hooks (`AddMeshGenerationJob`, `InsertMeshGenerationNode`) ([MeshGenerationContext](https://docs.unity.com/en-us/engine/current/script-reference/unityengine/uielements/meshgenerationcontext)). `Painter2D` is an "Object to draw 2D vector graphics" with a canvas-like path API (`BeginPath`, `MoveTo`, `LineTo`, `Arc`, `ArcTo`, `BezierCurveTo`, `QuadraticCurveTo`, `ClosePath`, `Fill`, `Stroke`, `PushClip`/`PopClip`, dash patterns, gradients and `fillTexture`) and can `SaveToVectorImage` ([Painter2D](https://docs.unity.com/en-us/engine/current/script-reference/unityengine/uielements/painter2d)).

Under the managed API the work is native. `Painter2D` forwards to a static `UIPainter2D` class with an opaque native handle; in attached mode `Stroke`/`Fill` take a native snapshot and a `Painter2DJob : IJobParallelFor` calls `UIPainter2D.ExecuteSnapshotFromJob`; the header comments describe strokes as triangle strips "inflated by `k_EdgeBuffer` pixels" (the anti-aliasing margin), fills tessellated through LibTess, gradients baked into a 64x1 lookup texture, and `PushClip` warned as "very expensive, as it involves per-triangle clipping on the CPU" and losing antialiased edges ([UIRPainter2D.cs](https://github.com/Unity-Technologies/UnityCsReference/blob/master/Modules/UIElements/Core/Renderer/UIRPainter2D.cs)). `UIPainter2D.bindings.cs` declares `extern Create/BeginPath/MoveTo/LineTo/Arc/Fill/Stroke/PushClip/...` against `Modules/UIElements/Core/Native/Renderer/UIPainter2D.bindings.h` ([UIPainter2D.bindings.cs](https://github.com/Unity-Technologies/UnityCsReference/blob/master/Modules/UIElements/Core/Native/Renderer/UIPainter2D.bindings.cs)); `MeshBuilderNative` exposes `MakeBorder` (per-side colours, widths and four corner radii), `MakeSolidRect`, `MakeTexturedRect` (texture, sprite, 9-slice), `MakeBoxShadow` (offset, blur and spread radii, corner radii, inset) and two vector-graphics builders, all `[NativeMethod(IsThreadSafe = true)]` ([UIRMeshBuilder.bindings.cs](https://github.com/Unity-Technologies/UnityCsReference/blob/master/Modules/UIElements/Core/Native/Renderer/UIRMeshBuilder.bindings.cs)).

The per-frame GPU contract is `UIRenderDevice`. Its vertex declaration is Position (float3), Color (UNorm8x4), TexCoord0 (float4: UV in xy, layout UV in zw), TexCoord4 (uint4 flags and IDs), TexCoord5 (float4 circle-arc data or text extra-dilate), plus optional "extras" channels whose "order must match UIRUtility.k_ExtrasChannelOrder". Vertices live in pages (`maxVerticesPerPage` 0xFFFF because "On DX11, 0xFFFF is an invalid index"), with mesh managers chosen per platform and frees deferred "until frame rendering completes" behind GPU fences. Draws come from a linked list of `RenderChainCommand`s: consecutive draws sharing a page, material, texture slots and stencil state merge into `DrawBufferRange`s that are kicked to a `CommandList` (nested or world-space rendering) or the native `Utility.DrawRanges(...)`; texture slots are 1, 2, 4 or 8 per batch via shader keywords, and a stencil `IncrementSaturate`/`DecrementSaturate` push/pop plus a scissor stack (`PushScissor`/`PopScissor`, a scissor change kicks the batch) handle clipping; shader keywords select solid, textured, text and SVG-gradient variants, and gradient and shader-info textures are bound per chain ([UIRenderDevice.cs](https://github.com/Unity-Technologies/UnityCsReference/blob/master/Modules/UIElements/Core/Renderer/UIRenderer/UIRenderDevice.cs)). `UIRUtility` fixes `k_MaxMaskDepth = 7; // Requires 3 bits in the stencil` ([UIRUtility.cs](https://github.com/Unity-Technologies/UnityCsReference/blob/master/Modules/UIElements/Core/Renderer/UIRUtility.cs)). The manual confirms the split: "When masking with rectangle shapes, Unity uses axis-aligned rectangles as the clipping region, this is called rectangle clipping. When masking with rounded corners or arbitrary shapes, Unity uses stencil masking", nested masks break batching, `UsageHints.MaskContainer` reduces it, and "UI Toolkit requires depth and stencil buffers to properly support masking and nesting" ([USS masking](https://docs.unity.com/en-us/engine/6000.6/manual/uitoolkits/uielements/uie-uss/uie-masking)). The renderer directory also holds `UIRBoxShadowProfile.cs`, `UIRCurvatureGeometry.cs`, `UIRAtlasManager.cs`, `UIRDynamicAtlasPage.cs`, `UIRGradientSettingsAtlas.cs`, `UIRBackdropReadRegions.cs` and `UIRVectorImageManager.cs` ([Renderer listing](https://github.com/Unity-Technologies/UnityCsReference/tree/master/Modules/UIElements/Core/Renderer)).

Text: "UI Toolkit uses Advanced Text Generator to render text, a text rendering module that uses Harfbuzz, ICU, and FreeType to deliver comprehensive Unicode support and text shaping capabilities"; font assets are created as "Font Asset > SDF", "the font atlas is dynamically generated as you enter text", and static font assets are not supported ([Get started with text](https://docs.unity.com/en-us/engine/6000.5/manual/uitoolkits/uielements/uie-work-with-text/uie-get-started-with-text); [Advanced Text Generator](https://docs.unity.com/en-us/engine/6000.3/manual/uitoolkits/uielements/uie-work-with-text/uie-advanced-text-generator)). The compare page lists "UI anti-aliasing", "textureless elements" and "dynamic texture atlas" as UI Toolkit-only runtime features ([compare](https://docs.unity.com/en-us/engine/current/manual/uitoolkits/ui-system-compare)).

Render targets and world space: a Screen Space Overlay panel can render to a `Target Texture`, and World Space render mode adds colliders; `backdrop-filter` works only in Screen Space Overlay ([Panel Settings](https://docs.unity.com/en-us/engine/current/manual/uitoolkits/uielements/uie-support-for-runtime-ui/uie-render-runtime-ui/uie-runtime-panel-settings)). In World Space, "Pixels Per Unit" (default 100) maps panel pixels to world units, a Panel Renderer has Dynamic or Fixed size modes and a pivot, "the z-distance from the camera determines the sorting order of root Panel Renderers", and "Integration with 2D sorting layers isn't currently supported" ([Create a World Space UI](https://docs.unity.com/en-us/engine/6000.6/manual/uitoolkits/uielements/uie-support-for-runtime-ui/world-space-ui/create)).

Relative to FenrirDraw2D: Unity's `MeshWriteData` plus texture is the same shape as a `DrawList2D` vertex/index append with a texture slot, but Unity adds per-vertex flags/IDs for shader-side transform, clip, opacity and colour pages, and uses stencil rather than scissor for non-rectangular masks.

### f. Scripting fit

The whole public surface is C# (`VisualElement`, USS parsing, events, bindings, `Painter2D`), but the module's `Native` directory binds the layout solver (`LayoutNative.bindings.cs`), text (`TextNative.bindings.cs`), the painter (`UIPainter2D.bindings.cs`), mesh building (`UIRMeshBuilder.bindings.cs`) and the renderer (`UIRenderer.bindings.cs`, `PanelRenderer.bindings.cs`, `UIRendererJobProcessor.bindings.cs`) ([Native listing](https://github.com/Unity-Technologies/UnityCsReference/tree/master/Modules/UIElements/Core/Native); [Native/Renderer listing](https://github.com/Unity-Technologies/UnityCsReference/tree/master/Modules/UIElements/Core/Native/Renderer)). So the tree, style cascade, event dispatch and binding system are managed, while layout solving, tessellation, text shaping and draw submission are native. A C#-optional engine copying this would keep exactly those native parts and could keep the tree native too.

## 2. Unreal UMG and Slate

### a. Authoring model

Slate "is a completely custom and platform agnostic user interface framework" with "A complete set of macros ... to simplify the process of declaring and creating new widgets"; composition nests slots with `SNew` and `+ SVerticalBox::Slot()` chaining, which "makes it simple to re-arrange UI elements quickly for prototyping and iteration" ([Slate Overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/slate-overview-for-unreal-engine)). In source: "Slate widgets are constructed through SNew and SAssignNew", `SLATE_BEGIN_ARGS`/`SLATE_END_ARGS` add "support for widget construction via SNew and SAssignNew", `SLATE_ATTRIBUTE` adds "a attribute to the declaration of your widget. An attribute can be a value or a function", `SLATE_ARGUMENT`s "can only be values", `SLATE_SLOT_ARGUMENT`/`SLATE_DEFAULT_SLOT` add slots, and `SLATE_EVENT` adds "event handler support to the declarative syntax" ([DeclarativeSyntaxSupport.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Source/Runtime/SlateCore/Public/Widgets/DeclarativeSyntaxSupport.h)). Widget authors are told "STOP. DO NOT INHERIT DIRECTLY FROM WIDGET! ... consider inheriting from LeafWidget or Panel" ([SWidget.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Source/Runtime/SlateCore/Public/Widgets/SWidget.h)); "A CompoundWidget is the base from which most non-primitive widgets should be built. CompoundWidgets have a protected member named ChildSlot" ([SCompoundWidget.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Source/Runtime/SlateCore/Public/Widgets/SCompoundWidget.h)); "A LeafWidget is a Widget that has no slots for children" ([SLeafWidget.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Source/Runtime/SlateCore/Public/Widgets/SLeafWidget.h)); "A Panel arranges its child widgets on the screen. Each child widget should be stored in a Slot" ([SPanel.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Source/Runtime/SlateCore/Public/Widgets/SPanel.h)).

UMG is "a visual UI authoring tool which can be used to create UI elements such as in-game HUDs, menus"; a Widget Blueprint has a Designer tab for "the visual layout of the interface and basic functions" and a Graph tab that "provides the functionality behind the Widgets used" ([UMG UI Designer User Guide](https://dev.epicgames.com/documentation/en-us/unreal-engine/umg-ui-designer-user-guide?application_version=4.27)). `UWidget` "is the base class for all wrapped Slate controls that are exposed to UObjects", each implementing `RebuildWidget()` "when the underlying SWidget needs to be constructed" ([Widget.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Source/Runtime/UMG/Public/Components/Widget.h)); `UUserWidget` is "A widget that enables UI extensibility through WidgetBlueprint" with `NativeConstruct`/`NativeTick` hooks and `AddToViewport(ZOrder)` ([UserWidget.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Source/Runtime/UMG/Public/Blueprint/UserWidget.h)). Pure-Slate game UI goes through `GEngine->GameViewport->AddViewportWidgetContent(SNew(...))` ([Using Slate In-Game](https://dev.epicgames.com/documentation/en-us/unreal-engine/using-slate-in-game?application_version=4.27)).

Mode: retained with invalidation. "Invalidation caches Slate widgets' information, then monitors them for changes"; Invalidation Boxes, Global Invalidation and Retainer Panels cache, and "Widgets that change on a frame-by-frame basis should be marked as Volatile" ([Optimization Guidelines for UMG](https://dev.epicgames.com/documentation/en-us/unreal-engine/optimization-guidelines-for-umg-in-unreal-engine)). `EInvalidateWidgetReason` distinguishes `Layout` ("if your widget needs to change desired size. This is an expensive invalidation"), `Paint`, `Volatility` and `ChildOrder` ([InvalidateWidgetReason.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Source/Runtime/SlateCore/Public/Widgets/InvalidateWidgetReason.h)).

### b. Layout

Two-pass: `ComputeDesiredSize` ("Compute the ideal size necessary to display this widget ... CacheDesiredSize() guarantees that the size of descendants is computed and cached before that of the parents") and `OnArrangeChildren` ("Compute the Geometry of all the children ... Each type of Layout panel should arrange children based on desired behavior") ([SWidget.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Source/Runtime/SlateCore/Public/Widgets/SWidget.h)). UMG's Canvas Panel uses anchors: "Minimum (X,Y) and Maximum (X,Y) Anchors parameters and offset parameters determine location of each widget", offsets are "in Slate Units", and "Preset Anchors is the most common method" ([UMG Anchors](https://dev.epicgames.com/documentation/unreal-engine/umg-anchors-in-unreal-engine-ui)); the slot's `FAnchorData` holds `Offsets` (FMargin), `Anchors` and an `Alignment` pivot "Starting in the upper left at (0,0), ending in the lower right at (1,1)" ([CanvasPanelSlot.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Source/Runtime/UMG/Public/Components/CanvasPanelSlot.h)). Scaling: project-wide "Application Scale", a "DPI Scale Rule" (shortest side, longest side, horizontal or vertical) and a "DPI Curve" keyed by resolution ([DPI Scaling](https://dev.epicgames.com/documentation/en-us/unreal-engine/dpi-scaling-in-unreal-engine)). Epic advises Canvas Panels only for root layouts because "Canvas Panels and Overlays increment" layer IDs and so add draw calls ([Optimization Guidelines](https://dev.epicgames.com/documentation/en-us/unreal-engine/optimization-guidelines-for-umg-in-unreal-engine)).

### c. Styling

`FSlateStyleSet` is "A slate style chunk that contains a collection of named properties that guide the appearance of Slate" exposing `GetBrush`, `GetColor`, `GetFontStyle` and typed `GetWidgetStyle<T>` lookups by `FName` ([SlateStyle.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Source/Runtime/SlateCore/Public/Styling/SlateStyle.h); [ISlateStyle.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Source/Runtime/SlateCore/Public/Styling/ISlateStyle.h)); the overview shows styles set by name such as `Set("ToolBarButton.Pressed", ...)` ([Slate Overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/slate-overview-for-unreal-engine)). There is no selector language. CommonUI adds style data assets that "separate styling information from UI elements"; "Any changes you make to a style asset will take effect on every Common UI widget that uses it", with Template Styles as project-wide defaults ([Common UI plugin](https://dev.epicgames.com/documentation/en-us/unreal-engine/common-ui-plugin-for-advanced-user-interfaces-in-unreal-engine); [Common UI Quickstart](https://dev.epicgames.com/documentation/en-us/unreal-engine/common-ui-quickstart-guide-for-unreal-engine)). Animation is UMG's timeline (`PlayAnimation(UWidgetAnimation*, ...)` on `UUserWidget`) ([UserWidget.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Source/Runtime/UMG/Public/Blueprint/UserWidget.h)). No stylesheet hot reload is documented in the pages read.

### d. Data flow and events

Slate properties are `TAttribute<T>` ("Attribute object") that hold a value or a bound getter (`IsBound()`) ([Attribute.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Source/Runtime/Core/Public/Misc/Attribute.h)); UMG's `PROPERTY_BINDING` macro wraps a Blueprint delegate into such a getter ([Widget.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Source/Runtime/UMG/Public/Components/Widget.h)). Epic's guidance: "When you bind attributes to fields in your UI, they poll the attribute every frame" and "Never use raw attribute binding" ([Optimization Guidelines](https://dev.epicgames.com/documentation/en-us/unreal-engine/optimization-guidelines-for-umg-in-unreal-engine)). The UMG Viewmodel plugin (Beta in 5.9) is "a more efficient alternative to raw attribute binding, as it only updates widgets when you update the variables"; "The `FieldNotify` specifier is required to broadcast value changes to widgets", and bindings are One Time, One Way to Widget, One Way to Viewmodel or Two Way ([UMG Viewmodel](https://dev.epicgames.com/documentation/en-us/unreal-engine/umg-viewmodel-for-unreal-engine)).

Events are virtual functions returning `FReply`: "A Reply is something that a Slate event returns to the system to notify it about certain aspect of how an event was handled", with `Handled()`, `Unhandled()`, `CaptureMouse`, `SetUserFocus` and `SetNavigation` ([Reply.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Source/Runtime/SlateCore/Public/Input/Reply.h)); `OnMouseButtonDown` is documented "This event is bubbled" ([SWidget.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Source/Runtime/SlateCore/Public/Widgets/SWidget.h)). CommonUI: "A `FReply` marks an event as Handled, which stops forwarding, or Unhandled"; Slate handles cardinal navigation by default and `FNavigationConfig` remaps keys, with per-widget Escape/Explicit/Wrap/Stop/Custom rules ([Input Fundamentals for CommonUI](https://dev.epicgames.com/documentation/en-us/unreal-engine/input-fundamentals-for-commonui-in-unreal-engine)).

Gamepad and routing between UI and game: CommonUI was "originally developed for Fortnite"; activatable widgets "can be toggled active or inactive, and only active ones receive input"; "Once per tick, Common UI finds the tree of nodes painted higher than any other tree" and routes input to its root ([CommonUI overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/overview-of-advanced-multiplatform-user-interfaces-with-common-ui-for-unreal-engine)). Input enters `UCommonGameViewportClient::InputKey`, the action router "gets the first chance at input", nodes check their action bindings and forward to the topmost child, and "Deactivated widgets are not added to the list of nodes" ([CommonUI Input Technical Guide](https://dev.epicgames.com/documentation/en-us/unreal-engine/commonui-input-technical-guide-for-unreal-engine)). `UCommonActivatableWidget::GetDesiredInputConfig` returns an `FUIInputConfig` (`ECommonInputMode` Menu/Game/All plus mouse capture) that "will override the existing one established by any previous activatable widget and restore it (if valid) upon deactivation"; `bIsModal` makes a widget "a root node for input routing, regardless of its actual parentage"; `GetDesiredFocusTarget` picks focus on activation ([CommonActivatableWidget.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Plugins/Runtime/CommonUI/Source/CommonUI/Public/CommonActivatableWidget.h); [Input Fundamentals](https://dev.epicgames.com/documentation/en-us/unreal-engine/input-fundamentals-for-commonui-in-unreal-engine)). Per-platform controller data assets map actions to button icons ([Common UI Quickstart](https://dev.epicgames.com/documentation/en-us/unreal-engine/common-ui-quickstart-guide-for-unreal-engine)).

### e. Rendering contract

"FSlateDrawElement is the building block for Slate's rendering interface. Slate describes its visual output as an ordered list of FSlateDrawElement s" with factories `MakeBox`, `MakeRotatedBox`, `MakeText`, `MakeShapedText`, `MakeGradient`, `MakeSpline`, `MakeCubicBezierSpline`, `MakeLines`, `MakeDashedLines`, `MakeViewport`, `MakeCustom`, `MakeCustomVerts`, `MakePostProcessPass` and `MakePostProcessBlur`, each taking an `FSlateWindowElementList` and a layer ([DrawElementTypes.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Source/Runtime/SlateCore/Public/Rendering/DrawElementTypes.h)). `FSlateWindowElementList` "Represents a top level window and its draw elements" ([DrawElements.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Source/Runtime/SlateCore/Public/Rendering/DrawElements.h)). `OnPaint` populates "A list of FDrawElements" at a layer and returns "The maximum layer ID attained by this widget or any of its children" ([SWidget.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Source/Runtime/SlateCore/Public/Widgets/SWidget.h)); "Draw calls in Slate are grouped by widgets' Layer IDs" ([Optimization Guidelines](https://dev.epicgames.com/documentation/en-us/unreal-engine/optimization-guidelines-for-umg-in-unreal-engine)).

`FSlateElementBatcher` is "A class which batches Slate elements for rendering" (`AddElements(FSlateWindowElementList&)`); `FSlateBatchData` tracks `bIsStencilBufferRequired` ([ElementBatcher.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Source/Runtime/SlateCore/Public/Rendering/ElementBatcher.h)); each `FSlateRenderBatch` carries a shader resource, `ESlateShader`, `ESlateDrawEffect` and `ESlateBatchDrawFlag` ([SlateRenderBatch.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Source/Runtime/SlateCore/Public/Rendering/SlateRenderBatch.h)). `FSlateVertex` is "a basic vertex seen by the Slate vertex buffers and shaders": `TexCoords[4]`, `MaterialTexCoords`, `Position` "in window space", `Color`, `SecondaryColor` ("Generally used for outlines") and `PixelSize[2]`; `ESlateShader` enumerates Default, Border, GrayscaleFont, ColorFont, LineSegment ("For drawing anti-aliased lines"), Custom, PostProcess, RoundedBox, SdfFont and MsdfFont; batch flags include NoBlending, PreMultipliedAlpha, NoGamma, InvertAlpha, Wireframe, TileU/TileV ([RenderingCommon.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Source/Runtime/SlateCore/Public/Rendering/RenderingCommon.h)). `FSlateRenderer` is the "Abstract base class for Slate renderers" whose `DrawWindows` "Creates necessary resources to render a window and sends draw commands to the rendering thread" ([SlateRenderer.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Source/Runtime/SlateCore/Public/Rendering/SlateRenderer.h)); the overview notes rendering "currently targets the ... Rendering Hardware Interface (RHI)" ([Slate Overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/slate-overview-for-unreal-engine)).

Clipping: `EWidgetClipping` has Inherit, ClipToBounds, ClipToBoundsWithoutIntersecting, ClipToBoundsAlways and OnDemand; "Axis-aligned clipping zone using Scissor Rects to clip - which avoids unnecessary pixel shader operations" and "Complex clipping zones use the stencil buffer to compose an arbitrary stack of clipping zones"; "Very few widgets clip now (by default), consisting mostly of scroll panels and editable text fields", and Slate "can no longer batch across clipping zones" ([Slate Clipping System](https://dev.epicgames.com/documentation/en-us/unreal-engine/using-the-slate-clipping-system-in-unreal-engine)). Rounded corners are a shader (`RoundedBox`); shadows and blur are post-process passes (`MakePostProcessBlur`).

Text: `FSlateTextShaper` is the "Bridging point between HarfBuzz and the Slate font system" with `ShapeBidirectionalText`, a FreeType "kerning only" path and `PerformHarfBuzzTextShaping` under `WITH_HARFBUZZ` ([SlateTextShaper.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Source/Runtime/SlateCore/Private/Fonts/SlateTextShaper.h)); `FSlateFontCache` "Caches characters into textures as needed" as an `ISlateAtlasProvider`, with `FShapedGlyphFontAtlasData` and `FSdfGlyphFontAtlasData` entries ([FontCache.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Source/Runtime/SlateCore/Public/Fonts/FontCache.h)). World-space and render-to-texture: `UWidgetComponent` "provides a surface in the 3D environment on which to render widgets normally rendered to the screen. Widgets are first rendered to a render target, then that render target is displayed in the world", in World or Screen space with a draw size and redraw throttles ([WidgetComponent.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Source/Runtime/UMG/Public/Components/WidgetComponent.h); [Widget Components](https://dev.epicgames.com/documentation/unreal-engine/widget-components-in-unreal-engine)).

Relative to FenrirDraw2D: Slate's batches are also vertex/index arrays with a texture and a shader selector, but the vertex is richer (two UV sets, secondary colour, pixel size) and the shader enum (border, rounded box, line segment, SDF/MSDF font) replaces per-command pipeline descriptions.

### f. Scripting fit

Slate is C++ throughout; UMG wraps it in `UObject`s so Blueprints (visual scripting) can author and drive it (`UWidget`, `UUserWidget`), and Blueprint property bindings become `TAttribute` getters ([Widget.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Source/Runtime/UMG/Public/Components/Widget.h)). There is no C# layer in the engine; a C#-optional engine following this shape would keep the widget tree, layout, batching and text native and expose a wrapper layer like UMG's.

## 3. Godot 4 Control nodes

### a. Authoring model

`Control` is the "Base class for all GUI controls. Adapts its position and size based on its parent control" ([Control](https://docs.godotengine.org/en/stable/classes/class_control.html)). Authoring is the scene editor or code; Godot's philosophy page says a scene "works like a class in pure code", scenes compose and inherit, and the editor runs on the engine's own UI ("This leads to a reliable and flexible UI system, as it powers the editor itself") ([Godot's design philosophy](https://docs.godotengine.org/en/stable/getting_started/introduction/godot_design_philosophy.html)). A custom control extends `Control` and overrides `_draw()` (checking `size` "to ensure everything is kept in-bounds"), `_get_minimum_size()` (so containers "don't squish the control"), `_gui_input()` and `_notification()` for `NOTIFICATION_MOUSE_ENTER/EXIT`, `FOCUS_ENTER/EXIT`, `THEME_CHANGED`, `VISIBILITY_CHANGED` and `RESIZED` ([Custom GUI controls](https://docs.godotengine.org/en/stable/tutorials/ui/custom_gui_controls.html)). Mode: retained scene tree; `_draw()` commands "are cached and remembered, so further calls are unnecessary" until `queue_redraw()` ([Custom drawing in 2D](https://docs.godotengine.org/en/stable/tutorials/2d/custom_drawing_in_2d.html)).

### b. Layout

Each control has four offsets, "a distance in pixels relative to the top-left corner of the parent control" by default, and four anchors from 0.0 to 1.0 that move the reference point; differing anchors make the control "resize along with its parent", and layout presets set common combinations ([Size and anchors](https://docs.godotengine.org/en/stable/tutorials/ui/size_and_anchors.html)). Containers "take over layout from anchors": children's positioning is ignored, size flags (Fill, Expand, Shrink Begin/Center/End, Stretch Ratio) steer them, and the built-ins are Box, Grid, Margin, Center, Aspect Ratio, Split, Panel, Scroll, Tab and Flow; a custom container handles `NOTIFICATION_SORT_CHILDREN`, calls `fit_child_in_rect()` per child and `queue_sort()` on change ([Using Containers](https://docs.godotengine.org/en/stable/tutorials/ui/gui_containers.html)). `_get_minimum_size()`, `custom_minimum_size`, `custom_maximum_size`, `size_flags_*` and `grow_*` complete the model, and `layout_direction` gives RTL layout ([Control](https://docs.godotengine.org/en/stable/classes/class_control.html)).

Resolution: stretch mode Disabled (one unit equals one pixel), Canvas Items (base size stretched to the window) or Viewport (render at base size then scale); stretch aspect Ignore/Keep/Keep Width/Keep Height/Expand; a `content_scale_factor` multiplier; fractional or integer scale; projects are DPI-aware by default on Windows and macOS; Godot recommends "Canvas Items with Expand for most desktop and mobile games" and anchors/containers for aspect ratios, plus raising the Default Theme Scale for large base resolutions ([Multiple resolutions](https://docs.godotengine.org/en/stable/tutorials/rendering/multiple_resolutions.html)).

### c. Styling

There is no stylesheet; a `Theme` is "A resource used for styling/skinning Control and Window nodes" with six item types (Color, Constant, Font, Font size, Icon, StyleBox), per theme type, and "A theme resource assigned to a control applies to the control itself, as well as all of its direct and indirect children" ([Theme](https://docs.godotengine.org/en/stable/classes/class_theme.html)). "A theme only describes the configuration"; each control decides how to draw it; lookup order is local overrides, each ancestor's theme (variation, class, parent classes), the project theme, then the default theme, and "Even if the item doesn't exist in any theme, a corresponding default value for that data type will be returned" ([GUI skinning](https://docs.godotengine.org/en/stable/tutorials/ui/gui_skinning.html)). Type variations extend a base type (a `GrayButton` overriding `Button`'s `normal` style) ([Theme type variations](https://docs.godotengine.org/en/stable/tutorials/ui/gui_theme_type_variations.html)); `theme_type_variation` on a control gets highest priority then falls back to class names ([Control](https://docs.godotengine.org/en/stable/classes/class_control.html)). No variables, selectors or transitions exist in this model; animation is Godot's general tweening (not covered by the pages read). Live preview: the theme editor has "a preview section for testing your changes live", but scene changes "will not be reflected in the preview automatically" without reload ([Using the theme editor](https://docs.godotengine.org/en/stable/tutorials/ui/gui_using_theme_editor.html)).

### d. Data flow and events

No binding system is documented for Controls; data flows through signals and code (`[Signal]`, `[Export]` in C#). Input order per Viewport: embedded-window handling, `_input()`, then "Control._gui_input() (via the Viewport)" where a Control consumes with `accept_event()`, then `_shortcut_input()`, `_unhandled_key_input()`, `_unhandled_input()` ("ideal for full-screen gameplay events, so they are not received when a GUI is active"), then physics picking. "GUI mouse events also travel up the scene tree" as far as `mouse_filter` allows, while "GUI keyboard and joypad events do not travel up the scene tree" ([Using InputEvent](https://docs.godotengine.org/en/stable/tutorials/inputs/inputevent.html)). `mouse_filter` is Stop (default; marks handled and blocks others), Pass (bubbles unhandled to the parent) or Ignore; `_gui_input` is skipped when the parent has `clip_contents` and the event is outside, or when `_has_point()` rejects the position; `accept_event()` "Marks an input event as handled" so `_unhandled_input()` never sees it ([Control](https://docs.godotengine.org/en/stable/classes/class_control.html)). Focus and gamepad: `focus_mode` None/Click/All, `focus_neighbor_*` with automatic nearest-control guessing, `focus_next/previous`, `grab_focus()`; `ui_up`/`ui_down`/`ui_focus_next` and the other `ui_*` actions in the input map drive focus, so the docs warn against reusing them in gameplay and advise calling `grab_focus()` on scene start ([GUI navigation](https://docs.godotengine.org/en/stable/tutorials/ui/gui_navigation.html)).

### e. Rendering contract

"The rendering server is the API backend for everything visible. The whole scene system mounts on it to display"; it "is completely opaque: the internals are entirely implementation-specific and cannot be accessed" ([RenderingServer](https://docs.godotengine.org/en/stable/classes/class_renderingserver.html)). A `CanvasItem` (base of `Control` and `Node2D`) is a server-side canvas item whose `_draw()` adds commands: `draw_rect`, `draw_texture_rect`, `draw_string`, `draw_mesh`, `draw_multimesh`, `draw_polygon`, `draw_primitive`, `draw_msdf_texture_rect_region`, `draw_lcd_texture_rect_region`, with `clip_children` modes (DISABLED/ONLY/AND_DRAW, "based on the node's alpha channel", not nestable), `material`, `modulate`, `z_index` and `get_canvas_item()` returning the RID ([CanvasItem](https://docs.godotengine.org/en/stable/classes/class_canvasitem.html)). The server API is `canvas_item_add_rect/texture_rect/polygon/polyline/mesh/multimesh/triangle_array/primitive/msdf_texture_rect_region/lcd_texture_rect_region/clip_ignore/animation_slice`, `canvas_item_set_clip`, `canvas_item_set_custom_rect`, `canvas_item_set_material`, `canvas_item_set_transform`, `canvas_item_clear` ([RenderingServer](https://docs.godotengine.org/en/stable/classes/class_renderingserver.html)). Internally `RendererCanvasRender::Item` stores a linked list of commands (`TYPE_RECT, TYPE_NINEPATCH, TYPE_POLYGON, TYPE_PRIMITIVE, TYPE_MESH, TYPE_MULTIMESH, TYPE_PARTICLES, TYPE_TRANSFORM, TYPE_CLIP_IGNORE, TYPE_ANIMATION_SLICE`) in 4 KB blocks, with `clip`, `custom_rect`, `material` and `z_final`, consumed by `canvas_render_items(...)` ([renderer_canvas_render.h](https://github.com/godotengine/godot/blob/master/servers/rendering/renderer_canvas_render.h)). The RenderingDevice backend batches: a `Batch` holds an instance range, `TextureInfo`, `material`, `Item *clip`, `ShaderVariant`, render primitive, `use_lighting/use_msdf/use_lcd/has_blend`, modulate and MSDF range, over 128-byte `InstanceData` (rect: modulation, dst_rect, src_rect; primitive: points, uvs, colors) in buffers of 16384 instances ([renderer_canvas_render_rd.h](https://github.com/godotengine/godot/blob/master/servers/rendering/renderer_rd/renderer_canvas_render_rd.h)). The architecture doc confirms "All rendering methods feature 2D batching", 2D is LDR sRGB with no depth buffer, 2D MSAA is available, and "Line2D and some CanvasItem `draw_*()` methods do their own antialiasing using triangle strips and vertex colors" ([Internal rendering architecture](https://docs.godotengine.org/en/stable/engine_details/architecture/internal_rendering_architecture.html); [Custom drawing](https://docs.godotengine.org/en/stable/tutorials/2d/custom_drawing_in_2d.html)).

Text: `TextServer` is the "low-level API backend for managing fonts and rendering text" with `create_shaped_text`, `shaped_text_add_string`, `shaped_text_shape`, `shaped_text_draw`, antialiasing None/Grayscale/LCD, hinting, subpixel positioning, MSDF and oversampling ([TextServer](https://docs.godotengine.org/en/stable/classes/class_textserver.html)); `TextServerAdvanced` is the "ICU/HarfBuzz/Graphite backed Text Server implementation with BiDi, shaping and advanced font features support" ([text_server_adv.h](https://github.com/godotengine/godot/blob/master/modules/text_server_adv/text_server_adv.h); [SCsub](https://github.com/godotengine/godot/blob/master/modules/text_server_adv/SCsub)). MSDF "allows rendering fonts at any size" but small text "will not look as clear as rasterized fonts, due to the lack of hinting"; fallbacks, OpenType features, system fonts, emoji (CBDT/SVG, not COLR) and variable fonts are supported ([Using Fonts](https://docs.godotengine.org/en/stable/tutorials/ui/gui_using_fonts.html)). Rounded corners and shadows are `StyleBoxFlat` theme items (the skinning page describes StyleBoxes as "how a panel-like background is drawn"). World-space and render-to-texture: a `SubViewport` is a render target whose `ViewportTexture` "is applied to an object in the scene"; "SubViewports don't automatically receive input, unless they receive it from their direct SubViewportContainer parent node" ([Using Viewports](https://docs.godotengine.org/en/stable/tutorials/rendering/viewports.html)).

Relative to FenrirDraw2D: Godot keeps a retained command list per item inside the server rather than handing the host a vertex buffer; `draw_polygon`/`canvas_item_add_triangle_array` is the closest to a `DrawList2D` append, and clipping is a per-item rect or an alpha mask, not a scissor per command.

### f. Scripting fit

Godot's core, Controls, the canvas renderer and text servers are C++; C# "is implemented with the modern .NET runtime", scripts are `partial` classes extending node types, and "Godot 4.5 requires .NET 8 or later"; properties of `GodotObject`-based types "require native (interop) calls as they talk to Godot's C++ core", passing raw arrays or strings "requires marshalling which is comparatively pricey", and C# "currently cannot be exported to the web platform" ([C# basics](https://docs.godotengine.org/en/stable/tutorials/scripting/c_sharp/c_sharp_basics.html)). The glue is generated (`--generate-mono-glue`), the API assemblies and source generators are built by `build_assemblies.py` and shipped as NuGet packages ([modules/mono/README.md](https://github.com/godotengine/godot/blob/master/modules/mono/README.md)), and the managed API lives in `modules/mono/glue/GodotSharp` beside `runtime_interop.cpp` ([glue listing](https://github.com/godotengine/godot/tree/master/modules/mono/glue)). So everything is native and C# is a client, which is the C#-optional shape by construction.

## 4. NoesisGUI

### a. Authoring model

Noesis is "a highly efficient lightweight C++ library" built on XAML, "a declarative markup language", with "fully mergeable, shared XAML files" for parallel designer/developer editing ([NoesisGUI product page](https://www.noesisengine.com/noesisgui/)). Design intent: "The Framework API tries to be as similar to WPF as possible" and "any kind of deviation from WPF is considered a bug"; Noesis does not auto-generate `.g.cs` code-behind, uses `float` where WPF uses `double`, and "is aimed at dynamic interfaces, so most content is redrawn every frame rather than cached" ([NoesisGUI in comparison with WPF/UWP](https://www.noesisengine.com/docs/Gui.Core.WPFComparison.html)). The element tree is WPF's: `DependencyObject` → `Visual` ("the point of connection between the user world and the Renderer system") → `UIElement` (layout, input, events) → `FrameworkElement` (styles, data binding) → `Control` (templating; a `ControlTemplate` is "a script to create a set of child elements") → `ContentControl`/`ItemsControl`; "Styling is really a lightweight form of data binding" ([Architecture](https://www.noesisengine.com/docs/Gui.Core.Architecture.html)). A reusable widget is a `UserControl` or a `ControlTemplate` ("A template allows you to completely replace a control's visual tree") ([Styling](https://www.noesisengine.com/docs/Gui.Core.StylingTutorial.html)). Mode: retained render tree "cached so the system can repaint without waiting on user code", painted back to front ([Architecture](https://www.noesisengine.com/docs/Gui.Core.Architecture.html)).

### b. Layout

"a two phase model with Measure and Arrange passes" ([Architecture](https://www.noesisengine.com/docs/Gui.Core.Architecture.html)); panels are Canvas ("absolute position, that is, using x and y coordinates"), StackPanel, WrapPanel, DockPanel, Grid (Auto, star and absolute rows/columns, spans), UniformGrid and Viewbox; alignment defaults to Stretch; margins and padding per side; "Viewbox is the ideal container to make your application Resolution Independent" ([Layout and Panels](https://www.noesisengine.com/docs/Gui.Core.LayoutPanelTutorial.html)). The pages read do not state a DPI model beyond the Viewbox and the view's logical size set at `CreateView`/`SetSize` ([Rendering Architecture](https://www.noesisengine.com/docs/Gui.Core.RenderingTutorial.html)).

### c. Styling

WPF styles: a `Style` groups `Setter`s, a `TargetType` without `x:Key` "gets implicitly applied to all elements of that target type within the same scope", `BasedOn` inherits, resource dictionaries merge, and "Every application must provide a ResourceDictionary containing styles and templates for all controls"; property triggers (`IsMouseOver`, `IsPressed`) with `EnterActions`/`ExitActions` run storyboards (`ColorAnimation`, `ThicknessAnimation`); `ControlTemplate` with `TemplateBinding`, `ContentPresenter` and `PART_` parts ([Styling](https://www.noesisengine.com/docs/Gui.Core.StylingTutorial.html)). Hot reload: XAML, resource dictionaries, styles, textures and fonts reload in a running app, preserving UI state, driven by resource providers' change delegates, in Profile builds only, remotely through the Inspector ([Hot Reload](https://www.noesisengine.com/docs/Gui.Core.HotReloadTutorial.html)).

### d. Data flow and events

Bindings are WPF's: OneWay, TwoWay, OneWayToSource, OneTime, `UpdateSourceTrigger`, `INotifyPropertyChanged` for plain properties, `DataContext` inheritance up the logical tree, value converters, `ObservableCollection`/`INotifyCollectionChanged` for `ItemsSource`, `StringFormat`; in C++ properties are exposed through `NsProp` in reflection macros and `OnPropertyChanged` ([Data Binding](https://www.noesisengine.com/docs/Gui.Core.DataBindingTutorial.html)). Input events "tunnel in preview form and then bubble", and command bindings map gestures to commands ([Architecture](https://www.noesisengine.com/docs/Gui.Core.Architecture.html)). Gamepad: `KeyboardNavigation` "Provides logical and directional navigation between focusable objects" via `DirectionalNavigation`, `TabNavigation`, `IsTabStop`, `TabIndex`, `MoveFocus` and `PredictFocus` ([KeyboardNavigation](https://www.noesisengine.com/docs/Gui.Core._KeyboardNavigation.html)); the Unity plugin "Implemented gamepad events using the new Input System Package" ([Unity tutorial](https://www.noesisengine.com/docs/Gui.Core.Unity3DTutorial.html)). Input injection: views are "fed input events" on the UI thread; "View instances are not thread-safe" ([Rendering Architecture](https://www.noesisengine.com/docs/Gui.Core.RenderingTutorial.html)). The pages read do not document a "did the UI consume this" return for game pass-through; the Unity tutorial exposes `VisualTreeHelper.HitTest`.

### e. Rendering contract

Noesis is "a resolution-independent, vector-based rendering engine built to leverage modern graphics hardware" that "utilizes original font files to render text" ([product page](https://www.noesisengine.com/noesisgui/)). Threading: a UI thread and a render thread; "Under no circumstances our core library will create threads under the hood"; per frame the UI thread calls `view->Update(time)`, the render thread calls `UpdateRenderTree()`, then `RenderOffscreen()` (intermediate textures "such as for shadows and opacity groups", which "takes place before binding the main surface"), then `Render()`; the client implements the abstract `RenderDevice`, whose settings include glyph-cache size and offscreen sample count, and "Instances of RenderDevice are not thread-safe" ([Rendering Architecture](https://www.noesisengine.com/docs/Gui.Core.RenderingTutorial.html)).

The device contract (from the official API notes and the C# SDK source, since the native header is in the licensed SDK): abstract members `Caps`, `CreateRenderTarget(label, width, height, sampleCount, needsStencil)`, `CloneRenderTarget`, `SetRenderTarget`, `BeginTile`/`EndTile`, `ResolveRenderTarget`, `CreateTexture`, `UpdateTexture`, `BeginOffscreenRender`/`EndOffscreenRender`, `BeginOnscreenRender`/`EndOnscreenRender`, `MapVertices(bytes)`/`UnmapVertices`, `MapIndices`/`UnmapIndices` and `DrawBatch(ref Batch)` ([RenderDevice.cs](https://github.com/Noesis/Managed/blob/master/Src/Noesis/Core/Src/Core/RenderDevice.cs)). Vertex attributes are Pos (R32G32_FLOAT), Color (R8G8B8A8_UNORM), Tex0/Tex1 (R32G32_FLOAT), Coverage (R32_FLOAT), Rect (R16G16B16A16_UNORM), Tile and ImagePos (R32G32B32A32_FLOAT); there are 21 vertex shaders named by format (e.g. `PosColorTex0RectImagePos`) and pixel-shader families Clear, Mask, Path_*, Path_AA_*, SDF_*, SDF_LCD_*, Opacity_*, Upsample, Downsample, Shadow, Blur and Custom_Effect; `Batch` carries `pixelShader` for custom shaders, `singlePassStereo`, and `UniformData` (values, dword count, hash) per constant buffer; stencil modes include Clear, Disabled_ZTest and Equal_Keep_ZTest; "Vertex colors are always sRGB"; scissoring must be set or disabled explicitly; `UpdateTexture()` "is guaranteed to never be called during a render pass" ([RenderDevice API notes](https://www.noesisengine.com/docs/Gui.Core.RenderDeviceNotes.html)). Text became SDF in 3.0 ("New text rendering algorithm using SDF (Signed Distance Fields)"; "Everything is rendered using A8"; "Custom RenderDevice implementations need to be upgraded with new shader for rendering distance fields"), and 3.0.8 avoids offscreen rendering for opacity on simple nodes ([3.0 changelog](https://www.noesisengine.com/docs/Gui.Core.Changelog_v30.html)). Shapes are Rectangle, Ellipse, Line and Path with SVG path mini-language, solid/gradient/image brushes and pen-like strokes ([Rendering shapes](https://www.noesisengine.com/docs/Gui.Core.ShapesTutorial.html)). Render to texture and world space: in Unity a `NoesisView` on a non-camera object "automatically switches to Render Texture", and "The user interface can also be rendered directly in 3D, without using render-to-texture" with World Space UI ([Unity tutorial](https://www.noesisengine.com/docs/Gui.Core.Unity3DTutorial.html)).

Relative to FenrirDraw2D: Noesis does not hand over a plain draw list; it drives the host's device through a fixed shader table, stencil state and offscreen targets, so the host supplies shaders and pipelines rather than consuming data.

### f. Scripting fit

The core is native C++ ("No third-party software or external dependencies required" ([product page](https://www.noesisengine.com/noesisgui/))). The C# SDK ships as NuGet packages (`Noesis` core and `NoesisApp` framework) ([Managed getting started](https://www.noesisengine.com/docs/Gui.Core.GettingStartedManaged.html)); its source uses `[DllImport(Library.Name)]` with `Library.Name = "Noesis"` (or `"__Internal"` on statically linked platforms) for entry points such as `Noesis_Init`, `Noesis_Shutdown`, `Noesis_SetXamlProvider`, and `ReleaseUnusedProxies` "release[s] their underlying Noesis C++ instances", i.e. C# objects are proxies over native ones ([NoesisGUI.cs](https://github.com/Noesis/Managed/blob/master/Src/Noesis/Core/Src/Core/NoesisGUI.cs); [Library.cs](https://github.com/Noesis/Managed/blob/master/Src/Noesis/Core/Src/Core/Library.cs)). The C# `RenderDevice` registers callbacks with `Noesis_RenderDevice_SetCallbacks` so native code can call C# overrides, while `NativeRenderDevice` wraps the shipped GL/D3D/Vulkan/Metal devices ([RenderDevice.cs](https://github.com/Noesis/Managed/blob/master/Src/Noesis/Core/Src/Core/RenderDevice.cs)). This is the clearest "native core, optional C#" precedent in the set: XAML parsing, layout, styling, binding resolution, tessellation and text stay native; C# sees proxies and can own the device.

## 5. RmlUi

### a. Authoring model

"RmlUi is the C++ user interface package based on the HTML and CSS standards" that "aims at being a light-weight and performant library with its own layout engine and few dependencies"; it takes HTML/CSS-like files and outputs vertices, indices and draw commands, and "The library strictly runs as a result of calls to its API, never in the background" ([readme](https://github.com/mikke89/RmlUi/blob/master/readme.md)). Documents are RML files whose tags become `Element`s; a `Context` is "an independent collection of documents with its own size and input state" ([Core overview](https://mikke89.github.io/RmlUiDoc/pages/cpp_manual/core_overview.html)). Reuse: RML templates (`<template name="basic" content="content">`, applied with `<body template="basic">` or inline `<template src="...">`) ([Templates](https://mikke89.github.io/RmlUiDoc/pages/rml/templates.html)) and C++ custom elements derived from `Element` registered through an `ElementInstancer` (`ElementInstancerGeneric<T>`), with `OnUpdate`, `OnRender` ("most custom rendering can be accomplished through the use of custom decorators"), `ProcessDefaultAction`, `OnAttributeChange`/`OnPropertyChange` and `GetIntrinsicDimensions` for replaced elements ([Custom elements](https://mikke89.github.io/RmlUiDoc/pages/cpp_manual/custom_elements.html)). Mode: retained element tree; `Update()` "must be called before Context::Render, but after any elements have been changed" ([Context.h](https://github.com/mikke89/RmlUi/blob/master/Include/RmlUi/Core/Context.h)).

### b. Layout

RCSS "is based on the CSS2 specification, with certain elements removed or altered to suit the needs of RmlUi", with parts of CSS3; chapters cover the box model, visual formatting, tables and flexboxes ([RCSS](https://mikke89.github.io/RmlUiDoc/pages/rcss.html)). Flexbox supports `display: flex`/`inline-flex`, direction, wrap, `flex`/grow/shrink/basis, the four alignment properties and `gap`; not `order`, `flex-basis: content` or `visibility: collapse`; deviations include approximate baseline alignment and minimum sizes applied only in column mode ([Flexboxes](https://mikke89.github.io/RmlUiDoc/pages/rcss/flexboxes.html)). Units: px, dp, em, rem, vw, vh, ex, in/cm/mm/pt/pc, %, and `x` for resolution in media queries; "The `dp` unit behaves like `px` except that its size can be set globally to scale relative to pixels" ([Syntax](https://mikke89.github.io/RmlUiDoc/pages/rcss/syntax.html)) through `Context::SetDensityIndependentPixelRatio`, which "Changes the ratio of the 'dp' unit to the 'px' unit" ([Context.h](https://github.com/mikke89/RmlUi/blob/master/Include/RmlUi/Core/Context.h)). The context's dimensions "drive relative lengths" ([Contexts](https://mikke89.github.io/RmlUiDoc/pages/cpp_manual/contexts.html)).

### c. Styling

Selectors, cascade and inheritance follow CSS; the README lists flexbox, animations and transitions, transforms, media queries, border radius, custom properties and variables, box shadows, mask images, linear/radial/conic gradient decorators, filters and backdrop filters ([readme](https://github.com/mikke89/RmlUi/blob/master/readme.md)). Custom properties: "A custom property is any property whose name begins with two dashes (`--`)", used with `var()` including fallbacks, inherited ("visible to that element and all of its descendants"), usable inside functions like `rgba()`, resolved into animations, with themes switched by `Context::ActivateTheme()`; "Custom properties cannot themselves be animated or transitioned" ([Custom properties](https://mikke89.github.io/RmlUiDoc/pages/rcss/custom_properties.html)). Decorators (image, tiled, ninepatch, gradients, shader, text) and font effects (glow, outline, shadow, blur) are RmlUi additions ([RCSS](https://mikke89.github.io/RmlUiDoc/pages/rcss.html)). Hot reload: `ElementDocument::ReloadStyleSheet` will "Reload the document's style sheet from source files" (style tags and external sheets, not inline attributes) ([ElementDocument.h](https://github.com/mikke89/RmlUi/blob/master/Include/RmlUi/Core/ElementDocument.h)); a runtime debugger shows element info, box model and outlines ([Debugger](https://mikke89.github.io/RmlUiDoc/pages/cpp_manual/debugger.html)).

### d. Data flow and events

Data bindings are MVC: "The data model is the interface between the user data, and the views and controllers assigned to the model"; `Context::CreateDataModel` returns a `DataModelConstructor` with `Bind`, `BindFunc`, `BindEventCallback`, `RegisterStruct`/`RegisterMember`, `RegisterArray`, `RegisterScalar` and `RegisterTransformFunc`; "`DirtyVariable()` should be called every time the data is changed on the client side", before `Context::Update` ([Data model](https://mikke89.github.io/RmlUiDoc/pages/data_bindings/model.html)). Views are `data-attr-*`, `data-attrif-*`, `data-class-*`, `data-style-*`, `data-if`, `data-visible`, `data-for`, `data-rml`, `data-alias-*` and `{{ }}` text; `data-value` and `data-checked` "enable two-way bindings"; `data-event-*` is a controller ([Views and controllers](https://mikke89.github.io/RmlUiDoc/pages/data_bindings/views_and_controllers.html)). Events run capture, target and bubble phases, with `StopPropagation()`/`StopImmediatePropagation()`, default actions after listeners, `EventListener::ProcessEvent`, and inline `onclick`-style attributes routed through an application `EventListenerInstancer` ([Events](https://mikke89.github.io/RmlUiDoc/pages/cpp_manual/events.html)). Focus and gamepad: `focus`, `tab-index` and `nav`/`nav-up/right/down/left` (`none`, `auto`, `tree-order`, `#id`) "determine how the focus is moved when pressing one of the keyboard navigation buttons" ([User interface](https://mikke89.github.io/RmlUiDoc/pages/rcss/user_interface.html)). Routing to the game: "RmlUi does not read user input directly, instead, it requires the application to feed its contexts with input events"; `ProcessMouseMove` returns "True if the mouse is not interacting with any elements in the context", `ProcessKeyDown` returns "True if the event was not consumed", and `IsMouseInteracting()` is the hover/activation hint; `ProcessMouseLeave()` helps when "switching to controller input" ([Input](https://mikke89.github.io/RmlUiDoc/pages/cpp_manual/input.html); [Context.h](https://github.com/mikke89/RmlUi/blob/master/Include/RmlUi/Core/Context.h)).

### e. Rendering contract

The host derives from `Rml::RenderInterface`. Required: `CompileGeometry(Span<const Vertex>, Span<const int>)` ("Indices define sets of triangles in a counter-clockwise winding order"), `RenderGeometry(geometry, translation, texture)`, `ReleaseGeometry`, `LoadTexture`, `GenerateTexture` (RGBA pixels, e.g. font atlases), `ReleaseTexture`, `EnableScissorRegion`/`SetScissorRegion` (window space; "The scissor region ignores transforms"). Optional feature sets: clip masks (`EnableClipMask`, `RenderToClipMask` with `Set`/`SetInverse`/`Intersect`; stencil is one implementation), `SetTransform` (column-major 4x4), layers (`PushLayer`, `CompositeLayers` with blend modes and filters, `PopLayer`), `SaveLayerAsTexture`, `SaveLayerAsMaskImage`, `CompileFilter` (CSS-named blur, drop-shadow, etc.) and `CompileShader` (`linear-gradient`, `radial-gradient`, `conic-gradient`, generic `shader`); "Generated textures and vertex colors are given in the sRGB color space with premultiplied alpha", so blend with `(ONE, ONE_MINUS_SRC_ALPHA)`; `transform` needs clip masks and transforms, `filter`/`backdrop-filter` need layers and filters, `box-shadow` needs layers, render textures and blur ([Render interface](https://mikke89.github.io/RmlUiDoc/pages/cpp_manual/interfaces/render.html)). `Vertex` is `Vector2f position` ("usually in pixels"), `ColourbPremultiplied colour` ("RGBA-ordered 8-bit/channel colour with premultiplied alpha") and `Vector2f tex_coord` ([Vertex.h](https://github.com/mikke89/RmlUi/blob/master/Include/RmlUi/Core/Vertex.h)). Text: "RmlUi has no default font, so at least one font must be loaded" via `LoadFontFace` or `@font-face`, with fallback faces ([Fonts](https://mikke89.github.io/RmlUiDoc/pages/cpp_manual/fonts.html)); "The default font engine used in RmlUi provides an implementation based on the FreeType library", replaceable through `FontEngineInterface` (`LoadFontFace`, `GetFontFaceHandle`, `PrepareFontEffects`, `GetFontMetrics`, `GetStringWidth`, `GenerateString` producing a `TexturedMeshList`), with `bitmap_font` and `harfbuzz` samples ([Font engine interface](https://mikke89.github.io/RmlUiDoc/pages/cpp_manual/interfaces/font_engine.html)). Shaping of complex scripts and BiDi is therefore not in the core engine; the pages read do not claim it. Render to texture and world-space are left to the host (a context can be "rendered onto a texture" for an in-world terminal) ([Contexts](https://mikke89.github.io/RmlUiDoc/pages/cpp_manual/contexts.html)). Backends in the repo (OpenGL 2/3, Vulkan, SDL GPU, DirectX 11/12 with SDL/GLFW/Win32/X11/Wayland/SFML) "are meant to be copied and modified" ([readme](https://github.com/mikke89/RmlUi/blob/master/readme.md)).

Relative to FenrirDraw2D: the required subset of `RenderInterface` (indexed `{position, premultiplied colour, uv}` vertices, a texture handle, a scissor) is almost exactly a `DrawList2D`; the difference is that RmlUi expects premultiplied alpha and `int` indices, and that its advanced effects need host-implemented layers and shaders.

### f. Scripting fit

C++ core; the Lua plugin is "designed to resemble Javascript as closely as possible", exposes elements, documents, contexts and events, and "Not all aspects of RmlUi are accessible from Lua; for example, custom decorators can only be created in C++" ([Lua manual](https://mikke89.github.io/RmlUiDoc/pages/lua_manual.html)); scripting plugins hook `LoadInlineScript`/`LoadExternalScript` on documents ([ElementDocument.h](https://github.com/mikke89/RmlUi/blob/master/Include/RmlUi/Core/ElementDocument.h)). No C# binding is part of the project. The whole engine (parse, cascade, layout, geometry generation, font engine) is native by design, and the data-model API (bind by name, dirty by name) is the natural seam for a managed language.

## 6. Coherent Gameface

### a. Authoring model

Gameface "is a game UI middleware" powered by "Cohtml (HTML engine) and Renoir (rendering engine)"; developers "build UIs for desktop, console, and mobile games using web technologies (HTML, CSS, JavaScript)"; it "runs a standard-compliant HTML5 engine", works with React, Preact and jQuery, and "is not a 'WebView'", not based on WebKit, Chromium, Gecko or IE ([Overview](https://docs.coherent-labs.com/cpp-gameface/what_is_gfp/overview/)). The JavaScript engine is V8: the changelog records "Fixed CVE-2022-4147 and several similar vulnerabilities in the V8 scripting engine" (3.1.4.5), "Added a library option to set the scripting engine (V8) flags" (1.60.0) and "Added support for Inline EcmaScript 6 modules" (1.65.0) ([Feature releases](https://docs.coherent-labs.com/cpp-gameface/changelog/feature/)). Mode: retained DOM; a `View` on the UI thread "holds the DOM and executes the JavaScript code" ([Technical overview](https://docs.coherent-labs.com/cpp-gameface/integration/technicaloverview/)).

### b. Layout

"every element in Gameface has `display: flex;` and `box-sizing: border-box;` by default"; "`display: inline` and `display: block` are simulated with flex by changing the flex-direction"; `flex-shrink` defaults to 0, `min-width/height: auto` are 0, percentages on absolutely positioned elements resolve against the direct parent, and `<html>` is 100vw by 100vh ([Differences to traditional browsers](https://docs.coherent-labs.com/cpp-gameface/what_is_gfp/htmlfeaturesupport/)). The changelog's "--use-compatibility-yoga" option (2.0.0) shows a Yoga-based solver behind the flex layout ([Feature releases](https://docs.coherent-labs.com/cpp-gameface/changelog/feature/)). Units: `font-size` accepts px, em, rem, vw and vh; `calc()`, `min()`, `max()`, `clamp()` and CSS variables are supported with the restriction that "%" cannot be mixed with other units in calc ([CSS properties](https://docs.coherent-labs.com/cpp-gameface/content_development/supported_features_tables/cssproperties/)). Layout tasks are scheduled per View and "only after glyph loading tasks are complete" ([Technical overview](https://docs.coherent-labs.com/cpp-gameface/integration/technicaloverview/)).

### c. Styling

Real CSS: the property table lists `!important`, CSS variables, `@keyframes` and `animation`, `@font-face`, `border-radius`, `box-shadow`, 2D/3D `transform`, `filter` (partial), `mask-image` (partial), `mix-blend-mode`, `overflow`, `text-shadow`, `letter-spacing`; `position` supports relative, absolute and fixed; grid is unsupported ([CSS properties](https://docs.coherent-labs.com/cpp-gameface/content_development/supported_features_tables/cssproperties/)). Hot reload is not covered by the pages read.

### d. Data flow and events

Data binding exists "to eliminate the need to move as much as possible of the data to the UI": a C++ object is exported with `view->CreateModel("thePlayer", &player)` (types described in `CoherentBind`), attached with `data-bind-value`, `data-bind-html`, `data-bind-style-*`, `data-bind-class`, `data-bind-class-toggle`, `data-bind-if`, `data-bind-for` (`iter:{{model.array}}`), and `data-bind-[eventName]`; updates flow model to DOM ("will automatically update anytime the model changes"), with `CreatePreciseHandle`/`UpdatePreciseHandle` or `ElementAdded/Updated/Removed` for fine-grained updates, and "call `SynchronizeModels` right before calling `Advance` on your view"; "Since it's written in C++ the system has better performance than all JavaScript libraries" ([HTML data binding](https://docs.coherent-labs.com/cpp-gameface/integration/ui_scripting/htmldatabinding/)). Events: "your application has to capture input events from the OS and notify Cohtml about them" through `View::MouseEvent`, `KeyEvent`, `TouchEvent`, `GestureEvent` and `System::UpdateGamepadState`; events bubble through the DOM with default handlers; the host passes a `bool` through `userData` (`cohtmlView->MouseEvent(event, nullptr, &eventHandled)`) and forwards to the game when it is false; "Interruption during the capturing phase or the target phase guarantees that the event won't be handled by UI"; cursor changes and clipboard go through `ViewListener` callbacks because "Cohtml itself will not modify the OS-controller cursor" ([Input handling](https://docs.coherent-labs.com/cpp-gameface/integration/optional_features/inputhandlingcpp_native/)). Spatial/gamepad navigation in the C++ docs was not located in the pages read (a "Gamepad Support" page is linked but was not fetched).

### e. Rendering contract

Cohtml draws a View into a user-provided texture set with `cohtml::ViewRenderer::SetRenderTarget`; "The texture must have **4** color channels and depth and stencil buffers attached"; "Cohtml performs incremental rendering by updating only the parts of the UI texture that have changed". Cohtml "asynchronously records rendering commands" into command buffers; Renoir's Command Processor converts them "into backend command buffers" for the client's graphics API, pooled per frame; the View runs on the UI thread and `ViewRenderer::Paint()` on the render thread; "The backends themselves are objects that implement the `renoir::RendererBackend` interface", registered via `SystemRenderer::RegisterRenderThread`; bundled backends are DirectX 11/12, OpenGL 3.3+, OpenGL ES 3, Vulkan and Metal ([Rendering architecture](https://docs.coherent-labs.com/cpp-gameface/integration/rendering/)). The backend interface (documented in the Coherent GT reference for the same Renoir library; the Gameface API page was not reachable) is "A Renoir renderer backend implements API or engine-specific rendering" with `FillCaps`, `BeginCommands`/`EndCommands`, create/destroy and map/unmap vertex, index and constant buffers, `CreateTexture`/`UpdateTexture`, `CreatePipelineState` ("bundles shaders and blend and depth-stencil settings"), `WrapUserRenderTarget`, `WrapUserTexture`, depth-stencil textures, samplers and `ExecuteRendering` ("Actual rendering commands that operate on updated and ready resources") ([renoir::RendererBackend](https://coherent-labs.com/Documentation/cpp-gt/de/da3/classrenoir_1_1_renderer_backend.html)). Text: "Cohtml uses single-channel SDF (signed distance fields) to render fonts in order to achieve high performance", at the cost of "a loss of fine details" and rounded corners at large sizes; "Cohtml uses path tessellation algorithms after a certain size, which is currently 256px"; "when a GPOS table is present, HarfBuzz will be used instead of FreeType to handle the kerning"; bitmap (A8) and MSDF (RGB) user fonts can be supplied; fallback is per character ([Fonts](https://docs.coherent-labs.com/cpp-gameface/content_development/fonts_frontend/)). Complex text layout uses ICU (changelog: ICU prebuilt libraries, "Removed the need to manually set the EnableComplexTextLayout View option" in 1.63.0) ([Feature releases](https://docs.coherent-labs.com/cpp-gameface/changelog/feature/)).

Relative to FenrirDraw2D: like Noesis, Gameface owns the pipeline (pipeline states, depth-stencil, render targets) and asks the host to execute recorded command buffers; it does not emit a plain triangle list for the host to interpret.

### f. Scripting fit

Native C++ engine (Cohtml, Renoir) with JavaScript on V8 as the UI language and C++ data binding as the game-facing API; the overview offers "whitebox control over rendering, tasks, logging, memory, and resource loading" ([Overview](https://docs.coherent-labs.com/cpp-gameface/what_is_gfp/overview/)). Unity and Unreal plugins exist (separate doc trees). For a C#-optional engine this is the "embed a browser-like engine" option: everything stays native and the managed side only exports models.

## 7. Immediate-mode counterpoints

### Dear ImGui

Authoring is code-only and immediate-mode: a "bloat-free graphical user interface library for C++" that "outputs vertex buffers you can render in your own 3D pipeline", "Designed primarily for developers and content-creators, not the typical end-user!", whose weaknesses are stated as "Doesn't look fancy by default" and "Limited layout features, intricate layouts are typically crafted in code" ([imgui.cpp](https://github.com/ocornut/imgui/blob/master/imgui.cpp); [README](https://github.com/ocornut/imgui/blob/master/docs/README.md)). The FAQ is explicit: "Dear ImGui is NOT designed to create a user interface for games, although with ingenious use of the low-level API you can do it"; it is "designed and optimized to create debug tools", and "Style values are currently not easily scalable dynamically" ([FAQ](https://github.com/ocornut/imgui/blob/master/docs/FAQ.md)). The README lists what is missing: no right-to-left or bidirectional text or shaping, and "Accessibility features are not supported" ([README](https://github.com/ocornut/imgui/blob/master/docs/README.md)). Styling is a flat `ImGuiStyle` struct (`WindowRounding`, `FrameRounding`, `Colors[ImGuiCol_COUNT]`, `AntiAliasedLines`, `ScaleAllSizes` which does "not scale fonts") ([imgui.h](https://github.com/ocornut/imgui/blob/master/imgui.h)). Input routing uses `io.WantCaptureMouse`/`WantCaptureKeyboard` ("in this case do not dispatch them to your main game/application") and gamepad navigation needs `ImGuiConfigFlags_NavEnableGamepad` plus `ImGuiBackendFlags_HasGamepad` ([imgui.h](https://github.com/ocornut/imgui/blob/master/imgui.h)).

Rendering contract: `ImDrawData` is "All draw command lists required to render the frame"; an `ImDrawList` is "generally one per window, conceptually ... a dynamic 'mesh' builder" with `CmdBuffer` ("Typically 1 command = 1 GPU draw call"), `IdxBuffer` and `VtxBuffer`; `ImDrawCmd` has `ClipRect`, `TexRef`, `VtxOffset`, `IdxOffset`, `ElemCount` and `UserCallback`; `ImDrawVert` is "pos + uv + col = 20 bytes by default"; indices are 16-bit unless changed in `imconfig.h`; anti-aliasing is geometric (`ImDrawFlags_AAFill`, `AALines`); fonts are rasterised into one atlas texture and "It is the rendering backend responsibility to upload texture into your graphics API" ([imgui.h](https://github.com/ocornut/imgui/blob/master/imgui.h); [BACKENDS.md](https://github.com/ocornut/imgui/blob/master/docs/BACKENDS.md)). FenrirDraw2D's `Vertex2D` is literally this layout ([FenrirDraw2D README](../../../packages/FenrirDraw2D/README.md)).

### Clay

Clay is "a high performance 2D UI layout library" in a "Single 4.8k LOC clay.h file with zero dependencies" with a "Flex-box like layout model" ([README](https://github.com/nicbarker/clay/blob/main/README.md)). Authoring is nested `CLAY(id, {config})` macros with `layoutDirection`, `sizing` (`CLAY_SIZING_FIT/GROW/FIXED/PERCENT`), `padding`, `childGap`, `childAlignment`; reusable components are plain C functions; IDs come from `CLAY_ID`/`CLAY_IDI` (stable) or `CLAY_AUTO_ID`. Each frame `Clay_EndLayout` returns a `Clay_RenderCommandArray` of `RECTANGLE`, `BORDER`, `TEXT`, `IMAGE`, `SCISSOR_START/END`, `OVERLAY_COLOR_BEGIN/END` and `CUSTOM` commands, each with `boundingBox`, `renderData`, `id`, `zIndex` and `commandType`; "Clay only supports a simple set of UI element primitives, such as rectangles, text and images", rendering of borders and rounded corners "is left up to the user", and text measurement is delegated through `Clay_SetMeasureTextFunction` ("It is essential that this function is as fast as possible"). It "was originally designed for Immediate Mode rendering", but render-command IDs "can be mapped to persistent graphics objects across multiple frames / layouts" for retained renderers; there is no styling system, no text shaping (fonts are a `uint32_t fontId` the user maps), and no multi-threading ([README](https://github.com/nicbarker/clay/blob/main/README.md)). Relative to FenrirDraw2D: Clay stops one level above a draw list (rectangles, text runs, images with scissor pairs), so a host would tessellate those into `DrawList2D` commands.

## Patterns across systems

**What every retained system shares.** Unity, Unreal, Godot, Noesis, RmlUi and Gameface all keep a tree of elements in memory and rebuild only what changed (Unity: "You declare the UI structure once, UI Toolkit takes care of rendering and updates based on the changes to the tree" ([Introduction](https://docs.unity.com/en-us/engine/6000.7/manual/best-practice-guides/bpg-uiad-index/introduction-to-ui-toolkit)); Slate's `EInvalidateWidgetReason` ([InvalidateWidgetReason.h](https://github.com/EpicGames/UnrealEngine/blob/release/Engine/Source/Runtime/SlateCore/Public/Widgets/InvalidateWidgetReason.h)); Godot's cached `_draw` commands ([Custom drawing](https://docs.godotengine.org/en/stable/tutorials/2d/custom_drawing_in_2d.html)); Noesis's cached render tree ([Architecture](https://www.noesisengine.com/docs/Gui.Core.Architecture.html)); Gameface's incremental rendering ([Rendering](https://docs.coherent-labs.com/cpp-gameface/integration/rendering/))). Each runs a layout pass (Yoga; Measure/Arrange; desired size then arrange; anchors then container sort; RCSS formatting), a style-resolution pass (USS cascade; XAML styles as "a lightweight form of data binding"; Godot theme lookup from overrides up to the default theme; RCSS computed values "calculated during the `Context::Update` call" ([Core overview](https://mikke89.github.io/RmlUiDoc/pages/cpp_manual/core_overview.html))), and a paint pass that emits batched triangles under a clip stack: Unity's `DrawBufferRange`s with scissor and stencil push/pop, Slate's layer-grouped batches with scissor rects and a stencil stack, Godot's `Batch`es with `Item *clip`, RmlUi's `SetScissorRegion` plus optional clip mask, Noesis's `Batch.stencilRef`, Gameface's required depth-stencil target. Each has a text path that shapes (HarfBuzz in Unity, Slate, Godot, Gameface; FreeType-only by default in RmlUi) and rasterises glyphs into an atlas or distance field. Axis-aligned clips are a scissor and everything else is stencil in Unity and Slate alike.

**Where they differ.**
- *Who owns the GPU.* Slate, Unity, RmlUi, Dear ImGui and Clay hand over data (vertices, indices, a texture, a clip) and let the host draw; Noesis and Gameface invert it, asking the host to implement a device/backend with a fixed shader table or pipeline states and to run offscreen passes. Godot sits in between: the host never sees the data because the server owns both the commands and the renderer.
- *Vertex richness.* Dear ImGui and RmlUi stop at position, colour and UV; Slate adds a second UV set, a secondary colour and a pixel size; Unity adds flags/IDs that index shader-side pages for transforms, clips, opacity and colour; Noesis adds coverage, rect, tile and image-position attributes. The richer the vertex, the more of the UI's effects (rounded boxes, borders, AA, SDF text) move into shaders and the fewer batch breaks.
- *Authoring language.* Web-like text formats (UXML/USS, RML/RCSS, HTML/CSS) and XAML are what the three middleware products and Unity chose; Unreal and Godot rely on editors plus code. Only Gameface runs an actual browser-grade language stack (V8).
- *Binding model.* Observable, mode-based bindings (Unity, Noesis, Unreal Viewmodel) versus dirty-by-name models (RmlUi, Gameface) versus per-frame polling (Slate `TAttribute`) versus none (Godot, ImGui, Clay).
- *Input routing.* All retained systems bubble; capture/tunnel exists in Unity, Noesis and RmlUi; the explicit "did the UI consume this" answer differs: RmlUi returns it from `Process*`, Gameface writes a `bool` through `userData`, Dear ImGui sets `WantCapture*`, Godot orders `_gui_input` before `_unhandled_input`, Unreal's CommonUI layers an input-config stack on top of Slate's `FReply`.

**Which choices make the UI approachable to a modern software developer, per the engines' own stated goals.**
- Unity's documented goal is the web split: structure, style and behaviour "similar to how you might with HTML, CSS, and JavaScript", for "Better collaboration", "Reusability" and "Faster iteration" with "global style management and live authoring" ([Introduction to UI Toolkit](https://docs.unity.com/en-us/engine/6000.7/manual/best-practice-guides/bpg-uiad-index/introduction-to-ui-toolkit)); its compare page lists UI Toolkit for "UI Designers" because of its "document-based approach" and UI Builder, while noting technical artists "might not be comfortable with UI Toolkit's web-like approach" ([Comparison](https://docs.unity.com/en-us/engine/current/manual/uitoolkits/ui-system-compare)). Yoga's own pitch is the same: a CSS subset gives developers "a familiar model" and "enables sharing code between native platforms and the browser" ([About Yoga](https://www.yogalayout.dev/docs/about-yoga)).
- Gameface's stated purpose is to let teams build game UI "using web technologies (HTML, CSS, JavaScript)", aimed at web and front-end developers, with React and jQuery compatibility and data binding "written in C++" to keep logic out of JavaScript ([Overview](https://docs.coherent-labs.com/cpp-gameface/what_is_gfp/overview/); [HTML data binding](https://docs.coherent-labs.com/cpp-gameface/integration/ui_scripting/htmldatabinding/)).
- RmlUi's stated aim is a "light-weight and performant library with its own layout engine and few dependencies" that still speaks "the HTML and CSS standards" and whose Lua API "has been designed to resemble Javascript as closely as possible" ([readme](https://github.com/mikke89/RmlUi/blob/master/readme.md); [Lua manual](https://mikke89.github.io/RmlUiDoc/pages/lua_manual.html)).
- Noesis bets on WPF literacy and tooling: "any kind of deviation from WPF is considered a bug", Blend projects ship with every sample, and "fully mergeable, shared XAML files" let designers and developers "edit in parallel" ([WPF comparison](https://www.noesisengine.com/docs/Gui.Core.WPFComparison.html); [product page](https://www.noesisengine.com/noesisgui/)).
- Unreal's stated approachability lever is the visual editor plus a declarative C++ syntax that "makes it simple to re-arrange UI elements quickly for prototyping and iteration" ([Slate Overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/slate-overview-for-unreal-engine)), with CommonUI and the Viewmodel plugin added so that "UI designers and programmers [can] work separately" ([UMG Viewmodel](https://dev.epicgames.com/documentation/en-us/unreal-engine/umg-viewmodel-for-unreal-engine)).
- Godot's stated lever is composition: scenes "work like a class in pure code", and the editor itself is built from the same Control nodes, which "leads to a reliable and flexible UI system" ([Design philosophy](https://docs.godotengine.org/en/stable/getting_started/introduction/godot_design_philosophy.html)).
- Dear ImGui states the opposite audience ("developers and content-creators, not the typical end-user") and Clay states its scope as layout only ([imgui.cpp](https://github.com/ocornut/imgui/blob/master/imgui.cpp); [Clay README](https://github.com/nicbarker/clay/blob/main/README.md)).

Across the stated goals, the recurring approachability choices are: a text format for structure and a stylesheet with selectors and variables (so designers and version control can handle the UI without the engine's editor), a flexbox or Measure/Arrange layout with pixel units and a scale factor (so web or desktop intuition transfers), observable bindings with explicit modes (so UI code does not poll), bubbling events plus a first-class focus/gamepad model, a visual tool that edits the same files, and hot reload. The rendering contract is invisible to that developer in every case; where it differs is only in how much the host engine must implement.

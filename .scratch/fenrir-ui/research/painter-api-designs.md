# What a complete 2D painter API consists of, and how the established painters implement it

Research for the UI effort: what the drawing layer under a game UI must offer, studied across Skia (and SkiaSharp), NanoVG, Vello, Dear ImGui's `ImDrawList`, Unity's `Painter2D`/`MeshGenerationContext`, Godot's `CanvasItem`/`RenderingServer`, Flutter's `Canvas`/`Paint`/Impeller, ThorVG, the Rive Renderer and Blend2D, plus the text building blocks they stand on. Read on 2026-11-10 from the primary sources linked at each claim; a Sources list closes the file. It decides nothing about FenrirEngine's painter. Where a source could not be read, the text says so instead of guessing.

## Summary

1. Every mature painter has the same **core**: a path (move/line/cubic/close, with quad, arc and rect/rounded-rect/circle helpers), fill and stroke with a paint that is a solid colour, a gradient (linear and radial everywhere; sweep/conic in most) or an image, stroke width/cap/join/miter limit, an affine transform with a save/restore stack, a rectangular clip, images, and text drawn from a font. The ones that leave any of these out (ImGui: no gradients beyond per-vertex colour, no path clip; Clay/RmlUi-style command lists: no paths at all) are explicitly minimal.
2. The **common** layer is path/anti-aliased clipping, opacity and blend-mode layers composited offscreen (`saveLayer`, `push_layer`, `PushLayer`), dashes, even-odd fill rule, nine-slice images and a paragraph layout API; the **rare** layer is image filters (blur, drop shadow, colour matrix, backdrop), runtime shaders, mesh/vertex draws, luminance masks and material elevation shadows, found in Skia, Flutter, Vello and ThorVG only.
3. **Text** is never done by the painter alone: HarfBuzz shapes, ICU (or FriBidi) does bidi and line breaks, FreeType or stb_truetype rasterises, and a layout library (SkParagraph, Parley, Godot's TextServer) sits on top. Blend2D and ThorVG are the only ones with their own TrueType/OpenType stacks; Slug is the only one that rasterises glyphs directly from outlines on the GPU.
4. **Tessellation/AA** splits into four families with stated trade-offs: CPU tessellation with 1 px transparent fringes (NanoVG, ImGui, Godot's `antialiased` feathers, Rive's coverage triangles); stencil-then-cover with MSAA (NanoVG concave fills, Skia Ganesh/Graphite tessellation steps, Impeller); analytic coverage in software or compute (Blend2D, ThorVG SW, Vello compute, Pathfinder); and per-pixel curve evaluation in the fragment shader (Loop-Blinn, Slug, SDF/MSDF glyphs, NanoVG's `sdroundrect` gradients).
5. **Output contracts** cluster into two shapes: painters that own a GPU backend and expose "render to this texture" (Skia, Vello, Impeller, Rive, ThorVG GL/WebGPU), and painters that hand the host triangles: an interleaved pos/uv/colour vertex array, an index array (16-bit by default in ImGui, RmlUi uses `int`), and an ordered command list where each command names one texture, one scissor rectangle and an index range (ImGui), or a per-call paint/scissor/blend parameter block and vertex ranges (NanoVG's `renderFill`/`renderStroke`/`renderTriangles`).
6. **Retained vs immediate**: ImGui rebuilds every draw list every frame by design; Skia and Flutter record (`SkPicture`, `Picture`/`DisplayList`) and replay; Godot stores draw commands server-side and only re-records on `queue_redraw()`; Unity caches `generateVisualContent` output until `MarkDirtyRepaint`; ThorVG keeps a retained scene graph and renders only changed paints; Vello encodes a `Scene` that the caller resets or keeps.
7. **C# bindings** take one of three shapes: a handle plus one P/Invoke per draw call (SkiaSharp's `SKCanvas` wraps `sk_canvas_*` through `libSkiaSharp`), a managed facade over a native method-bind table (Godot's `NativeFuncs`/`godotsharp_method_bind_ptrcall`), or managed code that fills vertex buffers directly (Unity's `MeshWriteData`) while native code tessellates (`Painter2D`).
8. Fenrir's `DrawList2D` already matches the ImGui/RmlUi contract (interleaved vertices, 16/32-bit indices, per-command texture and scissor, index range and base vertex) and goes beyond it with a pipeline table, four texture slots, blend modes, colour spaces and 128 parameter bytes; what it lacks against NanoVG's contract is any per-call paint block (gradient matrices, extents, feather), a stencil/cover path for concave fills, a layer/offscreen notion and a scissor transform.
9. Glyph rendering on the GPU is overwhelmingly a bitmap atlas (ImGui, NanoVG's fontstash, Impeller's `GlyphAtlas`, Skia's "99.99% case"), with SDF/MSDF for scale independence (Unity TextCore, Godot MSDF fonts, Skia's SDFT ".009% case", msdf-atlas-gen) and outline rendering as paths only for very large glyphs (Skia, Vello).
10. The one place the field is still moving is Vello's sparse strips (CPU flattening and tiling, GPU raster through vertex/fragment shaders only) and Graphite's planned "GPU compute based path rasterization", both chosen to escape MSAA's quality limits and compute-shader portability problems at the same time.

## 1. Skia (and SkiaSharp)

Skia is the reference point: everything else in this file either copies its surface or deliberately leaves parts of it out.

### a. Surface of the API

`SkCanvas` "provides an interface for drawing, and how the drawing is clipped and transformed" and holds "a stack of matrices and clips"; colour and style are "specified explicitly in each draw call, via a SkPaint" ([SkCanvas.h](https://github.com/google/skia/blob/main/include/core/SkCanvas.h), [SkCanvas overview](https://skia.org/docs/user/api/skcanvas_overview/)). The draw set ([api.skia.org SkCanvas](https://api.skia.org/classSkCanvas.html)): `drawPoints`/`drawPoint`/`drawLine`, `drawRect`, `drawRRect`, `drawDRRect` (difference of two rounded rects), `drawOval`, `drawCircle`, `drawArc`, `drawRoundRect`, `drawPath`, `drawImage` (with `SkSamplingOptions`), `drawImageNine`, `drawImageLattice`, `drawTextBlob`, `drawGlyphs`, `drawPicture`, `drawVertices`, `drawPatch` (Coons patch), `drawAtlas` (sprites with `SkRSXform`), `drawDrawable`, `drawRegion`, `drawPaint`, `drawColor`, and the experimental `drawMesh` (GPU/SkSL only). Shadows are a utility, not a canvas method: `SkShadowUtils::DrawShadow` draws "an offset spot shadow and outlining ambient shadow for the given path using a disc" light, with a 3D light position and flags ([SkShadowUtils.h](https://github.com/google/skia/blob/main/include/utils/SkShadowUtils.h)).

Clipping: `clipRect`, `clipRRect`, `clipPath` each take an `SkClipOp` and a `doAntiAlias` flag, "with an aliased or anti-aliased clip edge"; `clipRegion` and `clipShader` take no AA flag ([api.skia.org SkCanvas](https://api.skia.org/classSkCanvas.html)). Transforms: `save`, `saveLayer`, `restore`, `translate`, `scale`, `rotate` (with optional pivot), `skew`, `concat` (`SkMatrix` or `SkM44`), `setMatrix`, `resetMatrix`. `saveLayer` "also allocates a surface for subsequent drawing", and `SaveLayerRec` carries `fBounds` ("hints at layer size limit"), `fPaint` ("modifies overlay"), `fBackdrop` (an image filter applied to the copied prior content), `fBackdropTileMode`, `fColorSpace`, and flags `kPreserveLCDText`, `kInitWithPrevious`, `kF16ColorType` ([SkCanvas.h](https://github.com/google/skia/blob/main/include/core/SkCanvas.h)).

The paint model ([api.skia.org SkPaint](https://api.skia.org/classSkPaint.html)): `Style` is `kFill_Style`, `kStroke_Style` or `kStrokeAndFill_Style`; `setStrokeWidth` (zero is a hairline), `setStrokeCap` (butt/round/square, default butt), `setStrokeJoin` (miter/round/bevel, default miter), `setStrokeMiter`; `setAntiAlias` and `setDither` are "requests, not guarantees"; `setColor`/`setColor4f` with an optional colour space; `setBlendMode` is a helper over `setBlender` (null blender means SrcOver); `setShader` (gradients, images); `setMaskFilter`, `setColorFilter`, `setImageFilter`, `setPathEffect`. The paint "does not directly implement dashing or blur, but contains the objects that do so". The effect families ([SkPaint overview](https://skia.org/docs/user/api/skpaint_overview/)): `SkPathEffect` (dash, corner, discrete) modifies geometry before the mask; `SkShader` covers linear, radial, two-point conical and sweep gradients plus bitmap, noise and compose shaders; `SkMaskFilter` modifies the alpha mask (blur); `SkColorFilter` (colour matrix, table) modifies source colour before blending; `SkBlendMode` holds the Porter-Duff and blend modes. `SkImageFilters` is "a set of factory functions providing useful SkImageFilter effects": Arithmetic, Blend, Blur, ColorFilter, Compose, Crop, DisplacementMap, DropShadow, DropShadowOnly, Image, Magnifier, MatrixConvolution, MatrixTransform, Merge, Offset, Picture, RuntimeShader, Shader, Tile, Dilate, Erode and the distant/point/spot diffuse and specular lighting filters ([SkImageFilters.h](https://github.com/google/skia/blob/main/include/effects/SkImageFilters.h)). Runtime effects: SkSL is "very similar to GLSL" but "you are programming a stage of the Skia pipeline"; `SkRuntimeEffect` builds `SkShader`, `SkColorFilter` and `SkBlender` objects from SkSL, each of which "contributes a function to the GPU's fragment shader", so even a deep tree of effects is "only a single GPU fragment shader" per draw ([SkSL](https://skia.org/docs/user/sksl/)).

### b. Text

Skia separates glyph drawing (`SkFont`, `SkTextBlob`, `drawGlyphs`) from shaping and layout, which live in modules. `SkShaper` shapes UTF-8 through run iterators for font, bidi level ("even means left-to-right and odd means right-to-left"), ISO 15924 script and BCP-47 language; the HarfBuzz backend provides `MakeShaperDrivenWrapper`/`MakeShapeThenWrap` (behind `SK_SHAPER_HARFBUZZ_AVAILABLE`), CoreText is an alternative, `MakePrimitive` is the fallback, and `MakeIcuBiDiRunIterator`/`MakeHbIcuScriptRunIterator` name ICU. `Options::width` is "the horizontal space available before wrapping", and a `RunHandler` receives `beginLine`, `runInfo`, `commitRunInfo`, `runBuffer`, `commitRunBuffer`, `commitLine`; `SkTextBlobBuilderRunHandler` is the "Helper for shaping text directly into a SkTextBlob" ([SkShaper.h](https://github.com/google/skia/blob/main/modules/skshaper/include/SkShaper.h)). SkParagraph's `Paragraph` is the rich-text layer: `layout(SkScalar width)`, `paint(SkCanvas*, x, y)`, `getRectsForRange`, `getGlyphPositionAtCoordinate`, `getWordBoundary`, `getLineMetrics`, intrinsic widths, `didExceedMaxLines`, a `visit` callback over glyph runs ([Paragraph.h](https://github.com/google/skia/blob/main/modules/skparagraph/include/Paragraph.h)). Flutter's Impeller FAQ confirms who uses it: text layout and shaping "happens to be SkParagraph which is part of Skia" ([Impeller FAQ](https://github.com/flutter/flutter/blob/master/docs/engine/impeller/docs/faq.md)).

On the GPU, `SubRunContainer::MakeInAlloc` picks a strategy per run: "Only consider using direct or SDFT drawing if not drawing hairlines and not too big"; "Process masks including ARGB - this should be the 99.99% case"; "Process SDFT - This should be the .009% case"; "Handle path subruns. Mainly, large or large perspective glyphs with no color"; the rest go to "the drawing of last resort", which "scales out of the atlas to the screen, so quality will suffer". The atlas path "enforces max size 254px" because "Bilerp sampling requires 1px atlas padding" ([SubRunContainer.cpp](https://github.com/google/skia/blob/main/src/text/gpu/SubRunContainer.cpp)). Graphite keeps the same split as render steps: `BitmapTextRenderStep`, `SDFTextRenderStep`, `SDFTextLCDRenderStep` ([graphite/render](https://github.com/google/skia/tree/main/src/gpu/graphite/render)).

### c. Tessellation and anti-aliasing

Ganesh runs a chain of path renderers in priority order: `DashLinePathRenderer`, `AAConvexPathRenderer`, `AAHairLinePathRenderer`, `AALinearizingConvexPathRenderer`, `AtlasPathRenderer`, `SmallPathRenderer`, `TriangulatingPathRenderer`, `TessellationPathRenderer` (when supported), and finally `DefaultPathRenderer`: "We always include the default path renderer (as well as SW), so we can draw any path" ([PathRendererChain.cpp](https://github.com/google/skia/blob/main/src/gpu/ganesh/PathRendererChain.cpp)). The tessellation renderers prepare GPU data for "a path's tessellated geometry": `PathCurveTessellator` draws "outer curve" patches where "Quadratics are converted to cubics and triangles are converted to conics with w=Inf", `PathWedgeTessellator` draws 5-point wedges such that "Once stencilled, these wedges alone define the complete path", both issuing "fixed-count instanced draw calls over the patches" ([PathTessellator.h](https://github.com/google/skia/blob/main/src/gpu/ganesh/tessellate/PathTessellator.h)); `PathTessellateOp` "Tessellates a path directly to the color buffer, using one single render pass. This currently only works for convex paths" and uses MSAA for AA ([PathTessellateOp.h](https://github.com/google/skia/blob/main/src/gpu/ganesh/ops/PathTessellateOp.h)). Graphite's `Renderer` "decomposes the technique into a series of RenderSteps that must be executed in the specified order", with the stencil rule that "their last step leaves the stencil set to 0"; steps may emit "analytic coverage via fragmentCoverageSkSL()" (including LCD coverage) and may be "outset beyond shape's bounds for AA" ([graphite/Renderer.h](https://github.com/google/skia/blob/main/src/gpu/graphite/Renderer.h)). The step list shows the whole toolbox in one directory: `TessellateCurves`, `TessellateWedges`, `TessellateStrokes`, `MiddleOutFan`, `CoverBounds`, `CoverageMask` (atlas), `AnalyticRRect`, `AnalyticBlur`, `AnalyticRRectBlur`, `CircularArc`, `PerEdgeAAQuad`, `Vertices`, `Mesh`, `WideTile`, and the text steps ([graphite/render](https://github.com/google/skia/tree/main/src/gpu/graphite/render)). Chrome's launch post states the direction: Graphite assigns each draw a depth value so "opaque foreground objects can eliminate overdraw automatically" and clipping becomes depth-only draws, and the team wants compute because "GPU compute based path rasterization would allow us to improve over both the visual quality of MSAA" and CPU rasterisation ([Introducing Skia Graphite](https://blog.google/chromium/introducing-skia-graphite-chromes/)). This post is Chrome's, not skia.org's; no skia.org Graphite design page was found.

### d. Output contract

Skia owns its backends. An `SKCanvas`/`SkCanvas` is obtained from a surface, and the backends that "receive SKCanvas drawing commands" are raster, GPU (via a `GRContext` matched "one to one with OpenGL contexts or Vulkan devices"), PDF, XPS, SVG, Picture and Null; Skia "does not create an OpenGL context or a Vulkan device for you" and in GL mode "assumes that the correct OpenGL context has been made current" ([learn.microsoft.com SKCanvas](https://learn.microsoft.com/en-us/dotnet/api/skiasharp.skcanvas)). A host engine integrates by wrapping its own GL/Vulkan/Metal/D3D texture as a Skia render target and flushing; there is no vertex/command-list hand-off.

### e. Retained or immediate, and caching

Immediate at the API, with recording as a first-class object: "SkPicture records drawing commands made to SkCanvas. The command stream may be played in whole or in part at a later time", generated by `SkPictureRecorder` or `SkDrawable` or deserialised; it has a cull rect "used as a bounding box hint", `approximateOpCount` ("some calls expand into several operations and others are optimized away"), `approximateBytesUsed`, `serialize`, and `makeShader` to use a picture as a fill ([api.skia.org SkPicture](https://api.skia.org/classSkPicture.html)). Shadows "may be cached, depending on the path type and canvas matrix" ([SkShadowUtils.h](https://github.com/google/skia/blob/main/include/utils/SkShadowUtils.h)).

### f. Language bindings: SkiaSharp

SkiaSharp is "a cross-platform 2D graphics API for .NET platforms" on Skia, shipping native assets per platform ([SkiaSharp README](https://github.com/mono/SkiaSharp/blob/main/README.md)). The pattern is handle plus one P/Invoke per call. `SKCanvas : SKObject` holds a native `Handle`; `DrawRect` is a null check, `SkiaApi.sk_canvas_draw_rect (Handle, &rect, paint.Handle);` and `GC.KeepAlive`; `DrawPath` calls `sk_canvas_draw_path (Handle, path.Handle, paint.Handle)`; `ClipRect` calls `sk_canvas_clip_rect_with_operation (Handle, &rect, operation, antialias)`; `Restore()` is `sk_canvas_restore (Handle)`. Managed-side work is limited to argument checks, early-outs for identity transforms, composing pivot overloads out of translate/transform/translate, pinning `SKPoint[]` with `fixed` for `sk_canvas_draw_points`, and building `SKTextBlob`s for the string `DrawText` overloads ([SKCanvas.cs](https://github.com/mono/SkiaSharp/blob/main/binding/SkiaSharp/SKCanvas.cs)). `SKObject` is "a tracked native object": a handle dictionary maps each native pointer to one wrapper (`HandleDictionary.GetOrAddObject`), `OwnsHandle` decides whether dispose destroys the native object, and reference-counted types release through `SafeUnRef` ([SKObject.cs](https://github.com/mono/SkiaSharp/blob/main/binding/SkiaSharp/SKObject.cs)). "SkiaApi is the single internal type through which EVERY P/Invoke into libSkiaSharp flows", with `private const string SKIA = "libSkiaSharp";` and a `USE_DELEGATES` path that resolves symbols lazily ([SkiaApi.cs](https://github.com/mono/SkiaSharp/blob/main/binding/SkiaSharp/SkiaApi.cs)). The generated declaration file and the C-API headers were not located in the current tree layout, so the generator is not described here.

## 2. NanoVG

### a. Surface of the API

"Small antialiased vector graphics rendering library for OpenGL", with an API "loosely modeled on the HTML5 canvas API" ([README](https://github.com/memononen/nanovg/blob/master/README.md)). Drawing is "begin a path, define its geometry, set the fill or stroke, then fill or stroke it". The header groups ([nanovg.h](https://github.com/memononen/nanovg/blob/master/src/nanovg.h)): frame (`nvgBeginFrame` with device pixel ratio, `nvgCancelFrame`, `nvgEndFrame`); composite operations following "the HTML Canvas model with OpenGL-style blend factors" (`nvgGlobalCompositeOperation`, `nvgGlobalCompositeBlendFunc[Separate]`); state (`nvgSave`, `nvgRestore`, `nvgReset`); render styles (`nvgShapeAntiAlias`, `nvgStrokeColor`, `nvgStrokePaint`, `nvgFillColor`, `nvgFillPaint`, `nvgMiterLimit`, `nvgStrokeWidth`, `nvgLineCap`, `nvgLineJoin`, `nvgGlobalAlpha`); transforms (`nvgResetTransform`, `nvgTransform`, `nvgTranslate`, `nvgRotate`, `nvgSkewX/Y`, `nvgScale`, `nvgCurrentTransform`, plus 2×3 matrix helpers); images (`nvgCreateImage[Mem|RGBA]`, `nvgUpdateImage`, `nvgImageSize`, `nvgDeleteImage`); paints (`nvgLinearGradient`, `nvgBoxGradient`, `nvgRadialGradient`, `nvgImagePattern`, each "transformed by the current transform when passed to nvgFillPaint or nvgStrokePaint"); scissoring (`nvgScissor`, `nvgIntersectScissor`, `nvgResetScissor`, rectangles only); paths (`nvgBeginPath`, `nvgMoveTo`, `nvgLineTo`, `nvgBezierTo`, `nvgQuadTo`, `nvgArcTo`, `nvgClosePath`, `nvgPathWinding`, `nvgArc`, `nvgRect`, `nvgRoundedRect`, `nvgRoundedRectVarying`, `nvgEllipse`, `nvgCircle`, `nvgFill`, `nvgStroke`). Fill uses the even-odd rule; holes are cut with `nvgPathWinding(vg, NVG_HOLE)` ([README](https://github.com/memononen/nanovg/blob/master/README.md)). There are no dashes, no path clipping, no layers and no filters; `nvgFontBlur` is the only blur.

The paint is one struct: `NVGpaint { float xform[6]; float extent[2]; float radius, feather; NVGcolor innerColor, outerColor; int image; }`, so a linear, box or radial gradient and an image pattern are all one rounded-rect-SDF gradient parameterised differently ([nanovg.h](https://github.com/memononen/nanovg/blob/master/src/nanovg.h)); the fragment shader's `sdroundrect` computes the distance and `mix(innerCol, outerCol, d)` ([nanovg_gl.h](https://github.com/memononen/nanovg/blob/master/src/nanovg_gl.h)). The scissor is also a transformed rectangle, `NVGscissor { float xform[6]; float extent[2]; }`, evaluated per fragment as a soft mask.

### b. Text

Fonts load from file or memory (`nvgCreateFont[Mem][AtIndex]`), with fallback fonts (`nvgAddFallbackFont`), `nvgFontSize`, `nvgFontBlur`, `nvgTextLetterSpacing`, `nvgTextLineHeight`, `nvgTextAlign`; drawing is `nvgText` and `nvgTextBox`, measuring `nvgTextBounds`, `nvgTextGlyphPositions`, `nvgTextMetrics`, `nvgTextBreakLines`, all in local space ([nanovg.h](https://github.com/memononen/nanovg/blob/master/src/nanovg.h)). Rasterisation "uses stb_truetype, or optionally FreeType" ([README](https://github.com/memononen/nanovg/blob/master/README.md)) through fontstash: a glyph atlas packed by a skyline packer ("Atlas based on Skyline Bin Packer by Jukka Jylänki", "Bottom left fit heuristic"), rasterised by stb_truetype or FreeType (`FONS_USE_FREETYPE`), uploaded by dirty rectangle through `renderUpdate`, grown with `fonsExpandAtlas` or reset with `fonsResetAtlas`, with an exponential blur for `nvgFontBlur`, and quads emitted by `fonsTextIterNext` ([fontstash.h](https://github.com/memononen/nanovg/blob/master/src/fontstash.h)). No shaping, no bidi; line breaking is `nvgTextBreakLines` over a width.

### c. Tessellation and anti-aliasing

CPU flattening and stroking into triangle strips and fans with "fringes". `NVG_ANTIALIAS` "means that the renderer adjusts the geometry to include anti-aliasing. If you're using MSAA, you can omit this flags"; `NVG_STENCIL_STROKES` "means that the render uses better quality rendering for (overlapping) strokes", with the difference "mostly visible on wider strokes" and the flag omittable "for speed"; the render target "must have a stencil buffer" ([README](https://github.com/memononen/nanovg/blob/master/README.md)). The GL backend ([nanovg_gl.h](https://github.com/memononen/nanovg/blob/master/src/nanovg_gl.h)): a concave fill is stencil-then-cover in three passes, "Draw shapes" with colour writes off and `GL_INCR_WRAP`/`GL_DECR_WRAP` on front/back faces over each sub-path's triangle fan (non-zero winding counted in the stencil), "Draw anti-aliased pixels" where the stencil is 0 using the fringe strips, and "Draw fill" of the bounding quad where the stencil is non-zero, zeroing it as it goes. A single convex path skips the stencil (`GLNVG_CONVEXFILL`: fan plus fringe). Strokes with `NVG_STENCIL_STROKES` draw the base with `EQUAL 0`/`GL_INCR` to prevent double coverage, then the AA pass with a threshold, then "Clear stencil buffer"; without the flag each strip is drawn directly and "Overlapping sharp turns may show double coverage". The fragment shader's `strokeMask` goes "from [0..1] to clipped pyramid, where the slope is 1px".

### d. Output contract

The backend interface is `NVGparams` ([nanovg.h](https://github.com/memononen/nanovg/blob/master/src/nanovg.h)): `userPtr`, `edgeAntiAlias`, and callbacks `renderCreate`, `renderCreateTexture(type, w, h, imageFlags, data)`, `renderDeleteTexture`, `renderUpdateTexture(image, x, y, w, h, data)`, `renderGetTextureSize`, `renderViewport(width, height, devicePixelRatio)`, `renderCancel`, `renderFlush`, `renderFill(paint, compositeOperation, scissor, fringe, bounds, paths, npaths)`, `renderStroke(paint, compositeOperation, scissor, fringe, strokeWidth, paths, npaths)`, `renderTriangles(paint, compositeOperation, scissor, verts, nverts, fringe)`, `renderDelete`. Vertices are `NVGvertex { float x,y,u,v; }` and each `NVGpath` carries `first, count, closed, nbevel, fill, nfill, stroke, nstroke, winding, convex` pointing into one vertex array. Colour is not per vertex: it comes from the paint. The GL backend turns each call into a `GLNVGcall` (type FILL/CONVEXFILL/STROKE/TRIANGLES, image, path range, triangle range, uniform offset, blend factors) and a `GLNVGfragUniforms` block (`scissorMat`, `paintMat`, `innerCol`, `outerCol`, `scissorExt`, `scissorScale`, `extent`, `radius`, `feather`, `strokeMult`, `strokeThr`, `texType`, `type`), and in `renderFlush` uploads the whole frame's vertex buffer once with `glBufferData`, sets "view and texture just once per frame", then iterates the calls ([nanovg_gl.h](https://github.com/memononen/nanovg/blob/master/src/nanovg_gl.h)). "All frame data is buffered and flushed in nvgEndFrame()" ([README](https://github.com/memononen/nanovg/blob/master/README.md)). Ports exist for DX11, Metal and bgfx ([README](https://github.com/memononen/nanovg/blob/master/README.md)), which is the evidence that the contract is backend-neutral.

### e. Retained or immediate

Immediate: everything between `nvgBeginFrame` and `nvgEndFrame` is re-issued each frame, and glyphs are rasterised into the atlas "as needed within that span" ([README](https://github.com/memononen/nanovg/blob/master/README.md)). No display list.

### f. Language bindings

The README lists "a .NET P/Invoke binding" among users ([README](https://github.com/memononen/nanovg/blob/master/README.md)); its design was not studied. The C API is flat handles and floats, which is why P/Invoke per call is the natural shape.

## 3. Vello (compute renderer, Vello CPU, Vello GPU / vello_hybrid)

### a. Surface of the API

Vello is "a compute-centric 2D graphics rendering engine written in Rust, using wgpu", meant to "fill the same role as Skia, Cairo" with "a PostScript-inspired imaging model" ([docs.rs vello](https://docs.rs/vello/latest/vello/), [README](https://github.com/linebender/vello/blob/main/README.md)). The API is a `Scene` ([docs.rs Scene](https://docs.rs/vello/latest/vello/struct.Scene.html)): `fill(style: Fill, transform, brush, brush_transform, shape)`, `stroke(style: Stroke, transform, brush, brush_transform, shape)`, `draw_image(image, transform)`, `draw_blurred_rounded_rect(transform, rect, color, radius, std_dev)` (an analytic blurred rounded rect, the only filter), `draw_glyphs(font) -> DrawGlyphs` builder, `push_layer(clip_style, blend, alpha, transform, clip)` where "The transform applies only to the clip shape", `push_clip_layer`, `push_luminance_mask_layer`, `pop_layer`, `append(other, transform)` (O(N)), `reset`. Brushes are `BrushRef` (solid, gradient, image; variants not described on the page). Shapes come from kurbo (paths with lines, quads, cubics, arcs, rects, rounded rects, circles) and stroke styles carry width/join/cap/miter/dash. Clipping is any path, always anti-aliased; blend modes and opacity are per layer.

### b. Text

The compute crate lists `skrifa` for glyph outlines and exposes `DrawGlyphs`, `Glyph`, `FontEmbolden` and `NormalizedCoord` for variable fonts ([docs.rs vello](https://docs.rs/vello/latest/vello/)); glyphs are drawn as outlines through the same path pipeline. The sparse-strips family has `glifo/` for "text and glyph-run support" and `vello_cpu` a `text` feature for "glyph rendering via glyph_run", with glyph caching "experimental and not recommended" ([README](https://github.com/linebender/vello/blob/main/README.md), [vello_cpu README](https://docs.rs/crate/vello_cpu/latest/source/README.md)). Shaping and layout are outside Vello, in Parley, whose planned software renderer would let users import it "without depending on a graphics API like Vello" ([Linebender roadmap May 2024](https://linebender.org/blog/roadmap-may-2024/)).

### c. Tessellation and anti-aliasing

The compute renderer encodes a scene "into compact path, draw, transform, and resource buffers", resolved into a `Recording` of GPU operations dispatched by `WgpuEngine`, using "prefix-scan algorithms" to parallelise what "traditional renderers often perform sequentially" ([ARCHITECTURE.md](https://github.com/linebender/vello/blob/main/ARCHITECTURE.md)). The design post describes GPU flattening "with one thread per curve", tile allocation per path, coarse rasterisation inserting segments into per-tile lists with `atomicExchange`, backdrop via `atomicAdd` and a prefix sum per tile scanline, then fine rasterisation; AA is an "exact area calculation" of winding; the cost is that it "won't run on older hardware or drivers" and "buffers are simply allocated and hoped to be big enough" ([Fast 2D rendering on GPU](https://raphlinus.github.io/rust/graphics/gpu/2020/06/13/fast-2d-rendering.html)). The quality trade-off is stated on the AA enum: `Area` AA integrates "the winding number over its square area", is "very accurate" when winding is 0 or 1 everywhere "but can result in conflation artifacts otherwise", and "generally has better performance than the multi-sampling methods"; `Msaa8` and `Msaa16` are the alternatives ([AaConfig](https://docs.rs/vello/latest/vello/enum.AaConfig.html)). Robust dynamic memory was the top 2024 priority because it "is essential to display large scenes without graphical artifacts" ([roadmap](https://linebender.org/blog/roadmap-may-2024/)).

Sparse strips are the newer architecture, after Raph Levien's "Potato: a hybrid CPU/GPU 2D renderer design" doc, relying on "efficient tiling, sorting, and sparse strip allocation" ([sparse_strips README](https://skia.googlesource.com/external/github.com/linebender/vello/+show/00b1f9688e2efd8a4e7fc65f03e3e7a2eef9b04d/sparse_strips/README.md)). Paths are flattened, binned into tiles and represented as "sparse horizontal strips"; coverage is kept near boundaries while "fully covered regions can be represented compactly", limiting work and memory "to the parts of the scene that affect the final image". `vello_cpu` rasterises and composites strips into a pixmap with SIMD and threads; `vello_gpu` does the same CPU preprocessing and uploads "scheduled strips and paint data" for GPU raster and compositing through wgpu or WebGL2 "using vertex and fragment rendering rather than compute shaders" ([ARCHITECTURE.md](https://github.com/linebender/vello/blob/main/ARCHITECTURE.md)). The hybrid README states "CPU-based tiling and GPU-accelerated fine rasterization" with "a balanced solution for a variety of hardware" ([vello_hybrid README](https://skia.googlesource.com/external/github.com/linebender/vello/+/bf5b0f968356bec23fefe76e715e2f91502893eb/sparse_strips/vello_hybrid/README.md)); the current README makes `vello_gpu` "the primary production GPU renderer as it matures" and moves the compute renderer under `research/` as "experimental" ([README](https://github.com/linebender/vello/blob/main/README.md)). Vello CPU claims "optimized SIMD implementations for all major architectures" with `u8_pipeline` for speed and `f32_pipeline` for accuracy; it does not yet support "Complex filter graphs" ([vello_cpu README](https://docs.rs/crate/vello_cpu/latest/source/README.md)).

### d. Output contract

Own backend: `Renderer::new(device, RendererOptions)` and `render_to_texture(device, queue, scene, texture, RenderParams { base_color, width, height, antialiasing_method })` ([docs.rs vello](https://docs.rs/vello/latest/vello/)). The host supplies a wgpu device and a target texture; `vello_cpu` renders to a `Pixmap` the host uploads. A host that wants Vello inside its own GPU frame integrates at the texture, not the draw list.

### e. Retained or immediate

A `Scene` is an encoding the caller owns: "Rendering does not clear a scene, so retained scenes should be reset between frames", and `append` lets sub-scenes be composed with a transform ([docs.rs Scene](https://docs.rs/vello/latest/vello/struct.Scene.html)). Vello CPU recommends `flush()` before rendering when multithreaded ([vello_cpu README](https://docs.rs/crate/vello_cpu/latest/source/README.md)).

### f. Language bindings

None official in C#; not documented in the primary sources read.

## 4. Dear ImGui's `ImDrawList`

### a. Surface of the API

`ImDrawList` is "A single draw command list (generally one per window, conceptually you may see this as a dynamic "mesh" builder)" ([imgui.h](https://github.com/ocornut/imgui/blob/master/imgui.h)). Primitives: `AddLine` (`(p1, p2, col, thickness = 1.0f, flags = 0)`), `AddLineH/V`, `AddRect`, `AddRectFilled`, `AddRectFilledMultiColor`, `AddQuad[Filled]`, `AddTriangle[Filled]`, `AddCircle[Filled]`, `AddNgon[Filled]`, `AddEllipse[Filled]`, `AddText` (two overloads, one with font/size/wrap/clip), `AddBezierCubic`, `AddBezierQuadratic`, `AddPolyline`, `AddConvexPolyFilled`, `AddConcavePolyFilled`, `AddImage`, `AddImageQuad`, `AddImageRounded`; a path builder `PathClear`, `PathLineTo`, `PathLineToMergeDuplicate`, `PathFillConvex`, `PathFillConcave`, `PathStroke`, `PathArcTo`, `PathArcToFast`, `PathEllipticalArcTo`, `PathBezierCubicCurveTo`, `PathBezierQuadraticCurveTo`, `PathRect`; state `PushClipRect`/`PushClipRectFullScreen`/`PopClipRect`, `PushTexture`/`PopTexture`, `PushDrawFlag`/`PopDrawFlag`; `AddCallback`, `AddDrawCmd`, `CloneOutput`; `ChannelsSplit`/`ChannelsMerge`/`ChannelsSetCurrent` for out-of-order submission; and raw `PrimReserve`, `PrimUnreserve`, `PrimRect`, `PrimRectUV`, `PrimQuadUV`, `PrimWriteVtx`, `PrimWriteIdx`, `PrimVtx`. `ImDrawFlags` carries per-corner rounding (`RoundTopLeft`… `RoundAll`), stroke `Closed`, `JoinMiter`, `CapSquare`, AA toggles `AAFill`/`AALines`/`AALineEnds`, stroke position `StrokeInside`/`StrokeCenter`/`StrokeCenterBiased`/`StrokeOutside`/`StrokeLegacy`, `TextNoPixelSnap`, `UseTexForRoundCorners`, `UseVtxOffset` ("allows large meshes with 16-bit ImDrawIdx"); the older `ImDrawListFlags` were merged into it in 1.93 ([imgui.h](https://github.com/ocornut/imgui/blob/master/imgui.h)). Colour is per vertex only (`ImU32`); there are no gradients other than `AddRectFilledMultiColor`, no path clip, no transforms (the caller transforms points), no blend modes and no layers.

### b. Text

Default rasteriser is stb_truetype, "not ideal for fonts rendered at small sizes, which may appear a little blurry"; `imgui_freetype` (`IMGUI_ENABLE_FREETYPE`) adds auto-hinting that "tends to improve the readability of small fonts" and colour emoji with FreeType 2.10+. Since 1.92 the atlas is dynamic: "the ImFontAtlas is initially created using a 512x128 texture, then grows as glyphs and fonts are used", glyph ranges are unnecessary, `PushFont(nullptr, new_size)` changes size at runtime, and backends need `ImGuiBackendFlags_HasTextures`. Oversampling (`OversampleH`) trades texture size for quality; the docs do not discuss subpixel rendering, only `PixelSnapH`. Atlas data is `Alpha8` or `RGBA32` ([FONTS.md](https://github.com/ocornut/imgui/blob/master/docs/FONTS.md)). No shaping or bidi.

### c. Tessellation and anti-aliasing

Everything is CPU triangles. `AddConvexPolyFilled` with AA builds two rings: inner vertices at the requested colour half a fringe inside the edge, outer vertices offset outward with `col_trans` (alpha zero), mitred up to `IM_POLYLINE_MITER_LIMIT` (4.0) then bevelled, interior as a fan; "Filled shapes must always use clockwise winding order. The anti-aliasing fringe depends on it." Lines take normals per segment and quads, with AA caps when `AALines`/`AALineEnds`. Since 1.93 AA lines use "super sampled textures" baked into the atlas chosen by `_SelectLineTexture()` ("For no anti-alias we use fully opaque texture, and no fringe expansion"). Circles sample a precomputed `ArcFastVtx[]` table in `PathArcToFast`, segment counts come from `SetCircleTessellationMaxError`, and the fringe is `_FringeScale`, the reciprocal of pixel density ([imgui_draw.cpp](https://github.com/ocornut/imgui/blob/master/imgui_draw.cpp)).

### d. Output contract

`ImDrawVert` is `pos` (ImVec2), `uv` (ImVec2), `col` (ImU32), "20 bytes by default. Override layout with IMGUI_OVERRIDE_DRAWVERT_STRUCT_LAYOUT". `typedef unsigned short ImDrawIdx;` "Default: 16-bit (for maximum compatibility with renderer backends)", overridable to 32-bit in `imconfig.h`. `ImDrawCmd` ("generally maps to 1 GPU draw call, unless it is a callback"): `ClipRect` (ImVec4 x1,y1,x2,y2), `TexRef` (ImTextureRef to the atlas or a user texture), `VtxOffset`, `IdxOffset`, `ElemCount` (a multiple of 3), `UserCallback`, `UserCallbackData`/`Size`/`Offset`. `ImDrawData` ("All draw command lists required to render the frame + pos/size coordinates to use for the projection matrix"): `Valid` ("Only valid after Render() is called and before the next NewFrame()"), `FrameCount`, `TotalIdxCount`, `TotalVtxCount`, `CmdLists` (ImVector<ImDrawList*>), `DisplayPos`, `DisplaySize`, `FramebufferScale`, `OwnerViewport`, `Textures` (ImVector<ImTextureData*>*), plus `DeIndexAllBuffers()` and `ScaleClipRects()`. `ImTextureData` carries `Status` (`OK`, `Destroyed`, `WantCreate`, `WantUpdates`, `WantDestroy`), `Format`, `Width`, `Height`, `BytesPerPixel`, `Pixels`, `UpdateRect`, `Updates`, `UnusedFrames`, `TexID` ([imgui.h](https://github.com/ocornut/imgui/blob/master/imgui.h)). The backend's job ([BACKENDS.md](https://github.com/ocornut/imgui/blob/master/docs/BACKENDS.md)): iterate `draw_data->Textures` and create/update/destroy per status (destroy only once `UnusedFrames > 0`); enable alpha blending, disable culling and depth, enable scissor, bilinear sampling; set an orthographic projection covering `DisplayPos` to `DisplayPos + DisplaySize`; upload each list's vertex and index buffers; per command convert `ClipRect` to framebuffer space with `FramebufferScale` and "always subtract draw_data->DisplayPos from clipping bounds", skip empty clips, bind `pcmd->GetTexID()`, draw `ElemCount / 3` indexed triangles from `IdxOffset` with `VtxOffset` added; set `ImGuiBackendFlags_RendererHasVtxOffset` or "rendering will be limited to 64K vertices per window"; call `UserCallback` except `DrawCallback_ResetRenderState`, which means re-apply state. The README's framing: "It outputs optimized vertex buffers that you can render anytime in your 3D-pipeline-enabled application" and "It never touches your GPU directly" ([README](https://github.com/ocornut/imgui/blob/master/docs/README.md)).

### e. Retained or immediate

Immediate: draw lists are rebuilt each frame, and the README warns not to "mistake immediate mode GUI for immediate mode rendering", since the output is batched into few draw calls ([README](https://github.com/ocornut/imgui/blob/master/docs/README.md)).

### f. Language bindings

Not read from primary sources; the many C# wrappers (not studied here) bind the C API generated from `imgui.h`.

## 5. Unity `Painter2D` / `MeshGenerationContext`

### a. Surface of the API

`Painter2D` is an "Object to draw 2D vector graphics" ([Painter2D](https://docs.unity3d.com/6000.2/Documentation/ScriptReference/UIElements.Painter2D.html)): `BeginPath`, `MoveTo`, `LineTo`, `BezierCurveTo` (cubic), `QuadraticCurveTo`, `Arc`, `ArcTo`, `ClosePath`, `Fill`, `Stroke`; properties `fillColor`, `strokeColor`, `lineWidth`, `lineCap`, `lineJoin`, `miterLimit` ("the limit on the ratio of the miter length to the stroke width"), `strokeGradient`; `SaveToVectorImage` saves "to a VectorImage object", `Clear` works on detached painters, `Dispose` frees unmanaged resources. Newer versions add `PushClip`/`PopClip`, `SetDashPattern`, `fillTexture` and `strokeFillGradient` (seen only in search listings of later docs, not verified on a page read). The sibling route is `MeshGenerationContext.Allocate(vertexCount, indexCount, texture)` returning `MeshWriteData`, `DrawText`, `DrawVectorImage`, `DrawMesh`, temp-mesh allocation from jobs, `InsertMeshGenerationNode`, `AddMeshGenerationJob` ([MeshGenerationContext](https://docs.unity3d.com/6000.2/Documentation/ScriptReference/UIElements.MeshGenerationContext.html)). Transforms, clipping and opacity come from the VisualElement tree, not the painter.

### b. Text

UI Toolkit font assets hold "a font atlas texture file that contains all of the characters", Static (baked) or Dynamic (filled on use) or Dynamic OS. Render modes: bitmap (`SMOOTH`, `RASTER`, `COLOR`, hinted variants) and SDF, which "stores contour distance as grayscale gradients" so text stays sharp when scaled and supports outlines and shadows; `SDFAA` is fast and the default for Dynamic, `SDF32/16/8` oversample for accuracy. Padding "creates room for the SDF gradient" (1:10 ratio recommended) and Multi Atlas Textures add atlases when one fills ([UIE-font-asset](https://docs.unity3d.com/6000.2/Documentation/Manual/UIE-font-asset.html)). Shaping internals are not documented on the pages read.

### c. Tessellation and anti-aliasing

Not documented on the API pages. `Allocate` requires "clock-wise winding order given that Y+ goes down" ([Allocate](https://docs.unity3d.com/6000.2/Documentation/ScriptReference/UIElements.MeshGenerationContext.Allocate.html)); how `Painter2D` tessellates and anti-aliases is native and unpublished. The UnityCsReference source for `Painter2D` was not located in the tree listing fetched, so no claim is made.

### d. Output contract

Reversed relative to ImGui: the UI system owns the renderer and the user writes vertices into it. `Vertex` "Represents a vertex of geometry for drawing content of VisualElement" with `position`, `tint`, `uv`, and `nearZ` as the z for flat UI ([Vertex](https://docs.unity3d.com/6000.2/Documentation/ScriptReference/UIElements.Vertex.html)); the public page lists no other fields, so the internal layout (clip/transform page indices and similar) is unverified. `Allocate`: "The maximum is 65535 (or UInt16.MaxValue)" vertices, indices in multiples of 3, "If a valid texture was passed, then the Vertex.uv values should be used to map the texture to the geometry", returned vertex count 0 means out of memory, and "UI Toolkit might store the texture in an internal atlas" ([Allocate](https://docs.unity3d.com/6000.2/Documentation/ScriptReference/UIElements.MeshGenerationContext.Allocate.html), [MeshGenerationContext](https://docs.unity3d.com/6000.2/Documentation/ScriptReference/UIElements.MeshGenerationContext.html)). `MeshWriteData` exposes `vertexCount`, `indexCount`, `SetNextVertex`, `SetNextIndex`, `SetAllVertices`, `SetAllIndices`, and must not be stored "outside the scope of VisualElement.generateVisualContent" ([MeshWriteData](https://docs.unity3d.com/6000.2/Documentation/ScriptReference/UIElements.MeshWriteData.html)); the `uvRegion` page was not reachable.

### e. Retained or immediate

Retained: content is generated in the `generateVisualContent` callback and kept; the pages read do not state the invalidation call (`MarkDirtyRepaint`) explicitly, so that is from general Unity knowledge and left unverified here.

### f. Language bindings

C# is the only public surface. `Painter2D` holds unmanaged resources (`Dispose`), so the drawing calls cross into native code; `MeshWriteData` is filled from managed code. The split is "managed writes vertices, native tessellates paths".

## 6. Godot `CanvasItem` and `RenderingServer` canvas items

### a. Surface of the API

`CanvasItem` draw calls ([class_canvasitem](https://docs.godotengine.org/en/stable/classes/class_canvasitem.html)): `draw_line`, `draw_dashed_line`, `draw_polyline[_colors]`, `draw_arc`, `draw_multiline[_colors]`, `draw_rect`, `draw_circle`, `draw_ellipse`, `draw_ellipse_arc`, `draw_texture`, `draw_texture_rect`, `draw_texture_rect_region`, `draw_msdf_texture_rect_region`, `draw_lcd_texture_rect_region`, `draw_style_box` (nine-patch via StyleBox), `draw_primitive`, `draw_polygon`, `draw_colored_polygon`, `draw_string`, `draw_multiline_string`, `draw_string_outline`, `draw_char[_outline]`, `draw_mesh`, `draw_multimesh`, `draw_set_transform`, `draw_set_transform_matrix`, `draw_animation_slice`, `draw_end_animation`. Most shape calls take `width` (negative means a thin two-point primitive) and `antialiased`. There is no path builder, no gradient paint (gradients are textures), no dash beyond `draw_dashed_line`; clipping is `clip_children` (`CLIP_CHILDREN_DISABLED/ONLY/AND_DRAW`, and "Clipping nodes cannot be nested or placed within a CanvasGroup"); blending and effects come from `material` (`CanvasItemMaterial` or a shader), `modulate`/`self_modulate`, `z_index`, `light_mask`, `texture_filter`/`texture_repeat`. The server mirrors it as `canvas_item_add_*` (line, polyline, multiline, rect, circle, ellipse, texture_rect[_region], msdf/lcd texture rect region, nine_patch, primitive, polygon, triangle_array, mesh, multimesh, particles, set_transform, clip_ignore, animation_slice) plus `canvas_item_set_clip`, `set_custom_rect`, `set_material`, `set_z_index`, `set_transform`, `set_modulate`, `set_visibility_layer`, `set_light_mask`, and canvas lights and occluders ([class_renderingserver](https://docs.godotengine.org/en/stable/classes/class_renderingserver.html)).

### b. Text

`TextServer` is "a low-level API" behind `TextLine`, `TextParagraph` and `Font`: `create_font`, `font_set_data`, `create_shaped_text`, `shaped_text_add_string`, `shaped_text_shape`, `shaped_text_get_glyphs`, `shaped_text_draw`, `shaped_text_get_line_breaks`, `shaped_text_fit_to_width`, with `Direction` and `LineBreakFlag` enums; fonts support `font_set_multichannel_signed_distance_field`, `font_set_msdf_pixel_range`, `font_set_msdf_size`, subpixel positioning (disabled "each glyph is rasterized once" through quarter-pixel), hinting, and antialiasing `NONE` (1-bit), `GRAY` (8-bit), `LCD` ("suitable only for rendering horizontal, unscaled text in 2D") ([class_textserver](https://docs.godotengine.org/en/stable/classes/class_textserver.html)). `TextServerAdvanced` is "An implementation of TextServer that uses HarfBuzz, ICU and SIL Graphite to support BiDi, complex text layouts and contextual OpenType features" ([class_textserveradvanced](https://docs.godotengine.org/en/stable/classes/class_textserveradvanced.html)). MSDF fonts render "at any size, without having to re-rasterize them", "always look crisp, even at huge sizes", but have a "Higher baseline cost", no hinting at small sizes, and "LCD subpixel optimization cannot be enabled for MSDF fonts" ([gui_using_fonts](https://docs.godotengine.org/en/stable/tutorials/ui/gui_using_fonts.html)).

### c. Tessellation and anti-aliasing

Two paths. The `antialiased` parameter attaches "half transparent 'feathers'" to boundaries (circle, rect, ellipse, dashed line; "supported only for positive width" for arcs and polylines); "This is the recommended method, as it has a lower performance impact in most cases", but "they work by generating additional geometry", and "Polygon2D, TextureProgressBar, and several custom drawing methods don't feature an antialiased property". MSAA 2D (Forward+/Mobile only) covers geometry edges and sprite edges but not nearest-neighbour texture interiors, custom shaders, Light2D specular or fonts ([2d_antialiasing](https://docs.godotengine.org/en/stable/tutorials/2d/2d_antialiasing.html), [class_canvasitem](https://docs.godotengine.org/en/stable/classes/class_canvasitem.html)). For odd widths the tutorial advises shifting endpoints by 0.5 ([custom_drawing_in_2d](https://docs.godotengine.org/en/stable/tutorials/2d/custom_drawing_in_2d.html)).

### d. Output contract

The server owns rendering. RIDs are "opaque handles to the server implementation"; "All objects are drawn to a viewport" and "all visible objects are some form of canvas item" parented into a canvas attached to a viewport ([class_renderingserver](https://docs.godotengine.org/en/stable/classes/class_renderingserver.html), [using_servers](https://docs.godotengine.org/en/stable/tutorials/performance/using_servers.html)). No vertex-level contract is exposed except `draw_mesh`/`add_triangle_array`.

### e. Retained or immediate

Retained server-side display lists: "The _draw function is only called once, and then the draw commands are cached and remembered, so further calls are unnecessary", re-recorded on `queue_redraw()`; "canvas items don't need to be redrawn on every frame, improving the performance significantly" ([custom_drawing_in_2d](https://docs.godotengine.org/en/stable/tutorials/2d/custom_drawing_in_2d.html), [class_canvasitem](https://docs.godotengine.org/en/stable/classes/class_canvasitem.html)). On the server, primitives once added "can't be modified", so the item is cleared and re-added, while transforms may change freely; "RenderingServer expects references to be kept around" ([using_servers](https://docs.godotengine.org/en/stable/tutorials/performance/using_servers.html)).

### f. Language bindings

The C# API "strives to be as idiomatic as is reasonably possible" with PascalCase; properties and methods on `GodotObject` types "require native (interop) calls as they talk to Godot's C++ core", and arrays and strings "require marshalling which is comparatively pricey" ([c_sharp_basics](https://docs.godotengine.org/en/stable/tutorials/scripting/c_sharp/c_sharp_basics.html)). The glue is `NativeFuncs`, a `[GenerateUnmanagedCallbacks]` partial class whose "order of the methods defined in NativeFuncs must match the order" of the array in `glue/runtime_interop.cpp`, offering `godotsharp_method_bind_get_method` (a MethodBind looked up by class and method name), `godotsharp_method_bind_call` (Variant-boxed) and `godotsharp_method_bind_ptrcall` (raw `void**` args and `void*` return) ([NativeFuncs.cs](https://github.com/godotengine/godot/blob/master/modules/mono/glue/GodotSharp/GodotSharp/Core/NativeInterop/NativeFuncs.cs)). That a `DrawRect` call resolves to a MethodBind and a ptrcall is an inference from these declarations, not read in generated code.

## 7. Flutter `Canvas`/`Paint`, `Picture`, Impeller

### a. Surface of the API

`Canvas` "Creates a canvas for recording graphical operations into the given picture recorder", with a current transform and clip; draws: `drawArc`, `drawAtlas`/`drawRawAtlas`, `drawCircle`, `drawColor`, `drawDRRect`, `drawImage`, `drawImageNine`, `drawImageRect`, `drawLine`, `drawOval`, `drawPaint`, `drawParagraph`, `drawPath`, `drawPicture`, `drawPoints`/`drawRawPoints`, `drawRect`, `drawRRect`, `drawRSuperellipse`, `drawShadow` (for a `Path` at a material elevation), `drawVertices`; clips `clipPath`, `clipRect` (with `ClipOp`), `clipRRect`, `clipRSuperellipse`, each with `doAntiAlias` defaulting to true; `save`, `saveLayer` ("creates a new group which subsequent calls will become a part of", flattened on restore with the paint's `colorFilter` and `blendMode`), `restore`, `restoreToCount`, `getSaveCount`, `translate`, `scale`, `rotate`, `skew`, `transform` (4×4 column-major), `getTransform`, `getLocalClipBounds`, `getDestinationClipBounds` ([Canvas](https://api.flutter.dev/flutter/dart-ui/Canvas-class.html)). `Paint` is "A description of the style to use when drawing on a Canvas": `blendMode`, `color`, `colorFilter`, `filterQuality`, `imageFilter`, `invertColors`, `isAntiAlias`, `maskFilter` (blur), `shader`, `strokeCap`, `strokeJoin`, `strokeMiterLimit`, `strokeWidth`, `style` (`PaintingStyle.fill`/`stroke`) ([Paint](https://api.flutter.dev/flutter/dart-ui/Paint-class.html)). This is Skia's model with the SkiaSharp-style names.

### b. Text

`ParagraphBuilder` "Builds a Paragraph containing text with the given styling information" via `pushStyle`/`addText`/`pop`/`addPlaceholder`, configured by a `ParagraphStyle` for alignment, truncation and ellipsizing; `Paragraph` "retains the size and position of each glyph in the text and can be efficiently resized and painted", with `layout(ParagraphConstraints)`, `getBoxesForRange`, `getPositionForOffset`, `getWordBoundary`, `getLineBoundary`, `computeLineMetrics`, `getGlyphInfoAt`, intrinsic widths and `didExceedMaxLines`, drawn by `Canvas.drawParagraph` ([ParagraphBuilder](https://api.flutter.dev/flutter/dart-ui/ParagraphBuilder-class.html), [Paragraph](https://api.flutter.dev/flutter/dart-ui/Paragraph-class.html)). Under Impeller, layout and shaping stay in SkParagraph; Impeller's Typographer "renders shaped glyph runs but does no text layout or shaping" and its `GlyphAtlas` is "A texture containing the bitmap representation of glyphs in different fonts" of type `kAlphaBitmap` ("only an 8-bit color channel") or `kColorBitmap` ("N32 premul colors"), with a rectangle packer and a generation id to match frames ([Impeller README](https://github.com/flutter/flutter/blob/master/engine/src/flutter/impeller/README.md), [glyph_atlas.h](https://github.com/flutter/flutter/blob/master/engine/src/flutter/impeller/typographer/glyph_atlas.h), [Impeller FAQ](https://github.com/flutter/flutter/blob/master/docs/engine/impeller/docs/faq.md)).

### c. Tessellation and anti-aliasing, and why Impeller replaced Skia

Impeller "precompiles a smaller, simpler set of shaders at engine-build time so they don't compile at runtime"; its objectives are predictable performance ("builds all pipeline state objects upfront"), instrumentability, portability ("author shaders once and convert them to backend-specific formats"), modern APIs ("uses, but doesn't depend on, features available in modern APIs like Metal and Vulkan") and concurrency ([docs.flutter.dev Impeller](https://docs.flutter.dev/perf/impeller)). The FAQ gives the reason: Flutter apps "via their use of Skia, were susceptible to the problem of jank" from just-in-time shader compilation, warm-up failed ("developers abandoned this self-serve warmup mechanism"), and Skia "can and does generate and compile shaders at runtime"; even Graphite's "design decisions made to support those requirements make offline shader compilation impossible". Impeller has "no runtime shader generation, reflection, or compilation", needs fewer than 50 shaders, and uses stencil-then-cover, crediting Skia: "Ideas such as stencil-then-cover that Impeller now uses originated from Skia". "Impeller has no direct dependencies on Skia", keeping SkParagraph and Skia's codecs; it "outperforms the old renderer not only in worst-frame timed benchmarks, but is also faster on average" and costs "around 100kb" ([Impeller FAQ](https://github.com/flutter/flutter/blob/master/docs/engine/impeller/docs/faq.md)). The README's layout puts `renderer` as "The very lowest level of the renderer that is still backend agnostic", `entity` as "a framework for building 2D renderers" with pass rewriting for "collapsing passes, or, eliding them completely", `compiler` (impellerc), `geometry`, `typographer`, `display_list` ("The replacement for //impeller/aiks"), and a tessellator utility ([Impeller README](https://github.com/flutter/flutter/blob/master/engine/src/flutter/impeller/README.md)). The dedicated anti-aliasing doc was not reachable, so MSAA details are not asserted. Status: default on iOS ("the only supported rendering engine on iOS"), Android API 29+ with an OpenGL fallback, and desktop "as of Flutter 3.47"; web stays on Skia ([docs.flutter.dev Impeller](https://docs.flutter.dev/perf/impeller)).

### d. Output contract

Own backend (Metal, Vulkan, OpenGL ES). The engine renders the compositor's layer tree into the platform surface; embedders integrate through the Embedder API, not a draw list (the FAQ lists "Embedder API users" as a priority) ([Impeller FAQ](https://github.com/flutter/flutter/blob/master/docs/engine/impeller/docs/faq.md)).

### e. Retained or immediate

Recorded. `PictureRecorder` "Records a Picture containing a sequence of graphical operations"; `Picture` is "An object representing a sequence of recorded graphical operations" with `approximateBytesUsed`, `toImage`, `toImageSync`, `dispose` ([PictureRecorder](https://api.flutter.dev/flutter/dart-ui/PictureRecorder-class.html), [Picture](https://api.flutter.dev/flutter/dart-ui/Picture-class.html)). In the engine the record is a `DisplayList`, which "encapsulates a persistent sequence of rendering operations", "used in a similar manner to the Skia SkPicture mechanism", built by `DisplayListBuilder`, read back through `DlOpReceiver`, with RTree culling ([display_list.h](https://github.com/flutter/flutter/blob/master/engine/src/flutter/display_list/display_list.h)).

### f. Language bindings

Dart only; not applicable to C#.

## 8. ThorVG

### a. Surface of the API

"A production-ready vector graphics engine designed for creating interactive apps and creative tools", C++, small footprint, CPU-optimised ([README](https://github.com/thorvg/thorvg/blob/main/README.md)). Features: shapes, solid and linear/radial/conic gradients, stroking with "width, joins, caps, dash patterns, and trimming", a "retained-mode scene graph and hierarchical transformations", "W3C compositing and blending modes, masking, clipping, and nested scenes", text, images (SVG, PNG, JPEG, WebP, raw), effects (blur, drop shadow, tint, tritone, colour replacement, fill), Lottie and GIF. The header ([thorvg.h](https://github.com/thorvg/thorvg/blob/main/inc/thorvg.h)): `Paint` base with `rotate`, `scale`, `translate`, `transform` (3×3), `opacity` (0–255, "may require multiple render pass for composition"), `mask` (MaskMethod, e.g. `Alpha`), `blend` (BlendMethod), `bounds`, `duplicate`, `visible`; `Shape` with `moveTo`, `lineTo`, `cubicTo`, `close`, `appendRect` (rounded via rx/ry), `appendCircle`, `appendPath` (command and point arrays), `strokeWidth`, `strokeFill` (colour or gradient), `strokeDash` (odd patterns repeated), `strokeCap`, `strokeJoin`, `strokeMiterlimit` (default 4), `trimpath`, `fill`, `fillRule` (NonZero default, EvenOdd), `order` (stroke before or after fill); `Fill` with `colorStops`, `spread` (`Pad`…), `LinearGradient::linear`, `RadialGradient::radial` (focal), `ConicGradient::conic`; `Picture::load`/`size`/`origin`/`paint(id)`; `Scene::add`/`remove`/`paints` and `Scene::add(SceneEffect, ...)` for `DropShadow` ("Apply a drop shadow effect with a Gaussian Blur filter"), `GaussianBlur`, `Fill`, `Tint`, `Tritone`; `Text` with `font`, `size`, `text`, `fill`, `outline`, `wrap`, `layout`, `align`.

### b. Text

"unicode, scalable TTF/OTF fonts, and multi-line text layout" with its own loader; `Text::wrap/layout/align` is the paragraph API ([README](https://github.com/thorvg/thorvg/blob/main/README.md), [thorvg.h](https://github.com/thorvg/thorvg/blob/main/inc/thorvg.h)). No HarfBuzz, FreeType or ICU dependency is listed among the optional dependencies (OpenMP, GL/WebGL, wgpu-native, libpng, libjpeg-turbo, libwebp) ([README](https://github.com/thorvg/thorvg/blob/main/README.md)); the shaping depth is not documented, so complex-script support is unverified.

### c. Tessellation and anti-aliasing

Backends "CPU/SIMD (Software)" with AVX2 and NEON, OpenGL/ES, WebGL, WebGPU (WebGPU "approximately 1.8× higher rendering throughput" than OpenGL on an M1, "may vary") ([README](https://github.com/thorvg/thorvg/blob/main/README.md)). The software rasteriser's algorithm is not described in the sources read. Performance claims: "~2.9× faster" than "a widely-used vector graphics engine" (ThorVG v1.1 vs Skia v148, M2 Pro, 2K), "approximately 30%" from SIMD, a binary "as small as approximately 170KB".

### d. Output contract

Own backends via `Canvas` targets: `SwCanvas::target(buffer, stride, w, h, ColorSpace)` on a caller-owned buffer ("Do not access buffer during Canvas::add() - Canvas::sync()"), `GlCanvas::target(display, surface, context, id, w, h, cs)` ("assumes that the appropriate OpenGL context is already current", `ABGR8888S` only), `WgCanvas::target(device, instance, target, w, h, cs, type)` with surface or texture targets ([thorvg.h](https://github.com/thorvg/thorvg/blob/main/inc/thorvg.h)). A host integrates by giving ThorVG an FBO id or wgpu texture.

### e. Retained or immediate

Retained with explicit update/draw/sync: "A canvas is an entity responsible for drawing the target"; `add(target, at)` transfers ownership; `update()` processes "Only paint objects that have changed" and "may be performed asynchronously"; `draw(clear)` may run asynchronously and "may implicitly call update()"; `sync()` "must be called after the draw() regardless of threading"; `dirtyRegions()` exposes partial rendering when `EngineOption::SmartRender` is supported; `Initializer::init(threads)` sets a thread pool ("A value of 0 disables worker threads") ([thorvg.h](https://github.com/thorvg/thorvg/blob/main/inc/thorvg.h)). Partial rendering "updates only the portions of a vector scene that have changed" and offers little for highly dynamic content ([README](https://github.com/thorvg/thorvg/blob/main/README.md)).

### f. Language bindings

A C API (`-Dbindings="capi"`), WebAssembly, and listed bindings for Android (Kotlin), Flutter, Swift, Unity (C#), Python, Rust, D and npm ([README](https://github.com/thorvg/thorvg/blob/main/README.md)); the C# binding's shape was not read.

## 9. Rive Renderer

### a. Surface of the API

The public abstraction is `rive::Renderer` with `save`, `restore`, `transform(Mat2D)`, `drawPath(RenderPath*, RenderPaint*)`, `clipPath(RenderPath*)`, `drawImage(...)` and `drawImageMesh(...)` (both ending in `float opacity`); `RenderPaint` with `style`, `color`, `thickness`, `join`, `cap`, `blendMode`, `shader(rcp<RenderShader>)`, `invalidateStroke`; `RenderPath` with `addRenderPath(path, transform)`, `addRawPath`, `addPath`; `RenderShader` (gradients), `RenderImage`, `RenderBuffer` with `map`/`unmap` ([renderer.hpp](https://github.com/rive-app/rive-runtime/blob/main/include/rive/renderer.hpp)). The path-building methods (`moveTo`, `cubicTo`, fill rule) live in other headers not read. Clipping is by path only; blend modes are per paint; the renderer is "custom-built for Rive content, for animation, and for runtime" ([renderer README](https://github.com/rive-app/rive-runtime/blob/main/renderer/README.md)).

### b. Text

The renderer draws glyphs as paths ("the same rendering algorithm that makes it possible to render paths and text insanely fast") ([Introducing Vector Feathering](https://rive.app/blog/introducing-vector-feathering)); shaping is outside the renderer and not covered by the sources read.

### c. Tessellation and anti-aliasing

`RenderContext` is the "Top-level, API agnostic rendering context for RiveRenderer" owning GPU buffers for "pixel local storage path rendering": curves are tessellated into a shared tessellation texture (midpoint fan and outer cubic patches), each path gets a 16-bit id, simple gradients use two texels and complex ones a row of the gradient texture, clips get unique ids in a clip buffer, and the interlock mode is chosen in `beginFrame()`: `disableRasterOrdering` means "Use atomic mode (preferred) or depthStencil instead of rasterOrdering", and `msaaSampleCount > 0` "forces depthStencil mode"; feathering renders into an "Atlas for offscreen feathering" ([render_context.hpp](https://github.com/rive-app/rive-runtime/blob/main/renderer/include/rive/renderer/render_context.hpp)). The GL tiers are "Pixel Local Storage: best — Apple GPUs, modern mobile", fragment shader interlock (NVIDIA, Intel), R/W texture or `EXT_shader_pixel_local_storage` fallbacks, and MSAA for "truly minimal drivers" ([C++ renderers doc](https://rive.app/docs/runtimes/cpp/renderers.md)). AA is coverage from triangles: "tessellating triangles around vector edges to calculate coverage", each adding signed coverage by winding, Bézier geometry "tessellated into self-overlapping triangle patches"; feathering widens the one-pixel ramp to "any width based on the feathering strength" with a bell curve, computed analytically rather than by Gaussian convolution ([How Rive reinvented feathering](https://rive.app/blog/how-rive-reinvented-feathering-for-the-vectorian-era)). Where tessellation runs (CPU or GPU) is not stated in the pages read; the header's "tessellation texture" implies GPU-side evaluation but that is inference.

### d. Output contract

Own backends: D3D11, D3D12, Metal, Vulkan, OpenGL/WebGL2, each through `RenderContext*Impl::MakeContext`, with render targets wrapped from the host's textures and a `FrameDescriptor` (`loadAction`, `clearColor`, `msaaSampleCount`, `disableRasterOrdering`, `ditherMode`) per `beginFrame`/`flush`; "Most apps leave these at defaults" ([C++ renderers doc](https://rive.app/docs/runtimes/cpp/renderers.md)). Resource budgets are explicit: `pushDraws()` and `allocateGradient()` return false when full and the caller issues a `logicalFlush()` and retries ([render_context.hpp](https://github.com/rive-app/rive-runtime/blob/main/renderer/include/rive/renderer/render_context.hpp)).

### e. Retained or immediate

Immediate per frame (`beginFrame` … draw calls … `flush`), with the runtime's artboards as the retained model above it.

### f. Language bindings

Not read; Rive ships C# runtimes for Unity but their renderer binding was not studied.

## 10. Blend2D (CPU)

### a. Surface of the API

`BLContext` is the rendering context: `save`/`restore` (with `BLContextCookie`), `set_fill_style`/`set_stroke_style` (colours, gradients, patterns), `set_comp_op`, `set_global_alpha`, `set_fill_alpha`/`set_stroke_alpha`, stroke `width`, `miter_limit`, `join`, `start_cap`/`end_cap`, `dash_array`, `dash_offset`, `transform_order`; `translate`, `scale`, `skew`, `rotate`, `apply_transform` and `post_*` variants, `user_to_meta`; `clip_to_rect`, `restore_clipping` (rectangular clips only); `fill_all`, `fill_rect`, `fill_round_rect`, `fill_circle`, `fill_ellipse`, `fill_chord`, `fill_pie`, `fill_triangle`, `fill_polygon`, `fill_path`, `fill_geometry` and matching `stroke_*`, `fill_utf8_text`, `fill_glyph_run`, `blit_image`, `flush` ([BLContext](https://blend2d.com/doc/classBLContext.html)). `BLPath` has `move_to`, `line_to`, `quad_to`, `cubic_to`, `conic_to`, `arc_to`, `arc_quadrant_to`, `elliptic_arc_to` (SVG 'A'), `close`, `add_box/rect/circle/ellipse/round_rect/arc/chord/pie/line/triangle/polyline/polygon`, `add_path` with ranges and transforms, `add_reversed_path`, `add_stroked_path`, `transform`, `fit_to`, `get_bounding_box`, `hit_test` ([BLPath](https://blend2d.com/doc/classBLPath.html)). The stroker "uses curve offsetting instead of flattening" ([about](https://blend2d.com/about.html)).

### b. Text

Own font engine: "basic support for TTF and OTF fonts" without FreeType or OS libraries. `BLGlyphBuffer` "Can hold either text or glyphs and provides basic memory management that is used for text shaping, character to glyph mapping, glyph substitution, and glyph positioning", with a primary buffer for text/glyphs and a secondary for positions, `set_utf8_text` and friends, `glyph_run()` output ([BLGlyphBuffer](https://blend2d.com/doc/classBLGlyphBuffer.html)). The text group page was not reachable, so the GSUB/GPOS coverage is not asserted.

### c. Tessellation and anti-aliasing

Pure CPU: "a high-quality and high-performance analytic rasterizer", with pipelines produced by a JIT built on AsmJit ("uses JIT compilation to generate optimal 2D pipelines at runtime") for X86/X86_64/AArch64 from SSE2 to AVX-512, and an experimental portable pipeline where JIT is unavailable ([about](https://blend2d.com/about.html)). Multithreading is "asynchronous rendering" where render calls go into a command queue that workers process band by band; `BLContextCreateInfo::thread_count` is the "Number of worker threads to use for asynchronous rendering, if non-zero" and zero means synchronous ([about](https://blend2d.com/about.html), [BLContextCreateInfo](https://blend2d.com/doc/structBLContextCreateInfo.html)). Claims: a prototype "was already faster than both Qt and Cairo in composition", the tiger at "1.5ms to render the same tiger on Apple M3 by using a single thread and 1ms when using two threads", and a caveat that a single comparison against Vello "alone cannot be used to draw any conclusions" ([about](https://blend2d.com/about.html)). The benchmark page compares AGG, Cairo, Qt, Skia and JUCE with `bl_bench` over shapes from 8×8 to 256×256 and Solid/Linear/Radial/Conic/Pattern styles, focused on "raw rendering performance and not on caching" ([performance](https://blend2d.com/performance.html)).

### d. Output contract

A `BLImage` in memory; a host uploads it as a texture. No GPU path.

### e. Retained or immediate

Immediate calls into a context, optionally queued to worker threads; `flush` with `BLContextFlushFlags` ([BLContext](https://blend2d.com/doc/classBLContext.html)).

### f. Language bindings

A C API is first-class ("The C API is listed for users who need it") ([doc index](https://blend2d.com/doc/index.html)); no official C# binding was found in the sources read.

## 11. Text building blocks, independently

**HarfBuzz** "is a text-shaping engine": shaping "is the process of translating a string of character codes" into positioned glyphs, depending on string, font, script and language, via OpenType GSUB/GPOS ("the dominant format"), Graphite or AAT ([what is HarfBuzz](https://harfbuzz.github.io/what-is-harfbuzz.html)). Its scope is "a single horizontal (or vertical) line using the font provided": "HarfBuzz won't help you with bidirectionality" ("Libraries such as ICU and fribidi can do this for you"), "won't help you with line breaking, hyphenation, or justification" (ICU's break iterator is suggested), and "won't help you with text that contains different font properties" (runs must be split) ([what HarfBuzz doesn't do](https://harfbuzz.github.io/what-harfbuzz-doesnt-do.html)). Consumers here: Skia (SkShaper), Godot (TextServerAdvanced).

**FreeType** is a font engine "designed to be small, efficient, highly customizable, and portable" for TrueType, CFF, WOFF, OpenType, Type 1, SFNT bitmap (including colour emoji), PCF, FNT, BDF, PFR; it renders "a high-quality monochrome bitmap, or anti-aliased pixmap, using 256 levels of 'gray'", has a "full-featured and efficient TrueType bytecode interpreter" and an auto-hinter, and "doesn't provide APIs to perform higher-level features like text layout" ([freetype.org](https://freetype.org/freetype2/docs/index.html)). Render modes: `NORMAL` (8-bit AA), `LIGHT`, `MONO`, `LCD`/`LCD_V` (3× width/height), and `SDF`, whose "positive (unsigned) 8-bit bitmap values can be converted to the single-channel signed distance field" by subtracting 128 with an adjustable spread; load flags `FT_LOAD_NO_HINTING`, `FT_LOAD_TARGET_*`, `FT_LOAD_COLOR` (BGRA bitmaps, SVG since 2.12, COLR v0) ([ft2-glyph_retrieval](https://freetype.org/freetype2/docs/reference/ft2-glyph_retrieval.html)). Consumers: NanoVG (optional), ImGui (`imgui_freetype`), msdfgen's loader.

**stb_truetype** parses TrueType/OpenType (CFF/Type 2 handled), extracts metrics and shapes, renders "to one-channel bitmaps with antialiasing (box filter)" and "to one-channel SDF bitmaps" (`stbtt_GetGlyphSDF`), packs atlases with `stbtt_PackBegin/PackFontRanges/PackEnd` (stb_rect_pack "optional, but you really want it"), and oversamples: "Oversampling a font increases the quality by allowing higher-quality subpixel positioning", "especially valuable at smaller text sizes". It does no hinting (an open todo), no shaping (kerning tables and "basic GPOS-based kerning" only), and warns "NO SECURITY GUARANTEE -- DO NOT USE THIS ON UNTRUSTED FONT FILES" because it "does no range checking of the offsets found in the file"; since 1.06 its rasteriser "more accurately measures pixel coverage" except where shapes overlap ([stb_truetype.h](https://github.com/nothings/stb/blob/master/stb_truetype.h)). Consumers: NanoVG/fontstash, ImGui by default.

**msdfgen / msdf-atlas-gen.** A multi-channel SDF can "reproduce sharp corners almost perfectly by utilizing all three color channels", decoded as the "median of the three channels"; modes `sdf`, `psdf`, `msdf`, `mtsdf` (MSDF plus true SDF in alpha). Generation: `loadGlyph` (FreeType), `shape.normalize()`, `edgeColoringSimple`, `generateMSDF` with a `Projection` and `Range`; the shader computes `screenPxRange()*(sd - 0.5)`, must read the channels "in linear space just like the alpha channel and not as sRGB", and `screenPxRange()` "must never be lower than 1" and below 2 "there is a high probability that the anti-aliasing will fail" ([msdfgen](https://github.com/Chlumsky/msdfgen/blob/master/README.md)). msdf-atlas-gen produces the atlas plus JSON/CSV/Artery layout with per-glyph `advance`, `planeBounds`, `atlasBounds`; atlas types `hardmask`, `softmask`, `sdf`, `psdf`, `msdf`, `mtsdf`; `-pxrange` (default 2) and `-size`; glyphs "are bin-packed in an irregular fashion" or `-uniformgrid`; `ImmediateAtlasGenerator` for one-shot and `DynamicAtlas` for glyphs "on-the-fly" ([msdf-atlas-gen](https://github.com/Chlumsky/msdf-atlas-gen/blob/master/README.md)). Consumers of the idea: Godot MSDF fonts, Unity SDF font assets, Skia SDFT.

**Slug** "renders shapes on the GPU directly from outline data composed of quadratic Bézier curves": each glyph is a quad over its bounds, a shader computes coverage from the curves, "no precomputed texture images or signed distance fields", two data textures per font (curves and spatial structure), claimed as "the only existing GPU method that renders properly antialiased glyphs with no artifacts under both magnification and minification"; it also does layout features (kerning, ligatures, OpenType features, colour emoji) and vector graphics; commercial, with the paper at JCGT ([sluglibrary.com](https://sluglibrary.com/)). The paper PDF ([JCGT 6(2)](https://jcgt.org/published/0006/02/02/)) was downloaded but could not be text-extracted in this environment, so the banding scheme is not quoted here.

**GPU glyph approaches, side by side.**
- *Bitmap atlas* (ImGui, fontstash, Impeller, Skia's "99.99% case"): rasterise per size on the CPU, pack, draw textured quads; cheap and hintable, re-rasterised per size.
- *SDF/MSDF atlas* (Unity, Godot, Skia SDFT, msdf-atlas-gen): one atlas for many sizes, outlines and shadows for free, loses hinting and LCD ([gui_using_fonts](https://docs.godotengine.org/en/stable/tutorials/ui/gui_using_fonts.html)).
- *Loop-Blinn*: triangulate the interior and render each curve's control triangle with the implicit test "u² − v" ("For convex curves, a positive result means the pixel is outside the curve"), cubics classified as "serpentine, cusp, or loop" ("the preprocessing—assignment of procedural texture coordinates—is nontrivial"), AA from "an approximate signed distance based on gradients", with the constraint "Bézier convex hulls cannot overlap" and reliance on MSAA at triangle edges; resolution independent "without tessellation or sampling artifacts" ([GPU Gems 3 ch. 25](https://developer.nvidia.com/gpugems/gpugems3/part-iv-image-effects/chapter-25-rendering-vector-art-gpu)).
- *Slug*: per-pixel curve evaluation, no atlas, exact coverage (above).
- *Vello/Pathfinder style*: glyphs are paths through the general rasteriser. Pathfinder "can compute exact fractional trapezoidal area coverage on a per-pixel basis" ("effectively 256xAA"), renders fonts "with slight hinting", supports LCD subpixel AA, and tiles on the CPU with SIMD/Rayon in its D3D9 mode or on the GPU with compute in D3D11 mode ([Pathfinder README](https://github.com/servo/pathfinder/blob/main/README.md)); Vello draws glyph outlines with `DrawGlyphs` (above).

## 13. What a complete painter must have

**Core (every mature vector painter studied has it):**
- A path with move/line/cubic/close, quads, arcs, and rect/rounded-rect/circle helpers — Skia, NanoVG, Vello (kurbo), Unity Painter2D, Flutter, ThorVG, Rive, Blend2D. (ImGui has lines/beziers/arcs in `Path*` but only convex or concave fills, no stroker joins beyond miter; Godot has no path at all.)
- Fill and stroke with width, cap, join and miter limit — Skia, NanoVG, Vello, Unity, Flutter, ThorVG, Rive (`thickness`, `join`, `cap`), Blend2D.
- A paint that is a solid colour, a linear gradient or a radial gradient, or an image — Skia, NanoVG (box gradient as the third), Vello, Flutter, ThorVG (conic too), Blend2D (conic too), Unity (gradients), Rive (shader).
- An affine transform with save/restore — Skia, NanoVG, Vello (per op plus layers), Flutter, ThorVG (per paint), Rive, Blend2D, Godot (`draw_set_transform`).
- A rectangular clip — all, including ImGui's `PushClipRect` and NanoVG's `nvgScissor`.
- Images drawn into a rectangle with a sampler — all.
- Text drawn from a loaded font — all except Rive's public header (glyphs are paths there).
- Anti-aliased edges by default — all (Godot requires the `antialiased` flag or MSAA).

**Common (most have it):**
- Path (non-rectangular) and anti-aliased clipping — Skia, Vello, Flutter, ThorVG (mask/clip paints), Rive (`clipPath`), Unity (`PushClip` in newer versions). Not NanoVG, ImGui, Blend2D (`clip_to_rect` only).
- Opacity/blend layers composited offscreen — Skia `saveLayer`, Vello `push_layer`, Flutter `saveLayer`, ThorVG `opacity`/`blend` ("may require multiple render pass"), RmlUi `PushLayer`/`CompositeLayers`. Not NanoVG, ImGui, Blend2D (global alpha only).
- Blend modes beyond src-over — Skia, Vello, Flutter, ThorVG, Rive, Blend2D, NanoVG (GL blend funcs).
- Dashes — Skia (`SkDashPathEffect`), Vello (stroke style), ThorVG, Blend2D, Godot (`draw_dashed_line`), Unity (`SetDashPattern` in later docs). Not NanoVG, ImGui.
- Even-odd and non-zero fill rules — Skia, Vello, ThorVG (`fillRule`), Blend2D, Unity (`FillRule` per search listing, unverified), NanoVG (even-odd only), Rive (Clockwise fill rule mentioned for feathering).
- Nine-slice / lattice images — Skia (`drawImageNine`, `drawImageLattice`), Flutter (`drawImageNine`), Godot (`add_nine_patch`, StyleBox), RmlUi via geometry. Not NanoVG, Vello, ImGui (`AddImageRounded` only).
- A paragraph layout API — Skia (SkParagraph), Flutter (ParagraphBuilder), Godot (TextParagraph), ThorVG (`Text::wrap/layout/align`), NanoVG (`nvgTextBox`), Unity (TextCore).
- Recording/replay or server-side retention — Skia (SkPicture), Flutter (Picture/DisplayList), Godot (canvas items), Unity (generateVisualContent), ThorVG (scene), Vello (Scene). Not NanoVG, ImGui, Blend2D.
- Per-vertex coloured meshes — Skia (`drawVertices`), Flutter (`drawVertices`), Godot (`draw_mesh`, `add_triangle_array`), ImGui (everything), Unity (`Allocate`), Rive (`drawImageMesh`).

**Rare:**
- Image filters (blur, drop shadow, colour matrix, displacement, lighting, backdrop) — Skia (`SkImageFilters`, `SaveLayerRec::fBackdrop`), Flutter (`imageFilter`), ThorVG (scene effects), Vello (blurred rounded rect only), RmlUi (`CompileFilter`).
- Runtime shaders in the paint — Skia (SkSL `SkRuntimeEffect`), Godot (materials), RmlUi (`CompileShader`).
- Luminance masks — Vello (`push_luminance_mask_layer`), ThorVG (mask methods).
- Material-elevation shadows — Skia (`SkShadowUtils`), Flutter (`drawShadow`).
- Analytic feathering — Rive.
- Coons patches, atlases of sprites with RSXform — Skia, Flutter.
- Hit testing on paths — Blend2D (`hit_test`), Flutter/Skia via `Path.contains` (not studied).
- Text on a path — SkiaSharp `DrawTextOnPath`.

These are the painters and UI layers that hand the host something to draw, rather than drawing themselves. `DrawList2D` is included so the reader can see where it stands; nothing here designs its successor.

Where `DrawList2D` already matches or exceeds: it is the ImGui contract (interleaved vertices, 16/32-bit indices, per-command texture and scissor, index range, base vertex) with Unity-style multi-texture and a pipeline table ImGui and RmlUi lack, explicit blend modes and colour spaces none of the triangle contracts carry, and a parameter block (128 bytes) that could hold a NanoVG-style paint (`NVGpaint` is 6+2+1+1+4+4 floats and an int, under 80 bytes). Where it falls short of what the others hand over: NanoVG's contract carries a fringe width, a stroke width, fill bounds and a *transformed* scissor with feathering, and its stencil-then-cover fills need a backend step the plain "one command, one draw" model has no slot for; RmlUi's carries layers (`PushLayer`/`CompositeLayers` with blend mode and filters), clip masks drawn from geometry, a per-draw transform matrix, and retained compiled geometry; ImGui's carries a dynamic texture lifecycle (`ImTextureData` status) and user callbacks for state resets; Clay's carries no geometry at all, leaving rounded rectangles and text to the host. None of the triangle contracts express gradients except as parameter blocks (NanoVG) or shaders (RmlUi `CompileShader`); the GPU-owning painters (Skia, Vello, Impeller, Rive) never expose a contract at this level at all.

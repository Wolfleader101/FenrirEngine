# 01: One mirror registration, and Install registers an extension in one call

**What to build:** the four registration structs derive from one `MirrorRegistration`, the five makers share one `MakeMirror`, and `Scripting::InstallImpl` registers an extension's four lists through one registry method instead of four runs of a lambda (spec: "One mirror registration").

- **`include/FenrirScripting/ComponentRegistry.hpp`**: `struct MirrorRegistration { std::string name; std::string typeName; std::size_t size = 0; std::size_t alignment = 0; bool scriptDefined = false; std::function<Iris::CallResult<void>(const Iris::Component&)> validate; }`, documented once with what the four structs' field comments say today (the name C# uses, the C# struct it is checked against and why a script cannot claim a name for a struct of its own, the size and alignment the C# struct must match, a script-defined one's lifetime, what `validate` reports). `ComponentRegistration : MirrorRegistration` keeps `type`, `readOnly`, `required`; `EventRegistration : MirrorRegistration` keeps `bind`; `SharedStructRegistration : MirrorRegistration` adds nothing; `ResourceRegistration : MirrorRegistration` keeps `scope`, `readOnly`, `find`, `insert`, `remove`. Each struct's own comment says what its kind is and which maker makes it, as today, without restating the base's fields. `template <typename T, typename Mapping = T> MirrorRegistration MakeMirror(std::string name)` holds the mapping size and alignment assert, the `Iris::StructValue<Mapping>` assert, and sets the six fields (`scriptDefined` false). `MakeComponent`, `MakeEvent`, `MakeSharedStruct` and `Detail::MakeResource` start from `MakeMirror<T, Mapping>` (slicing it into the derived struct by assignment or a constructor taking the base) and add their kind's asserts (default constructibility, trivial copyability where the kind needs it) and extras. `MakeComponent`'s designated initialiser becomes assignments. A component's `size` and `alignment` are set from `sizeof(T)` and `alignof(T)` beside its `ComponentType`, so the base reads alike for every kind.
- **`src/ScriptData.cpp`**: the script-defined `ComponentRegistration{...}` initialiser (around line 245) becomes assignments, setting `size` and `alignment` from the report as the event one does.
- **`src/ComponentRegistry.hpp`**: `std::optional<std::string> ComponentRegistry::AddExtension(ScriptingExtension& extension, App& app)`. For each event, `bind(app)` first, failing with "the event '<name>' in extension '<extension>' names a queue the app already has under another type"; then each list's registrations moved into its table with `Add`, failing with "a component in extension '<extension>' has an empty or duplicate name" (noun from `RegistryTable::Noun`, article from its first letter, as Install's lambda spells it). Its comment says a failure midway leaves what was added, because Install discards the registry with the Scripting it was building. `RegistryTable` and the tables are unchanged.
- **`src/Scripting.cpp`**: the second startup stage's body is the three context assignments and `for (auto& extension : config.extensions) if (auto failure = state->components.AddExtension(extension, app)) return StartupFailure{*failure, {}};`. The `addAll`, `nothing` and `bindQueue` lambdas go.
- **`Tests/Rules/RegistryTableTests.cpp`**: cases for `AddExtension`: four kinds registered from one extension and found by their tables; a name taken by another kind fails with the noun and article of the kind that failed ("an event", "a shared struct"); an event whose queue the app holds under another type fails naming the event; a failure midway leaves the earlier registrations (the documented behaviour). The physics drift tests (`PhysicsScriptingTests.cpp`) and `ChangeBufferTests.cpp` compile unchanged.

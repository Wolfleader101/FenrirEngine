Filed from the built-in-extension grilling (spec decisions 5, 8). Cut from `builtin-extension-02-natives-on-the-contract`, since both regenerate the built-in binding's outputs. It also edits `packages/Iris/Tools/Iris.Bindings/src/`, where the generator-hygiene spec's tickets are working (describe-api's kind classifier, the unread wire records, the fixture copy, literal formatting): start it after those merge, and rebase onto their result. The cross-spec wait is here in text because `Blocked by:` may only name tickets of this folder.

Built (2026-10-28), with two of the three bindings short of the text, both for reasons outside Iris.Bindings' used-types rule:

- **Physics keeps its `[bound-types]` table and does not use the built-in binding.** `packages/FenrirPhysics/api/FenrirPhysics.api.toml`, the package's own selection, selects `Fenrir::Transform` and `Fenrir::Entity` as bound types (its components and events hold them), so `FenrirPhysics.api.json` describes both as bound types while the built-in binding mirrors them as structs. Adding the built-in binding to `uses` then fails the refusal this ticket keeps, whether the table stays (`Fenrir::Entity is mirrored by the binding it uses, FenrirScripting.binding.toml, but [bound-types] names it too`) or goes (`FenrirPhysics.api.json selects it as a bound type and FenrirECS.api.json as a shared struct: select it as one`). Making them nested there instead would hand the `Fenrir::Entity` fields to the built-in binding's `EntityLink` mirror, and that mirror is in the built-in binding's `readonly-structs`, so `Joint.BodyA` and `Joint.BodyB`, which physics C# assigns, would become `readonly` fields, and every `= EntityLink.None` would read `= new()` (the same value, not the same bytes). What the generator would need, for physics to use the built-in binding: (1) a way for a binding to bind a type a used binding mirrors as a bound type of its own, with its own `[bound-types]` entry in force (today's refusal, which protects a binding from two spellings of one type, would have to admit an own entry that names the used mirror's C# type); or (2) a used mirror held by a field here without the "a field holding a read-only struct is readonly too" rule, and a per-mirror default expression (`EntityLink.None`) the used binding states once, so the physics mirrors stay byte-identical through the mirror. (1) is the smaller change and keeps physics's `EntityLink` fields as they are; the entries say `include = "FenrirScripting/Generated/FenrirScriptingMappings.hpp"`, which `uses` would then include anyway.
- **DebugDraw uses the built-in binding, but its selection still names `Fenrir::EntityValue`.** `ShapeOptions::relativeTo` and `TextOptions::relativeTo` default to `EntityValue(0xFFFFFFFFu)`, a constructor call `tools/describe-api` records for a selected bound type only; unselected, it fails (`the default 'EntityValue(0xFFFFFFFFu)' is not one the description records`). The `EntityValue.hpp` header line goes (the type is reached through `ScriptOptions.hpp`, and the description is unchanged); the `[types]` line stays, with a comment saying why. The same holds for physics's `ScriptQueries::QueryFilter::ignoreBody`. What the tool would need: `tools/describe-api` reading a used binding's bound types as selected ones, which means a selection naming the bindings it uses, or the binding configuration being read by the tool.
- **Renderer** is as the ticket says. Its mappings header loses its own `EntityValue` size assert and `EntityValueMapping.hpp` include (the built-in binding's header, now included, carries both) and its generated-from line names one description; its natives header and registration change that line only.
- Every C# mirror of the three packages is byte-identical to the committed one; the built-in binding's natives, mirrors and defaults test are unchanged.

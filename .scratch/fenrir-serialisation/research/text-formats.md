# Text formats for scene files and data assets

Research for [03 Which text formats suit scene files and data assets, and what libraries read them?](../issues/03-text-formats-for-game-data.md). Read on 2026-11-10 from the primary sources in the Sources section; every claim carries a `[S<n>]` pointer, and each source names the version, tag, commit or document date read. Items that could not be confirmed from a primary source say so.

The map's constraints ([map.md](../map.md), Notes): one text format serves scene files, game-defined data assets and dev-time settings; it is hand-editable, diff- and merge-friendly, writes typed and polymorphic references, and its library stays `PRIVATE` to one package (ADR-0010's pattern [S0]), appearing in no public header. The engine today is C++20, CMake 3.20, built with MSVC and clang presets on Windows (CI builds `msvc-x64-release` only) [S1].

## Summary

- **No surveyed format is hand-editable, mergeable and typed at once.** JSON is tool-friendly and reader-rich but has no comments, no trailing commas, no `NaN`/`Infinity` and no type syntax; YAML and KDL carry types natively (tags, `(type)` annotations); TOML and the INI-like Godot format read best as flat tables but nest badly; Godot, Unity and Bevy each ended up with their own grammar or dialect.
- **Comments are lost on every rewrite** by every surveyed C++ library and all but one C# library (Tomlyn): comment preservation is a property of the writer, not the format, so a format chosen "for comments" buys them only in files the tool never rewrites.
- **Merge behaviour is decided by identity and layout, not syntax**: git merges lines; what breaks merges is renumbered ids (Godot 3's integer ids, fixed with pseudo-random ids in 4.0), indentation-wide rewrites and multi-line diffs from missing trailing commas. Unity ships a semantic merge tool for its YAML; nobody else does.
- **Two libraries need no new submodule in C#** (System.Text.Json is in the runtime) and only JSON/JSONC reads identically from both languages with in-box tools; for YAML, `yaml-cpp` and YamlDotNet already disagree on what `yes` means.
- **A C++ reader with structured `line:column` errors exists for TOML (toml++), YAML (yaml-cpp, rapidyaml) and not for JSON** (nlohmann: byte index, text-only line/column; RapidJSON: offset, "does not keep track of line number"; simdjson: error code; Glaze: byte count plus a formatter) nor KDL (ckdl: no location).
- **Glaze is out on today's toolchain**: it requires C++23, CMake 3.31 and Visual Studio 2026 / Build Tools 14.50 with `/Zc:preprocessor` [S23]; the repo is C++20 on CMake 3.20 [S1].

Notes per candidate:

- **JSON.** The only format here with a reader in every language's standard kit (System.Text.Json in .NET [S30]; nothing in C++'s standard library). Its spec permits implementations to limit nesting depth, number precision and string length (RFC 8259 §9) [S2]; STJ's default depth is 64 [S30]. JSON5 is explicitly "not intended to be used for machine-to-machine communication" [S4], and **no surveyed C++ or C# library reads JSON5** (nlohmann [S20], RapidJSON [S21], simdjson [S22], Glaze [S23], STJ [S30] each read at most comments and trailing commas). JSONC, by contrast, is readable by nlohmann (`ignore_comments`, 3.9.0+; trailing commas only in the unreleased 3.13.0) [S20], RapidJSON (`kParseCommentsFlag`, `kParseTrailingCommasFlag`) [S21], Glaze (`opts.comments`, `read_jsonc`) [S23] and STJ (`JsonCommentHandling.Skip`, `AllowTrailingCommas`) [S30]; simdjson reads neither [S22].
- **TOML.** Built for config, and its own community says it "nests very poorly" (kdl.dev's comparison [S15]). A nested list of structs is either `[[rows]]` headers (one per row) or inline tables, which until 1.1.0 could not span lines or end with a comma [S7][S8]. 1.1.0 shipped on 2025-12-24 [S9], so the live libraries split: toml++ v3.4.0 (2023) is TOML 1.0 and its unreleased `master` is 1.1 [S24]; Tomlyn 2.11.x is "TOML 1.1.0 only" and "does not support TOML 1.0" [S31]; Glaze's TOML is 1.1 [S23]. A file that uses 1.1's multi-line inline tables is unreadable by a 1.0 reader.
- **YAML.** The "Norway problem" (`no` parsed as `false`) is YAML 1.1's bool type [S11b]; the 1.2 core schema keeps only `true`/`false` and drops `!!binary`, `!!omap`, the `<<` merge key and underscore digit separators, aiming to be "a valid superset of JSON" [S11]. Unity's files declare `%YAML 1.1` and Unity's own parser "does not support the full YAML specification", "does not support tags" (beyond its own) and does not handle multi-document input [S40][S41]. YAML libraries also differ on bools in typed fields: yaml-cpp's `convert<bool>` accepts `y/n`, `yes/no`, `true/false`, `on/off` [S27b], and YamlDotNet's typed-bool path accepts `true|y|yes|on` / `false|n|no|off` while its untyped path accepts only `true`/`false` [S32]; a file is only "YAML 1.2" if the engine writes it so.
- **Godot's format.** INI-like sections carrying a GDScript-like Variant syntax: `[gd_scene load_steps=4 format=3 uid="uid://..."]`, `[ext_resource type="Texture2D" uid="uid://..." path="res://..." id="2_eorut"]`, `[sub_resource type="CapsuleShape3D" id="CapsuleShape3D_fdxgg"]`, `[node name="Cube" type="Node3D"]` with `transform = Transform3D(1, 0, 0, …)` [S12]. The parser is `core/variant/variant_parser.cpp` (69,928 bytes at master sha `30af2df8`) and the scene reader/writer `scene/resources/resource_format_text.cpp` (67,413 bytes at sha `1a8ac9ad`) [S13][S13b]; inline objects are `Object(ClassName, "prop": value, …)` instantiated via `ClassDB` [S13]. The docs say the format is "mostly human-readable and easy for version control systems to manage" and that `;` comments "will be discarded when saving the file using the Godot editor" [S12].
- **KDL 2.0.0.** Node-based: every node has a name, ordered arguments, properties and an optional children block, so a record is `row a=1 b=2` and a tree is nesting; `(type)` annotations attach a type to any value or node, with reserved annotations including `u8`…`u128`, `f32`, `f64`, `uuid`, `url`, `base64` (§3.8) [S14]. Spec licence is CC BY-SA 4.0 [S14b]. The listed C++ implementation is `kdlpp`, "distributed as part of the ckdl project and needs C++20" [S15b]; **no repository named `kdl-cpp` was found** (two searches returned only ckdl/kdlpp and ROS kinematics "KDL" results) [S28b]. kdl.dev lists Zellij, Niri, Bikeshed and orogene as users; no game engine [S15].
- **S-expressions.** RFC 9804 (June 2025) is the modernised Rivest draft: everything is an octet string or a list, there are no numbers or booleans, and the only typing is a `[display-hint]` prefix [S16]. EDN adds tagged elements (`#inst`, `#uuid`, user tags with a prefix), `;` comments, commas as whitespace, maps whose order carries "no semantics" [S17]. Neither has a surveyed C++ or C# library, so in practice this is the custom-grammar option with a Lisp surface.
- **RON.** Rust-shaped: optional struct names, native enum variants (`Newtype(1.5)`, `Struct(x: 1.0)`), `Some`/`None`, comments, trailing commas, `inf`/`NaN` numbers [S18][S19]; its README says it is "not self-describing" and that round trips through `ron::Value` are not yet guaranteed [S18]. No C++ or C# implementation was sought; using it from Fenrir would mean writing a parser.
- **A small custom grammar.** Three of the surveyed engines own their grammar: Godot (above), Unity (a "custom subset of YAML" parsed by "UnityYAML" [S40][S41]) and Bevy, whose BSN work chose a hand-written lexer/parser over a serde data model; the thread's maintainer preferred a custom parser because it means "less code to ship at runtime" and worried "some aspects of BSN will be hard to encapsulate in the serde data model" [S45][S47]. The concrete cost Godot paid is ~137 KB of C++ for parser plus text saver/loader [S13][S13b], zero third-party licences, and a format no editor highlights or validates out of the box. The benefit all three bought is the same: references, types and polymorphism are syntax (`ExtResource("…")`, `!u!4 &id`, enum variants), not a convention layered on a generic tree.

## For hand editing and review

**Comments.** Every format but JSON has them (table above). What matters is whether the library the engine rewrites files with keeps them: among the C++ libraries none does (toml++ issue #28 "Preservation of comments and whitespace" closed "not planned" on 2026-10-13, maintainer: "They are not data. They're comments." [S24b]; yaml-cpp #457 "Currently there is no option to do this", duplicate of #154 open since 2015 [S27c]; rapidyaml's node type has no comment bit [S28]; nlohmann treats comments as whitespace [S20]; kdlpp's DOM has no comment field [S29]). In C#, only Tomlyn keeps them, through its "lossless, trivia-preserving syntax tree" [S31]; STJ's `JsonNode` has no comment API [S30]; YamlDotNet's scanner drops them by default and the object serialiser can only emit new ones from `[YamlMember(Description)]` [S32]. Godot's editor discards them too [S12]. Consequence: comments survive only in files the engine never rewrites (hand-authored data assets, settings), or the engine stores them as data (a `description` field).

**Trailing commas.** JSON forbids them [S2], so appending an element modifies the previous line, and every "add one item" diff touches two lines; JSON5, TOML arrays, RON allow them [S4][S7][S19]; YAML block style, KDL, TOML tables and Godot sections have no separator to forget [S10][S14][S12].

**Multi-line strings.** TOML `"""`/`'''` [S7], YAML `|`/`>` [S10], KDL `"""` with dedent and raw `#"…"#` [S14], RON raw strings [S19]; JSON none, JSON5 only backslash-newline continuation [S4].

**A tuning table (nested list of structs).** KDL reads best (one node per row: `row hp=100 speed=3.5`); TOML needs `[[rows]]` per row or, from 1.1.0, multi-line inline tables [S7][S8]; YAML `- {hp: 100, speed: 3.5}` flow rows inside block lists [S10]; JSON an array of one-line objects, with the comma problem above; Godot's format has no struct rows except `Dictionary`/`Object(...)` values [S13].

**Float round-tripping.** Writers surveyed: nlohmann v3.12.0 uses Grisu2 ("shortest possible decimal … which rounds back", with Grisu2's known not-always-shortest caveat) and the unreleased 3.13.0 switches to Żmij [S20b]; RapidJSON uses Grisu2 and, unless `kParseFullPrecisionFlag` is set, **parses with up to 3 ULP error by default** [S21]; Glaze ports Żmij [S23b]; yaml-cpp 0.9.0 uses Dragonbox for "shortest known unique representation" [S27]; toml++ prints "the shortest text that parses back to the same double" [S24]; rapidyaml's c4core uses `std::to_chars` under C++17 and warns its default `FTOA_FLEX` "may cause a truncation of the precision" [S28c]; .NET's `double.ToString()`/STJ are shortest-round-trip since .NET Core 3.0 [S30b][S30c], Tomlyn uses `"R"` [S31b], YamlDotNet `"G"` [S32b]. Unity side-steps the question by optionally writing IEEE-754 hex (`0x3F800000`) [S42]. **NaN and infinities:** JSON cannot carry them [S2]; nlohmann and Glaze silently write `null` [S20][S23b]; RapidJSON needs `kWriteNanAndInfFlag` [S21]; simdjson parses them only with `SIMDJSON_ENABLE_NAN_INF` [S22]; STJ writes them as the strings `"NaN"`/`"Infinity"` under `AllowNamedFloatingPointLiterals`, which its docs warn "can potentially produce JSON that cannot be parsed by other JSON implementations" [S30d]. TOML, YAML, KDL, JSON5 and RON carry them natively (table).

**Stable key ordering for byte-identical rewrites.** No generic format defines order (JSON "unordered", TOML "not guaranteed", YAML "do not have an order", KDL properties "SHOULD NOT be assumed" [S2][S7][S10][S14]), so the writer decides, and libraries disagree: nlohmann's default `json` sorts keys (`std::map`) and only `ordered_json` keeps insertion order [S20c]; toml++'s `toml::table` is a `std::map` sorted by key [S24c]; kdlpp's properties are a sorted `std::map` [S29]; Glaze writes struct members in declaration order [S23c]; yaml-cpp, rapidyaml, RapidJSON, STJ's `JsonObject` and Tomlyn keep insertion order [S27d][S28][S21][S30e][S31c]. A byte-identical rewrite from two languages therefore needs an ordering rule owned by the engine (declaration order from the API description, ADR-0042) and a writer driven by it, plus one float formatter and one indentation rule on both sides.

**Diffs and three-way merges.** git's built-in `text` driver is a "3-way file level merge" over lines, with `union` as the only other text option; a semantic merge is a custom `merge.<name>.driver` command given `%O %A %B` [S50]. So formats differ by how many lines one edit touches: block YAML and KDL change one line per fact; JSON changes two per list append (comma); re-indenting a YAML block or reformatting a JSON object rewrites every line. Hunk headers can name the enclosing record for section-headed formats (TOML `[table]`, Godot `[node …]`) via `diff.<name>.xfuncname`; git ships patterns for cpp, csharp, markdown and others but none for these formats [S50]. Engine evidence: Godot 2.0 left XML because it was "not friendly to VCS (Git, SVN)" [S43]; Godot 4's ids changed from integers to `1_7bt6s`-style pseudo-random ids to "minimize conflicts when merging, but still user readable (so, not UUID)" [S44], with the saver seeding its generator from the path hash so rewrites are deterministic [S13b]; Unity's `UnityYAMLMerge` merges `.unity`, `.prefab` and `.meta` "semantically" and other YAML assets only with `--force`, with a float epsilon in `mergerules.txt` [S46]; O3DE's prefabs are JSON with JSON Patch overrides chosen because plain text in source control avoids "merge and diff difficulties that XML often causes" [S48]. Writing only non-default fields shrinks diffs (O3DE, Flax, Bevy's draft BSN writer) but a Bevy reviewer flagged the fragility when defaults change [S47b].

## For the data model

**A typed reference (path or id plus a type).**
- JSON: a convention object `{"ref": "...", "type": "T"}` or a string with a scheme; O3DE uses JSON Patch paths into nested instances [S48]; Flax writes inline hex GUID strings and `TypeName` keys [S49]; Unity `{fileID: 123, guid: ..., type: 2}` [S42].
- YAML: a tag (`!ref path`) or Stride's `ref!! <guid>` for in-file links and `guid:path` for assets [S49b]; yaml-cpp exposes `Node::Tag()` and resolves `%TAG` handles [S27e]; rapidyaml resolves local and `%TAG`-handled tags [S28d].
- TOML: a string or an inline table `{ path = "...", type = "T" }`; no type syntax [S7].
- KDL: `(T)"path"` or a node `ref "path" type="T"`; the spec reserves `uuid` and `url` annotations [S14].
- Godot: `ExtResource("1_7bt6s")` / `SubResource("…")`, typed by the `[ext_resource type=…]` header, and `uid://…` identities that "always ha[ve] priority" over paths [S12][S44b].
- RON: a newtype `Ref("path")` [S19].

**A polymorphic value (derived type in a base-typed field).** Native in YAML (a tag on the mapping; Stride tags every component `!TransformComponent`, user types as `!Namespace.Type,Assembly` [S49b]; YamlDotNet `WithTagMapping` emits a tag only when the runtime type differs [S32c]), KDL (a `(Derived)` annotation or the node name), Godot (`Object(Derived, …)` [S13]) and RON (enum variants [S19]). A convention in JSON: STJ's `[JsonPolymorphic]`/`[JsonDerivedType]` write a `$type` discriminator that "must be placed at the start of the JSON object" unless `AllowOutOfOrderMetadataProperties` is set [S30f]; O3DE adds `$type` holding a class name or UUID [S48b]; Flax `TypeName` [S49]. TOML has no mechanism but a `type = "Derived"` key [S7]. Unity cannot do it at all for inline classes (a dog/cat/giraffe array deserialises as three base instances); only `UnityEngine.Object` references keep their type [S42b].

**Sub-objects embedded in a file.** Nested values in every format; identity for cross-reference is the question. Godot and Unity flatten: `[sub_resource id=…]` sections referenced by `SubResource(id)` [S12], and one YAML document per object with `&fileID` anchors [S42]; Stride keeps a flat `Parts` list keyed by GUID with `ref!!` links [S49b]; O3DE nests `Instances` with `Source` and `Patches` [S48]; Flax a flat `Data` array with `ParentID` [S49]. YAML anchors/aliases exist for shared sub-objects but rapidyaml requires scalar keys and Glaze's YAML limits block-collection anchors [S28d][S23d].

**Binary blobs.** JSON: base64 string (no spec type). YAML 1.1 had `!!binary`; 1.2 removed it from the type library [S11]. TOML: a string [S7]. KDL reserves `base64` and `base85` string annotations [S14]. Godot writes `PackedByteArray(…)` inline and reserves its binary `.scn`/`.res` for large data, suggesting Git LFS for those [S12][S44c]; Unity writes typed arrays as one hex scalar (`0100000002000000i`) [S42]. Sidecar files are what every engine uses for real payloads (models, images); a text format should only carry small blobs.

Observations:

- **Build cost as a `PRIVATE` submodule.** The header-only four (nlohmann, RapidJSON, Glaze, toml++) add no library target; nlohmann's single header is 1.9 MB and toml++'s 547 KB per translation unit that includes them, which is why both offer multi-header trees and toml++ a compiled mode [S20][S24]. The compiled four (simdjson, yaml-cpp, rapidyaml, ckdl) are static libraries like Jolt and SDL [S1]. ckdl is the only one whose CMake defaults tests on and exports no namespaced target [S29]. All stay out of public headers if the package keeps the parsed tree private and exposes engine types, which the map requires [map.md].
- **Glaze does not fit the toolchain** (C++23, CMake 3.31, VS 2026 / MSVC 14.50) [S23]; the repo is C++20 on CMake 3.20 [S1]. It is the only one with compile-time reflection, and it ships TOML 1.1 and a YAML 1.2 reader/writer behind the same `glz::meta`, but its YAML lacks merge keys, multi-document streams and complex keys [S23d][S23e]. It is worth re-checking when the toolchain moves.
- **Line and column.** toml++, yaml-cpp and rapidyaml report both as structured fields; nlohmann only in message text; RapidJSON and simdjson give an offset; ckdl gives nothing [S20][S21][S22][S24][S27][S28][S29]. The map's "editor-ready" goal (diagnostics for broken files) favours the first three or an engine-owned parser.
- **RapidJSON is stale as a release** (v1.1.0, 2016) though its master still receives fixes [S21]; pinning means pinning a commit.
- **Reflection in the library** is not what the map wants: types are described by `describe-api`'s `<Package>.api.json` (ADR-0042) [map.md], so a tree-based reader (nlohmann, RapidJSON DOM, toml++ `toml::table`, yaml-cpp `Node`, rapidyaml `Tree`) that the engine walks with its own type descriptions fits better than a struct-mapping one (Glaze, simdjson `from`).

## What this means for the format decision (ticket 12)

Findings, not a decision:

1. **Hand-editability and tool-rewritability pull apart.** A file the engine rewrites loses comments in every C++ library surveyed; a file the engine never rewrites (settings, hand-authored data assets) keeps them in any format but JSON. Deciding which files are tool-owned and which are human-owned matters more than the format's comment syntax.
2. **Typed and polymorphic references are native only in YAML tags, KDL annotations and a custom grammar.** JSON and TOML need a `$type`/`type` convention, which STJ, O3DE and Flax all converged on and which works, at the cost of a reserved key and an ordering rule.
3. **Merge-friendliness comes from identity and layout**: stable readable ids (Godot's fix), one fact per line (block YAML, KDL, TOML, Godot's format), no renumbering on save, deterministic ordering from the type description, and a shortest-round-trip float writer on every writer.
4. **The library landscape favours TOML and YAML for diagnostics** (toml++, yaml-cpp, rapidyaml report line and column) and JSON/JSONC for cross-language reach (STJ in-box); KDL's C++ story is one C11 library with no error locations and a sorted-property DOM, so KDL in Fenrir would mean an engine-owned parser.
5. **A custom grammar is a real option with a known price**: ~137 KB of C++ in Godot [S13][S13b], tooling built from zero, and a second parser if C# tools ever need the files; its payoff is references and types as syntax and ownership of every error message and rewrite rule, which Godot, Unity and Bevy each judged worth it.
6. **Toolchain facts**: Glaze needs C++23/CMake 3.31/VS 2026 [S23] and the repo is C++20/CMake 3.20 [S1]; toml++'s release is TOML 1.0 while Tomlyn and Glaze are 1.1-only [S24][S31][S23]; RapidJSON's last release is 2016 [S21].

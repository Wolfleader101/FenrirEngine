# How C++ engines describe their types for serialisation and editors

Research for [04-how-engines-reflect-types-for-files](../issues/04-how-engines-reflect-types-for-files.md). Read 2026-11-10 against engine source at pinned tags or commits, official docs, library sources and the WG21 papers (every pin is in "Sources" at the end). Fenrir's baseline for comparison is `tools/describe-api` (ADR-0042, `tools/describe-api/SCHEMA.md`): a libclang tool reads a package's selected headers and writes a committed, language-neutral `<Package>.api.json` of its plain-data types (fixed kinds, offsets, literal defaults, doc comments, enums, tagged unions; no strings, no dynamic containers, no inheritance, pointers opaque).

## The field in one table

| Engine or library | Where the description is written | Where it lives at run time | What a file names a type by | Doc comments reach the editor |
| --- | --- | --- | --- | --- |
| Unreal 5.9 | `UPROPERTY()` etc. in headers, harvested by UHT (a C# tool, not a C++ parser) | generated `.generated.h`/`.gen.cpp` compiled into the module; `UClass`/`FProperty` objects built at start-up | class path, with per-property `FPropertyTag` (name, type, struct/enum name, GUIDs) | yes (tooltips from comments, editor-only) |
| Godot 4.5 | hand-written `_bind_methods()`: `ADD_PROPERTY(PropertyInfo(...), "set", "get")` | `ClassDB` (setter/getter pairs through `Variant`; no offsets) | class name string + `script` resource path (+ `script_class`) | no (docs are separate XML) |
| O3DE 2510.2 | hand-written `Reflect(ReflectContext*)`: `SerializeContext`, `EditContext`, `BehaviorContext` | `ClassData`/`ClassElement` registry with offsets, UUIDs, RTTI | UUID (ObjectStream) or name with UUID fallback (JSON `$type`) | no (descriptions are typed strings) |
| Flax 1.13 | `API_CLASS`/`API_FIELD(Attributes="...")` markers parsed by Flax.Build's own tokenizer | generated C# wrappers (inspected by .NET reflection) + `BinaryModule` type table with sizes and per-struct `GetField`/`SetField` thunks | fully qualified managed name `Namespace.Type` + Guid ids | yes (`/// <summary>` becomes `[Tooltip]`) |
| Bevy 0.17/0.20 | `#[derive(Reflect)]` | `TypeRegistry` of `TypeInfo` (named fields, type paths, custom attributes) | `TypePath` string (module path + ident) | feature-gated (`documentation`) |
| Lumix (2026-11) | `//@ property min 0` comments scanned by a string-matching tool | fluent registry of getter/setter properties with attributes; committed `*.gen.h` | component name + per-module hand-written binary with version branches | no |
| Hazel, Wicked | none: hand-written YAML/binary per component and a hand-written panel | none | hard-coded keys / registered name strings | no |
| RTTR, refl-cpp, Boost.Describe, magic_enum, glaze, cereal | macros or templates inside the C++ | compiled registry or constexpr descriptors; nothing on disk | none built in (cereal: registered name) | never |
| C++26 (P2996 + P3394) | the declaration itself, plus `[[=expr]]` annotations | consteval `std::meta::info`; a program must dump it | n/a | no (comments are not reflected) |

The split that matters for Fenrir: **Unreal, Flax and Lumix generate from the headers** (like describe-api) but emit code that is compiled in, not a neutral file; **Godot, O3DE, RTTR register by hand at run time** and the description is only reachable from a running program; **Bevy and the compile-time libraries declare in-language**. Only Godot publishes a committed language-neutral dump (`extension_api.json`), and it is produced by running the engine, carries no offsets for `Object` classes, and omits hints, usage flags and defaults for properties. Nothing read here does what describe-api does: parse headers with a real C++ front end and commit a layout-bearing neutral description.

## Mechanism

**Unreal: header harvesting, generated C++, compiled in.** The system is opt-in: a type is `UCLASS()`/`USTRUCT()`/`UENUM()` with `GENERATED_BODY()` and `#include "X.generated.h"` as the last include; each reflected member is one `UPROPERTY(...)` line. UnrealBuildTool runs UnrealHeaderTool when a header changed; UHT "isn't a real C++ parser. It understands a decent subset of the language and actively tries to skip any text that it can", and ignores `#ifdef` except `WITH_EDITOR`/`WITH_EDITORONLY_DATA`. Since 5.1 UHT is C# inside UBT (`Engine/Source/Programs/Shared/EpicGames.UHT`; plugin exporters are `[UhtExporter]` methods in `*.ubtplugin.csproj`) and the C++ UHT was deprecated. Output is `.generated.h` per header and `.gen.cpp` per module, written only when changed and never committed; Epic's stated reason for generating C++ rather than data is that it "computes member offsets/etc… at startup using C++ expressions, rather than trying to reverse engineer the packing behavior of a particular platform/compiler/optimization combo". The run-time model is `UField > UStruct > {UClass, UScriptStruct, UFunction}`, `UEnum`, and `FField > FProperty > {FBoolProperty, FEnumProperty, FNumericProperty, FObjectPropertyBase, FOptionalProperty, FStructProperty, ...}` with `ArrayDim`, `ElementSize`, `PropertyFlags`, iterated by `TFieldIterator<FProperty>`. Cost: one macro per type, one `UPROPERTY` per field; an unannotated member is legal and invisible. [UE blog "Unreal Property System (Reflection)"; UE 5.9 docs: Objects, Unreal Header Tool, 5.1 release notes; UE 5.5 API: `FProperty`]

**Godot: macros plus a hand-filled run-time registry; no header parsing.** `GDCLASS(Class, Base)` generates `get_class_static()`, `initialize_class()` (registers in ClassDB and calls `_bind_methods()`) and the `_get_property_listv` chain. Each class's static `_bind_methods()` calls `ClassDB::bind_method(D_METHOD("set_x", "x"), &T::set_x)` for a setter and a getter and then `ADD_PROPERTY(PropertyInfo(Variant::FLOAT, "x", PROPERTY_HINT_RANGE, "0,20,0.01"), "set_x", "get_x")`; `ClassDB::add_property` resolves both `MethodBind`s and stores a `PropertyInfo` plus a `PropertySetGet`. `ClassDB::ClassInfo` holds `inherits_ptr`, `method_map`, `constant_map`, `enum_map` (with `is_bitfield`), `signal_map`, `property_list`, `property_setget`, `creation_func`, flags and an `APIType` (core, editor, extension). There is no field offset anywhere: a property is a setter/getter pair invoked through `Variant`, so reading a file is `Object::set(name, Variant)`. Cost per field: a setter, a getter, two `bind_method` lines and one `ADD_PROPERTY`; godot-cpp is the same shape. [godot 4.5-stable `core/object/object.h` L494-566, `core/object/class_db.h` L84-150, `class_db.cpp` L1458-1512; docs "GDExtension C++ example"]

**O3DE: intrusive id macros plus three hand-written builder chains.** Every type has a UUID literal: `AZ_TYPE_INFO(T, "{uuid}")`, `AZ_RTTI(T, "{uuid}", Bases...)` (adds virtual `RTTI_GetType`/`RTTI_IsTypeOf`/`RTTI_AddressOf`, up to five bases), `AZ_COMPONENT(T, "{uuid}")` for components; non-intrusive types use `AZ_TYPE_INFO_SPECIALIZE`. A static `Reflect(AZ::ReflectContext*)` per class does `serializeContext->Class<T, Base>()->Version(n, converter)->Field("name", &T::m_member)` (offset by member-pointer arithmetic, `sizeof`, pointer/enum traits, element type id, RTTI helper, container info), then `azrtti_cast`s the context to `EditContext` for `->DataElement(UIHandlers::Slider, &T::m, "Label", "Tooltip")->Attribute(Attributes::Min, 0.f)` and to `BehaviorContext` for `->Property("x", getter, setter)`. The registry is `ClassData {name, typeId, version, converter, factory, serializer, eventHandler, container, azRtti, editData, elements, attributes}` and `ClassElement {name, nameCrc, typeId, dataSize, offset, azRtti, genericClassInfo, editData, flags FLG_POINTER|FLG_BASE_CLASS|...}`. Unreflection runs the same function with `IsRemovingReflection()`. Cost per field: three hand-written lines (serialize, edit, behavior) plus the UUID per type. [o3de 2510.2 `AzCore/RTTI/TypeInfoSimple.h` L602-606, `RTTIMacros.h` L129-191, `Component/Component.h` L376-382, `Serialization/SerializeContext.h` L484-581, L882-990, L2062-2100, `RTTI/ReflectContext.h` L105-138; docs "Reflecting for serialization"]

**Flax: marker macros parsed by the build tool, generating C# and C++ glue.** `API_CLASS`, `API_STRUCT`, `API_ENUM`, `API_FIELD`, `API_PROPERTY`, `API_FUNCTION` expand to nothing in C++ (`Source/Engine/Core/Config.h`); Flax.Build's `BindingsGenerator.Parsing.cs` tokenizes the headers itself (not libclang), normalising `/// <summary>` comments and reading tags (`Attributes`, `ReadOnly`, `Hidden`, `NoPod`, parameter `defaultvalue`). Each type also carries `DECLARE_SCRIPTING_TYPE(T)`; the generator emits `ScriptingTypeInitializer T::TypeInitializer(module, fullname, size, &TInternal::InitRuntime, ...)` into the module's `.Gen.cpp`, which at static init appends a `ScriptingType {Fullname, Type (Script/Structure/Enum/Class/Interface), BaseTypeHandle, Interfaces, Size}` to `BinaryModule::Types` and `TypeNameToTypeIndex`. Classes carry no field list in C++; structs get generated `GetField(ptr, name, Variant&)`/`SetField` switches; member reflection (`GetFields`, `GetFieldSignature`, `InvokeMethod`) is answered by `ManagedBinaryModule` with .NET reflection over the generated C# wrapper. Cost per field: `API_FIELD(Attributes="EditorOrder(2), EditorDisplay(\"Light\"), Limit(0, 1000, 0.01f)") float X = 1.0f;` and optionally `API_AUTO_SERIALIZATION()` per type. [FlaxEngine 1.13.7014.1 `Source/Engine/Core/Config.h` L49-61, `Source/Tools/Flax.Build/Bindings/BindingsGenerator.Parsing.cs` L75-152, L374-390, `BindingsGenerator.Cpp.cs` L2396-2440, L2613-2620, `Source/Engine/Scripting/ScriptingType.h` L108-290, L379-420, `BinaryModule.h` L118-223, `BinaryModule.cpp` L612-621; docs "Attributes"]

**Bevy: derive macros plus a run-time `TypeRegistry`.** `#[derive(Reflect)]` generates `Reflect`, `PartialReflect`, `Typed`, `GetTypeRegistration` and the kind trait (`Struct`/`TupleStruct`/`Enum`); the type must be `'static + Send + Sync` and every field `Reflect`. `TypeRegistry::register::<T>()` stores a `TypeRegistration` and recursively registers field types; with the default `auto_register_inventory` feature every non-generic derived type is collected at start-up. Type data such as `ReflectDefault`, `ReflectComponent`, `ReflectSerialize` is attached by `#[reflect(Default, Component)]`. Introspection goes through `TypeInfo` → `StructInfo` → `NamedField {name, type_path, type_info, docs, custom_attributes}` and the `ReflectRef` kinds `Struct, TupleStruct, Tuple, List, Array, Map, Set, Enum, Opaque`. Cost: one derive per type, nothing per field unless opting out. [bevy v0.17.3 `crates/bevy_reflect/src/lib.rs` L85-114, L515-530, `type_registry.rs` L29-33, L135-203, `fields.rs` L12-66, `kind.rs` L15-60, `derive/src/lib.rs` L135-153]

**Lumix: annotation comments scanned by a string tool, generating committed C++.** `src/meta/meta.cpp` "scans the source code for lines containing `//@`" and "does not preprocess C++ nor does it fully parse C++". Headers carry `//@ component_struct icon ICON_FA_CAMERA`, `float fov; //@ property radians`, `float near; //@ property min 0`, `bool is_ortho; //@ property label "Orthographic"`, `//@ end`. The output `render_module.gen.h` ("Generated by meta.cpp", "must not be edited directly") is committed and `#include`d inside `RenderModule::reflect()`, expanding to a fluent builder `reflection::build_module("renderer").cmp<...>("camera", "Render / Camera").var_prop<&RenderModule::getCamera, &Camera::fov>("Fov").radiansAttribute()...`. Properties are getter/setter pairs on the module, not offsets. Regeneration is a manual script or a premake pre-build step. [LumixEngine 9b2f82e `docs/meta.md`, `src/meta/meta.cpp`, `src/renderer/render_module.h`, `src/renderer/render_module.gen.h`, `src/engine/reflection.h`, `scripts/premake5.lua` L214-219]

**Hazel and Wicked: no reflection.** Hazel's components are plain structs; `SceneSerializer.cpp` writes each by hand with yaml-cpp (`out << YAML::Key << "TransformComponent" ... "Translation" << tc.Translation`) and `SceneHierarchyPanel.cpp` draws each by hand with ImGui, so every field is written three times. Wicked's `wi::Archive` has explicit `operator<<`/`>>` per supported type ("so that non-specified types will have compile error!") and each component hand-writes `Serialize(wi::Archive&, EntitySerializer&)` with a read branch and a write branch, plus a hand-written editor window and hand-written Lua bindings. [Hazel 1feb705 `Hazel/src/Hazel/Scene/SceneSerializer.cpp`, `Hazelnut/src/Panels/SceneHierarchyPanel.cpp`; WickedEngine 257e532 `WickedEngine/wiArchive.h`, `wiScene_Serializers.cpp`, `Editor/MaterialWindow.cpp`]

**Libraries.** RTTR registers at static init in a `.cpp`: `RTTR_REGISTRATION { registration::class_<T>("T").constructor<>().property("x", &T::x)(metadata("GUI_LABEL", "...")); }`, expanding to a static object whose constructor runs the body; `RTTR_ENABLE(Base)` inside the class adds the virtuals for dynamic type; `RTTR_REGISTRATION_FRIEND` for private members. refl-cpp is compile-time and non-intrusive: `REFL_AUTO(type(T, bases<B>), field(x, serializable()), func(f))` specialises `type_info__<T>`; everything is `constexpr` (`for_each(refl::reflect<T>().members, ...)`); private fields need a friend declaration you write. Boost.Describe is one macro per type: `BOOST_DESCRIBE_STRUCT(T, (Bases), (m1, m2))` outside the type, or `BOOST_DESCRIBE_CLASS` inside for private members; `describe_members<T, mod_public | mod_inherited>` gives mp11 lists of `{name, pointer, modifiers}`; `BOOST_DESCRIBE_ENUM`/`BOOST_DEFINE_ENUM_CLASS` for enums. magic_enum needs nothing per enum: it parses `__PRETTY_FUNCTION__`/`__FUNCSIG__`. glaze reflects aggregates with no macros (member counting plus function-name parsing, 128 members max; `glz::meta<T>` for the rest). cereal has no description at all: the author writes `template<class Archive> void serialize(Archive&, std::uint32_t version)` naming fields with `CEREAL_NVP`. [rttr 7edbd58 `README.md`, `src/rttr/detail/registration/registration_impl.h` L290-303, `rttr_enable.h` L82-87, `registration_friend.h` L68-72; refl-cpp 27fbd7d `include/refl.hpp` L4299-4384, `examples/example-serialization.cpp`; describe 9093a9f `doc/describe/classes.adoc` L23-129, `enums.adoc` L22-64; magic_enum v0.9.8 `doc/limitations.md`; glaze v9.1.0 `docs/pure-reflection.md`, `README.md` L388-478; cereal v1.3.2 `include/cereal/cereal.hpp` L55-72]

**What it costs, summarised.** Per type: one macro (Unreal, Godot, Flax, Bevy, Describe) or a UUID plus macro plus a `Reflect` function (O3DE) or a registration block (RTTR). Per field: nothing (Bevy, glaze, magic_enum, Describe lists the names once), one annotated declaration (Unreal, Flax, Lumix), one builder line per context (O3DE: up to three; RTTR: one), or three to four hand-written sites (Godot: setter, getter, two binds, `ADD_PROPERTY`; Hazel: struct, serializer, panel; Wicked: read, write, window, Lua). describe-api sits at the cheapest end (the declaration and its doc comment, with the selection file naming the type once) and is the only one where the cost buys a committed neutral file.

## Coverage

**Strings, dynamic arrays, maps.** Unreal reflects `FString`/`FName`/`FText`, `TArray`, `TMap`, `TSet` (delta-serialised within properties unless `ArNoIntraPropertyDelta`) and `TOptional` via `FOptionalProperty`; template parameters cannot be nested. Godot's whole value space is the closed `Variant::Type` list (BOOL, INT, FLOAT, STRING, the math types, COLOR, STRING_NAME, NODE_PATH, RID, OBJECT, CALLABLE, SIGNAL, DICTIONARY, ARRAY and the `PACKED_*_ARRAY`s); typed containers are hints (`PROPERTY_HINT_ARRAY_TYPE`, `PROPERTY_HINT_DICTIONARY_TYPE`). O3DE has an `IDataSerializer` per primitive, `AZStd::string` through `GenericClassBasicString`, and `SerializeGenericTypeInfo<>` specialisations for `vector`, `fixed_vector`, `list`, `array`, `set`, `unordered_set`, `pair`, `tuple`, `map`, `unordered_map`, `bitset`, `shared_ptr`, `unique_ptr`, `optional`, `any`; `vector<int>` and `vector<float>` are distinct registered type ids. Flax's `Serialization` namespace overloads `ShouldSerialize/Serialize/Deserialize` for the scalars, `String`, `StringAnsi`, `Guid`, `DateTime`, the math types, `Array<T>`, `Dictionary<K,V>`, every reference kind, and any `ISerializable`. Bevy maps `String` to an opaque value, `Vec<T>` to `List`, `HashMap` to `Map`, `HashSet` to `Set`, arrays to `Array`. Lumix's property visitor is the closed set `float, int, u32, EntityPtr, Vec2, Vec3, IVec3, Vec4, Path, bool, const char*` plus `ArrayProperty` and `BlobProperty`; no maps, no nested structs. RTTR maps `std::vector/list/deque/array` and `set/map/unordered_*` automatically through `variant_sequential_view`/`variant_associative_view` and supports `std::string`; refl-cpp and Describe hand you the member type and leave containers to your visitor (Boost.JSON handles described classes, optionals, variants and containers by category). [UE 5.9 docs UProperties, UE 5.5 API `FArchive`, `FProperty`; godot `core/variant/variant.h`, `object.h` L85, L92; o3de `AZStdContainers.inl` L2235-3859, `Json/JsonSystemComponent.cpp` L64-125; flax `Serialization/Serialization.h` L56-680; bevy `impls/alloc/string.rs`, `vec.rs`, `std/collections/hash_map.rs`; lumix `src/engine/reflection.h`; rttr `detail/impl/sequential_mapper_impl.h` L511-824, `associative_mapper_impl.h` L415-450; boost json `include/boost/json/conversion.hpp` L601-622]

**Nested structs and optionals.** Unreal `USTRUCT`s nest by value ("share the reflection and serialization capabilities but are value types and are not garbage collected") and `FStructProperty` recurses. Godot has no user-definable struct: nested data is a sub-`Resource` or a `Dictionary`, and "optional" is a NIL `Variant` (null objects are skipped on save unless `PROPERTY_USAGE_STORE_IF_NULL`). O3DE nests any reflected class by value and models `optional<T>` as a 0-or-1-element container. Flax nests `API_STRUCT` + `API_AUTO_SERIALIZATION` values and has no optional ("deserialization works more like populate existing object with data rather than full load"). Bevy requires `#[derive(Reflect)]` all the way down and reflects `Option<T>` as an enum with `None`/`Some` variants. [UE 5.9 docs Structs; godot `resource_format_text.cpp` L1943-1945; o3de `AZStdContainers.inl` L1909-2015; flax docs "Serialization", `Cpp.cs` L1978-2110; bevy `impls/core/option.rs` L110-132]

**Enums and flags.** Unreal: `UENUM()` with `meta=(Bitflags)` + `ENUM_CLASS_FLAGS`, integer bitmasks via `meta=(Bitmask, BitmaskEnum="EColorBits")`; the file tag carries `EnumName` and `EnumRedirects` can remap values. Godot: ints flagged `PROPERTY_USAGE_CLASS_IS_ENUM`/`CLASS_IS_BITFIELD` with `PROPERTY_HINT_ENUM "a,b,c"`/`PROPERTY_HINT_FLAGS`, bound with `BIND_ENUM_CONSTANT`/`BIND_BITFIELD_FLAG`. O3DE: `serializeContext->Enum<E>()->Value("First", E::First)`; JSON writes a known value as its name, an unknown as an int, flag sets as `["Flag2","Flag4"]`. Flax: ints unless `API_ENUM(Attributes="EnumString")`. Bevy: Rust data-carrying enums via the `Enum` kind. Lumix backs enums as `i32` with an `EnumAttribute` for names (even dynamic per-instance ones). magic_enum reflects names with no per-enum code but is bounded to `[-128, 127]` by default (overridable per enum, span under 65536), does not handle aliased values ("won't work if a value is aliased": `enum_name(ShapeKind::Box)` gives the first declared name) and treats flags via `enum_range<E>::is_flags`. [UE 5.9 docs UProperties, Core Redirects; godot `object.h` L56-60, L112-119, `class_db.h` L534-541; o3de `SerializeContext.h` L600-640, docs "JSON data types"; flax `ScriptingType.h` `Enum.StringSerialization`; lumix `render_module.cpp::reflect`; magic_enum v0.9.8 `doc/limitations.md`, `README.md` L182-219]

**References to other objects, typed and polymorphic.** Unreal reflects `UObject*`, `TObjectPtr`, `TSubclassOf` (class-typed), `TSoftObjectPtr`, and distinguishes a *reference* from an *owned subobject* with `Instanced` ("Each instance gets a unique copy of the assigned default object. Implies EditInline and Export") and `Export` ("as a subobject block rather than just its reference"); the GC walks reflected references, so "storing a raw unreflected UObject pointer is usually dangerous". Godot references resources by `Variant::OBJECT` with `PROPERTY_HINT_RESOURCE_TYPE "Texture2D"` (an `ext_resource` by uid/path, or an inline `sub_resource`) and nodes by `NodePath`. O3DE flags a pointer field `FLG_POINTER`, requires the pointee reflected, and resolves the dynamic type by RTTI; entities are `AZ::EntityId`. Flax writes `ScriptingObject*`, `ScriptingObjectReference<T>`, `SoftObjectReference<T>`, `AssetReference<T>`, `WeakAssetReference<T>`, `SoftAssetReference<T>` all as Guids remapped through `ISerializeModifier::IdsMapping` on load. Bevy forbids references entirely (owned `'static` data only); entity ids are remapped by `ReflectMapEntities`; `Handle<A>` is a reflected enum with its own serde. Lumix uses `EntityPtr` plus `Path` with a `ResourceAttribute`; Wicked remaps `uint64` entities and names resources in a per-archive list. [UE blog; UE 5.9 docs UProperties; godot `object.h` L71, L88, L125; o3de `SerializeContext.h` L916-990, docs "JSON data types" L28-32; flax `Serialization.h` L457-520; bevy `lib.rs` L104-108, `bevy_ecs/src/reflect/map_entities.rs` L14-30, `bevy_asset/src/handle.rs` L132-140; lumix `reflection.h`; wicked `wiECS.h`]

**Plain data versus owning or "asset" types: one mechanism or two?** One mechanism, everywhere that has one. Unreal's `USTRUCT` (value, no GC) and `UCLASS` (GC, CDO, subobjects, editor integration, replication) share the property system; `TStructOpsTypeTraits<T>` gives a struct per-type opt-ins (`WithSerializer`, `WithPostSerialize`, `WithNetSerializer`, `WithSerializeFromMismatchedTag`). Godot has no plain-data path at all: a component is a `Node`, an asset a `Resource`, both `Object`s described identically; the only fixed-layout values are the engine's own `Variant` built-ins. O3DE puts components and asset types through the same `SerializeContext` with the `EditContext` marking what the asset editor shows. Flax's `ISerializable` serves scripts, actors, structs and `JsonAsset` payloads alike, while binary assets (textures, models) are a separate chunked format with its own upgraders. Bevy's components and assets both `#[derive(Reflect)]`, with ECS adding `ReflectComponent`/`ReflectResource` type data. Lumix and Wicked keep files independent of reflection altogether (hand-written binary per module), using the registry only for the inspector and scripting. [UE 5.9 docs Objects, Structs; UE 5.5 API `TStructOpsTypeTraitsBase2`; godot `object.h`; o3de `EditContextConstants.inl` L44; flax `JsonAsset.h` L13-48, `Content/Upgraders/BinaryAssetUpgrader.h` L60-180; bevy `bevy_ecs/src/reflect/component.rs` L80-134; lumix `world.cpp`; wicked `wiECS.h`]

**Against describe-api.** Its kinds (`i8`…`u64`, `f32`, `f64`, `bool`, `char16`, `enum`, `struct`, `array`, `pointer`) are a strict subset of every engine's value space; what is missing for data assets is exactly what the map's Notes say: text, variable-length lists, maps, optionals, and typed references. Every engine that has these treats them as *kinds the writer knows*, not as layout: a string is "text", a list is "N of kind K", a reference is "an id of a type". No engine serialises an opaque pointer; each has a reference kind that names the target type and stores an id (Unreal class path, Godot uid/path, O3DE entity id or asset id, Flax Guid). The `enum` kind is already richer than most (names, values, docs, underlying type); flags need only a marker.

## Polymorphism

**What the file stores.** Unreal: the class path of each object (which is why Core Redirects can remap `ClassRedirects`/`StructRedirects`/`EnumRedirects` at load), and per property an `FPropertyTag {Name, Type, Size, ArrayIndex, StructName, StructGuid, EnumName, InnerType, ValueType, PropertyGuid}`; `FProperty::CanSerializeFromTypeName` checks a tag against the live property. Godot: `[node type="RigidBody3D"]`, `[sub_resource type="CapsuleShape3D"]`, `[ext_resource type="Texture2D" uid="uid://..." path="res://..."]`, resolved by `ClassDB::instantiate(type)`; a scripted object stores its native base as `type` and the script as an ordinary `script = ExtResource(...)` property, plus `script_class="Name"` in the header when the script has a global name. O3DE ObjectStream: `<Class name="..." field="..." type="{UUID}" version="n">` where `type` is the *actual* run-time UUID, so a base-typed pointer field stores the derived type; O3DE JSON: pointers "are serialized out to the type that they point to" with a `$type` key holding the class name, or `"{UUID} Name"` when `FindClassId(Crc32(name))` finds more than one. Flax: `"TypeName": "FlaxEngine.StaticModel"` (fully qualified managed name) plus `"ID"` Guid; `SceneObjectsFactory::Spawn` calls `Scripting::FindScriptingType(fullname)` across every `BinaryModule` and checks `IsAssignableFrom`. Bevy: a `TypePath` string as the key of a one-entry map (`{"bevy_transform::components::transform::Transform": (...)}`), resolved by `registry.get_with_type_path`; a short path that is ambiguous returns `None`. **How a base-typed field reads a derived value.** Unreal: every `UObject` carries its `UClass`; `Instanced`/`Export` subobjects are written as nested blocks under their own class, so the field's declared type is only a constraint. **Against describe-api.** Every engine that names script types neutrally in files does it with one registry keyed by a string the language does not own (Godot class name + script path, Flax `Namespace.Type`, Unreal class path) or with a self-describing per-type schema in the file (O3DE `ScriptProperty` list, Lumix Evox, Hazel `ScriptFields`). describe-api's `<Package>.api.json` is already such a registry entry for C++; a C# data-asset type needs the same record written by a generator on the C# side (Godot's Roslyn generators and Flax's `ManagedBinaryModule` are the models), and reload survives when values are held by name (Godot's `StateBackup`, Hazel's buffers, Flax's JSON round-trip), never by handle.

## C++26 reflection: state as of 2026-11-10

- **Adopted.** Seven papers went into draft C++26 at Sofia in June 2025: P2996 (Reflection for C++26, R13 dated 2025-06-20), P3394 (Annotations for Reflection), P3293 (splicing a base class subobject), P3491 (`define_static_string/object/array`), P1306 (expansion statements), P3096 (function parameter reflection) and P3560 (constexpr exceptions as reflection error handling). C++26's technical work completed at the March 2026 London meeting ("On Saturday, the ISO C++ committee completed technical work on C++26"). [Sutter, trip reports June 2025 and March 2026; cppreference C++26 compiler support]
- **What it gives.** The `^^` operator yields a `std::meta::info` for a type, member, template, namespace or enumerator; `[: r :]` splices it back; `nonstatic_data_members_of(^^T, access_context)`, `members_of`, `bases_of`, `enumerators_of`, `identifier_of`/`has_identifier`/`display_string_of`, `offset_of`, `size_of`, `alignment_of`, `bit_size_of`, `type_of`, `parent_of`, `reflect_constant`/`reflect_object`, and `define_aggregate` (an incomplete class plus member descriptions; "not nearly as powerful as generalized code injection"). Private members need `access_context::unchecked()`. Everything is consteval: there is no run-time registry unless a program builds one (into static storage via `define_static_array`). [P2996R13 §§ "The reflection operator", "Splicers", "define_aggregate"]
- **Annotations.** P3394 adds `[[=expr]]` where `expr` is a constant expression of structural type; `annotations_of(item)` and `annotations_of_with_type(item, type)` retrieve them; the paper's own examples are clap-style CLI options and a serde-style `[[=serde::rename("first name")]]` on a field. This is the slot for ranges, display names and read-only flags; strings go through a `char const*` member. [P3394R4]
- **Not in C++26.** Token injection (P3294, "Code Injection with Token Sequences", R2 2024-10-15, "augmenting P2996 to add code injection") was not adopted; Bloomberg's fork "does not implement any features proposed by P3294". Comments are not reflected. [P3294R2; clang-p2996 `P2996.md`]
- **Compilers.** GCC 16 ships it: "`-std=c++26 -freflection`" with P2996R13, P3394R4, P3096R12, P3560R2, P3293R3, P3491R3 and P1306R5 listed as implemented; cppreference credits GCC 16 with the core feature and a partial `<meta>`; Boost.Describe's CI already tests "experimental support for reflection (requires GCC 16.2 and `-freflection`)". Clang upstream: P2996, P3394, P3293, P3491, P3096 all "No"; expansion statements "Clang 23 (Partial)". Bloomberg's clang-p2996 fork is the reference implementation (`-std=c++26 -freflection`, optional `-fparameter-reflection`, `-fexpansion-statements`) and is "highly experimental… DO NOT use this project to build any artifacts destined for production". MSVC's conformance page (updated 2026-10-16) lists no reflection paper at all. [gcc.gnu.org/gcc-16/changes.html; clang.llvm.org/cxx_status.html; bloomberg/clang-p2996 `P2996.md`; describe `changes.adoc`; learn.microsoft.com conformance page]
- **Libraries moving onto it.** glaze has an optional P2996 backend (GCC 16+, clang-p2996) that lifts its aggregate-only and 128-member limits and reads private members; Boost.Describe's stated goal was always to be replaced by compiler-supplied metadata. [glaze v9.1.0 `README.md` L28-65, L301-321; describe `overview.adoc`]
- **Bearing on Fenrir.** Fenrir builds with MSVC, Clang and GCC (ADR-0042's "natural" alignment target), so C++26 reflection is not usable in engine headers before MSVC and upstream Clang ship it, and the describe-api tool cannot be replaced by it: a consteval reflection runs inside the compiled program, sees no comments, and cannot write a file without a program per type. What it could do later is replace the libclang front end for *layout and names* in a dump program, or let a binding's C++ side check its generated mirror against the real struct at compile time. Annotations (`[[=Range(0, 1)]]`) are the one piece worth designing toward now: describe-api could accept the same vocabulary in doc commands or attributes today and move it to `[[= ]]` when the compilers allow.

## What this means for widening the API description

1. **Keep the generator, add kinds, not a registry.** Every engine with a header-driven generator (Unreal, Flax, Lumix) treats the header as the one source and generates the rest; the hand-registered engines (Godot, O3DE) pay three to four lines per field and cannot see comments. The cheapest known cost per field is the declaration plus its comment, which is what describe-api charges.
2. **The missing kinds are the same five everywhere:** `string` (UTF-8 text), `list` (N of a kind), `map` (optional; Godot and O3DE have it, Lumix and Wicked do not), `optional`, and a typed `reference` (target type + id, never a raw pointer). Describe them as kinds the writer understands, as every engine does; offsets are irrelevant for them (Godot stores none for any `Object`, Flax stores only `Size` and thunks).
3. **Polymorphism in the file is a type name or id next to the value**, in every engine; none needs C++ inheritance for that. describe-api's tagged union is already the closed form; an open form (a slot naming a base or interface, resolved through the registry) is the Godot/O3DE/Flax shape.
4. **Stable ids beat spellings.** O3DE (UUID) and Unreal Blueprints (`PropertyGuid`) survive renames for free; Bevy (`TypePath`) and Godot (class name + 171 compatibility entries) pay in tables. A description that records a stable id per type and field, or at least a rename table beside the committed JSON, would avoid Bevy's problem.
5. **Version and rename hooks belong to the description, not the format.** O3DE's `Version(n, converter)` and Unreal's custom versions are per type; Godot and Flax have only file-level versions and hand-written fallbacks. A per-type version in the API description, diffed by CI as the description already is, would be a real advance over all but O3DE.
6. **Unknown fields are dropped by everyone; unknown types are kept by the two editors that care about round-trip** (Godot's `MissingResource`/`MissingNode`, Flax's `MissingScript`). The level-editor tickets should decide which Fenrir wants.
7. **Doc comments are the generator's unique asset.** No run-time registry or library has them; Unreal and Flax get them only because they parse headers. Editor metadata should be a fixed vocabulary (min, max, step, display name, group, read-only, hidden, multiline, resource type) carried in the description, from doc commands now and `[[=...]]` annotations when C++26 reaches MSVC and Clang.
8. **Script types enter the same registry by name**, with a generator on the script side (Godot's Roslyn generators, Flax's managed module), and survive reload because values are held by name (Godot's `StateBackup`, Flax's JSON round-trip). Fenrir's C# generator already reads the description; the reverse record (a C# data-asset type's description) is the piece to add.

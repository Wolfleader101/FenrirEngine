# What the engine can describe and name today

Research for [What can the engine describe and name today, and what gap do files open?](../issues/08-what-the-engine-can-describe-today.md). Primary source: this repository at commit `5011f241`, read in place (no web). Every path below is relative to the repository root at that commit; `file:NN` is a line number there. Vocabulary is `GLOSSARY.md`'s: *scene*, *asset*, *asset handle*, *asset owner*, *sub-asset*, *scene resource*, *app resource*, *component*, *component type*, *API description*, *bound type*, *native resource*, *shared struct*, *script report*, *admission*.

## 1. The API description (`tools/describe-api`)

**What it records.** One committed `packages/<Package>/api/<Package>.api.json` per selection, language-neutral, written only when its bytes change, dependencies first then ordinal by name so the same headers give the same bytes on any platform (`tools/describe-api/SCHEMA.md:7-16`). The file records `package`, `pointerSize` (always 8), `alignment` (always `"natural"`) and `types` (`SCHEMA.md:11-16`).

- **Categories:** `struct`, `tagged-union`, `bound-type`, `enum` (`SCHEMA.md:25`).
- **Roles** (selected types): `component`, `event`, `scene-resource`, `app-resource`, `shared-struct`, `bound-type`, plus `enum` for an enum no field holds; a type described only because a field uses it gets `nested` (`tools/describe-api/README.md:23-33`, `SCHEMA.md:26`). `scene-resource` and `app-resource` were added by ADR-0043 (`docs/adr/0043-...md:11`, `docs/adr/0042-...md:28`).
- **Per type:** `name` (the selection's spelling or clang's canonical one), `size`, `alignment`, `doc` (`SCHEMA.md:24-28`). A `struct` lists every non-static data member in storage order with `name`, `offset`, `kind`, `type`, array `elementKind`/`elementType`/`length`, `default` (every field has one) and `doc` (`SCHEMA.md:30-42`). A `tagged-union` records its `tag` field, `unionOffset`, `kinds` (name, tag value, kind keys, doc) and `defaultKind` (`SCHEMA.md:44-53`). A `bound-type` records only `size` and `alignment`; its members are never read, and a template specialisation the headers never instantiate is instantiated to measure it (`SCHEMA.md:55-57`, `README.md:41`). An `enum` records `underlying` and each enumerator's `name`, `value`, `doc` (`SCHEMA.md:59-61`).
- **Kinds:** `i8`..`i64`, `u8`..`u64`, `f32`, `f64`, `bool`, `char16`, `enum`, `struct` (a described struct, tagged union or bound type by value), `array` (fixed `length`, elements never arrays), `pointer` (8 opaque bytes, target never described). `char` is `u8`, `char32_t` is `u32`, an enumerator-less enum (`entt::entity`) is its underlying integer (`SCHEMA.md:63-77`; `Describer.cs:578-612`).
- **Defaults** are read from the default member initialiser and recorded as values: literals, `std::numbers` constants and operators on them, enumerators, `std::numeric_limits` `infinity()`/`max()`/`lowest()`, `{}`/`T{}`/no initialiser for a nested struct or bound type, a designated aggregate initialiser for some members, a bound type's constructor with literal arguments (matched to components by parameter name), and braced lists for arrays. A scalar, enum, pointer or array of them with no initialiser fails (`SCHEMA.md:79-96`; `README.md:71-72`).
- **Doc comments** (`/** */`, `/*! */`, `///`) are recorded as text without markers and `@brief`; paragraphs joined with spaces and separated by `\n\n`; other tags stay as written (`SCHEMA.md:98-100`).

**What it refuses** (each a diagnostic naming type and member; all failures in one run, `README.md:65-88`):

- A reference member: "a shared type holds values, not references" (`Describer.cs:607-609`).
- A virtual function; a base class with data members or virtual functions, so no inheritance of state (`Describer.cs:389-404`, `README.md:78-79`). The map's note that structs with members on both base and derived cannot be described is confirmed by `CheckPlainData`'s `HasData(baseRecord)` test (`Describer.cs:399-403`).
- A user-declared copy, move, assignment or destructor: "not trivially copyable" (`Describer.cs:406-412`). This is how `std::string`, `std::vector`, `std::map`, `std::optional` of a non-trivial type and `std::variant` fail: a member of such a type is classified as a `struct` kind and the record is then described as `nested`, where `CheckPlainData` rejects it (`Describer.cs:594-596, 649`; the fixture's `Failing::Copied` and `NonTriviallyCopyableMember` are the tests, `tools/describe-api/tests/Fixture/Failing.hpp:44-55`). There is no `string`, `list` or `optional` kind in the API description; the natives description has a `string` kind for `std::string_view` parameters only (`SCHEMA.md:141`, ADR-0044 `docs/adr/0044-...md:16`).
- Private members outside the tagged-union shape unless `private-members` names the type (`README.md:35-39`); bit-fields; arrays of arrays; `long double`, `wchar_t` and any other type of no kind (`README.md:81-83`).
- glm's vectors cannot be described because they are anonymous unions, which is why they are bound types (`docs/adr/0043-...md:15`).

**Who runs it, when.** Twelve package selections exist: FenrirAnimation, FenrirApp, FenrirAssets, FenrirECS, FenrirInput, FenrirMath, FenrirPhysics, FenrirRenderer, FenrirScripting, FenrirSkeleton, FenrirWindow (`packages/*/api/*.api.toml`), plus three binding-private selections (`packages/FenrirAssets/Scripting/api/FenrirAssetsScripting.api.toml`, `FenrirDebugDraw/Scripting/api/FenrirDebugDrawScripting.api.toml`, `FenrirInput/Scripting/api/FenrirInputScripting.api.toml`). FenrirScene, FenrirCore, FenrirTime, FenrirScheduler, FenrirLogger and FenrirDebugDraw (package level) have none. Each joins through `fenrir_describe_api(<target> api/<Package>.api.toml)` in its `CMakeLists.txt` (`packages/FenrirECS/CMakeLists.txt:37`, `packages/FenrirRenderer/CMakeLists.txt:237`, ...), which `cmake/FenrirDescribeApi.cmake:34-48` turns into a custom target under `fenrir-describe-api`, passing the target's include directories, definitions and the C++ standard as an `@file` (`FenrirDescribeApi.cmake:67-90`). The ordinary build never runs it (`FenrirDescribeApi.cmake:1-3`, `README.md:57`). CI's `api-descriptions.yml` configures with `-DFENRIR_ENABLE_SCRIPTING=ON -DFENRIR_ENABLE_RENDERER=OFF`, builds `fenrir-describe-api` then `fenrir-generate-bindings`, and fails on `git diff --exit-code` (`.github/workflows/api-descriptions.yml:52-68`), on pull requests only, Windows runner, ignoring `**.md`, `docs/**`, `.scratch/**` (`api-descriptions.yml:9-16`).

*Gap in CI's check:* with the renderer off, `packages/FenrirWindow` and `packages/FenrirRenderer` are never added (`CMakeLists.txt:95-97`), so their descriptions and bindings are not regenerated or checked in CI; the workflow's comment still says "no package it builds has an API description yet" (`api-descriptions.yml:49-51`), which is stale since FenrirWindow and FenrirRenderer gained selections.

**Could a game project run it on its own headers today?** Mechanically yes: the tool is a .NET console program over libclang's NuGet packages, needing no LLVM install (`README.md:5`), runnable by hand as `dotnet run --project tools/describe-api/src -- <selection> [compile arguments | @file]` (`README.md:63`), and `fenrir_describe_api()` is an ordinary CMake function any project that adds FenrirEngine as a subdirectory can call (`cmake/FenrirDescribeApi.cmake:34`; the root `CMakeLists.txt:66-68` includes the module and adds `tools/describe-api`). What a game would need: a `<Name>.api.toml` naming its headers and each type's role (`README.md:9-21`); the .NET SDK (`FenrirDescribeApi.cmake:13, 28`); plain-data types only (above); and, for C#, a `<Name>.binding.toml` naming the SDK's defaults file, `uses` for the engine bindings whose mirrors it holds, and the generated outputs' paths (`packages/Iris/Tools/Iris.Bindings/README.md:38-118`, `packages/FenrirScripting/api/FenrirScripting.binding-defaults.toml:1-8`), joined through `iris_generate_binding()` (`Iris.Bindings/README.md:22-36`) or FenrirScripting's `FenrirScriptingExtension.cmake`, which runs both steps for a package extension (`packages/FenrirScripting/cmake/FenrirScriptingExtension.cmake:20-23, 126-128`). No example project does this: the demos' C# components are plain `IComponent` structs with no selection (`examples/AnimationDemo/scripts/Playback.cs:31`, `examples/PhysicsDemo/scripts/Character.cs:57`; no `*.api.toml` or `*.binding.toml` under `examples/`). Nothing installs or exports the CMake module (no `install(`/`export(` in `CMakeLists.txt` or `cmake/*.cmake`), so a game that consumes an installed engine rather than the source tree has no entry point.

## 2. The C# side (Iris, FenrirScripting, the binding generator)

**What the script report knows at admission.** The report is what a script assembly says it defines when it loads: components and events, each as a full type name, size and alignment (`packages/FenrirScripting/src/ScriptComponents.hpp:11-27`). The SDK's source generator writes a table calling `ScriptComponents.Report<T>()` once per `IComponent` struct, which sends `typeof(T).FullName`, `Unsafe.SizeOf<T>()` and an alignment measured with a probe struct (`packages/FenrirScripting/Managed/Fenrir.Scripting/ScriptComponents.cs:12-38`); the native `RegisterScriptComponent` pushes that into the engine context's reporting slot (`packages/FenrirScripting/src/Bindings.cpp:146-153`, events at `:323`). The report itself holds no fields. Field-level knowledge comes second, from Iris's reflection: `TypeQueries.Fields` returns each declared field's name, type full name and assembly, a `Kind` (`Bool`, `Char`, `Int8`..`UInt64`, `Float`, `Double`, `String`, `Enum`, `Struct`, `Object`, `Array`, `Other`), static/readonly flags, visibility, byte offset (only when the struct is blittable) and attributes (`packages/Iris/Managed/Iris.Bridge/TypeQueries.cs:19-22, 155-172`). FenrirScripting folds that into a *fingerprint*: `size/alignment;field:type:kind@offset;...`, or `;opaque` for a type it cannot read (`packages/FenrirScripting/src/IrisAdapters.cpp:45-71`), kept per owned layout across generations (`ScriptData.hpp:15-27`). Admission order: report, then every native component, event, shared struct and resource checked against its C# struct (`ValidateStruct` checks name, size, field count and each field's name, offset and kind, nested structs, enums and fixed arrays included, `packages/Iris/Native/include/Iris/Component.hpp:93-103`; `IrisAdapters.cpp:242-257`), then the script's components and events registered all or nothing, then stale script data dropped and new event queues made (`ScriptData.hpp:87-96`, GLOSSARY *Admission*).

**How `DynamicComponentType` lays a script component out.** A reported description becomes `DynamicComponentType(name, size, alignment)` (`ScriptComponents.hpp:30-33`): a block of plain bytes identified by a name, at most 64 KiB, size a multiple of a power-of-two alignment (`packages/FenrirECS/include/FenrirECS/DynamicComponent.hpp:9-55`). Its `Id()` is a hash of the name (`DynamicComponent.hpp:44-49`). Wrapped by `ComponentType::Dynamic` (`ComponentType.hpp:35-36, 81-87`), it is stored in a `ByteStorage`, an EnTT sparse set of opaque fixed-size elements in pages of up to 256 elements or 64 KiB, allocated once and never moved; a new element is all zero bytes, which is C#'s `default` (`packages/FenrirECS/src/ByteStorage.hpp:26-45`). Two descriptions of one name must agree on size and alignment or the list refuses the add (`DynamicComponent.hpp:18-20`, `EntityList.hpp:168-173`). A changed fingerprint on reload clears every scene's components of that name (`ScriptData.cpp:29-36`). The ECS sees bytes only: field names, kinds and offsets live in the C# type and Iris's reflection of it, never in the ECS.

**How native resources and bound types cross.** A native resource is a plain-data scene or app resource given the role `scene-resource` or `app-resource` in the package's selection, mirrored as a C# struct marked `[NativeResource]`, registered through `MakeSceneResource`/`MakeAppResource`, and reached by C# through `Resources.Get<T>()` in place (`docs/adr/0043-...md:11`; `packages/FenrirScripting/include/FenrirScripting/ComponentRegistry.hpp:184-268`). `Sky` and `SkyLight` are the two described ones (`packages/FenrirRenderer/api/FenrirRenderer.api.toml:19-20`). A resource with a vector (`InputClaims`) crosses as a fixed-size copy described from the binding's own selection (`docs/adr/0043-...md:12`). A bound type is recorded by layout only and mapped by hand in the binding's `[bound-types]` table to its C# type and mapping header (`Iris.Bindings/README.md:114-118`); `AssetHandle<T>` is one (`packages/FenrirAssets/api/FenrirAssets.api.toml:11-21`), mapped field-by-field to `Fenrir.Assets.AssetHandle<Mesh>` etc. in `packages/FenrirAssets/Scripting/include/FenrirAssetsScripting/AssetMappings.hpp:1-47`, crossing by pointer (`in`/`out AssetHandle<T>`) since the asset-handles amendment to ADR-0044 (`docs/adr/0044-...md:22`). `Entity` is a shared struct of two fields (`m_entityId` u32 at 0, `m_entityList` pointer at 8, 16 bytes) that every other package describes as `nested` through `private-members` (`packages/FenrirECS/api/FenrirECS.api.json:7-27`, `FenrirPhysics.api.toml:16`). Other bindings' mirrors are named through `[uses]` rather than regenerated (`docs/adr/0044-...md:19`).

**Could a C# class with strings and lists be described the same way?** No. A component is an `unmanaged` struct: "plain data, no references" (`Fenrir.Scripting/IComponent.cs:11-17`; every ECS entry point is `where T : unmanaged, IComponent`, `Entity.cs:59-154`). `TypeQueries` can see `String`, `Object` and `Array` kinds (`TypeQueries.cs:22, 127-132`) but writes an offset only for blittable structs (`TypeQueries.cs:160, 169`), and the fingerprint does not look inside a nested struct (`packages/FenrirScripting/README.md:572-573`). The precedents for text are a fixed 256-byte `Name` mirrored as a `fixed byte` buffer with `GetText`/`SetText` over UTF-8 (`Fenrir.Scripting/Name.cs:6-48`; `Iris.Bindings/README.md:183-184`, `fixed-buffers`), and `string` as a native-function parameter crossing as a pointer and length (`docs/adr/0044-...md:16`; `DebugDraw`'s group is text passed beside a struct, `docs/adr/0043-...md:14`). Lists cross only as spans a native fills, with the count folded after (GLOSSARY *Crossing form*).

## 3. The ECS (`FenrirECS`)

**`ComponentType` and `DynamicComponent` as the run-time door.** `ComponentType` names one kind of component, native (`ComponentType::Native<T>()`) or dynamic (`ComponentType::Dynamic(DynamicComponentType)`), for code that knows a component only at run time; it carries no name ("naming a component (for scripts, an inspector or a file) is the caller's business; a dynamic type's name is part of its DynamicComponentType") and no reference to any list, so one value serves every scene (`packages/FenrirECS/include/FenrirECS/ComponentType.hpp:17-36`). `EntityList` takes one for `Get` (a `void*` to the component, or null), `Has`, `Add` (default-constructed if native, zeroed if dynamic), `Remove`, `Count`, `Clear(type)`, `ForEachWith(span<ComponentType>)` mixing native and dynamic, and `Watch` (`EntityList.hpp:149-205`). A native component known only by name has no door: there is no registry from a string to `ComponentType::Native<T>` in FenrirECS; FenrirScripting's `ComponentRegistry` is the one place a native component is held under a name (`ComponentRegistry.hpp:16-37, 77-100`), built from each extension's generated registration lists, and C# resolves names to ids through it (`Fenrir.Scripting/RegistryIds.cs:7-40`).

**`EntityList`'s operations.** `CreateEntity` (gives `Transform`, `Name` and `Relationship` through the creating constructor), `ReserveEntity`/`CompleteEntity` for hand-out-then-fill (deferred changes), `GetEntity(id)`, `HandleOf(id)` (a handle whether or not the entity still exists), `DestroyEntity`, `HasEntity`, `Clear`, typed `ForEach`/`View`/`Group`, and the `ComponentType` family above (`EntityList.hpp:40-205`; `packages/FenrirECS/src/EntityList.cpp:11-32`). Reparenting is on `Entity`: `AddChild`/`RemoveChild` link `Relationship`'s `parent`, `firstChild`, `nextSibling`, `prevSibling` (`Entity.hpp:135-171`; `packages/FenrirECS/src/Entity.cpp:47-72`); `ForEachChild` walks the sibling chain (`Entity.hpp:217-233`). Entity ids are EnTT ids (index plus version) exposed as `uint32_t` (`Entity.hpp:104, 147`); `Entity::AddComponent` on an entity that has the component removes and re-adds it (`Entity.hpp:173-185`).

**`ComponentWatch` and tracked sets.** `Watch(type)` records every add and remove of one type in one list, however it happens (typed calls, `ComponentType` calls, destroy, clear), in order, until `Drain()`; edits to a value are not changes (`ComponentWatch.hpp:45-72`; `EntityList.hpp:199-205`). `TrackedComponents` keeps the set of entities with a type as of its last drain, starting full from a scan, and each drain names the entities whose component came or went (`TrackedComponents.hpp:14-60`). Dynamic storages record straight into watch records (`ByteStorage.hpp:40-44`). Neither tracks field edits, so nothing today can say "this component's value changed" (relevant to dirty tracking for save).

**Can an entity be named or found by anything but its handle?** Every entity has a `Name` component, a fixed 256-byte UTF-8 buffer (`DefaultComponents.hpp:42-105`), but there is no lookup by name in `EntityList` (`EntityList.hpp` has `GetEntity(id)`, `HandleOf(id)`, `HasEntity(id)` only). `App` finds scenes by name with a linear search (`packages/FenrirApp/src/App.cpp:284-298, 330-344`). Entities are found by handle, by query (`ForEach`, `View`, `ForEachWith`), or by walking `Relationship`. No stable id survives a save: an EnTT id is a slot and version of one `EntityList`, and `Entity` also holds the list's pointer (`Entity.hpp:147-149`; `FenrirECS.api.json:13-25`).

**`WorldTransform` and parenting when a hierarchy is rebuilt.** The world transform is never stored: `GetWorldTransform` composes the entity's `Transform` with its ancestors' through `Relationship` on each call, `GetWorldMatrix` is the exact product, `SetWorldTransform` writes the local `Transform` against the parent's world (`WorldTransform.hpp:8-47`). So a rebuild needs only each entity's local `Transform` and its parent link, parents before children (so `AddChild` finds a valid parent, `Entity.cpp:47-53`). The one existing rebuild-from-data is `AssetStore::SpawnNodes`: a model's `ModelNode` list (name, `sourceId`, `rest` transform, `parent` index always lower than the node's own, kind) is spawned parents-first into entities with `Name.Set`, `Transform = rest` and `above.AddChild(entity)`, under an optional parent (`packages/FenrirAssets/include/FenrirAssets/Model.hpp:69-108`; `packages/FenrirAssets/src/SpawnNodes.cpp:45-74`), returning a `SpawnedNodes` with the root and one `Entity` per node (`SpawnNodes.hpp:9-23`). `ModelNode::sourceId` is the precedent for a file-stable identity that is "not a name, so it is exact when names repeat" (`Model.hpp:74-78`).

## 4. Scenes and the app (`FenrirScene`, `FenrirApp`)

**What a `Scene` holds.** A `std::string` name (`GetName`/`SetName`), one `EntityList`, and resources in an `unordered_map<std::type_index, unique_ptr<void, deleter>>`, declared after the entity list so resources end first (`packages/FenrirScene/include/FenrirScene/Scene.hpp:13-81`). `GetResource<T>`/`AddResource<T>(args...)` (replace, constructed before the old is destroyed)/`RemoveResource<T>` are the whole API, all by C++ type; the scene "stores resources of any type without knowing it" (`Scene.hpp:26-73`). `App` holds app resources the same way (`packages/FenrirApp/include/FenrirApp/App.hpp:477-531, 674-683`).

**Creation, activation, destruction.** `App::CreateScene(name)` pushes a heap-allocated `Scene` (no duplicate-name check), `ChangeActiveScene(name)` sets the active index by linear name search (error log if missing), `DestroyScene(name)` erases by name and refuses the active scene, `GetScene(name)` returns the first match or, with an error, scene 0, `GetActiveScene()`, `ForEachScene` (`App.hpp:620-645`; `App.cpp:279-344`). One heap allocation per scene keeps `Entity` handles and references valid across creates and destroys (`App.hpp:657-660`). Scenes are built by C++ code: the demo scaffold's `DemoScene` is a name plus `std::function<void(App&, Scene&)> spawn` (`examples/DemoScaffold/include/FenrirDemoScaffold/DemoScaffold.hpp:52-68`), entered by `CreateScene` + `ChangeActiveScene` (`examples/DemoScaffold/src/DemoScaffold.cpp:329-336`) and left by changing to a holder scene and destroying (`DemoScaffold.cpp:316-327`). Packages add their scene resources in code at install: `PhysicsWorld`, `SkeletonPoses`, `Detail::Animators`, `DebugDraw` (grep of `scene.AddResource<` across `packages/*/src`); app resources include `AssetStore`, the input, window and renderer install records and `Overlay`.

**What a scene resource would need to be written and read back.** Today a scene resource is reached by `std::type_index` only (`Scene.hpp:33, 54`); it has no name in `FenrirScene`. The nearest name is in FenrirScripting's `ResourceRegistration`: a C++ type under a registered name, with scope (`Scene`/`App`), `find`/`insert`/`remove` lambdas over `GetResource<T>`/`AddResource<T>`/`RemoveResource<T>` of the active scene, and the size, alignment and C# struct it is validated against (`ComponentRegistry.hpp:184-245`). Only plain-data resources are registered and described (`Sky`, `SkyLight`, `FenrirRenderer.api.toml:19-20`); `PhysicsWorld`, `SkeletonPoses`, `Animators` and `DebugDraw` have behaviour or containers and are reached from C# through facades (GLOSSARY *Facade*). So a scene file today could name only the two described plain-data resources, through a registry that exists only when scripting is installed; everything else needs a name and a description it does not have, or a package-owned load/save seam.

## 5. Assets (`FenrirAssets`, ADR-0021)

**How a load names a file.** `AssetStore::Load<T>(path, owner)`: a relative path resolves against the asset root, an absolute one is taken as given, `file#Label` names a sub-asset, `builtin:` names a registered built-in (`packages/FenrirAssets/include/FenrirAssets/AssetStore.hpp:208-231`). The root comes from `AssetsConfig::root`, default `assets/` beside the executable; a relative root is relative to the working directory when the store is made (`AssetStore.hpp:75-83`; `packages/FenrirAssets/src/AssetStore.cpp:282-284`). `Resolve` splits at the last `#`, normalises `root / file`, and builds a key `file[#label]` (`AssetStore.cpp:101-127`). Sub-asset labels are numbered as the model's lists: `#Mesh0`, `#Material0`, `#Image0`, `#Skeleton0`, `#Clip0` (`Model.hpp:95-104`); a model loads only unlabelled and its parts only labelled (`AssetStore.cpp:359-368`).

**Deduplication, owners, revisions.** Each kind has a table of `AssetRecord`s with a `byKey` map from the resolved key to a slot (`packages/FenrirAssets/src/AssetStoreState.hpp:24-44`); a path already loaded as that kind returns the same handle and adds the owner (`AssetStore.hpp:211-212`). Owners are the app or a scene, not counted, and an asset is freed when its last owner ends or on `Unload` (`AssetStore.hpp:85-110, 309-316`). `revision` starts at 1 and is bumped by `Replace`, each material set and each `Reset` that removes an override, so the renderer re-uploads on change (`AssetStore.hpp:287-345`). `FromSameFile(a, b)` tells whether two assets came from one file (`AssetStore.hpp:347-354`). The record's `key` (the loaded path and label) is private to the store: no public call returns an asset's path from its handle (`AssetStoreState.hpp:32-33`; the public API in `AssetStore.hpp:196-518` has no `PathOf`/`KeyOf`).

**`AssetHandle<T>`.** `{uint32 index, uint32 generation}`, generation zero only in the empty handle, equality defaulted, trivially copyable, kept in components as plain data and keeping nothing alive (`packages/FenrirAssets/include/FenrirAssets/AssetHandle.hpp:134-156`). Kinds: `Mesh`, `Image`, `Material`, `Shader`, `Model`, `Skeleton`, `Clip`, `BoneMask`, `InstanceList`, nine slot tables (`AssetHandle.hpp:9-51`). It is a bound type in every description that holds one (`FenrirAssets.api.toml:11-21`, `FenrirRenderer.api.toml:30-33`, `FenrirAnimation.api.toml:33-34`, `FenrirSkeleton.api.toml:34`), mapped by hand to `Fenrir.Assets.AssetHandle<T>` (`AssetMappings.hpp:40-47`) and crossing by pointer (`docs/adr/0044-...md:22`); C#'s `Assets.Load<T>(path, owner)` calls the kind-neutral native and wraps the handle (`packages/FenrirAssets/Managed/Fenrir.Assets/Assets.cs:34-38`; `packages/FenrirAssets/Scripting/src/AssetsScripting.cpp:193-199`).

**Which kinds exist and which are only made in code.** Loaded from files: images (PNG, JPEG, HDR, `.cubemap` text files), models (glTF, GLB, FBX, OBJ) with their meshes, materials, images, skeletons and clips as sub-assets (`AssetStore.hpp:212-226`; importers under `packages/FenrirAssets/src/Importers/` are cgltf, ufbx and stb). Shaders are compiled containers registered with `AddBuiltin<Shader>` under `builtin:` names (`AssetStore.hpp:264-271`; ADR-0021 `docs/adr/0021-...md:18`). Only ever made in code: `MaterialData` (shader handle, blend mode, cutoff, double-sided, and `std::map<std::string, MaterialValue>` overrides where `MaterialValue` is a `std::variant` of float, vectors and `MaterialTexture`; edited through the store's `SetFloat`/`SetTexture`/`Reset` calls, `packages/FenrirAssets/include/FenrirAssets/MaterialData.hpp:79-107`, `AssetStore.hpp:366-462`; a model importer also makes them), `InstanceListData` (vectors of `Mat4` and `Colour`, `InstanceListData.hpp:19-25`), `BoneMaskData` (entries of `std::string boneName`, weight, scope; `CreateBoneMask`/`IncludeInBoneMask`, `BoneMaskData.hpp:18-41`, `AssetStore.hpp:485-503`), render-target images (an `ImageData` with no pixels, `ImageData.hpp:50-76`), procedural meshes (`Add<Mesh>`, `AssetStore.hpp:241-248`) and clip event edits (`AddClipEvent`, `AssetStore.hpp:466-481`). Every asset data type holds `std::vector`s or `std::string`s, so none is describable by `describe-api` today; only `SamplerDescription` and `MaterialTexture` are described, as shared structs the material natives pass (`FenrirAssets.api.toml:7-9`).

**A component holding an `AssetHandle<Mesh>` in a file.** `MeshRenderer` holds `AssetHandle<Mesh> mesh` and `AssetHandle<Material> material` (`packages/FenrirRenderer/include/FenrirRenderer/Components.hpp:26-27`; `InstancedMeshRenderer` adds `AssetHandle<InstanceList>`, `:51-53`; `AnimationLayer` holds `AssetHandle<BoneMask>`, `AnimationLayer.hpp:49`). The handle is a slot and generation of one store's run, meaningless in a file. The name a file could write is the store's key, `path[#label]` relative to the asset root (`AssetStoreState.hpp:32-33`, `AssetStore.cpp:110-127`), or a `builtin:` name; neither is readable back from a handle through the public API today. Reading back would `Load<T>(key, owner)` for the scene being built (synchronous, main thread, `AssetStore.hpp:192-194`, ADR-0021 `:13`) before or as the component is written, since a stale or empty handle is skipped and logged once per handle rather than failing (`AssetStore.hpp:553-568`; ADR-0021 `:12`); a `builtin:` name may be named before its data exists and resolves later (`AssetStore.hpp:264-268`). Code-made assets (a material with overrides, an instance list) have no key and so no name at all.

## 6. Entity references in components

Every shared type with an `Entity` field (grep `Entity <name>` across `packages/*/include`), with how it is resolved today:

| Type (file:line) | Field(s) | Resolved by |
| --- | --- | --- |
| `Relationship` (`FenrirECS/Entity.hpp:159-171`) | `parent`, `firstChild`, `nextSibling`, `prevSibling` | Kept consistent by `Entity::AddChild`/`RemoveChild` (`Entity.cpp:47-72`); read by `ForEachChild` and `WorldTransform` |
| `Joint` (`FenrirPhysics/Joints.hpp:353-358`) | `bodyA`, `bodyB` (empty = world) | `IsValid()` each step; inactive with a warning while either is not a body entity of the joint's scene, back by itself when both are (`Joints.hpp:339-342`; `Joints.cpp:288-296`) |
| `VehicleWheel` (`Vehicles.hpp:531-534`) | `vehicle` (the chassis) | Must name an entity of its scene with a `Vehicle`; inactive with a warning otherwise; relinking rebuilds the vehicle (`Vehicles.hpp:527-530`) |
| `VehicleDifferential`, `VehicleAntiRollBar` (`Vehicles.hpp:582-587, 610-615`) | `leftWheel`, `rightWheel` | Matched by id against the vehicle's wheel set each rebuild; a dead wheel is treated as empty with a warning (`Vehicles.cpp:225-262`) |
| `VehicleWheelState` (`Vehicles.hpp:478-484`), `CharacterState` (`Characters.hpp:28-33`) | `groundBody`, `groundCollider` | Written by physics each step; "a handle: destroyed since, it is no longer valid" |
| `SkinnedMesh` (`FenrirRenderer/Components.hpp:76-79`) | `skeleton` | `IsValid()` and `SkeletonPose` presence each frame, not drawn and logged once otherwise (`Renderer.cpp:974-979`) |
| `BoneAttachment` (`FenrirSkeleton/BoneAttachment.hpp:54-62`) | `skeleton` (+ `BoneName bone`) | `IsValid() && HasComponent<SkeletonPose>()` then bone by engine name, re-resolved when the skeleton, name or instance build changes (`Attachments.cpp:245-280`) |
| `AnimationLayer` (`FenrirAnimation/AnimationLayer.hpp:43-45`) | `skeleton` | `IsValid()`, grouped per skeleton each frame (`Animators.cpp:343-349`) |
| Events: `ContactBegin`/`ContactEnd` (`Events.hpp:25-31, 48-54`), `TriggerEnter`/`TriggerExit` (`:61-65, 75-80`), `JointBroken` (`:93-97`), `AnimationEvent`, `ClipFinished`, `AnimationEventsDropped` (`AnimationEvents.hpp:27-29, 51-53, 65-67`) | body, collider, trigger, joint, skeleton, layer | Transient; readers check `HasEntity` (`EntityList.hpp:66-71`) |
| Shared structs: `Contact` (`PhysicsWorld.hpp:29-35`), `QueryFilter::ignoreBody` (`Queries.hpp:28`), the hit structs (`Queries.hpp:37-100`), `SpawnedNodes` (`SpawnNodes.hpp:16-22`), DebugDraw's `relativeTo` (`DebugDraw.hpp:51, 71`) | | Call-time values, never stored in a component |

Every field is a `Fenrir::Entity`: an EnTT id plus the owning `EntityList*` (`Entity.hpp:147-149`), described as `m_entityId` u32 and `m_entityList` pointer (`FenrirECS.api.json:13-25`). None is stable across a run. The uniform pattern is *tolerant lookup*: a target that is empty, dead, in another scene or missing its component makes the holder inactive with one warning, and it recovers when the target is valid again. A scene file must therefore write the seven component-held references (`Relationship` x4, `Joint` x2, `VehicleWheel`, `VehicleDifferential` x2, `VehicleAntiRollBar` x2, `SkinnedMesh`, `BoneAttachment`, `AnimationLayer`) as something other than an id, and the engine's own code already tolerates fix-up after creation (a joint with a not-yet-created body is merely inactive). Entities in another scene are never valid (`Joints.hpp:339-340`; GLOSSARY *Entity*).

## 7. Text and names in components

Two fixed-size name fields exist, both 256-byte zero-terminated UTF-8 buffers holding at most 255 bytes:

- `Fenrir::Name` (`FenrirECS/DefaultComponents.hpp:42-105`): `char name[256]`, private, `Set(const char*)` truncates with `strncpy` to 255 bytes, `Get`, `Clear`, `IsEmpty`, `Length`. Described as a `component` of one `array` field of 256 `u8` with a default of 256 zeros (`FenrirECS.api.json:43-56`), via `private-members` (`FenrirECS.api.toml:8-10`); mirrored as a `fixed byte Text[256]` buffer with `GetText`/`SetText` that cuts on a UTF-8 character boundary (`Fenrir.Scripting/Name.cs:6-48`).
- `Fenrir::BoneName` (`FenrirSkeleton/BoneAttachment.hpp:15-41`, ADR-0037): `char m_bytes[MaxBytes + 1]`, `Set(string_view, ILogger&)` *refuses* a name over 255 bytes or holding a zero byte rather than truncating ("a truncated name could match another bone"), `Get()` returns `nullopt` for an unterminated buffer, and an attachment naming a malformed buffer is diagnosed and never resolved (`Attachments.cpp:262-265`). Described via `private-members` (`FenrirSkeleton.api.toml:11-14`).

Other text in shared types is not a name field: `TextEvent`'s code point is a `char32_t` recorded as `u32` (`docs/adr/0044-...md:20`); `DebugDraw`'s `std::string_view group` is in a C++-only options struct, crossed as separate text (`DebugDraw.hpp:62`; `docs/adr/0043-...md:14`). Text with no fixed bound lives only in asset data and configuration (`ModelNode::name`, `BoneMaskEntry::boneName`, `MaterialData::overrides` keys, `CollisionLayer::name` in `PhysicsConfig`, `FenrirPhysics/CollisionLayers.hpp:15-20`), none of it a component. So the precedent for strings in components is: a fixed buffer, bounded at 255 bytes, with the bound enforced on write (truncate or refuse) and the buffer validated on read.

## 8. Existing reload (the script reload watcher)

`Detail::ReloadWatcher` is a pure decision class: it does no file access and keeps no clock; it is told the time and given two questions (`lookAtFile` returning a `Stamp` of last-write time and size, `canBeOpened`), asks the first at most once per `interval` (250 ms) and the second only once a change has stayed the same for `debounce` (400 ms), and answers `Idle`, `Settling` or `Ready` (`packages/FenrirScripting/src/ReloadWatcher.hpp:11-87`; `ReloadWatcher.cpp:5-32`). `MarkLoaded(stamp)` records what was loaded and forgets a pending change so a hand-loaded build is not loaded twice (`ReloadWatcher.hpp:58-67`). `GenerationLifecycle` owns it: `Poll(now)` and `ReloadIfReady(now)` (nothing escapes; a throw is logged), `Load`, `Reload` (hooks `beforeReload`, `stop`, release, wait for unload, new generation all-or-nothing, previous restored on failure), each generation a private copy of the file so the build can overwrite the original (`GenerationLifecycle.hpp:25-111`). `Scripting::State::PollForReload` calls `ReloadIfReady` at the start of each frame (`packages/FenrirScripting/src/Scripting.cpp:262-268`), configured by `ScriptingConfig::hotReload`, `reloadInterval`, `reloadDebounce`, `reloadDirectory`, `unloadTimeout` (`FenrirScripting/Scripting.hpp:52-76`). What survives a reload is decided by the fingerprint: unchanged layouts keep their data, changed or missing ones are dropped with a warning before any system runs; a broken build keeps the previous generation running and is not retried until the file changes (`packages/FenrirScripting/README.md:547-573`). Native components and events are never reloaded (`README.md:573`). The pieces a file hot reload could reuse: the stamp-and-debounce decision (polling, no OS watcher), the per-frame poll point, the all-or-nothing replace with restore, and the "compare the layout before touching data" rule. The one documented project file, `.feproj` with a `scriptAssembly` field (`Scripting.hpp:25`), is mentioned in that comment only: nothing in the repository reads or writes one.

## Gaps a file format opens

1. **Names for component types.** `ComponentType` carries no name and FenrirECS has no name-to-type table (`ComponentType.hpp:23-24`); only FenrirScripting's `ComponentRegistry` names native components, and only when scripting is installed. A file needs an engine-level registry from a neutral type name (the API description's `Fenrir::Transform`) to a `ComponentType` and its description, for native and dynamic components alike.
2. **Descriptions at run time.** The API description is a build-time artefact read by generators, never loaded by the engine; the ECS knows sizes and alignments only. Reading a file into component bytes needs the fields, kinds, offsets and defaults in memory, from the committed JSON, from a generated table, or from reflection C# already has (`TypeQueries.Fields`).
3. **Richer kinds than the description records.** No strings, variable-length lists, optionals, maps or polymorphism (`Describer.cs:406-412`, `SCHEMA.md:63-77`); every asset data type (`MaterialData`, `InstanceListData`, `BoneMaskData`, `Model`) is undescribable today. Data assets need a type model beyond "a C++ struct that is trivially copyable".
4. **Stable identity for entities.** `Entity` is an EnTT slot plus a list pointer; seven component types hold one (section 6). A scene file needs a per-file entity identity and a fix-up pass after creation, which the engine's tolerant lookups already allow.
5. **Names for assets from handles.** The store keys assets by `path[#label]` but exposes no path for a handle, and code-made assets have no key at all (`AssetStoreState.hpp:32-33`). Writing a component needs a handle-to-name query and a naming rule for code-made assets; reading needs a load-before-or-during-build order and a story for `builtin:`.
6. **Names for scene resources.** Reached by `std::type_index` only (`Scene.hpp:33`); the two described plain-data ones are named only in the scripting registry. The behaviour-carrying ones (`PhysicsWorld`, `SkeletonPoses`) need a package-owned save/load seam or to be reconstructed from configuration.
7. **A scene's identity and the scene list.** Scenes are found by name with no uniqueness check (`App.cpp:300-304`), built by code (`DemoScene::spawn`), and only the active scene is reachable from C#. A scene file names a scene and its contents; the app's list of scenes stays code (map: out of scope).
8. **Change tracking.** `ComponentWatch` reports adds and removes, never edits (`ComponentWatch.hpp:51-52`); asset revisions bump on store edits only. Dirty state for save, and reload that preserves unsaved edits, has no precedent beyond the asset revision counter.
9. **C# types with managed fields.** Components must be `unmanaged`; a C#-defined data asset with `string` or `List<T>` cannot cross as bytes and has no engine-side description beyond `TypeQueries`' kind flags without offsets.
10. **A game's own descriptions.** `fenrir_describe_api` works from the source tree but is not installed or exported, no example uses it, and the generated C# binding needs a `binding.toml` and the SDK defaults file (section 1). A game project defining types in C++ has no documented path to a description today.
11. **Text bounds.** The only string precedent is a 255-byte fixed buffer (truncate or refuse). A file format with unbounded text needs a decision on where unbounded strings may live (data assets, not components) or a bounded-string kind.
12. **CI coverage.** The dirty-tree check skips FenrirWindow's and FenrirRenderer's descriptions (`api-descriptions.yml:53`, `CMakeLists.txt:95-97`); any type-description pipeline a file format adds should be checked with the renderer on.

# Fenrir serialisation: data assets, scene files and dev-time data

Label: wayfinder:map

## Destination

A set of specs, one feature directory each (`.scratch/fenrir-serialisation-<name>/spec.md`), each ready for `/to-tickets`, plus ADRs for the hard-to-reverse calls, covering: **data assets** (game-defined typed data in files, what Godot calls a Resource, Unity a ScriptableObject and Unreal a DataAsset; defined from C++ and from C#), **scene files** (a FenrirScene's entities, components, hierarchy and scene resources, and prefabs), the **one text format** and how files are versioned and migrated, **where type descriptions come from** for reading and writing files, **asset identity and references**, **load, save and hot reload**, **dev-time data** (project settings, import sidecars, per-developer overrides), and **what the data layer must offer a level editor**, informed by research into what makes a good one. The development formats are designed so a cooked or binary shipping form can follow, but that form and the pipeline that writes it are not specified here. Editor UI is out of scope.

## Notes

- **The engine's one word is *scene*** (`GLOSSARY.md`, FenrirScene). *Map* and *level* are the game's words for a scene file. The field says *level editor*, so the editor research does too.
- **"Resource" is taken.** A scene resource or app resource is one-per-type package state (`GLOSSARY.md`), and *Asset* says *avoid: resource*. The game-defined typed data in a file is provisionally a **data asset** until [What is a data asset?](issues/10-what-a-data-asset-is.md) names it; *blueprint* is Unreal's and *resource* is ours, so neither.
- **Nothing is serialised today.** Demo scenes are C++ functions; materials are edited in code; the files the engine reads are models, images, shader containers and C# assemblies.
- **Reflection exists at build time, for plain data only.** `tools/describe-api` writes a committed `<Package>.api.json` (ADR-0042) for the eleven packages with a selection (FenrirScene, FenrirCore and FenrirDebugDraw have none): every shared type's fields, offsets, kinds, defaults and doc comments. Its kinds are integers, floats, bools, `char16`, enums, nested structs, tagged unions, bound types by layout, fixed arrays and opaque pointers: no strings (names are fixed 256-byte UTF-8 arrays, `BoneName`), no variable-length lists, no polymorphism; anything not trivially copyable is refused. Data assets were agreed to need richer types than components (strings, lists, nested lists, handles to other data assets); how the engine describes them is a ticket.
- **Inheritance is a registry fact, not a file encoding.** Every engine's file names a value's type beside it and answers "does this derived file fit this base-typed field" by a registry lookup and an is-a check; no engine describes inheritance as layout (tickets 01 and 04). C++ structs with members on both base and derived are not standard-layout, so describe-api cannot describe them today, but that is Fenrir's constraint, not the pattern's. The type model (inheritance, composition or another) is chosen, not copied, and Godot's file is a native class plus a script reference plus a property bag, with no field versioning at all.
- **Language-agnostic.** C++ and C# both define data asset types and component data; a file names a type neutrally, as the API description does. C# reaches the data through the existing scripting pipeline (ADR-0042, ADR-0043, ADR-0046).
- **Editor-ready, no editor.** The data layer and its API are designed so an inspector, a scene view and a level editor can sit on top; none is decided here. Prototypes may use throwaway ImGui panels to react to the data.
- **Both dev-time and baked-in data are in scope as concerns**: this map decides the development formats and what they must guarantee so a cooked form is possible later (identities that survive moving files, no absolute paths, type descriptions available without headers); the cooked form itself is fog.
- **The engine/game line holds** (ADR-0057's spirit): the engine offers building blocks (load, save, reflect, reference), not opinions about what a world is. Streaming, partitioning and brush-to-mesh baking are expected to be the game's or a tool's; brush geometry in the scene file stays open until the level editor research lands.
- **Libraries stay hidden** (ADR-0010): a text-format or reflection library is `PRIVATE` to the package that uses it and appears in no public header.
- **Conventions:** in this map *scene*, *asset*, *asset handle*, *asset owner*, *sub-asset*, *scene resource*, *app resource*, *component*, *API description*, *bound type* and *native resource* carry their meanings from `GLOSSARY.md`.
- **Skills:** grilling tickets call `grilling` and `domain-modeling`; package and seam questions also use `codebase-design`. Research tickets call `research` and put their findings in `.scratch/fenrir-serialisation/research/<name>.md` on a `research/<name>` branch, pushed, never merged.
- **Plan, don't do:** tickets produce decisions, not code (spikes are throwaway, on `prototype/…` branches).
- **Built specs are removed**, as on the physics and renderer maps: the commit that records a spec built deletes its directory.

## Decisions so far

<!-- one line per resolved ticket: [title](issues/NN-slug.md): gist -->

- [What can the engine describe and name today, and what gap do files open?](issues/08-what-the-engine-can-describe-today.md): describe-api describes trivially-copyable plain data only (no strings, lists, maps, variants or bases with data), for eleven packages, never run by the ordinary build, and a game could run it today with its own selection; the C# script report knows components by name, size, alignment and blittable fields, and the ECS stores script components as opaque pages; `ComponentType` and scene resources carry no name; entities are found only by handle, query or hierarchy; nine `Entity`-holding component fields, all resolved tolerantly each frame; two fixed 256-byte name fields are the only text in components; assets are keyed by root-relative path with `#Label` sub-assets and `builtin:` names, with no public path-from-handle query, and every asset data type holds vectors or strings; the script reload watcher is a clockless, debounced, all-or-nothing precedent; CI never regenerates the renderer's descriptions.
- [What makes a good level editor?](issues/05-what-makes-a-good-level-editor.md): designers judge editors by UX and iteration speed, not geometry tech; one-gesture convex blockout on a player-sized power-of-two grid, solid at once, thrown away cheaply; kits with fixed footprints and pivots, heavily instanced; gameplay wiring as per-connection target/input/parameter/delay, visible from both ends, fixed up per instance; open worlds loaded by region with cells, streaming sources, splines and foliage set in the editor; puzzles from a constrained palette with a visible budget; play-in-editor in seconds with explicit rules on what survives; nested groups and editor-only layers, in-place instances with per-instance overrides and revert, stable move-safe ids, no whole-file locks; snap on by default with units, orthographic views with measurements; live issue browsers and on-screen budgets; the complaints are laggy geometry, binary merges, brittle references, hidden state and instancing that is duplication.
- [Which text formats suit scene files and data assets, and what libraries read them?](issues/03-text-formats-for-game-data.md): no format is hand-editable, mergeable and typed at once; JSONC has readers everywhere (JSON5 has none in C++ or C#), TOML nests poorly and split into 1.0 and 1.1 readers, YAML carries typed tags, KDL has no real C++ library, RON none; every C++ library drops comments on rewrite, so comments survive only in files tools never rewrite; key order, float text and NaN handling differ per library, so byte-identical rewrites must follow the API description's declaration order and one engine-owned float rule; typed and polymorphic references are native only in YAML, KDL and Godot's own grammar, and a `$type` convention in JSON (Unity, Flax, O3DE); Glaze needs C++23 and VS 2026, so it is out; toml++, yaml-cpp and rapidyaml give line-and-column errors, nlohmann and RapidJSON offsets; Godot moved to pseudo-random readable ids and `.uid` sidecars for merges, Unity ships a YAML merge tool and discourages hand edits, Bevy's BSN is still unshipped, Unreal stays binary with one file per actor.
- [How do engines serialise scenes and prefabs?](issues/02-how-engines-serialise-scenes-and-prefabs.md): every authoring format gives entities a file-level id apart from the runtime handle and remaps on load (Godot name paths plus 4.6's `unique_id`, Unity per-file `fileID` plus `.meta` GUIDs, Unreal object paths plus `ActorGuid`, Source integer ids plus `targetname`s; Bevy and EnTT snapshots are same-process only); Godot and Unreal write only non-default fields, Unity, Bevy and Flecs every field; unknown types are kept as placeholders (Godot), preserved (Unity), dropped (Unreal) or refused (Bevy, Flecs); parents first with sibling order meaningful in Godot and Unity; scene-level state is object-less settings blocks (Unity), a settings actor (Unreal) or a type-keyed resources map applied after entities (Bevy, the closest to Fenrir's scene resources); prefabs come in three shapes, diff-against-source (Godot, Unity, Unreal), copy-and-fix-up (Source) and live inheritance (Flecs), with Bevy's BSN patches shipped code-only; additive loading is universal and only Unreal ships streaming cells; merges want text, stable ids, fixed order and a semantic merge driver, which is why Godot went to random string ids and Unreal to one file per actor.
- [How do engines hold dev-time data: project settings, import sidecars and per-developer overrides?](issues/07-dev-time-data-in-engines.md): Godot, Unity, Unreal and Flax have a project file plus a settings store, Bevy (and Fenrir today) only code, environment and features; project settings are window, backend, physics defaults, input map, names, first scene and packaging, and reference data assets rather than inline them; layering runs from engine defaults through project, platform and user files to the command line, and ships as a binary twin, a denylisted copy or a cooked asset; a sidecar is the asset's identity (Unity's `.meta` GUID), only its options plus a path-deterministic uid (Godot's `.import`), or options with no identity (Bevy); Unreal and Flax keep import data on the asset; a missing sidecar regenerates defaults everywhere; import caches live in one ignored directory; device choice is never a committed setting; Fenrir's `Install` configs are the shape of every settings store, with Flax the model for settings as data assets and Godot for plain config with its own reader, and `.feproj` is already named in a doc comment.
- [How do engines type, inherit and reference data assets?](issues/01-how-engines-type-data-assets.md): a data asset is a named-field class or struct everywhere, with the file naming its type (Flax, Unreal, O3DE and Stride by name; Godot by native base plus script reference; Unity by script GUID); the minimum vocabulary the API description lacks is strings, lists, nested objects and asset references; a base-typed field accepting a derived file is free because the file names its type, with the base relation a registry fact and never layout, so inheritance versus composition is a registry and picker question, not a layout one; polymorphism by value inside a file is where Unity and Unreal pay; references are id plus path (Godot, Stride, O3DE), id only (Unity, Flax) or path only (Unreal, Bevy), with sidecars retrofitted where a format cannot carry an id; most engines write only non-default values, making per-field defaults load-bearing; one shared instance per file, hot reload either mutates in place and signals or replaces and notifies; versioning is strongest where the upgrade hook sits beside the type (Unreal, O3DE, Stride) and absent in Godot and Bevy, which silently drop renamed fields.
- [How do C++ engines describe their types for serialisation and editors?](issues/04-how-engines-reflect-types-for-files.md): three families (header-driven generators in Unreal, Flax and Lumix; hand-filled registries in Godot, O3DE and RTTR; in-language declarations in Bevy and the C++ libraries), with describe-api the cheapest per field and the only one producing a committed, layout-bearing, language-neutral file; every engine has the five kinds it lacks (string, list, map, optional, typed reference by id) and none serialises a pointer; polymorphism is always a type name or id beside the value, resolved by registry lookup and an is-a check, so a tagged slot with allowed types covers the file; editor metadata is a fixed vocabulary per engine and doc-comment tooltips exist only where headers are parsed; per-type versions with upgrade hooks exist in Unreal, O3DE (whose JSON path ignores them) and cereal, renames are declarative redirect tables, unknown fields are dropped everywhere and unknown types kept only by Godot and Flax; scripts feed the same registry through a script-side generator keyed by a neutral name, and reload survives only values held by name; C++26 reflection is consteval only, sees no comments, and is shipped by GCC 16 alone, so it cannot replace describe-api; the recommendation is to add kinds, open the tagged union, record stable ids or rename tables and a per-type version in the description.
- [What do level editors demand of a scene format and engine API?](issues/06-what-level-editors-demand-of-the-data.md): brushes are three plane points per side with derived vertices (Source, TrenchBroom) and every engine with runtime CSG documents a bake to meshes, so baking outside the engine is the recommended path and brush geometry in the scene file can stay open; entity classes are a name plus typed properties the editor learns from a registry (Source's hand-written FGD is the one that drifts), and wiring is a string on the sender plus a name resolver; organisation (visgroups, groups, layers, cordons, cameras) is editor-only data that TrenchBroom keeps as ordinary entities with reserved keys; terrain, scatter, navmesh and lighting bakes are assets beside the scene referenced by id, with streaming cells Unreal's alone; an editor needs a property registry, undo-aware create, destroy, reparent and mutate (Bevy's remote protocol is the minimal list), picking, save-with-filters, hot reload and a play-in-editor copy; compiles collapse instances and drop editor data, and one-file-per-actor is re-embedded at cook; a stable per-entity id that survives instancing is what every prefab scheme leans on.
- [Where do the type descriptions that read and write files come from?](issues/09-where-type-descriptions-come-from.md): ADR-0060; the API description stays the one source and is widened (a `data-asset` role that may hold `std::string`, `std::vector`, `std::optional`, nested structs and typed references as kinds with offsets unused; an open slot for any registered type assignable to a base; `@version`, `@formerly` and a fixed editor-metadata vocabulary as doc commands); a new `tools/generate-type-registry` writes a committed C++ type registration per package that fills a run-time type registry in a new FenrirTypes package at `Install`, with no JSON parsed at run time; components keep the fixed-layout byte rule and data assets go through a generated per-type visitor behind one visitor interface; files name types by canonical name with no GUIDs; C# components and data asset types enter the registry at admission; games run the same tools with the .NET SDK at dev time; behaviour-carrying resources stay undescribed; CI's dirty-tree check gains the generator and runs with the renderer on.

## Not yet specified

- **The cooked or binary shipping form and the pipeline that writes it.** A shipped game needs one (the user's words). Whether it is a later spec on this map or its own effort is decided once [What must the development formats guarantee a cooked form?](issues/20-what-the-formats-guarantee-a-cooked-form.md) closes.
- **Spec boundaries:** how many specs, which tickets each gathers (data assets and reflection; scene files and prefabs; dev-time data; the level-editor-facing additions), and their order. Settled once the grilling tickets close.
- **Which existing engine assets become files:** materials (`MaterialData`, edited in code today), instance lists, bone masks, render-target images. Likely the first engine-provided data assets; waits on the data asset model and the format.
- **Editing support in the data layer:** what a running scene or asset store offers an editor beyond load and save (change tracking, dirty state, undo-friendly edits, validation diagnostics for broken files). Waits on load/save and hot reload.
- **Streaming building blocks:** what a game needs from scene files to stream an open world (additive load and unload, scene composition, cells) given that partitioning is the game's. Waits on the scene file and prefab tickets and the level editor research.
- **Text in data assets:** localisation and string tables, if data assets hold player-facing text. Waits on the type model.

## Out of scope

- Editor UI: an inspector, a scene view, a level editor's own tools and windows, editor layouts and window state.
- The demo apps' scene lists stay code.

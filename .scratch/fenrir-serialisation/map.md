# Fenrir serialisation: data assets, scene files and dev-time data

Label: wayfinder:map

## Destination

A set of specs, one feature directory each (`.scratch/fenrir-serialisation-<name>/spec.md`), each ready for `/to-tickets`, plus ADRs for the hard-to-reverse calls, covering: **data assets** (game-defined typed data in files, what Godot calls a Resource, Unity a ScriptableObject and Unreal a DataAsset; defined from C++ and from C#), **scene files** (a FenrirScene's entities, components, hierarchy and scene resources, and prefabs), the **one text format** and how files are versioned and migrated, **where type descriptions come from** for reading and writing files, **asset identity and references**, **load, save and hot reload**, **dev-time data** (project settings, import sidecars, per-developer overrides), and **what the data layer must offer a level editor**, informed by research into what makes a good one. The development formats are designed so a cooked or binary shipping form can follow, but that form and the pipeline that writes it are not specified here. Editor UI is out of scope.

**Six specs written, 2026-11-19, each ready for `/to-tickets`**, in dependency order: `.scratch/fenrir-serialisation-types/spec.md` (10 tickets), `.scratch/fenrir-serialisation-format/spec.md` (9), `.scratch/fenrir-serialisation-data-assets/spec.md` (11), `.scratch/fenrir-serialisation-scenes/spec.md` (10), `.scratch/fenrir-serialisation-csharp/spec.md` (9) and `.scratch/fenrir-serialisation-dev-time/spec.md` (8). Each ends with a "Gaps settled here" section naming the calls the spec made beyond the ADRs; writing them amended ADR-0077 (the writer's flow-style rule) and ADR-0083 (C# auto-properties are described; upgraders cross by name). **The types spec is built** (2026-11-22, integration branch `fenrir-serialisation-types`, PRs #410, #411, #413, #415, #417, #419 to #424): eleven tickets, ticket 11 (tagged unions in FenrirTypes) added when ticket 05 found the gap; ticket 07 added a `[registration] uses` key so a type several packages describe registers once in its owner, and ticket 09 made `RendererConfig::debugValidation` a `std::optional<bool>` so its build-dependent default describes the same in every build. Its directory is removed; git history keeps it. The other five are not built yet. **The format spec is ticketed** (2026-11-22): `.scratch/fenrir-serialisation-format/issues/01-10`, after the spec was brought in line with the built FenrirTypes; ticket 10 (a bound type's component order from its selection, so `Quat` writes `x, y, z, w`) was added then. 01 to 07 and 09 stack, 08 runs beside them off 02, 10 runs beside 01 and 02, and 03 waits for 10.

## Notes

- **The engine's one word is *scene*** (`GLOSSARY.md`, FenrirScene). *Map* and *level* are the game's words for a scene file. The field says *level editor*, so the editor research does too.
- **A scene file is authoring data, read once** (ADR-0078): the game loads it to make a scene and never writes it; the save path is for tools, an editor and code-built scenes. A save game is the game's own file, built from the engine's public blocks. Scene is also the word for a map, as in Godot and Unity; a separately compiled map form is the cooked form's question.
- **"Resource" is taken.** A scene resource or app resource is one-per-type package state (`GLOSSARY.md`), and *Asset* says *avoid: resource*. The game-defined typed data in a file is a **data asset** (ADR-0075, glossary); *blueprint* is Unreal's and *resource* is ours, so neither.
- **Nothing is serialised today.** Demo scenes are C++ functions; materials are edited in code; the files the engine reads are models, images, shader containers and C# assemblies.
- **Reflection exists at build time, for plain data only.** `tools/describe-api` writes a committed `<Package>.api.json` (ADR-0042) for the eleven packages with a selection (FenrirScene, FenrirCore and FenrirDebugDraw have none): every shared type's fields, offsets, kinds, defaults and doc comments. Its kinds are integers, floats, bools, `char16`, enums, nested structs, tagged unions, bound types by layout, fixed arrays and opaque pointers: no strings (names are fixed 256-byte UTF-8 arrays, `BoneName`), no variable-length lists, no polymorphism; anything not trivially copyable is refused. Data assets were agreed to need richer types than components (strings, lists, nested lists, handles to other data assets); how the engine describes them is a ticket.
- **Inheritance is a registry fact, not a file encoding.** Every engine's file names a value's type beside it and answers "does this derived file fit this base-typed field" by a registry lookup and an is-a check; no engine describes inheritance as layout (tickets 01 and 04). C++ structs with members on both base and derived are not standard-layout, so describe-api cannot describe them today, but that is Fenrir's constraint, not the pattern's. The type model (inheritance, composition or another) is chosen, not copied, and Godot's file is a native class plus a script reference plus a property bag, with no field versioning at all.
- **Language-agnostic.** C++ and C# both define data asset types and component data; a file names a type neutrally, as the API description does. C# reaches the data through the existing scripting pipeline (ADR-0042, ADR-0043, ADR-0046).
- **Editor-ready, no editor.** The data layer and its API are designed so an inspector, a scene view and a level editor can sit on top; none is decided here. Prototypes may use throwaway ImGui panels to react to the data. The editor research's first finding, for the editor effort's own map: designers judge an editor by its UX and iteration speed, not its geometry tech; one fixed UX issue saves twenty users an hour a day (ticket 05).
- **Both dev-time and baked-in data are in scope as concerns**: this map decides the development formats and what they must guarantee so a cooked form is possible later (identities that survive moving files, no absolute paths, type descriptions available without headers); the cooked form itself is fog.
- **The engine/game line holds** (ADR-0057's spirit): the engine offers building blocks (load, save, reflect, reference), not opinions about what a world is. Streaming, partitioning and brush-to-mesh baking are expected to be the game's or a tool's; brush geometry in the scene file stays open until the level editor research lands.
- **Libraries stay hidden** (ADR-0010): a text-format or reflection library is `PRIVATE` to the package that uses it and appears in no public header. The format needs none (ADR-0077's reader and writer are the engine's own, in `FenrirSerialisation`).
- **Conventions:** in this map *scene*, *asset*, *asset handle*, *asset owner*, *sub-asset*, *scene resource*, *app resource*, *component*, *API description*, *bound type* and *native resource* carry their meanings from `GLOSSARY.md`.
- **Skills:** grilling tickets call `grilling` and `domain-modeling`; package and seam questions also use `codebase-design`. Research tickets call `research` and put their findings in `.scratch/fenrir-serialisation/research/<name>.md` on a `research/<name>` branch, pushed, never merged.
- **Plan, don't do:** tickets produce decisions, not code (spikes are throwaway, on `prototype/…` branches).
- **Built specs are removed**, as on the physics and renderer maps: the commit that records a spec built deletes its directory.

## Decisions so far

<!-- one line per resolved ticket: [title](issues/NN-slug.md): gist -->

- [What can the engine describe and name today, and what gap do files open?](issues/08-what-the-engine-can-describe-today.md): describe-api describes trivially-copyable plain data only (no strings, lists, maps, variants or bases with data), for eleven packages, never run by the ordinary build, and a game could run it today with its own selection; the C# script report knows components by name, size, alignment and blittable fields, and the ECS stores script components as opaque pages; `ComponentType` and scene resources carry no name; entities are found only by handle, query or hierarchy; nine `Entity`-holding component fields, all resolved tolerantly each frame; two fixed 256-byte name fields are the only text in components; assets are keyed by root-relative path with `#Label` sub-assets and `builtin:` names, with no public path-from-handle query, and every asset data type holds vectors or strings; the script reload watcher is a clockless, debounced, all-or-nothing precedent; CI never regenerates the renderer's descriptions.
- [What makes a good level editor?](issues/05-what-makes-a-good-level-editor.md): designers judge editors by UX and iteration speed, not geometry tech; one-gesture convex blockout on a player-sized power-of-two grid, solid at once, thrown away cheaply; kits with fixed footprints and pivots, heavily instanced; gameplay wiring as per-connection target/input/parameter/delay, visible from both ends, fixed up per instance; open worlds loaded by region with cells, streaming sources, splines and foliage set in the editor; puzzles from a constrained palette with a visible budget; play-in-editor in seconds with explicit rules on what survives; nested groups and editor-only layers, in-place instances with per-instance overrides and revert, stable move-safe ids, no whole-file locks; snap on by default with units, orthographic views with measurements; live issue browsers and on-screen budgets; the complaints are laggy geometry, binary merges, brittle references, hidden state and instancing that is duplication.
- [Which text formats suit scene files and data assets, and what libraries read them?](issues/03-text-formats-for-game-data.md): no format is hand-editable, mergeable and typed at once; JSONC has readers everywhere (JSON5 has none in C++ or C#), TOML nests poorly and split into 1.0 and 1.1 readers, YAML carries typed tags, KDL has no real C++ library, RON none; every C++ library drops comments on rewrite, so comments survive only in files tools never rewrite; key order, float text and NaN handling differ per library, so byte-identical rewrites must follow the API description's declaration order and one engine-owned float rule; typed and polymorphic references are native only in YAML, KDL and Godot's own grammar, and a `$type` convention in JSON (Unity, Flax, O3DE); Glaze needs C++23 and VS 2026, so it is out; toml++, yaml-cpp and rapidyaml give line-and-column errors, nlohmann and RapidJSON offsets; Godot moved to pseudo-random readable ids and `.uid` sidecars for merges, Unity ships a YAML merge tool and discourages hand edits, Bevy's BSN is still unshipped, Unreal stays binary with one file per actor.
- [How do engines serialise scenes and prefabs?](issues/02-how-engines-serialise-scenes-and-prefabs.md): every authoring format gives entities a file-level id apart from the runtime handle and remaps on load (Godot name paths plus 4.6's `unique_id`, Unity per-file `fileID` plus `.meta` GUIDs, Unreal object paths plus `ActorGuid`, Source integer ids plus `targetname`s; Bevy and EnTT snapshots are same-process only); Godot and Unreal write only non-default fields, Unity, Bevy and Flecs every field; unknown types are kept as placeholders (Godot), preserved (Unity), dropped (Unreal) or refused (Bevy, Flecs); parents first with sibling order meaningful in Godot and Unity; scene-level state is object-less settings blocks (Unity), a settings actor (Unreal) or a type-keyed resources map applied after entities (Bevy, the closest to Fenrir's scene resources); prefabs come in three shapes, diff-against-source (Godot, Unity, Unreal), copy-and-fix-up (Source) and live inheritance (Flecs), with Bevy's BSN patches shipped code-only; additive loading is universal and only Unreal ships streaming cells; merges want text, stable ids, fixed order and a semantic merge driver, which is why Godot went to random string ids and Unreal to one file per actor.
- [How do engines hold dev-time data: project settings, import sidecars and per-developer overrides?](issues/07-dev-time-data-in-engines.md): Godot, Unity, Unreal and Flax have a project file plus a settings store, Bevy (and Fenrir today) only code, environment and features; project settings are window, backend, physics defaults, input map, names, first scene and packaging, and reference data assets rather than inline them; layering runs from engine defaults through project, platform and user files to the command line, and ships as a binary twin, a denylisted copy or a cooked asset; a sidecar is the asset's identity (Unity's `.meta` GUID), only its options plus a path-deterministic uid (Godot's `.import`), or options with no identity (Bevy); Unreal and Flax keep import data on the asset; a missing sidecar regenerates defaults everywhere; import caches live in one ignored directory; device choice is never a committed setting; Fenrir's `Install` configs are the shape of every settings store, with Flax the model for settings as data assets and Godot for plain config with its own reader, and `.feproj` is already named in a doc comment.
- [How do engines type, inherit and reference data assets?](issues/01-how-engines-type-data-assets.md): a data asset is a named-field class or struct everywhere, with the file naming its type (Flax, Unreal, O3DE and Stride by name; Godot by native base plus script reference; Unity by script GUID); the minimum vocabulary the API description lacks is strings, lists, nested objects and asset references; a base-typed field accepting a derived file is free because the file names its type, with the base relation a registry fact and never layout, so inheritance versus composition is a registry and picker question, not a layout one; polymorphism by value inside a file is where Unity and Unreal pay; references are id plus path (Godot, Stride, O3DE), id only (Unity, Flax) or path only (Unreal, Bevy), with sidecars retrofitted where a format cannot carry an id; most engines write only non-default values, making per-field defaults load-bearing; one shared instance per file, hot reload either mutates in place and signals or replaces and notifies; versioning is strongest where the upgrade hook sits beside the type (Unreal, O3DE, Stride) and absent in Godot and Bevy, which silently drop renamed fields.
- [How do C++ engines describe their types for serialisation and editors?](issues/04-how-engines-reflect-types-for-files.md): three families (header-driven generators in Unreal, Flax and Lumix; hand-filled registries in Godot, O3DE and RTTR; in-language declarations in Bevy and the C++ libraries), with describe-api the cheapest per field and the only one producing a committed, layout-bearing, language-neutral file; every engine has the five kinds it lacks (string, list, map, optional, typed reference by id) and none serialises a pointer; polymorphism is always a type name or id beside the value, resolved by registry lookup and an is-a check, so a tagged slot with allowed types covers the file; editor metadata is a fixed vocabulary per engine and doc-comment tooltips exist only where headers are parsed; per-type versions with upgrade hooks exist in Unreal, O3DE (whose JSON path ignores them) and cereal, renames are declarative redirect tables, unknown fields are dropped everywhere and unknown types kept only by Godot and Flax; scripts feed the same registry through a script-side generator keyed by a neutral name, and reload survives only values held by name; C++26 reflection is consteval only, sees no comments, and is shipped by GCC 16 alone, so it cannot replace describe-api; the recommendation is to add kinds, open the tagged union, record stable ids or rename tables and a per-type version in the description.
- [What do level editors demand of a scene format and engine API?](issues/06-what-level-editors-demand-of-the-data.md): brushes are three plane points per side with derived vertices (Source, TrenchBroom) and every engine with runtime CSG documents a bake to meshes, so baking outside the engine is the recommended path and brush geometry in the scene file can stay open; entity classes are a name plus typed properties the editor learns from a registry (Source's hand-written FGD is the one that drifts), and wiring is a string on the sender plus a name resolver; organisation (visgroups, groups, layers, cordons, cameras) is editor-only data that TrenchBroom keeps as ordinary entities with reserved keys; terrain, scatter, navmesh and lighting bakes are assets beside the scene referenced by id, with streaming cells Unreal's alone; an editor needs a property registry, undo-aware create, destroy, reparent and mutate (Bevy's remote protocol is the minimal list), picking, save-with-filters, hot reload and a play-in-editor copy; compiles collapse instances and drop editor data, and one-file-per-actor is re-embedded at cook; a stable per-entity id that survives instancing is what every prefab scheme leans on.
- [Where do the type descriptions that read and write files come from?](issues/09-where-type-descriptions-come-from.md): ADR-0074; the API description stays the one source and is widened (a `data-asset` role that may hold `std::string`, `std::vector`, `std::optional`, nested structs and typed references as kinds with offsets unused; an open slot for any registered type assignable to a base; `@version`, `@formerly` and a fixed editor-metadata vocabulary as doc commands); a new `tools/generate-type-registry` writes a committed C++ type registration per package that fills a run-time type registry in a new FenrirTypes package at `Install`, with no JSON parsed at run time; components keep the fixed-layout byte rule and data assets go through a generated per-type visitor behind one visitor interface; files name types by canonical name with no GUIDs; C# components and data asset types enter the registry at admission; games run the same tools with the .NET SDK at dev time; behaviour-carrying resources stay undescribed; CI's dirty-tree check gains the generator and runs with the renderer on.
- [What is a data asset: its type model, its name, and how C++ and C# define one?](issues/10-what-a-data-asset-is.md): ADR-0075; a data asset is a plain C++ struct or C# class in the `data-asset` role that may extend one other data asset type (no virtual functions), with the registry recording the base chain so `AssetHandle<WeaponData>` accepts a `Sword` file, and polymorphism only through references (ADR-0074's open slot narrowed to its reference form); it lives in FenrirAssets' store as one `AssetKind::Data` behind the existing `AssetHandle<T>`, one top-level asset per file with named embedded sub-assets (`file#name`), holding described kinds, asset handles and plain structs by value but never an `Entity`; instances are shared and read-only with edits through the store bumping the revision; a field left out takes the type's default and the writer omits defaults; no engine base struct and no behaviour; C# may extend C++ data asset types, not the reverse.
- [How are assets identified, and how do files reference them?](issues/11-asset-identity-and-references.md): ADR-0076; an asset's identity in files is its asset path (root-relative, forward slashes, extension included, `#label` for sub-assets, `builtin:` for embedded assets, `..` and absolute paths refused, case-sensitive with a dev warning), with no GUIDs, sidecars or id index; a reference is the path string alone, typed by the field and checked at load, with a missing or wrong-typed target leaving the handle empty and one diagnostic; handles are hard references loaded with the referencing file under its owner, cycles resolving through the store's deduplication; the store gains a path-from-handle query and named `Add`; a move tool rewrites references across the root's text files and is part of the spec; soft references go to the fog.
- [Which text format do files use, and how are they versioned and migrated?](issues/12-which-text-format-and-versioning.md): ADR-0077; after a measured comparison of TOML, JSON, JSON5 and YAML (`research/format-fit`, a78ddc75) files are JSON5 read and written by an engine-owned reader and writer with no submodule, comments kept as trivia and a fixed emit subset in declaration order with defaults omitted so the same data writes the same bytes; one envelope per file (`format`, `type`, `version`, `data`, `sub`) covers data assets, scenes (a `Fenrir::Scene` data asset with `resources` and `entities`) and settings; the writer emits one entity per block, id first, children after their parent, never reordering, with readable random ids minted once, which is what makes plain line merges work; extensions name role then format (`.asset.json5`, `.scene.json5`, `.settings.json5`); C++ is the reader of record and C# never parses; `format` versions the envelope and `@version` the type, with `@formerly` for renames, unknown fields warned and dropped, unknown types kept opaque, and per-type upgraders `(fromVersion, tree) -> tree` registered with the type registry in C++ and C#, no downgrade; loads are tolerant with file, line and column diagnostics and a counted result; no binary inline; a semantic merge driver goes to the fog.
- [What does a scene file hold, and how are entities identified and referenced in it?](issues/13-what-a-scene-file-holds.md): ADR-0078; a scene file is a `Fenrir::Scene` envelope with one scene, no name inside it, `resources` (described scene-resource types by canonical name, written first, applied after entities; behaviour resources never written) and `entities`; every saved entity carries a described `Fenrir::EntityId` component holding a readable random id minted once at save, `Entity` becomes an `entity` kind written as the target's id (`null` outside the file, one diagnostic), hierarchy is `parent` plus depth-first file order with sibling order kept and `Relationship` and `WorldTransform` never written; every described component is written with defaults omitted, undescribed state, `@transient` components and `Fenrir::Transient` entities with their children are skipped and counted, `char[N]` becomes a `fixed-string` kind; load is two passes inside one frame (reserve and map ids, then add components in file order and complete) with one watch add per component and no event; unknown components are kept opaque in `Fenrir::UnknownComponents` and written back; spawn functions and `SpawnModel` stay and a spawned model saves expanded; a scene file is authoring data read once and never written by the running game, save games are the game's own built from the public blocks, and scene is the word for a map.
- [Who loads and saves files, and what is the API?](issues/15-load-save-api-and-ownership.md): ADR-0079; three layers: `FenrirTypes` (registry and visitors, no tree), a new `FenrirSerialisation` (value tree with comments as trivia, JSON5 reader and writer, the bridge between a described value and a tree through the registry, upgraders, located diagnostics; depends on `FenrirTypes` and `FenrirLogger` only, and is what a game's save files compose) and `FenrirAssets` (the envelope, data asset and scene load and save, the move function); a scene file is instantiated, never a store asset, through `Assets::LoadScene(path, name)` and `Assets::LoadSceneInto(Scene&, path, parent)` (additive, the file's resources ignored and counted), synchronous on the main thread with the filled scene as owner, returning a `SceneLoadResult` of status, roots, counts and located diagnostics; `Assets::SaveScene` is an engine function minting missing entity ids and writing atomically; data assets use the store's doors (`Load<T>` with a diagnostics list, `TryGet`, named `Add`, `Edit<T>(handle, action)` generalising `EditMaterial`, `Replace`, `Save<T>`); `Assets::Move` rewrites references with a dry run under a thin `tools/move-asset` CLI; tests at each layer with golden files and the headless `App` fixture, no window.
- [How do prefabs work: instancing a scene file into another, overrides, nesting and inheritance?](issues/14-prefabs.md): ADR-0080; no prefab asset kind: any scene file or model file is instanced into a scene as a *scene instance* whose root carries a described `Fenrir::Instance { source }` component (the file's single root, or a synthetic root named after the file, `SpawnNodes`' rule), the source path's kind choosing the scene loader or `SpawnNodes` so a spawned model saves as one reference block; the host file writes an instance as `instance` plus a diff computed against a fresh load of the source (root `components` merged on top, `overrides` by source id with fields and `removed` component types, `removedEntities`, added entities as ordinary blocks), per field for values and per component and entity for add and remove, so propagation happens at load; inner entities keep their source ids scoped by the root and are addressed as `"<instance id>/<source id>"` chaining through nesting, with self-instancing refused; a *variant* (scene inheritance) is a scene file whose single root block is an instance, no `inherits` key; `Assets::Instantiate` spawns with a result of root, load result and source-id lookup, `LoadSceneInto` stays the unlinked merge, `Assets::Unpack` drops the link one level at a time, and a subtree `SaveScene` overload makes a prefab from a selection; "apply overrides to source" is editor policy in the fog.
- [What happens on hot reload of a data asset or scene file?](issues/17-hot-reload.md): ADR-0081; `ReloadWatcher` moves to `FenrirCore` and `FenrirAssets` keeps one per loaded file of every kind, polled between frames on the main thread behind `AssetsConfig::hotReload` (on by default, off when cooked); a data asset or imported asset is parsed into a private instance and `Replace`d under its handle with a revision bump, a failure keeping the old one with located diagnostics logged once, and `Assets::Reloaded()` lists this frame's swaps; a changed scene file patches the running scene by entity id (matched entities rewritten with parent and order, new added, dropped destroyed with children, run-time entities and unwritten components untouched, resources rewritten) and never destroys it, whole reload being the caller's two calls; an edited instance source re-patches every instance by source id with overrides reapplied; a C# reload re-reads the data assets and C# components of changed types from their files; a C++ rebuild is a restart; the engine owns it all with no external watcher.
- [What does the data layer offer a level editor?](issues/19-what-the-data-layer-offers-a-level-editor.md): ADR-0082; two additions fold into existing specs, an `@editor-only` doc command the cooker strips (type registry) and `Assets::CopyScene` for a play-in-editor copy in memory (load/save), everything else an editor needs being already decided (registry and metadata, run-time structural edits, `Edit`, scene and subtree save, hot reload with `Reloaded()`, the component-to-tree bridge for undo); brush geometry stays out of the scene file and bakes to mesh assets and existing components; wiring is a package's or the game's over `entity` fields, events and strings already in place; editor organisation is ordinary editor-only components and resources from an editor package, written like any other and opaque where the package is absent; world data (terrain, splines, scatter, navigation, bakes) is each a later package needing nothing new; units and grids ask nothing of the file; Blockout tool, Entity wiring and Editor organisation package go to the fog, graduating when a level editor effort begins and maps itself.
- [What does the C# side of data assets and scene files look like?](issues/16-csharp-data-assets-and-scene-data.md): ADR-0083; a C# data asset type is a class implementing `IDataAsset`, extending a C# or generated C++ data asset class, described by a new scripting source generator (entry, codecs, `[Upgrader]` registration) and admitted with the report all or nothing; the store's value tree is the truth for a C#-typed asset and the managed instance a view pulled through a per-generation cache keyed by handle and revision, one native handing the tree in a compact binary tree encoding and `Replace` handing it back, no `Edit` from C#; C++ data asset types reach C# as generated classes over the same tree, so C# never reads native bytes; the script report gains `entity`, `reference` and `fixed-string` kinds so C# components write to scene files like native ones; scenes reach C# through the `Assets` facade's doors named as in C++ with described result structs and `FindInInstance`; everything per type is generated, only the interface, attributes, cache, generic `TryGet`/`Replace` and facade conveniences are hand-written; tests follow the scripting fixtures with a compile-fail project.
- [What dev-time data does the engine hold, and in what files?](issues/18-dev-time-data.md): ADR-0084; one `<name>.project.json5` at the project root holds each package's Install config by canonical type name (a new `settings` role read through the generated visitor, code wiring `@transient`), read by `Fenrir::Project::Load` in `FenrirAssets` with `Get<T>()` filling a config at compile time before any Install so Install signatures stay; five layers merged field by field with provenance (code defaults, project, `.<platform>.`, `.local.` per developer and never committed, command line `--set`), no environment variables; project holds window, backend, physics limits, asset root, script assembly, first scene and data asset references, scenes hold per-scene environment, device choice is never committed; import sidecars `<source>.import.json5` are described options types with no identity and defaults when missing, sampler defaults staying on the material, imports still at load with an import cache in the fog; project and import files share the envelope, registry, versions and upgraders but are not assets: no handle, owner or hot reload.
- [What must the development formats guarantee a cooked form?](issues/20-what-the-formats-guarantee-a-cooked-form.md): ADR-0085; four promises named as a contract: identity is the root-relative typed path with no ids, no scanning and a writer that refuses absolute or escaping paths; descriptions are compiled in so nothing ships, and a cooked file is its value tree in the binary tree encoding read through the same bridge with `ReadTree` sniffing text or binary and upgraders still running; one door through the store and facade with a private `AssetSource` seam (directory now, pack later, imported assets pre-baked) and no contract on the root's layout beyond relative paths; embedding through the same seam under `builtin:` and a span-backed pack source. The cooker, pack format, compression, chunking, encryption, platform shaders, stripping rules, instance pre-expansion and the cooked project twin are a new effort, "Fenrir cooking", with its own map.

## Not yet specified

- **Fenrir cooking: the shipped form and the pipeline that writes it.** A shipped game needs one (the user's words). Decided by [What must the development formats guarantee a cooked form?](issues/20-what-the-formats-guarantee-a-cooked-form.md) to be its own effort with its own map, started when a game first needs a shipped build or first-run import costs bite. Its starting contract is ADR-0085's four promises: identity is the typed root-relative path with nothing scanned; descriptions are compiled in and a cooked file is its value tree in the binary tree encoding, read through the same bridge; one door over a private `AssetSource` seam, with imported assets pre-baked; embedding through the same seam. It decides the pack layout and index, compression, chunking, encryption, per-platform shaders, stripping of `@transient` and `@editor-only` types, whether instances are pre-expanded or kept, whether a scene gets its own baked map form (Source's VMF to BSP), the cooked project twin (platform folded in, local never cooked), and whether it absorbs the import cache.
- **Game save files:** a game's own saved state (which entities, which fields, its own file) is the game's to write, composed from the type registry and visitors, the JSON5 reader and writer and the entity id map (ADR-0078). Whether a convenience ("write these entities' described components to a file") earns an engine API is decided when a game asks.
- **Spec boundaries: settled, six specs in dependency order** (decided with the user once ticket 20 closed; each a `.scratch/fenrir-serialisation-<name>/spec.md`, removed once built):
  1. **types** (`fenrir-serialisation-types`): the `FenrirTypes` package, the describe-api widening (roles `data-asset` and `settings`, kinds `string`, `list`, `optional`, `reference`, `entity`, `fixed-string`, `path`, doc commands `@version`, `@formerly`, `@transient`, `@editor-only` and the metadata vocabulary), `tools/generate-type-registry`, and the CI dirty-tree check. ADR-0074, with the kinds and commands of ADR-0078, 0068 and 0070.
  2. **format** (`fenrir-serialisation-format`): the `FenrirSerialisation` package: value tree with trivia, JSON5 reader and writer with the emit subset, the bridge over the registry's visitor, upgraders, located diagnostics, the binary tree encoding, `ReadTree` sniffing, golden files. ADR-0077, with its parts of ADR-0079, 0069 and 0071. Depends on 1.
  3. **data-assets** (`fenrir-serialisation-data-assets`): `AssetKind::Data`, the envelope, `Load`, `TryGet`, named `Add`, `Edit`, `Replace`, `Save`, sub-assets, typed references checked at load, the path-from-handle query, the move tool, the `AssetSource` seam, the asset watcher and in-place reload. ADR-0075, 0062, and their parts of ADR-0079, 0067 and 0071. Depends on 2.
  4. **scenes** (`fenrir-serialisation-scenes`): scene files, `EntityId`, `Transient`, `UnknownComponents`, `Instance`, instances and variants, `LoadScene`, `LoadSceneInto`, `Instantiate`, `SaveScene` (scene and subtree), `Unpack`, `CopyScene`, the scene patch and instance re-patch. ADR-0078, 0066, and their parts of ADR-0079, 0067 and 0068. Depends on 3.
  5. **csharp** (`fenrir-serialisation-csharp`): `IDataAsset` and attributes, the data asset source generator, codecs for C++ and C# types, the generation cache, `TryGet` and `Replace` over the tree natives, the report's new kinds, the scene doors on the `Assets` facade. ADR-0083. Depends on 4.
  6. **dev-time** (`fenrir-serialisation-dev-time`): the project file and its five layers with provenance, `Project::Load` and `Get<T>`, import sidecars and the two options types, `--project`. ADR-0084. Depends on 3 (and 1 for the `settings` role and `path` kind).
- **Which existing engine assets become files:** materials (`MaterialData`, edited in code today), instance lists, bone masks, render-target images. Likely the first engine-provided data assets; the data asset model and the format are decided, so this waits on the spec boundaries.
- **A semantic merge driver:** a Fenrir merge tool keyed by entity id, component type and field (Unity's merge rules' shape, about 300 to 500 lines over the engine's own tree). Declined by [Which text format do files use?](issues/12-which-text-format-and-versioning.md): the layout rule makes plain line merges work, and two people appending at the end of a file conflict in every format; build it when a team meets that conflict often.
- **Editing support in the data layer:** what a running scene or asset store offers an editor beyond load and save (change tracking, dirty state, undo-friendly edits, validation diagnostics for broken files, and "apply this instance's overrides to its source" as a policy over the subtree save of ADR-0080), built on `Reloaded()` and the scene patch of ADR-0081. Load, save and hot reload are decided; waits on the level-editor ticket naming what an editor needs first.
- **Streaming building blocks:** what a game needs from scene files to stream an open world (additive load and unload, scene composition, cells) given that partitioning is the game's; a cell partition is a tool's computation over per-entity bounds and a flag, never a scene format feature (ticket 19). Additive load and instances are decided; waits on a game that streams.
- **Blockout tool:** a brush and CSG tool that bakes to mesh assets and `MeshRenderer` and `Collider` components, with its own file (three plane points per side, material, texture axes, vertices derived, if it ever enters a Fenrir file). Declined for the engine by [What does the data layer offer a level editor?](issues/19-what-the-data-layer-offers-a-level-editor.md); graduates when a level editor effort begins.
- **Entity wiring:** a Source-style input/output component and the system that fires it, as a package or the game's, over `entity` fields, events and strings already in the data layer; `@input`/`@output` doc commands would let an editor show connectable ends. Graduates when a game or the editor effort asks.
- **Import cache:** an ignored directory of imported results keyed by a content hash of source, options and platform, so a model or image is decoded once per change rather than at every load (Godot's `.godot/imported`, Unity's `Library`, Bevy's `imported_assets`). Declined now by [What dev-time data does the engine hold?](issues/18-dev-time-data.md) since imports run at load and nothing has shown the cost; graduates when load times hurt, or folds into the cooker.
- **Editor organisation package:** layers, groups, folded state, visgroups and cordons as `@editor-only` components and scene resources, written to the scene file and stripped when cooked. Graduates with the level editor effort.
- **Text in data assets:** localisation and string tables, if data assets hold player-facing text. The format is decided; waits on a game asking for it.
- **Soft references:** a path a game loads later rather than with the referencing file (Unreal's soft object pointers, Flax's soft references). Declined by [How are assets identified?](issues/11-asset-identity-and-references.md) until streaming needs one; a string field and a load call cover the rare case now.
- **Value inheritance between files ("based on"):** a data asset serving as another file's default, as Unreal's data-only Blueprints and Stride's archetypes do. Ruled out of the first version by [What is a data asset?](issues/10-what-a-data-asset-is.md); revisit once data assets exist and a game asks for it.

## Out of scope

- Editor UI: an inspector, a scene view, a level editor's own tools and windows, editor layouts and window state.
- The demo apps' scene lists stay code.
- Game save files: a game's own (ADR-0078); only the question of a convenience API stays in the fog.
- World-data packages (terrain, splines, scatter, navigation, lighting bakes): each its own effort; the data layer needs nothing new for them (ADR-0082).
- Editor machinery: picking, gizmos, per-entity bounds queries, the undo stack, selection, copying play changes back, partial and cordoned builds, budget views (ADR-0082).

# What do level editors demand of a scene format and engine API?

Type: research
Status: resolved
Blocked by: none

## Question

Read the same editors as [What makes a good level editor?](05-what-makes-a-good-level-editor.md) for their **data**: what their map and scene files hold, and what their engines expose so the editor can work, in the areas that constrain Fenrir's scene file and the building blocks the engine offers a tool: Source's `.vmf` and compiled BSP, Source 2's `.vmap` and its compile, TrenchBroom's `.map` with game definition files (FGD, `.def`), Unreal's `.umap`, Level Instances, Packed Level Actors and one-file-per-actor, Godot's `.tscn` as a level file, Unity's scenes with ProBuilder, Dunia, Forge, and Bevy's scene work.

- **Brush geometry:** how brushes, CSG and blockout geometry are stored (planes, polygons, half-spaces), when they are baked to meshes, and what the engine sees at runtime (meshes and colliders, or brushes themselves).
- **Entities and wiring:** how a map file names an entity's class and properties (FGD-style definitions the editor reads), and how gameplay wiring is stored (input/output connections, named targets, trigger volumes, logic entities).
- **Organisation in the file:** layers, visgroups, groups, folders, instances with overrides, cordons.
- **World data beyond entities:** terrain heightfields and layers, splines and roads, foliage and scatter, navigation meshes, lighting bake inputs and outputs, streaming cells and their bounds.
- **Engine API the editor needs:** a type and property registry to build property panels from, create/destroy/reparent entities at runtime, picking and bounds, snapping helpers, undo-friendly edits, saving a running scene, hot reload, and play-in-editor's scene copy or reset.
- **Compile steps:** what runs between the editor's file and the shipped level (BSP compile, lighting, navmesh, packing), and what the editor file keeps that the shipped one drops.

Write findings to a Markdown file on the `research/level-editor-data` branch (`.scratch/fenrir-serialisation/research/level-editor-data.md`), citing each claim's source and pinning the versions read, and link it here.

## Answer

Findings: `.scratch/fenrir-serialisation/research/level-editor-data.md` on branch `research/level-editor-data` (commit `43f41df7`), against the Valve Developer Community's VMF, FGD, I/O, BSP, `func_instance`, VMAP and DMX pages (read through the browser, as the wiki blocks fetches), TrenchBroom 2026.2's manual and source, Unreal 5.9 docs (the C++ API pages for packed level actors, property overrides and transactions were unreadable), Godot 4.7 docs and `resource_format_text.cpp` at `4.7-stable`, Unity 6.6 with ProBuilder 6.0.9 and AI Navigation 2.0.16, Bevy 0.20.1 (`bevy_world_serialization`, `bevy_scene`'s BSN, `bevy_remote`), and GDC and interview material on Dunia and Forge, whose formats are not public. Inferences are marked in the file, which ends with "What this means for Fenrir's data layer".

- **Brush geometry:** Source stores each side as three plane points plus material, UV axes, lightmap scale and smoothing groups, deriving vertices at load; the compiled BSP keeps brushes for collision beside the rendered faces. TrenchBroom writes the same planes in its format variants with external compilers. Source 2 replaced brushes with half-edge meshes in a DMX `.vmap` compiled to model, physics and world-node resources. Unreal's BSP brushes are blockout the docs say to convert to static meshes; Godot's CSG lives as scene nodes rebuilt at load with "Bake Mesh Instance" and "Bake Collision Shape"; Unity's ProBuilder keeps a mesh component in the scene that compiles to a mesh, with CSG experimental. No engine makes brushes the runtime's primary geometry, and all three with runtime CSG document a bake to meshes. If brushes ever enter the scene file, the universal shape is three plane points per side with derived vertices.
- **Entities and wiring:** Source: a class name plus free-form string keyvalues, with editor knowledge from an FGD that is only a reference for the editor (class, base classes, typed keys with display names, defaults and docs, inputs, outputs, helpers for size, spheres and lines); wiring stored only on the sender as `"OnTrigger" "target,Input,param,delay,times"`, targets by name or class with wildcards; triggers are brush entities, logic entities point entities. TrenchBroom hard-codes `target` and `targetname`. Godot writes nodes with name, type, parent and property lines plus `[connection signal= from= to= method=]` lines of node paths. Unity names classes by id and scripts by GUID, with exposure decided by its serialisation rules. Bevy names components by full type path. Forge wires with node-graph brains under a budget. A Fenrir wiring building block needs nothing from the format beyond a string field and a name resolver.
- **Organisation in the file:** Hammer keeps nested visgroups with ids and colours, a per-object editor block (colour, visgroup ids, group id, comments), group nesting, hidden wrappers, cameras, grid settings and cordon boxes in the VMF, all for Hammer only; `func_instance` references another VMF with name fix-up styles, ten `$variable` substitutions and an I/O proxy, collapsed by VBSP. TrenchBroom stores layers, groups and linked groups as plain `func_group` entities with reserved `_tb_*` keys any compiler can ignore: the lightest answer. Unreal: one file per actor (editor-only, embedded at cook), Level Instances (edit in context, commit propagates, embedded or streamed), Packed Level Actors (static meshes only, with a property-overrides member), Data Layer assets plus per-world instances. Godot: owner-based saving, `instance=ExtResource()` with only overridden properties, editable children, instance placeholders, groups, and 4.6's `unique_id` tracking nodes through renames. Unity: the transform hierarchy plus `SceneRoots`, `PrefabInstance` modifications and removed and added lists with stripped placeholders. Bevy has no hierarchy section; Forge has prefabs and mode prefabs.
- **World data beyond entities:** terrain is a displacement on a brush side (Source), landscape components with one height texture each and non-destructive edit layers plus splines (Unreal), a `TerrainData` asset referenced by a component (Unity), and only a heightmap collision shape in Godot. Scatter is a static-prop game lump (Source), instanced foliage clusters owning the surface with a partition grid (Unreal), terrain trees and details (Unity). Navmesh is an external `.nav` (Source), Recast tiles with static, dynamic and modifier modes and a builder commandlet (Unreal), a `NavMeshData` asset (Unity), a `NavigationMesh` resource baked in the editor or at runtime (Godot). Lighting is BSP lumps plus packed cubemaps (Source), an `.lmbake` needing UV2 (Godot, which warns of Base64 bloat otherwise), a separate Lighting Data Asset so the scene file stays stable (Unity). Streaming is per-actor spatial loading, runtime grids, cell sizes and HLOD per cell (Unreal), BSP leaves and clusters (Source), an octree (Source 2). Bake outputs belong beside the scene, referenced by id.
- **Engine API the editor needs:** a property registry (Godot's `get_property_list` dictionaries with name, type, hint, hint string and usage, validation, revert and change notification; Unity's `SerializedObject` and `SerializedProperty` with automatic undo dirtying and override styling; Bevy's type registry plus the remote protocol's schema; Source's hand-maintained FGD is the counter-example that drifts); create, destroy and reparent (Bevy's remote protocol with spawn, despawn, insert, remove, mutate, reparent and watch streams; Unity's undo-aware calls; Godot's `add_child` plus owner); picking by renderer and material index (Unity) or gizmo plugins (Godot); snapping needs nothing from the data beyond transforms; undo as per-property deltas recorded before the change, grouped and collapsible (Unity) or per-scene do and undo method and property pairs with explicit references for created and removed nodes (Godot); saving as pack-owned-nodes (Godot), save-scene (Unity) or a world filter with allow and deny lists and skip attributes (Bevy); hot reload as Live Coding reinstancing (Unreal), domain reload off (Unity), synchronise scene and script changes (Godot), planned `.bsn` reload (Bevy); play-in-editor as a scene reload losing changes (Unity), in-process worlds with "keep simulation changes" (Unreal), or a separate process with a remote scene tree (Godot).
- **Compile steps:** Source's VBSP, VVIS and VRAD keep brushes, the entity text with outputs and Hammer's face ids, drop visgroups, groups, editor blocks, cameras and cordons, collapse instances and absorb detail brushes, cubemaps, overlays and static props, add vis, lighting and packed content, with `.nav` external. Source 2 compiles the map to a bundle of resources in a VPK. TrenchBroom runs the game's compilers from profiles and omits marked layers. Unreal's cook converts formats, re-embeds one-file-per-actor actors, discards embedded Level Instances and builds HLOD, nav and minimaps through commandlets. Godot's bakes write resources in the editor and export converts text resources to binary by default. Unity has no scene compile; bakes are separate assets. Bevy has none. Far Cry 5 runs an incremental dependency-graph build over ten million nodes.
- **For Fenrir:** baking brushes to meshes outside the engine is every engine's recommended path, not a compromise, so brush geometry in the scene file can stay open at no cost; organisation needs no file section if it rides on entities with reserved components; a stable per-entity id that survives instancing is what every prefab and instance scheme leans on; per-entity files are a collaboration format, not a runtime one; Bevy's remote protocol is the cleanest minimal list of editor operations. Not read: Unreal's per-instance override format and undo API, Source 2's element model, s&box's compile.

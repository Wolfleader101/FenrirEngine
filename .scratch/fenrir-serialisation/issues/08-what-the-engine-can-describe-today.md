# What can the engine describe and name today, and what gap do files open?

Type: research
Status: resolved
Blocked by: none

## Question

Read this repository, not the web, and record exactly what the engine already has that reading and writing files would build on, so the reflection and data asset tickets argue from facts:

- **The API description** (`tools/describe-api`, `SCHEMA.md`, ADR-0042, ADR-0043, ADR-0044, ADR-0045, ADR-0046): which kinds, roles and categories it records; how defaults and doc comments are captured; what it refuses (strings, `std::vector`, inheritance, references); which packages run it and when (committed output, CI's dirty-tree check); whether a game project could run it on its own headers today and what that would take.
- **The C# side** (`packages/Iris`, `FenrirScripting`, the binding generator): what the script report knows about a C# component or shared struct at admission (names, offsets, kinds), how `DynamicComponentType` lays out a script component in the ECS, how native resources and bound types cross, and whether a C# class with strings and lists could be described the same way.
- **The ECS** (`FenrirECS`): `ComponentType` and `DynamicComponent` as the run-time door to a component known only by name; `EntityList`'s create, add, remove, reparent and query; `ComponentWatch` and tracked sets; whether an entity can be named or found by anything but its handle; what `WorldTransform` and parenting need when a hierarchy is rebuilt from a file.
- **Scenes and the app** (`FenrirScene`, `FenrirApp`): what a `Scene` holds (name, entity list, typed resources behind `type_index`), how scenes are created, activated and destroyed, and what a scene resource would need to be written to a file and read back (today it is reached by C++ type only).
- **Assets** (`FenrirAssets`, ADR-0021): how a load names a file (asset root, relative path, `#label` sub-assets), deduplication by path, owners, revisions, `AssetHandle<T>`'s generational form and its bound-type crossing, which asset kinds exist and which are only ever made in code (`MaterialData`, instance lists, bone masks, render-target images), and how a component holding an `AssetHandle<Mesh>` could be written to a file (by what name) and read back (loaded when?).
- **Entity references in components:** every shared component whose field is an `Entity` (joints, `SkinnedMesh`, `BoneAttachment`, animation layers, vehicles' wheels) and how each is resolved today, as the list a scene file must be able to write.
- **Text and names in components:** every fixed-size name field (`BoneName` and others) and how it is bounded, as the precedent for strings.
- **Existing reload:** how the script reload watcher works (`FenrirScripting`), as the precedent for hot reload of files.

Write findings to a Markdown file on the `research/engine-as-is` branch (`.scratch/fenrir-serialisation/research/engine-as-is.md`), citing file paths and the commit read, and link it here.

## Answer

Findings: `.scratch/fenrir-serialisation/research/engine-as-is.md` on branch `research/engine-as-is` (commit `85f6401b`), read at `5011f241`.

- **API description:** `tools/describe-api` writes `packages/<Pkg>/api/<Pkg>.api.json` with categories `struct`, `tagged-union`, `bound-type` and `enum`, roles `component`, `event`, `scene-resource`, `app-resource`, `shared-struct`, `bound-type`, `enum` and `nested`, and per field `name`, `offset`, `kind`, `type`, `default` and `doc`; kinds are the integers, `f32`/`f64`, `bool`, `char16`, `enum`, `struct`, fixed `array` and opaque `pointer`. Defaults come from default member initialisers, docs from `/** */` and `///`. It refuses references, virtuals, bases with data members, and anything not trivially copyable (so `std::string`, `std::vector`, `std::map` and `std::variant` all fail), bit-fields and arrays of arrays. Eleven packages plus FenrirScripting have selections (FenrirScene, FenrirCore, FenrirTime, FenrirScheduler, FenrirLogger and FenrirDebugDraw have none); the ordinary build never runs it; CI's `api-descriptions.yml` regenerates on PRs and fails on a dirty tree, but configures with the renderer off, so FenrirWindow's and FenrirRenderer's descriptions are never checked. A game could run it today (dotnet plus the libclang NuGet; `fenrir_describe_api` is a plain CMake function) given its own `.api.toml` and plain-data types, but no example does and nothing installs or exports the module.
- **C# side:** the script report carries name, size and alignment per `IComponent` and event; field names, types, kinds and offsets come from Iris's `TypeQueries.Fields` (offsets only for blittable structs) and fold into a fingerprint. Admission validates native components, events, shared structs and resources against the C# structs by name, size, field count, name, offset and kind, registers all or nothing, then drops stale data. A `DynamicComponentType(name, size, align)` becomes zeroed opaque pages in a `ByteStorage`; the ECS knows no fields. Native resources are mirrored `[NativeResource]` structs reached in place; bound types are mapped by hand; `AssetHandle<T>` crosses by pointer; `Entity` is a 16-byte nested shared struct. A C# class with strings or lists cannot be described: components must be `unmanaged`; the only text precedents are the 256-byte fixed `Name` buffer and `string` as a native-call parameter.
- **ECS:** `ComponentType` names a native or dynamic component but carries no name (naming for a file is "the caller's business"); `EntityList` has get, has, add, remove, count, clear, `ForEachWith` and `Watch` by `ComponentType`, `CreateEntity` (adding `Transform`, `Name` and `Relationship`), `ReserveEntity`/`CompleteEntity`, `HandleOf` and `DestroyEntity`; reparenting is `Entity::AddChild`/`RemoveChild` over `Relationship`'s four links. Watches record adds and removes only, never edits. No lookup by name: entities are found by handle, query or hierarchy walk; an id is an EnTT slot plus version plus the list pointer. `WorldTransform` is always computed, so a rebuild needs only local `Transform` and the parent link, parents first; `AssetStore::SpawnNodes` is the one rebuild-from-data precedent, and `ModelNode::sourceId` the one file-stable identity.
- **Scenes and the app:** a `Scene` is a `std::string` name, an `EntityList` and an `unordered_map<type_index, unique_ptr<void>>` of resources; `App::CreateScene` does not check for a duplicate name, `ChangeActiveScene`, `DestroyScene` and `GetScene` search by name, the active scene cannot be destroyed; demo scenes are `std::function` spawns. A scene resource has no name anywhere in FenrirScene; the only names are FenrirScripting's `ResourceRegistration` for plain-data ones (`Sky`, `SkyLight`); `PhysicsWorld`, `SkeletonPoses`, `Animators` and `DebugDraw` have behaviour and no description.
- **Assets:** `Load<T>(path, owner)` resolves against `AssetsConfig::root` (default `assets/` beside the executable), `file#Label` names sub-assets (numbered `#Mesh0`, `#Material0`, …), `builtin:` names the embedded ones; deduplicated by key per kind; owners app or scene, uncounted; `revision` from 1, bumped by `Replace` and material edits. `AssetHandle<T>` is `{index, generation}` over nine kinds. There is no public path-from-handle query (the key is private). Made only in code: `MaterialData` (a map of string to variant), `InstanceListData`, `BoneMaskData`, render-target `ImageData`, procedural meshes and clip events; every asset data type holds vectors or strings, so none is describable. A component's `AssetHandle<Mesh>` could be written as its store key or `builtin:` name and read back by a synchronous main-thread `Load` for the scene owner; code-made assets have no name.
- **Entity references:** `Relationship` (four links), `Joint.bodyA`/`bodyB`, `VehicleWheel.vehicle`, `VehicleDifferential` and `VehicleAntiRollBar`'s `leftWheel`/`rightWheel`, `SkinnedMesh.skeleton`, `BoneAttachment.skeleton`, `AnimationLayer.skeleton`, plus state structs (`VehicleWheelState`, `CharacterState` ground fields), events, hits, `SpawnedNodes` and DebugDraw's `relativeTo`. All are resolved by tolerant `IsValid()` and component checks each frame or step, going inactive with one warning and recovering by themselves; cross-scene entities are never valid. The findings hold a table with file and line.
- **Text in components:** exactly two fixed name fields: `Name` (`char[256]`, `Set` truncates to 255 bytes, described as an array of 256 `u8`, C# `fixed byte` cut on a UTF-8 boundary) and `BoneName` (`char[256]`, `Set` refuses over 255 bytes or an embedded zero; an unterminated buffer never resolves). Unbounded strings exist only in asset data and configs, never in a component.
- **Existing reload:** `Detail::ReloadWatcher` is a clockless, I/O-free decision class (stamp is mtime plus size, looked at every 250 ms, debounced 400 ms, then "can be opened") with `Idle`/`Settling`/`Ready`; `GenerationLifecycle` polls it each frame, loads a private copy, replaces all or nothing with a restore of the previous generation, and keeps data whose fingerprint is unchanged. Native components are never reloaded. The `.feproj` in `Scripting.hpp`'s doc comment has no reader or writer.
- **Nuances to the map's Notes:** the API description also records `char16`, tagged unions and bound types by layout, and the natives description (not the API description) has a `string` kind for `std::string_view` parameters; `.cubemap` text files (six face lines) are the one text format the engine reads today.

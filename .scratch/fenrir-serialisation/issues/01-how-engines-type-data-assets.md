# How do engines type, inherit and reference data assets?

Type: research
Status: resolved
Blocked by: none

## Question

How do engines model game-defined typed data in files (Godot's `Resource`, Unity's `ScriptableObject`, Unreal's `UDataAsset`, `UPrimaryDataAsset` and `UDataTable`, Bevy's typed assets with `Reflect`, Flax's JSON assets, Stride's assets, O3DE's asset system), in the areas that constrain Fenrir's data asset:

- **Typing:** how a file names its type, and whether the type is a class with fields, a plain struct, a table row, or a bag of parts. How script-defined (GDScript, C#, Blueprint, Lua) and native types share the one mechanism.
- **Inheritance and polymorphism:** whether one data asset type extends another; whether a field typed as a base accepts a derived file (Godot's `export var weapon: WeaponData` taking a `Sword.tres`); how Unreal's class-typed soft references and `TSubclassOf`, Unity's polymorphic `SerializeReference`, and composition-based alternatives (parts, traits, interfaces) each do it, and what each costs in tooling.
- **References:** how one data asset names another and how a component names a data asset: by path, by stable id (Unity GUID, Godot UID, Unreal object path), or both; what happens when a file moves; sub-resources embedded in a file versus external files (Godot's `sub_resource`, Unity's sub-assets, Unreal's subobjects).
- **Defaults and inheritance of values:** per-type defaults, Unreal's archetypes and Class Default Objects, Godot's `local_to_scene`, Unity's prefab-like variants for data.
- **Lifecycle:** loading (eager, lazy, async), sharing (one instance per file, duplication), hot reload on edit, and what scripts see when a type changes shape.
- **Versioning:** how a file written by an older type is read (renamed fields, removed fields, custom upgrade hooks, Unity's `FormerlySerializedAs`, Unreal's version custom serialisation).

Write findings to a Markdown file on the `research/engine-data-assets` branch (`.scratch/fenrir-serialisation/research/engine-data-assets.md`), citing each claim's source and pinning the versions read, and link it here.

## Answer

Findings: `.scratch/fenrir-serialisation/research/engine-data-assets.md` on branch `research/engine-data-assets` (commit `7cf031dc`), against Godot 4.7 docs and the `4.7-stable` source, Unity 6000.3 manual and `UnityCsReference` (Addressables 2.6.0), Unreal 5.9 conceptual pages and 5.6 API pages (source not read), Bevy 0.20.1, Flax 1.13, Stride 4.4.1 and O3DE 2605.0. Unverified items are marked in the file.

- **Typing:** every engine's data asset is a class or struct with named fields serialised by name; Unreal's `UDataTable` is the one tabular variant (one row struct per row). Six of seven put a type name in the file: Flax a `TypeName` from one C++ and C# type registry; Unreal a class path in the import table; O3DE `$type` as a class name or a UUID when ambiguous; Stride a YAML tag; Godot `type=` naming the *native* base plus a `script` reference, with `script_class` only an editor hint; Unity names the type by the script asset's `.meta` GUID; Bevy names nothing (the loader is chosen by extension) except reflect files keyed by Rust type path. Script and native types share one property mechanism everywhere. The minimum field vocabulary every engine supports and the API description lacks: strings, variable-length lists, nested objects by value and references to other assets.
- **Inheritance and polymorphism:** a base-typed field accepting a derived file is free in every engine because the referenced file names its own type; the type system only answers *is-a* at assignment (Godot `is_parent_class`, Flax `IsAssignableFrom`, Unreal `IsA` and `TSubclassOf`, O3DE `CanDowncast`). The base relation is data in a registry (Flax's base handle, O3DE's RTTI bases, Unreal's super index, Godot's base script), never layout. Polymorphism *by value inside* a file is where engines pay: Unity's `[SerializeReference]` (no built-in picker, no structs) and Unreal's instanced objects and `FInstancedStruct` need extra metadata and pickers, while Godot, Stride, O3DE and Flax have every nested value tag its own type. The editor cost is one query: enumerate the concrete descendants of a type. Epic's advice is to inherit data through data-only Blueprint classes, since data asset instances cannot be inherited from. Interfaces appear only as picker filters; no engine has a "parts" model for data assets (Bevy uses enums).
- **References:** stable id and path: Godot (`ext_resource uid= path=`, uid tried first with a path fallback and warning; 63-bit random ids, `.uid` sidecars since 4.4, an id cache; the editor rewrites dependents on move), Stride (`Guid:Url`), O3DE (`{guid, subId}` plus a hint). Id only: Unity (the `.meta` GUID; lose it and references break), Flax (a GUID in the header, with a registry mapping path to id; renames keep it). Path only: Unreal (a redirector left on move, with a fixup resave; no per-asset GUID) and Bevy. Hard versus soft loading is a field-type choice everywhere. Embedded sub-objects get file-local ids (`res://x.tres::id`, `fileID`, export index, part id, `#label`).
- **Defaults and value inheritance:** diff-against-default is the majority: Godot writes only values that differ from the script's or class's default (floats compared approximately), Unreal delta-serialises against the archetype (changing a C++ default retroactively updates instances that still matched the old one), O3DE strips values equal to a default-constructed object, Stride's archetypes mark members base, new or sealed, Flax diffs only prefab instances; Unity and Bevy write everything. Value inheritance between data files exists only as Unreal's data-only Blueprints and Stride's archetypes; Unity's presets are editor-only defaults; Godot's `resource_local_to_scene` is copy-on-instantiate, not inheritance.
- **Lifecycle:** one shared reference-counted instance per file identity in all seven; synchronous load by default with an asynchronous path everywhere (O3DE always asynchronous). Two hot-reload designs: mutate in place and signal (Godot's editor: an mtime scan, a reload that loads uncached, copies over the instance and emits `changed`, with a same-class check) versus replace the object and notify holders (O3DE, Bevy's `AssetEvent::Modified`, Flax). A type-shape change is uniformly "serialise instances to a name-keyed property bag, swap the code, restore by name, drop what no longer fits".
- **Versioning:** strongest in Unreal (per-subsystem custom version GUIDs, tagged properties tolerating adds and removes, core redirects for class, struct, enum, property and package renames, a hook for type changes) and O3DE (a version number with a converter on a node tree, name and type changes, class deprecation, per-field load results); then Stride (a per-dependency version plus upgraders on the YAML DOM before typed load, and aliases), Flax (an engine-build stamp plus old-name properties and a deprecation resave), Unity (`FormerlySerializedAs`, `MovedFrom`, missing types preserved); nothing in Godot and Bevy for field renames: Godot's loader calls `set()` and ignores failure, so renamed or removed properties are silently dropped on load and lost on the next save, with only a 3-to-4 class rename table and `MissingResource` for unknown types. Version stamps are per file (Flax, Stride, Unreal) or per type instance (O3DE, Unity on engine types).
- **Cross-cutting:** the engines with the best migration story put the upgrade hook next to the type and run it before or during typed deserialisation; the engines that retrofitted stable ids (Godot 4.4, O3DE) used sidecars for formats that cannot carry an id and kept the path as a fallback.
- **Against the map's Notes:** Godot's file does not name the script class as its type (native class plus script handle plus property bag), so language-neutral type naming follows Flax, Unreal and O3DE rather than Godot or Unity; Godot has no field versioning at all, so copying it must not extend to migration; no engine's reflection describes inheritance as layout, so the describe-api constraint is Fenrir's own, and Flax's generator describes class hierarchies while Bevy and O3DE get the same file-level polymorphism from flat tagged values; diff-against-default makes the API description's per-field defaults load-bearing, with the cost that changing a default rewrites unoverridden files; both hot-reload designs need types re-instantiable from a name-keyed bag and holders holding handles, not pointers.

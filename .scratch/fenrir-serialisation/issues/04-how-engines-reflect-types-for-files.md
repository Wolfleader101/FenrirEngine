# How do C++ engines describe their types for serialisation and editors?

Type: research
Status: resolved
Blocked by: none

## Question

How do C++ engines know a type's fields in order to read and write it from a file and show it in an inspector, in the areas that constrain how Fenrir widens its API description (ADR-0042, `tools/describe-api`): Unreal's UnrealHeaderTool and `UPROPERTY`, Godot's `ClassDB` and `GDCLASS` with `_bind_methods`, O3DE's `AZ::SerializeContext`, `EditContext` and `BehaviorContext`, Flax's code generator, Bevy's `#[derive(Reflect)]` and type registry, Hazel and other codegen-based engines, and libraries such as RTTR, refl-cpp, Boost.Describe and `magic_enum`, plus the C++26 reflection proposals' state.

- **Mechanism:** header parsing and code generation (libclang or a custom parser), macros registering at static-init time, templates and intrusive declarations, or a runtime registry filled by hand; what each costs the game developer per type and per field.
- **Coverage:** strings, dynamic arrays and maps, nested structs, optional values, enums and flags, pointers and references to other objects (typed, polymorphic), fixed-layout versus owning types; how plain-data components and richer "asset" types share or split the mechanism.
- **Polymorphism:** class hierarchies, interfaces or traits, type ids and how a base-typed field is read when the file holds a derived type.
- **Metadata:** per-field attributes editors need (ranges, display names, categories, read-only, tooltips from doc comments), and default values.
- **Versioning hooks:** per-type version numbers, field renames, custom upgrade functions, and how unknown fields are kept.
- **Scripts:** how script-defined types (C#, GDScript, Lua, Blueprint) are described through the same registry so files name them neutrally, and how a type's description survives script reload.

Write findings to a Markdown file on the `research/engine-reflection` branch (`.scratch/fenrir-serialisation/research/engine-reflection.md`), citing each claim's source and pinning the versions read, and link it here.

## Answer

Findings: `.scratch/fenrir-serialisation/research/engine-reflection.md` on branch `research/engine-reflection` (commit `639e4a1a`), read 2026-11-10 against Unreal 5.9 docs, the 5.5 API reference and Epic's reflection post (the engine repo is private), Godot `4.5-stable`, O3DE `2510.2`, Flax 1.13, Bevy 0.17.3 (0.20.1 for the scene-crate change), Lumix, Hazel and Wicked masters, RTTR, refl-cpp, Boost.Describe and Boost.JSON, magic_enum 0.9.8, glaze 9.1.0, cereal 1.3.2, cista, P2996R13, P3394R4 and P3294R2, the compiler support pages and Sutter's 2025 and 2026 trip reports. The file closes with a section reading everything against describe-api.

- **Mechanism:** three families. Header-driven generators (Unreal's UHT, a C# tool since 5.1 emitting generated headers and sources compiled in and never committed; Flax.Build's own tokenizer over `API_FIELD` attributes emitting C# wrappers and type initialisers; Lumix's comment scanner emitting committed generated headers), hand-filled run-time registries (Godot's `_bind_methods` with a setter, a getter, two binds and an `ADD_PROPERTY` per field and no offsets anywhere; O3DE's `Reflect()` with three lines per field across its serialise, edit and behaviour contexts plus a UUID per type; RTTR's static-init block), and in-language declarations (Bevy's `#[derive(Reflect)]`, Describe and refl-cpp macros, magic_enum and glaze compiler tricks). Hazel and Wicked have none. describe-api's cost per field (a declaration and a doc comment) is the cheapest in the field, and it is the only one producing a committed, layout-bearing, language-neutral file; Godot's `extension_api.json`, ADR-0042's cited model, is a run-time dump with no offsets for object classes and no hint, usage or default per property.
- **Coverage:** every engine with data assets has the same five kinds describe-api lacks: string, list, map, optional (Unreal's optional property, O3DE's zero-or-one container, Bevy's `Option`; Godot has nil, Flax none) and a typed reference storing an id (Unreal's class path with owned subobjects marked, Godot's uid or path or `NodePath`, O3DE's entity and asset ids, Flax's GUID; Bevy owns data only and remaps entities). Nobody serialises an opaque pointer. Plain components and richer assets share one mechanism everywhere that has one (Unreal's struct and class differ only in GC, defaults and subobjects; Godot has no plain-data path at all; Flax's binary assets are the one separate system, with real upgraders).
- **Polymorphism:** the file stores a type name or id beside the value in every engine (Unreal's class path and per-property tags with struct and enum names and GUIDs; Godot's `type=` plus script path; O3DE's UUID or `$type`; Flax's `TypeName`; Bevy's one-entry map keyed by type path). A base-typed slot is resolved by registry lookup then an assignability check. Bevy has no hierarchies and cannot hold a polymorphic field inside a struct. Among libraries only RTTR and cereal resolve a derived type by name at run time. Inheritance buys engines a constraint and shared fields, not a file encoding: a tagged slot with listed allowed types (describe-api's tagged-union shape, opened up) covers the file.
- **Metadata:** fixed vocabularies everywhere: Unreal's `meta=(ClampMin, ClampMax, DisplayName, EditCondition, ...)` and edit flags, editor-only and stripped; Godot's `PropertyInfo` with hint strings such as `"0,20,0.01,or_greater,suffix:m"`; O3DE's CRC-keyed attributes (min, max, step, suffix, read-only, visibility, change notify, category) that may be member-function pointers; Flax's .NET attributes passed verbatim; Bevy's typed `#[reflect(@0.0..=1.0)]`. Doc-comment tooltips exist only where headers are parsed (Unreal, Flax's `/// <summary>` to `[Tooltip]`, Bevy behind a feature); no library and not C++26 can see a comment. Defaults: Unreal's default-object delta, Godot instantiating the class once, O3DE's default-instance diff, Flax's `[DefaultValue]` generated from the C++ initialiser (describe-api's approach), Bevy's `ReflectDefault`.
- **Versioning hooks:** per-type versions only in Unreal (GUID-keyed custom versions), O3DE (`Version(n, converter)` editing a node tree, name and type changes, class deprecation; its newer JSON path ignores versions entirely and loads best-effort), Lumix and Wicked (hand-written per-module integers) and cereal. Godot has only file-format versions plus a class-rename table and `_set` fallbacks; Flax only an engine-build stamp with hand fixes and deprecation marks; Bevy nothing, and renaming a module breaks files unless the type path is pinned. Declarative renames: Unreal's core redirects, O3DE's name changes. Unknown fields are dropped by everyone (glaze alone captures them); unknown types are kept for round-tripping by Godot and Flax, dropped by Unreal, errors in O3DE and Bevy.
- **Scripts:** one registry keyed by a language-neutral string, fed by a script-side generator: Unreal's Blueprint classes are real classes with property GUIDs, reinstanced on compile; Godot's scripts contribute to the same property chain, GDScript's `@export` fills the same hints, C# property lists come from Roslyn source generators, GDExtension registers into the same ClassDB; Flax appends a `ScriptingType` per C# class so files always say `Namespace.Type`. O3DE does the opposite for Lua: a self-describing typed-variant list rebuilt from the table on reload (Lumix and Hazel likewise). Reload survives when values are held by name, never by handle. Only RTTR has a pure run-time registry and even it needs a C++ entry per class.
- **C++26:** P2996 plus annotations (P3394) and the related papers were adopted in June 2025 and C++26 was technically complete in March 2026; token injection is not in. GCC 16 ships `-freflection`; upstream Clang has nothing; Bloomberg's branch is experimental; MSVC lists no reflection paper. It is consteval only, sees no comments and writes no file, so it cannot replace describe-api, but annotation-style ranges are the vocabulary to design editor metadata toward.
- **Against describe-api:** add kinds (string, list, map, optional, typed reference) rather than a registry; open the tagged union into a name-or-id-tagged slot for polymorphism; record a stable id or a rename table per type and field (O3DE's UUIDs and Blueprint GUIDs survive renames; Bevy's type paths and Godot's names do not); put a per-type version in the description, where CI already diffs it; decide whether unknown types are kept, for the level-editor tickets; doc comments are the generator's unique asset; a C# data asset type needs the reverse record written by a generator on the C# side. describe-api's committed offsets are unusual in the field (Flax stores size and thunks only; Unreal refuses to describe layout externally) and are safe only because of its standard-layout restriction. RTTR is effectively dead and refl-cpp dormant; Describe, magic_enum and glaze are active, the latter two with P2996 backends.

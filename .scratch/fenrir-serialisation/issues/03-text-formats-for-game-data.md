# Which text formats suit scene files and data assets, and what libraries read them?

Type: research
Status: resolved
Blocked by: none

## Question

Compare the text formats a development-time scene file and data asset could use, as a format and as C++ and C# libraries, in the areas that constrain the one format Fenrir picks:

- **Candidates:** JSON (and JSON5 or JSONC for comments), TOML, YAML (Unity's flavour, with its known pitfalls), Godot's `.tscn`/`.tres` INI-like format, KDL, S-expressions, and the case for a small custom grammar.
- **For hand editing and review:** comments, trailing commas, multi-line strings, readability of nested lists of structs (a tuning table), float round-tripping (shortest representation, infinities, NaN), stable key ordering for byte-identical rewrites, and how diffs and three-way merges behave on each.
- **For the data model:** how each writes a typed reference (a path or id plus a type), polymorphic values (a derived type in a base-typed field), sub-objects embedded in a file, and binary blobs (base64, sidecar files).
- **Libraries, C++:** nlohmann/json, simdjson, RapidJSON, Glaze, toml++, yaml-cpp, rapidyaml, kdl-cpp; licence, size, build cost as a pinned `PRIVATE` submodule (ADR-0010's pattern), error reporting with line and column, and writing with preserved ordering and formatting.
- **Libraries, C#:** System.Text.Json, Tomlyn, YamlDotNet; whether the same file reads identically from both languages matters, or only C++ reads files and C# sees the loaded data.
- **Prior art:** which format each engine above chose and what they have said about regretting it (Unity's YAML merges, Godot's move from XML to its own format, Bevy's RON and BSN).

Write findings to a Markdown file on the `research/text-formats` branch (`.scratch/fenrir-serialisation/research/text-formats.md`), citing each claim's source and pinning the versions read, and link it here.

## Answer

Findings: `.scratch/fenrir-serialisation/research/text-formats.md` on branch `research/text-formats` (commit `a0e8d23b`), read 2026-11-10 against JSON RFC 8259, JSON5 1.0.0, TOML 1.0.0 and 1.1.0, YAML 1.2.2, KDL 2.0.0, RFC 9804 (S-expressions), RON 0.12.3, nlohmann/json 3.12.0, simdjson 5.1.1, RapidJSON 1.1.0 and master, Glaze 9.1.0, toml++ 3.4.0 and master, yaml-cpp 0.9.0, rapidyaml 0.16.0, ckdl 1.0, System.Text.Json (.NET 8 to 10), Tomlyn 2.11.1, YamlDotNet 18.1.0, Godot 4.7 and master, Unity 6.6, Bevy 0.19 and 0.20, O3DE, Flax, Stride and Unreal 5.9. Spec, C++ library, C# library and prior-art tables, and a "What this means for ticket 12" section.

- **Candidates:** no surveyed format is hand-editable, mergeable and typed at once. JSON has readers everywhere but no comments, trailing commas, NaN or infinity, or type syntax; JSON5 is read by no surveyed C++ or C# library (JSONC, comments plus trailing commas, is: nlohmann, RapidJSON, Glaze, System.Text.Json). TOML nests poorly and split on 2025-12-24 (toml++ 3.4.0 reads 1.0; Tomlyn and Glaze read 1.1 only). YAML 1.2 carries types as tags, but Unity's dialect is a 1.1 subset with its own parser. KDL 2.0 is node-based with `(type)` annotations, but its only C++ path is ckdl's wrapper (no error locations, sorted properties); `kdl-cpp` does not exist. S-expressions have no numbers; RON has enums and struct names natively but no C++ or C# implementation. Godot, Unity and Bevy each own their grammar; Godot's costs about 137 KB of C++.
- **Hand editing and review:** every C++ library drops comments on rewrite (toml++ closed the request as "not planned"; yaml-cpp and rapidyaml have no comment node; nlohmann and Glaze skip them), and in C# all but Tomlyn do, so comments survive only in files the engine never rewrites. JSON's missing trailing comma makes every list append a two-line diff. Float writers differ (Grisu2 in nlohmann and RapidJSON, which also parses with up to 3 ULP error by default; Żmij in Glaze; Dragonbox in yaml-cpp; `to_chars` in rapidyaml with a "may truncate" default; shortest in .NET). NaN and infinity: nlohmann and Glaze silently write `null`, System.Text.Json writes a quoted string, TOML, YAML, KDL, JSON5 and RON carry them. No spec defines key order: nlohmann's default, toml++'s table and ckdl sort keys, Glaze uses declaration order, the rest keep insertion order, so a byte-identical rewrite needs an engine-owned ordering rule (declaration order from the API description) plus one float and one indentation rule. git merges lines either way; section-headed formats get readable hunk headers through `xfuncname`.
- **Data model:** typed references are native only in YAML (tags; Stride's `ref!! guid`), KDL (`(T)"path"`), Godot (`ExtResource("1_7bt6s")`, `uid://`) and RON; JSON needs a convention (Unity's `{fileID, guid, type}`, Flax's GUID plus `TypeName`, O3DE's `$type`; System.Text.Json wants `$type` first unless told otherwise); TOML has only a `type = "…"` key. Polymorphism splits the same way, and Unity cannot do it for inline classes. Sub-objects: Godot and Unity flatten to id-keyed sections or documents; Stride and Flax keep flat lists keyed by GUID with parent ids; O3DE nests with JSON-Patch overrides. Blobs: YAML 1.2 dropped `!!binary`; KDL reserves `base64`; Godot writes packed arrays inline and keeps big data in binary files; every engine uses sidecars for real payloads.
- **C++ libraries:** structured line-and-column errors only from toml++, yaml-cpp and rapidyaml; nlohmann gives a byte offset with line and column only in the message text, RapidJSON an offset, simdjson an error code, ckdl nothing. Licences all MIT except simdjson (Apache-2.0 or MIT) and RapidJSON (MIT plus a BSD part and an excludable "Good, not Evil" file). Header-only: nlohmann (1.9 MB single header), RapidJSON, Glaze, toml++ (547 KB); compiled: simdjson, yaml-cpp, rapidyaml (c4core vendored since 0.16.0), ckdl (tests on by default, no namespaced target). Glaze is out on today's toolchain (C++23, CMake 3.31, VS 2026) against the repo's C++20 and CMake 3.20. RapidJSON's last release is 2016, so a commit would be pinned. simdjson gained a writer only in 4.0.0 (2025-09). Tree-based readers (nlohmann, RapidJSON's DOM, toml++, yaml-cpp, rapidyaml) suit description-driven reading better than struct-mapping ones.
- **C# libraries:** System.Text.Json is in-box and MIT: JSONC yes, JSON5 no, line and byte position on errors, ordered `JsonObject`, `[JsonPolymorphic]` with `$type`, source generation for NativeAOT. Tomlyn 2.11.1 (BSD-2, TOML 1.1 only, lossless trivia tree). YamlDotNet 18.1.0 (MIT, tag mapping for polymorphism, comments dropped by default; its typed bools accept `yes`/`no`/`on`/`off`, as yaml-cpp's do, but the untyped paths differ). Since C# sees loaded data through the scripting pipeline, the C++ reader is the reader of record and a C# library matters only for standalone tools; if C# ever reads files directly, the YAML-bool, TOML 1.0-versus-1.1 and `$type`-ordering divergences become bugs. JSON or JSONC is the only format with an in-box .NET reader whose accepted input is a subset of every C++ reader's.
- **Prior art:** Unity: a YAML 1.1 subset, one document per object, file-local `fileID`s plus `.meta` GUIDs, `stripped` placeholders, flat prefab modification lists; ships `UnityYAMLMerge` (scenes, prefabs and meta only); staff call hand editing unsupported with unhelpful errors; DOTS bakes to binary. Godot: left XML in 2.0 (2016) as unfriendly to version control for a format "inspired by TOML"; 4.0 replaced integer ids with `1_7bt6s` pseudo-random ids to minimise merge conflicts while staying readable (not UUIDs), seeded from the path hash; `uid://` takes priority over paths; `.uid` sidecars in 4.4 because a central id database conflicted on every branch. Bevy: RON scenes keyed by full type paths; BSN replaces them for patch and inheritance semantics (a critique of the data model, not RON's syntax), with a hand-written parser to ship less code, and `.bsn` files are still unshipped at 0.20 (2026-10) with parser and writer PRs open. Unreal stays binary and attacks collaboration with one file per actor. O3DE: JSON prefabs with JSON-Patch overrides, `$type`, defaults omitted. Flax: a flat JSON object list. Stride: YAML with a tag per component. Our Machinery: the in-memory model is authoritative and the file must be human-readable and merge easily.
- **Tensions with the map's Notes:** "hand-editable" and "rewritten by tools" pull apart, since no C++ library preserves comments: the format decision needs a tool-owned versus human-owned file split, or comments stored as data. Typed and polymorphic references in JSON are a convention the engine owns on both sides. Byte-identical rewrites must come from the API description's ordering, not the library.

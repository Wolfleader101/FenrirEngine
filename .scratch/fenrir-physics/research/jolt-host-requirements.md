## 1. Threading: the `JobSystem` interface

**Jolt does not need its own threads.** `PhysicsSystem::Update` takes a `JobSystem *` and spawns all its work through it ([PhysicsSystem.h L156-L162](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/PhysicsSystem.h#L156-L162)). `JobSystem` is an abstract interface the host implements:

- To write your own, implement `GetMaxConcurrency`, `CreateJob`, `FreeJob` and `QueueJob`/`QueueJobs`; jobs are ref-counted, and if the host stores a job pointer it must `AddRef()` it and `Release()` it after running ([JobSystem.h L43-L50](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Core/JobSystem.h#L43-L50)). `QueueJob` is called only when a job's dependencies are satisfied: dependency tracking is internal to Jolt ([JobSystem.h L48](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Core/JobSystem.h#L48)).
- Barriers (`CreateBarrier`, `DestroyBarrier`, `WaitForJobs`) track completion. Jobs get added to a barrier *while it is being waited on*, so the graph cannot be built ahead of time. `WaitForJobs` may run barrier jobs on the waiting thread, but it should not run other jobs that touch physics structures (race/deadlock risk). If QueueJob hands work to the engine's own scheduler, `WaitForJobs` may also need to wait for those engine tasks ([JobSystem.h L52-L66](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Core/JobSystem.h#L52-L66)). Only one thread may wait on a barrier at a time ([JobSystem.h L165-L166](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Core/JobSystem.h#L165-L166)).
- **`JobSystemWithBarrier`** implements all the barrier logic, leaving only `GetMaxConcurrency`, `CreateJob`, `FreeJob`, `QueueJob(s)` to the host ([JobSystemWithBarrier.h L12-L23](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Core/JobSystemWithBarrier.h#L12-L23)). Its `Wait` executes the barrier's jobs on the calling thread while waiting ([JobSystemWithBarrier.cpp L105-L117](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Core/JobSystemWithBarrier.cpp#L105-L117)).
- **Intended usage is the host's scheduler.** `JobSystemThreadPool` (which starts its own threads) is "considered an example implementation"; integrators are expected to provide a `JobSystem` "built on top of whatever job system your project uses" ([JobSystemThreadPool.h L20-L25](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Core/JobSystemThreadPool.h#L20-L25); same advice in [HelloWorld.cpp L238-L241](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/HelloWorld/HelloWorld.cpp#L238-L241)). Its thread count excludes the calling thread, which also runs jobs while waiting ([JobSystemThreadPool.h L41-L45](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Core/JobSystemThreadPool.h#L41-L45)).
- Sizing constants for a physics job system: `cMaxPhysicsJobs = 2048`, `cMaxPhysicsBarriers = 8` ([PhysicsSettings.h L25-L28](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/PhysicsSettings.h#L25-L28)). The number of parallel jobs some stages create depends on `GetMaxConcurrency()` ([PhysicsSystem.cpp L240](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/PhysicsSystem.cpp#L240)).
- `Update` waits for its jobs before returning: "no jobs will be running when this function returns" ([PhysicsSystem.h L159](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/PhysicsSystem.h#L159)). So it is a blocking call on the caller's thread.

**Minimal single-threaded setup.** `JobSystemSingleThreaded` has no threads, runs each job as soon as it is queued, reports `GetMaxConcurrency() == 1` and uses a dummy barrier ([JobSystemSingleThreaded.h L12-L60](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Core/JobSystemSingleThreaded.h#L12-L60)). Construct it with `JobSystemSingleThreaded(cMaxPhysicsJobs)`. Everything else is as in HelloWorld: `TempAllocatorImpl`, the three layer interfaces and `PhysicsSystem::Init` ([HelloWorld.cpp L231-L278](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/HelloWorld/HelloWorld.cpp#L231-L278)).

**Fit with FenrirScheduler's `ThreadPool`** (as of `1e0700d`): it exposes only `Enqueue(f, args...) -> std::future` over a mutex/condvar queue, with no thread-count getter ([ThreadPool.hpp L19-L78](../../../packages/FenrirScheduler/include/FenrirScheduler/ThreadPool.hpp)). That is enough to back `QueueJob` (enqueue a lambda that runs the job and then releases it). `GetMaxConcurrency` would need the pool's thread count, which the pool currently does not expose.

## 2. Lifetimes: bodies, `BodyID`s, shapes

**Process-global setup, once, before anything else:** `RegisterDefaultAllocator()` (or custom allocation hooks), the `Trace` and `AssertFailed` hooks, `Factory::sInstance = new Factory()`, `RegisterTypes()`; teardown is `UnregisterTypes()` and deleting the factory ([HelloWorld.cpp L214-L229, L361-L366](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/HelloWorld/HelloWorld.cpp#L214-L229)). These are shared by every `PhysicsSystem` in the process: one RTTI factory, one default material, one `DebugRenderer::sInstance`, shared custom shapes/collision dispatch, shared allocator/Trace/AssertFailed ([Architecture.md L859-L867](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L859-L867)).

**`PhysicsSystem::Init` fixes capacities up front:** max bodies, body-mutex count, max body pairs, max contact constraints. It also takes the three layer interfaces, which Jolt holds by reference: they "need to stay alive during the lifetime of the PhysicsSystem" ([PhysicsSystem.h L51-L59](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/PhysicsSystem.h#L51-L59)). `CreateBody` returns null when out of bodies ([HelloWorld.cpp L243-L245, L310](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/HelloWorld/HelloWorld.cpp#L243-L245)). If the pair/contact buffers overflow, contacts are dropped and `Update` reports it through `EPhysicsUpdateError` flags ([EPhysicsUpdateError.h L10-L16](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/EPhysicsUpdateError.h#L10-L16)).

**Body life cycle:** `CreateBody` → `AddBody` → `RemoveBody` → `DestroyBody`. You can't `new`/`delete` a `Body`, and `DestroyBody` does not remove the body from the system for you ([Architecture.md L28-L33](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L28-L33); [BodyInterface.h L87-L92](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/Body/BodyInterface.h#L87-L92)). A removed body keeps its state and can be re-added; `AddBody`/`RemoveBody` cycles are the supported way to take a body out temporarily ([Architecture.md L44](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L44); [HelloWorld.cpp L351-L355](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/HelloWorld/HelloWorld.cpp#L351-L355)). `CreateAndAddBody` combines the two steps ([BodyInterface.h L107-L108](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/Body/BodyInterface.h#L107-L108)). Removing a body does not wake its neighbours ([Architecture.md L421](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L421)).

**What is expensive:**
- *Adding bodies one at a time* makes the broad phase inefficient, and in extreme cases it runs out of nodes (`std::abort`). Use `AddBodiesPrepare` (callable from a background thread) / `AddBodiesFinalize` / `AddBodiesAbort` and `RemoveBodies`, or call `OptimizeBroadPhase` afterwards ([Architecture.md L35-L42](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L35-L42); [BodyInterface.h L95-L136](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/Body/BodyInterface.h#L95-L136)). `OptimizeBroadPhase` is expensive and should not run every frame ([PhysicsSystem.h L142-L148](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/PhysicsSystem.h#L142-L148)).
- *Cooking shapes.* Spheres and boxes can be constructed directly; other shapes are built from a `ShapeSettings` via `Create()`, which returns a `Result`. The settings cache the created shape: calling `Create` again returns the same shape unless you call `ClearCachedResult` ([Architecture.md L223-L248](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L223-L248)).

**`BodyID`:** a 32-bit value holding a 23-bit index (`cMaxBodyIndex = 0x7fffff`) and an 8-bit sequence number ([BodyID.h L17-L41](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/Body/BodyID.h#L17-L41)). IDs are reused only after many add/remove cycles. A lock on a stale ID fails ([Architecture.md L147](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L147)). A destroyed body's ID is no longer valid ([HelloWorld.cpp L354](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/HelloWorld/HelloWorld.cpp#L354)). `CreateBodyWithID` exists so that IDs can be reproduced exactly, e.g. for replicated or restored simulations ([BodyInterface.h L49-L51](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/Body/BodyInterface.h#L49-L51)). Each body carries a `uint64` user-data value, settable at creation through `BodyCreationSettings::mUserData` ([BodyCreationSettings.h L90](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/Body/BodyCreationSettings.h#L90); [Body.h L333-L334](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/Body/Body.h#L333-L334)), and activation callbacks pass it ([BodyActivationListener.h L21](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/Body/BodyActivationListener.h#L21)).

**Shapes are ref-counted (`RefTarget`)** and so are `ShapeSettings`, `Constraint`, `PhysicsMaterial`, `GroupFilter` and others. They start at refcount 0. Passing one to another object (a shape to a body) makes that object take a reference. `Ref<>`/`RefConst<>` manage the count. `Body` is the exception: it is destroyed only through `BodyInterface::DestroyBody` ([Architecture.md L873-L906](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L873-L906)). Stack-allocated ref-counted objects must call `SetEmbedded()` ([HelloWorld.cpp L300](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/HelloWorld/HelloWorld.cpp#L300)). Shapes can be shared between bodies ([Architecture.md L229](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L229)), and even between `PhysicsSystem`s, the only objects that can be ([Architecture.md L855-L856](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L855-L856)). A body's shape can be replaced with `BodyInterface::SetShape` (optionally recomputing mass) ([BodyInterface.h L164-L169](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/Body/BodyInterface.h#L164-L169)). A static body has no `MotionProperties` unless created with `mAllowDynamicOrKinematic` ([Architecture.md L22](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L22)).

**Sub-shape IDs** (32-bit paths into compound or mesh shapes) are invalidated when a shape's structure changes ([Architecture.md L191-L211](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L191-L211)).

## 3. Locking and access

- `PhysicsSystem` exposes a **locking** `BodyInterface` (`GetBodyInterface`) and a **non-locking** one (`GetBodyInterfaceNoLock`, "use with great care"). The same split exists for `BodyLockInterface` and `NarrowPhaseQuery` ([PhysicsSystem.h L114-L125, L197-L201](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/PhysicsSystem.h#L114-L125)). The locking variant uses a hashed, fixed-size mutex array (`MutexArray`). Multi-body access must use `BodyLockMultiRead`/`BodyLockMultiWrite` to avoid deadlock ([Architecture.md L126-L151](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L126-L151)).
- Single-threaded hosts may use `Body *` and the non-locking interface ([Architecture.md L153-L155](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L153-L155)).
- **During `PhysicsSystem::Update` you cannot read or write bodies or constraints:** all body and constraint mutexes are locked as Update starts ([Architecture.md L159](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L159); [PhysicsSystem.cpp L234-L236](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/PhysicsSystem.cpp#L234-L236)). No bodies can be added or removed during the step ([Architecture.md L589](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L589)).
- **Inside contact callbacks**, the locking interfaces deadlock. Use the `NoLock` variants, only read bodies, and do not change physics state ([ContactListener.h L69-L72](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/Collision/ContactListener.h#L69-L72)). Activation callbacks are read-only too ([Architecture.md L161](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L161)).
- **`PhysicsStepListener::OnStep`** runs before every collision step with all mutexes held. It may read and write bodies and constraints but not add or remove them. Listeners can run in parallel, so the listener must avoid races. It is not called when there are no active bodies or when dt is 0 ([PhysicsStepListener.h L21-L34](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/PhysicsStepListener.h#L21-L34)).
- `SetContactListener` must not be called during `Update` ([PhysicsSystem.h L65-L67](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/PhysicsSystem.h#L65-L67)).
- Some setters behave differently on `Body` and `BodyInterface`: `Body::SetLinearVelocity` does not wake a sleeping body, while `BodyInterface::SetLinearVelocity` does ([Architecture.md L421](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L421); [BodyInterface.h L202-L206](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/Body/BodyInterface.h#L202-L206)).
- Queries (`NarrowPhaseQuery`) can run concurrently with body changes. They lock each body briefly to snapshot a ref-counted `TransformedShape` ([Architecture.md L595-L599](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L595-L599); [README.md L25-L27](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/README.md?plain=1#L25-L27)).

## 4. Layers and the filters the host implements

- Each body is in exactly one **`ObjectLayer`** (16-bit by default, 32-bit with `JPH_OBJECT_LAYER_BITS`/`OBJECT_LAYER_BITS`). The host defines what a layer means ([Architecture.md L605](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L605)).
- `PhysicsSystem::Init` takes three interfaces ([Architecture.md L607-L610](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L607-L610)):
  - `BroadPhaseLayerInterface`: maps ObjectLayer to `BroadPhaseLayer` (each broad-phase layer is its own quad tree) and reports the number of broad-phase layers.
  - `ObjectVsBroadPhaseLayerFilter::ShouldCollide(ObjectLayer, BroadPhaseLayer)`.
  - `ObjectLayerPairFilter::ShouldCollide(ObjectLayer, ObjectLayer)`, which must be symmetric ([Architecture.md L624](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L624)).
  Reference implementations: [HelloWorld.cpp L67-L165](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/HelloWorld/HelloWorld.cpp#L67-L165).
- Keep broad-phase layers few. The usual minimum is two, static and moving, because a tree full of statics is expensive to update ([Architecture.md L591](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L591); [HelloWorld.cpp L97-L101](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/HelloWorld/HelloWorld.cpp#L97-L101)).
- Ready-made implementations: `ObjectLayerPairFilterTable` / `ObjectVsBroadPhaseLayerFilterTable` / `BroadPhaseLayerInterfaceTable` (a table), and the `...Mask` family (group/mask bits split from one ObjectLayer, Bullet-style) ([Architecture.md L642-L644](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L642-L644)).
- The full filter order: broad-phase layer → object layer (`ObjectLayerPairFilter` for simulation, `ObjectLayerFilter` for queries) → `GroupFilter` (simulation) / `BodyFilter` (queries) → `ShapeFilter`/`SimShapeFilter` → `ContactListener::OnContactValidate` (the most expensive place to reject) ([Architecture.md L646-L657](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L646-L657)).
- A body's layer can change at runtime with `BodyInterface::SetObjectLayer` ([Architecture.md L413](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L413)).

## 5. Callbacks: `ContactListener`, `BodyActivationListener`

**Registration:** one `ContactListener` and one `BodyActivationListener` per `PhysicsSystem`, both optional ([ContactListener.h L64-L67](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/Collision/ContactListener.h#L64-L67); [HelloWorld.cpp L280-L290](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/HelloWorld/HelloWorld.cpp#L280-L290)).

**Thread:** both run inside `PhysicsSystem::Update`, from job threads, several at once ([Architecture.md L160-L161](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L160-L161); [BodyActivationListener.h L19-L25](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/Body/BodyActivationListener.h#L19-L25)). Callbacks for one body pair are serialized ([ContactListener.h L74](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/Collision/ContactListener.h#L74)). The order across pairs is **not deterministic** ([Architecture.md L806](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L806)). Jolt's own SensorTest collects contacts under a mutex and keeps the list sorted "for determinism (contacts can be added from multiple threads)" ([SensorTest.cpp L172-L189](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Samples/Tests/General/SensorTest.cpp#L172-L189)).

**What a callback may do:** read bodies through the NoLock interfaces only, and make no physics-state changes (section 3). In `OnContactAdded`/`OnContactPersisted` the callback may modify the `ContactSettings` it is given: combined friction and restitution, inverse mass/inertia scales, `mIsSensor`, and surface velocities ([ContactListener.h L38-L51](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/Collision/ContactListener.h#L38-L51)). Activation callbacks may not write, activate or deactivate any body ([BodyActivationListener.h L20, L24](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/Body/BodyActivationListener.h#L20)).

**Contact lifecycle** ([ContactListener.h L84-L140](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/Collision/ContactListener.h#L84-L140)):
- `OnContactValidate`: runs before a contact is created and can reject it. Body 1's motion type is ≥ body 2's. It may not be called again while a contact persists.
- `OnContactAdded`: a new contact. Bodies are sorted so that `body1.ID < body2.ID`. It fires before the solver runs, so the impulse is unknown (velocities are pre-solve; see `EstimateCollisionResponse`).
- `OnContactPersisted`: the contact existed in the previous update too. A changed compound shape can reuse sub-shape IDs, so this event may refer to a different child shape.
- `OnContactRemoved(SubShapeIDPair)`: the bodies **cannot be accessed**. They are locked, may be mid-modification, or may already be removed or destroyed. Cache what you need at Added/Persisted time, or just record the removal and process it after `Update`. `PhysicsSystem::WereBodiesInContact` reports whether this was the pair's last contact.
- Granularity: for `Discrete` bodies, at most one Added/Persisted/Removed per body/sub-shape pair per collision step. `LinearCast` (CCD) bodies can get Added followed by Persisted in the same step ([ContactListener.h L75-L77](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/Collision/ContactListener.h#L75-L77)).
- **Sleeping ends contacts:** only active bodies report contacts. When a body sleeps, its contacts get `OnContactRemoved` ([ContactListener.h L104-L105](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/Collision/ContactListener.h#L104-L105)). Removed callbacks fire in the "Finalize Contact Cache" stage of the step ([Architecture.md L1007-L1012](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L1007-L1012)), and even in the early-out path when no bodies are active, as long as dt > 0 ([PhysicsSystem.cpp L191-L206](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/PhysicsSystem.cpp#L191-L206)). A body removed from the world produces `OnContactRemoved` in the next `Update` ([ContactListener.h L130](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/Collision/ContactListener.h#L130)).

**Sensors** ([Architecture.md L398-L413](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L398-L413)):
- A sensor is an ordinary body with `mIsSensor` (or `Body::SetIsSensor`). It reports through the same `ContactListener`, and its penetrations are not resolved.
- A **static** sensor is the cheapest, but it sees only active bodies: when the other body sleeps, the contact is lost (so you get Removed). A kinematic or dynamic sensor that is kept active also sees sleeping bodies, at a higher cost.
- Sensors detect static bodies only with `mCollideKinematicVsNonDynamic`. Sensors support only `Discrete` motion quality.
- To disable a sensor, remove it or move it to a non-colliding layer.
- `CharacterVirtual` contacts with sensors go through `CharacterContactListener`, not `ContactListener` ([Architecture.md L719-L723](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L719-L723)).

## 6. Stepping: `PhysicsSystem::Update`

- Signature: `EPhysicsUpdateError Update(float inDeltaTime, int inCollisionSteps, TempAllocator *, JobSystem *)`. The step of `inDeltaTime` is split into `inCollisionSteps` rounds of collision detection followed by integration ([PhysicsSystem.h L156-L162](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/PhysicsSystem.h#L156-L162)). It asserts `inCollisionSteps > 0` and `inDeltaTime >= 0` ([PhysicsSystem.cpp L182-L183](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/PhysicsSystem.cpp#L182-L183)).
- Guidance: stable at 60 Hz with 1 collision step ([Architecture.md L733-L740](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L733-L740)). For larger steps, use 1 collision step per 1/60 s, rounded up ([HelloWorld.cpp L344-L348](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/HelloWorld/HelloWorld.cpp#L344-L348)).
- Warm starting scales with the ratio of the current to the previous step dt ([PhysicsSystem.cpp L213-L216](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/PhysicsSystem.cpp#L213-L216)), so a constant fixed dt keeps that ratio at 1.
- **`TempAllocator`**: a stack allocator for per-step scratch data. Every allocation is freed by the end of `Update` ([PhysicsSystem.h L160-L161](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/PhysicsSystem.h#L160-L161); [TempAllocator.h L11-L14](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Core/TempAllocator.h#L11-L14)). The options are `TempAllocatorImpl` (one preallocated block; HelloWorld uses 10 MB as "a typical value"), `TempAllocatorMalloc`, and `TempAllocatorImplWithMallocFallback` ([HelloWorld.cpp L231-L236](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/HelloWorld/HelloWorld.cpp#L231-L236); [TempAllocator.h L33, L133, L167](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Core/TempAllocator.h#L33)).
- The step pipeline, stage by stage, is documented in [Architecture.md L910-L1036](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L910-L1036): broad-phase update, step listeners, gravity, islands, find collisions, velocity solve, integrate, CCD, contact cache finalize, position solve.
- The broad phase is rebuilt incrementally inside `Update`, so `OptimizeBroadPhase` is only for after bulk loading ([PhysicsSystem.h L142-L148](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/PhysicsSystem.h#L142-L148)).
- `Character` (the rigid-body character) needs `PostSimulation()` after every `Update`. `CharacterVirtual` is not in the world at all and is stepped by its own `Update` ([Architecture.md L705-L709](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L705-L709)).

## 7. Determinism

- **Guarantee (same binary):** the simulation is deterministic provided that (a) state-modifying APIs are called in exactly the same order, so that the state at the start of each step is identical, and (b) the same binary code runs. The CPU vendor does not matter ([Architecture.md L785-L790](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L785-L790)).
- **The thread count does not matter.** Jolt's determinism unit tests step the same scene with 0 worker threads and with 15, and require identical body state after every step ([PhysicsDeterminismTests.cpp L43-L109](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/UnitTests/Physics/PhysicsDeterminismTests.cpp#L43-L109)). Randomly adding and removing bodies *from different threads* breaks determinism because it breaks the call-order rule ([Architecture.md L836](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L836)).
- **Allowed liberties:** the binary state at `Update` is what matters. Adding body A then B is the same as B then A **if their `BodyID`s are the same**. Constraint add order may vary only if every constraint has a unique `mConstraintPriority` ([Architecture.md L844-L851](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L844-L851)). `BodyID`s depend on creation order; `CreateBodyWithID` pins them ([Architecture.md L842](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L842)).
- **Not deterministic in order:** listener callbacks (all four listener types), `GetActiveBodies` order, `NarrowPhaseQuery` result order, and `BroadPhaseQuery` results themselves (bounding boxes widen until maintenance). Sort or re-check these on the host side ([Architecture.md L804-L807](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L804-L807)).
- **`CROSS_PLATFORM_DETERMINISTIC` / `JPH_CROSS_PLATFORM_DETERMINISTIC`** is only for determinism across compiler, configuration, OS and architecture. It costs about 8% ([Architecture.md L792-L798](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L792-L798)). It disables FMA (`JPH_USE_FMADD` ignored) ([Build/README.md L26](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Build/README.md?plain=1#L26); [Jolt.cmake L963](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Jolt.cmake#L963)) and switches MSVC from `/fp:fast` to `/fp:precise` ([Build/CMakeLists.txt L205-L210](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Build/CMakeLists.txt#L205-L210)). The host's own code that feeds physics would also need precise FP, no FP contraction, consistent FPU state across threads, and Jolt's `Sin`/`Cos`, `QuickSort` and `Hash` in place of the std versions ([Architecture.md L826-L834](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L826-L834)). It is not needed for same-machine/same-build determinism.
- **Debugging and rollback:** `JPH_ENABLE_DETERMINISM_LOG` ([Build/README.md L34](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Build/README.md?plain=1#L34)). `SaveState`/`RestoreState` (with `StateRecorderFilter`) record only the state the step modifies. Host-side changes such as friction and add/remove must be replayed by the host ([Architecture.md L838-L842](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L838-L842); [PhysicsSystem.h L164-L174](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/PhysicsSystem.h#L164-L174)).

## 8. Precision: `JPH_DOUBLE_PRECISION`

- The default is float. Positions are accurate within about 5 km of the origin ([Architecture.md L750-L752](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L750-L752)).
- With `JPH_DOUBLE_PRECISION` (CMake `DOUBLE_PRECISION`), `Real`/`RVec3`/`RMat44` become `double`/`DVec3`/`DMat44`; otherwise they alias `float`/`Vec3`/`Mat44` ([Real.h L12-L36](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Math/Real.h#L12-L36)). **API boundary changes:** positions and world transforms (`RVec3`, `RMat44`) become double. Velocities, rotations (`Quat`) and the broad phase stay float ([Architecture.md L754-L772](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L754-L772)). Collision queries take a **base offset** and return float results relative to it ([Architecture.md L756](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L756); e.g. `ContactManifold::mBaseOffset`, [ContactListener.h L29](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/Collision/ContactListener.h#L29)). Double mode costs about 5-10% ([Architecture.md L764](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L764)).
- The `_r` literal and the `RVec3` alias let host code compile either way ([HelloWorld.cpp L33-L34](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/HelloWorld/HelloWorld.cpp#L33-L34)).
- It is an ABI-affecting define. It feeds `JPH_VERSION_ID` feature bit 1 ([Core.h L13-L14](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Core/Core.h#L13-L14)), and it must match on every platform for cross-platform determinism ([Architecture.md L803](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L803)).
- Conventions: right-handed, Y-up, column-major. SI units, with dynamic objects 0.1-10 m and speeds 0-500 m/s ([Architecture.md L742-L748](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L742-L748)).

## 9. Debug rendering

- `JPH_DEBUG_RENDERER` is defined by default in Debug and Release but **not** in Distribution ([Architecture.md L871](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L871)). The CMake knobs are `DEBUG_RENDERER_IN_DEBUG_AND_RELEASE` (ON) and `DEBUG_RENDERER_IN_DISTRIBUTION` (OFF) ([Build/CMakeLists.txt L85-L89](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Build/CMakeLists.txt#L85-L89)). Jolt applies it as a `PUBLIC` compile definition through a generator expression over **Jolt's configuration names** (`Debug,Release,ReleaseASAN,ReleaseUBSAN,ReleaseTSAN`) ([Jolt.cmake L913-L918](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Jolt.cmake#L913-L918)). The profiler define is configured the same way ([Jolt.cmake L920-L930](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Jolt.cmake#L920-L930)).
- **Interface:** derive from `DebugRenderer` and implement `DrawLine`, `DrawTriangle`, `CreateTriangleBatch` (two overloads), `DrawGeometry` and `DrawText3D`; call `Initialize()` from your constructor ([DebugRenderer.h L29-L46, L59, L104, L252-L285](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Renderer/DebugRenderer.h#L29-L46)). The instance registers itself as `DebugRenderer::sInstance`, one per process ([DebugRenderer.h L179](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Renderer/DebugRenderer.h#L179); [Architecture.md L863](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L863)). `DebugRendererSimple` reduces the work to `DrawLine`, `DrawTriangle` and `DrawText3D`, plus `SetCameraPos` for LOD ([DebugRendererSimple.h L15-L46](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Renderer/DebugRendererSimple.h#L15-L46)).
- **Pull-based:** nothing draws unless the host calls `PhysicsSystem::DrawBodies(settings, renderer)`, `DrawConstraints` and so on, and these take any `DebugRenderer *` ([PhysicsSystem.h L180-L190](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/PhysicsSystem.h#L180-L190)). `DebugRendererRecorder` writes `.jor` recordings for JoltViewer ([README.md L149](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/README.md?plain=1#L149)).
- **Cost when off:** the header `#error`s if it is included without `JPH_DEBUG_RENDERER` ([DebugRenderer.h L7-L9](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Renderer/DebugRenderer.h#L7-L9)), so code that uses it must be conditionally compiled. Jolt's docs don't quantify the runtime cost of leaving it on. They describe the Distribution build as "turns off all debugging support" and Release as able to "draw the world" ([Build/README.md L7-L13](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Build/README.md?plain=1#L7-L13)).
- **ABI hazard:** a mismatch in `JPH_DEBUG_RENDERER` between the Jolt library and the code including its headers causes unresolved virtuals at link time. `RegisterTypes()` checks the other ABI defines and aborts on mismatch ([Build/README.md L230-L240](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Build/README.md?plain=1#L230-L240)). The defines it checks are in `JPH_VERSION_ID`: double precision, cross-platform determinism, FP exceptions, profiler, external profiler, debug renderer, temp/custom allocator, 32-bit object layers, asserts, ObjectStream ([Core.h L13-L71](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Core/Core.h#L13-L71); [RegisterTypes.h L12-L24](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/RegisterTypes.h#L12-L24)).

## 11. Scale

- Shapes have no intrinsic scale. Scale comes from wrapping in a `ScaledShape`, which takes a local-space, possibly non-uniform, possibly negative (inside-out) scale ([Architecture.md L360-L364](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L360-L364); [ScaledShape.h L36](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/Collision/Shape/ScaledShape.h#L36)).
- **Validity per shape** (`Shape::IsValidScale`): Sphere and Capsule uniform only; TaperedCapsule uniform (the sign of Y may flip it); Box any; Cylinder uniform in XZ with Y free; Triangle any if its convex radius is 0, else uniform; RotatedTranslated and Compound must not cause shear in their children. Zero scale is never valid ([Shape.h L426-L438](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/Collision/Shape/Shape.h#L426-L438)). Rotating then scaling non-uniformly would shear, which is unsupported ([Architecture.md L187](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L187)).
- **Safe path:** `Shape::MakeScaleValid` returns the closest valid scale ([Shape.h L440-L445](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/Collision/Shape/Shape.h#L440-L445)). `Shape::ScaleShape` builds a valid scaled shape, pushing scale into compound children rather than shearing, and scales relative to the shape's origin. Most other APIs scale about the centre of mass ([Architecture.md L368-L378](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L368-L378); [Shape.h L342-L344](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Jolt/Physics/Collision/Shape/Shape.h#L342-L344)).
- **Changing scale at runtime:** there is no `ScaledShape::SetScale`, for thread safety with concurrent queries. Build a new shape and swap it in (`SetShape`), with care about creating impossible overlaps ([Architecture.md L375-L376](https://github.com/jrouwe/JoltPhysics/blob/v5.6.0/Docs/Architecture.md?plain=1#L375-L376)).

## Implications for FenrirPhysics

Facts the seam, ECS, stepping and events decisions must respect. These are constraints only; the choices are left to the decision tickets.

1. **Jolt types never need to cross the seam to get threads.** `JobSystem` is an abstract interface that FenrirPhysics can implement privately over FenrirScheduler's `ThreadPool` (QueueJob → `Enqueue`; barriers via `JobSystemWithBarrier`). `JobSystemSingleThreaded` is a zero-thread fallback. `GetMaxConcurrency` needs a thread count that `ThreadPool` does not currently expose. `Update` blocks the calling thread until all its jobs finish.
2. **Determinism on one machine and build holds regardless of thread count.** It does depend on FenrirPhysics issuing every create/add/remove/modify call in a reproducible order, and on `BodyID`s being reproducible (creation order, or `CreateBodyWithID`). Iteration order over the ECS when syncing to Jolt is therefore part of the determinism contract. `CROSS_PLATFORM_DETERMINISTIC` is not needed for the stated goal.
3. **Contact and activation callbacks arrive on job threads, mid-step, in non-deterministic order, with bodies locked.** They may not touch the ECS registry unsafely, change physics state, or (for Removed) read the bodies at all. Events reach gameplay deterministically only if they are buffered and sorted, then dispatched after `Update`. `OnContactRemoved` carries only `BodyID` and sub-shape IDs, so anything else (entity, layer) must be cached at Added time or looked up from a host-side map. The `uint64` body user data is available for an entity handle.
4. **Sleep ends contacts.** A sleeping body's contacts get Removed, and a static sensor loses an overlapping body when that body sleeps. Trigger "stay" semantics built on Jolt events must account for this, or sensors must be kinematic/dynamic and kept active.
5. **No body reads or writes are possible during `Update`.** ECS→physics writes (kinematic targets, forces, teleports) happen before the step, and physics→ECS reads (poses) after it. Jolt reports positions in world space, while `Transform` is parent-relative.
6. **Add/remove cost is asymmetric.** One-at-a-time adds degrade the broad phase. Batch APIs (`AddBodiesPrepare/Finalize`, `RemoveBodies`) and remove/re-add (state preserved) are the cheap paths. Shapes other than primitives are cooked once and shared by `Ref`. Capacities (bodies, pairs, contacts) are fixed at `Init`, and overflow shows up as `EPhysicsUpdateError` flags.
7. **Process-global state:** the allocator, Trace/AssertFailed (routable to FenrirLogger), the Factory, `RegisterTypes` and `DebugRenderer::sInstance` are per process, not per physics world. More than one physics world can exist, but they share these and may share only shapes.
8. **Layer filters are host objects that Jolt holds by reference for the world's lifetime.** The public layer vocabulary must map onto ObjectLayer (16 or 32 bits) plus a few broad-phase layers, with at least static and moving.
9. **Fixed step:** `Update(dt, collisionSteps, …)` wants a constant dt for warm starting. About 60 Hz with 1 collision step is the documented sweet spot; for larger dt, use 1 collision step per 1/60 s. The Tick accumulator's `tickRate` feeds `dt` directly.
10. **Scale is not a free transform component.** Non-uniform scale is valid only for some shapes, can't shear rotated compound children, and changing it means building a new shape and calling `SetShape`. `Shape::MakeScaleValid` / `ScaleShape` provide the clamping.
11. **Precision stays float** (matching the map). `RVec3` is then `Vec3`, but the seam must not expose `Real`/`RVec3`, so that a double build or another backend stays possible. Query results come relative to a base offset in double mode.
12. **Debug rendering is pull-based and compile-time gated.** The `DebugRenderer` subclass and `DrawBodies` calls must sit behind `#ifdef JPH_DEBUG_RENDERER` in private code. Plain debug-data output can collect lines and triangles from a private `DebugRendererSimple`. The define is keyed to Jolt's configuration names, not CMake's `RelWithDebInfo`/`MinSizeRel`.
13. **Build integration constraints:** use `add_subdirectory(<jolt>/Build)`. Jolt is C++17 in its own scope, without RTTI or exceptions, and defaults to the static MSVC runtime and LTO, both of which must match the host. The 5.6.0 GPU compute backends (DX12/VK/MTL/CPU) default ON and pull in Vulkan/dxc. Jolt's `-Werror`/`/WX` meets the engine's directory-wide `-Weverything` / `/W4`. ABI-affecting defines are verified at `RegisterTypes()`. Linking Jolt PRIVATE keeps its PUBLIC compile definitions and include path out of FenrirPhysics's consumers. Licence is MIT.

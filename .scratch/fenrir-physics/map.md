# FenrirPhysics

Label: wayfinder:map

## Destination

A set of specs, one feature directory each (`.scratch/fenrir-physics-<name>/spec.md`, so each spec's tickets sit beside it), each ready for `/to-tickets`, plus ADRs for the hard-to-reverse calls (where the backend seam goes, which side owns body state). The first is the **foundation spec**: the backend seam over Jolt, rigid bodies and shapes, collision layers, stepping, contact and trigger events, queries, debug rendering data, the physics scripting extension, and a physics demo scene in the DemoApp. Then one spec per feature family (constraints and joints, character controller, vehicles, ragdolls, soft bodies), each building on the foundation. The foundation spec is ticketable as soon as its own decisions close, without waiting on the feature families. **Foundation spec: written, `.scratch/fenrir-physics-foundation/spec.md`.**

**Joints spec: written and built**, `.scratch/fenrir-physics-joints/spec.md` (from tickets 20–29; its 14 tickets landed as PRs #14–#27). It covers joints between two rigid bodies or a body and the world, with limits, motors, springs, breaking, and connected bodies not colliding, in C++ and in C# through the physics scripting extension. It includes two DemoApp joints scenes, one built in C++ and one built in C#, each switched to like the F3 "Physics (C#)" scene. It adds an ADR only where a call is hard to reverse. The joint kinds must be ones the ragdoll spec can build on. Ragdoll skeletons and pose driving, vehicles, character bodies and soft bodies are not part of it; each gets its own spec.

**Character spec: written and built**, `.scratch/fenrir-physics-character/spec.md` (from tickets 30–39; its 15 tickets landed as PRs #28–#42), in the foundation spec's format. It covers a character body moved by game code with collide-and-slide: walking slopes up to a limit, stepping up stairs and sticking to the floor, a ground state (on ground, steep slope, in air, and what the ground is), gravity and jumping as velocity game code sets, riding moving and kinematic platforms, pushing dynamic bodies and contact events, changing shape with a room-to-stand check, and the motion-test and sweep queries the foundation deferred. It is in C++ and in C# through the physics scripting extension, with two DemoApp scenes on F5 (one built in C++, one in C#) through `DemoScenes`, and an ADR only where a call is hard to reverse. Not part of it: input mapping, the camera beyond the demo's own follow cameras, root motion, AI navigation and pathfinding, and network prediction. ADR-0014 is its one ADR.

**Now charting: the vehicles spec**, `.scratch/fenrir-physics-vehicles/spec.md` (tickets 40–48), in the foundation spec's format. It covers vehicles built on a dynamic rigid body: wheeled cars, motorcycles (leaning) and tracked vehicles, driven by input game code sets; the full drivetrain (engine, gearbox, differentials, anti-roll bars, suspension, tyres) as plain data with defaults that drive out of the box; per-wheel read-back and wheel poses written to wheel entities for drawing; tyre grip from the ground's `PhysicsMaterial`; trailers joined by the existing joints; and a vehicle debug-line category. Whether a character getting in and out is part of it is a ticket's call. It is in C++ and in C# through the physics scripting extension, with two DemoApp scenes on F6 (one built in C++, one only from C#) through `DemoScenes`, and an ADR only where a call is hard to reverse. Not part of it: input mapping, vehicle audio, AI driving, damage and destruction, and network prediction.

## Notes

- Vocabulary: **FenrirPhysics**, **physics backend**, **physics world** (see `GLOSSARY.md`, "FenrirEngine physics"). In this map, *component*, *system*, *event* and *entity* carry their ECS meanings from the glossary.
- **The backend is hidden at compile level.** No public FenrirPhysics header names or includes Jolt; Jolt is a private link dependency. Replacing it (Rapier, Box3d, an in-house engine) must not change FenrirPhysics's public interface or recompile its callers. This goes further than ADR-0008, whose EnTT header leak is a known smell, not a precedent.
- **Packages stay independent.** FenrirPhysics depends only on the core (App, Scheduler, Time, ECS, Scene, Math, Logger). Its C# support is a scripting extension (ADR-0009) that lives in FenrirPhysics and is built only when scripting is enabled. Debug rendering data is plain data that physics produces; no renderer depends on physics, and physics depends on no renderer.
- **Determinism:** the same inputs give the same simulation on the same machine and build.
- **Conventions:** meters, Y-up, right-handed (matching glm and the DemoApp camera); single-precision floats, like the rest of the engine.
- **Existing hooks:** `App::Run` runs `SchedulePriority::Tick` in a fixed-step accumulator loop (`Time::tickRate`), built for systems like physics. `Transform` is local to its parent through `Relationship` (`FenrirECS/Entity.hpp`); the physics backend simulates in world space.
- Skills: grilling tickets call `grilling` and `domain-modeling`; seam and module-shape questions also use `codebase-design`. Research tickets call `research` and put their findings on a `research/<name>` branch.
- Plan, don't do: tickets produce decisions, not code (the spike in "Spike: a box dropping onto a plane through the proposed seam" is throwaway).

## Decisions so far

<!-- one line per resolved ticket: [title](issues/NN-slug.md): gist -->

- [What does Jolt require of a host engine?](issues/01-what-jolt-requires-of-a-host.md): Jolt v5.6.0 can run on our `ThreadPool`; bodies are locked during a step; listeners run on job threads unordered and must be buffered; same-binary determinism holds given ordered API calls; much is process-global; several build defaults must be overridden.
- [How do other engines hide their physics backend?](issues/02-how-other-engines-hide-their-backend.md): seams are runtime interfaces (Godot, O3DE) or build-time typedefs (Unreal); all own opaque handles, simulate in world space with an adapter to the local hierarchy, and buffer contacts for one-thread delivery after the step; the usual leaks are backend tuning settings, documented behaviour differences, native pointers, and threading shaped by the backend.
- [Where does the backend seam go?](issues/03-where-the-backend-seam-goes.md): ADR-0010. Build-time seam: a private backend class with its only implementation in `src/Backend/Jolt/`; entities and components are the public identity; no tuning settings or escape hatch; tests against real Jolt; `Physics::Install` owns the backend's process-wide state.
- [How is physics modelled in the ECS?](issues/04-physics-in-the-ecs.md): ADR-0011. One `RigidBody` with a motion type; one `Collider` per entity holding a `CollisionShape` tagged union by value, compounds through child entities; optional `PhysicsMaterial`, `CollisionFilter`, `Trigger`; hull and mesh data cooked from caller-supplied vertices behind a FenrirPhysics handle; the ECS owns static and kinematic bodies, physics owns dynamic ones; adds and removes through new FenrirECS notifications, edits found by diffing each tick.
- [What is the physics world's lifecycle?](issues/06-physics-world-lifecycle.md): one world per scene, a scene resource (a new neutral per-scene slot in FenrirScene), paused while inactive, destroyed with its scene; reached by `PhysicsWorld::Of(scene)`; `PhysicsConfig` gives defaults, gravity is per world, capacities fixed at creation; FenrirApp fixes for stable scene addresses and `DestroyScene` are foundation prerequisites.
- [How do collision layers and filtering work?](issues/07-collision-layers-and-filtering.md): Godot-style 32-bit layer and mask on `CollisionFilter`, symmetric rule; the filter belongs to the body, triggers carry their own; layers optionally named in `PhysicsConfig`; private mapping to Jolt object layers; collision groups left to the feature families.
- [How do contact and trigger events reach game code?](issues/08-contact-and-trigger-events.md): engine events `ContactBegin`/`ContactEnd` (opt-in with a `ContactEvents` tag) and `TriggerEnter`/`TriggerExit`, no stay events; plain-data payloads naming body and collider entities; sleep hidden; sorted and sent after each step; reading each event once handed to the engine ("How does a system read each event exactly once?").
- [How do other engines deliver events to their systems?](issues/17-how-engines-deliver-events.md): FenrirApp's readers see events twice per frame, zero-or-many times in `Tick`, and race under parallel systems; Bevy gets exactly-once from per-reader cursors and gates its buffer swap on the fixed step; Unity and Godot deliver physics events once per step change; options listed without a choice.
- [What does the query API look like?](issues/09-physics-queries.md): raycast, shape cast (with a `CollisionShape` value), overlap and point overlap on `PhysicsWorld`, closest or all; plain-data hits naming body and collider entities; caller-supplied spans, no allocation; `QueryFilter` with mask, ignored body, triggers off by default; sees the last completed step; safe from parallel systems.
- [What does debug rendering data look like?](issues/10-debug-rendering-data.md): FenrirPhysics generates coloured `DebugLine`s itself (not Jolt's renderer) for colliders, contacts, velocities and bounds; off by default, enabled per world, regenerated after each step, read as a span; in every build; tests use new `IsSleeping`/`Bounds` queries; the DemoApp draws them with `GL_LINES`.
- [How does Jolt join the build?](issues/13-how-jolt-joins-the-build.md): submodule pinned to v5.6.0 under `packages/FenrirPhysics/libs/`, static, linked `PRIVATE`; dynamic MSVC runtime, no LTO, RTTI on, GPU backends, debug renderer, profiler and object stream off; engine warning flags kept off Jolt; Debug and Release supported; `FENRIR_ENABLE_PHYSICS` defaults ON; the spike verifies every preset.
- [What world transform does the engine define?](issues/14-engine-world-transform.md): FenrirECS free functions computed on demand (no cached component): `GetWorldMatrix` (exact) and `GetWorldTransform` (position, rotation, lossy scale), and `SetWorldTransform` for write-back; the DemoApp renderer and editor gizmo move onto them; C# gets them as built-in native functions.
- [How does FenrirECS report component adds and removes?](issues/15-fenrirecs-add-remove-notifications.md): `EntityList::Watch(ComponentType)` gives a `ComponentWatch` that records adds and removes in order, drained by a system; built on EnTT signals privately, with `ByteStorage` gaining the same; destruction and clearing report removals; several independent watches; no edits.
- [How does physics step?](issues/05-how-physics-steps.md): new `PreTick`/`PostTick` phases; physics runs in `PostTick` once per tick at `Time::tickRate` (drain watches, diff, forces, step, write back, events, debug lines); ticks per frame capped; physics systems sequential, Jolt jobs on the `ThreadPool` (single-threaded option); interpolation split into its own ticket.
- [Spike: a box dropping onto a plane through the proposed seam](issues/12-spike-box-onto-plane.md): works end to end on `prototype/fenrir-physics-spike` (user-verified in the DemoApp; deterministic; builds in Clang and MSVC x64, Linux unverified); Jolt does not leak; six spec lessons (watch needs an initial scan, kinematic moved every step, diff copy read back through `GetWorldTransform`, test tolerance for slop, convex-radius clamp, owner outlives `App::Run`); `ThreadPool` job adapter still a risk.
- [How do C# components hold a tagged union?](issues/16-csharp-tagged-union-components.md): no new mechanism; Iris's existing struct mapping accepts explicit layout, proved by a new scripting test; the physics contract hand-writes `CollisionShape` with checked `[UnscopedRef]` views and implicit conversions; scripts may use the pattern by hand; generator support waits for a second union.
- [How does a system read each event exactly once?](issues/18-read-each-event-once.md): ADR-0012. Per-reader cursors (`EventReader<T>`, C++ and C#) over the existing two buffers; `ReadEvents` removed; the swap waits for a fixed step; parallel sends buffered per system and appended in registration order; payloads stay plain data.
- [What does the physics scripting extension give C#?](issues/11-physics-scripting-extension.md): all physics components writable from C# (`Trigger` and `ContactEvents` gain `bool enabled`); native functions for forces, queries, contacts, sleep and bounds, gravity, debug draw and collision meshes; the four events via `EventReader<T>`; silent no-ops without a world or body; contract `Fenrir.Physics` plus a separate `FenrirPhysicsScripting` library, built only with physics and scripting on.
- [Is there transform interpolation, and who owns it?](issues/19-transform-interpolation.md): on by default (`RigidBody::interpolate`), interpolating between the last two steps into `Transform`; new once-per-frame `BeforeTicks` (restore the true pose, detect edits) and `AfterTicks` (write the blended pose) phases; teleports snap.
- [What does Jolt offer for constraints?](issues/20-what-jolt-offers-for-constraints.md): 12 two-body kinds, only hinge and swing-twist drivable for ragdolls; limits, motors and springs only on some kinds; anchors relative to the centre of mass, so the host must report shape changes; no built-in breaking (lambda against a threshold); one collision group per body, which queries ignore; constraints are removed before their bodies; no edit wakes bodies; removing one reorders the solve; no articulations.
- [How do other engines model joints?](issues/21-how-other-engines-model-joints.md): two models, a joint entity naming both bodies (Avian, Godot, Unreal, Unity ECS) or a component on one body naming the other (Unity, O3DE, bevy_rapier, whose own issue calls that un-ECS-like); kind as a field only in bevy_rapier and Unreal; breaking ranges from thresholds that destroy (Unity) or keep a broken state (Unreal) to none, with force reported for game code (Avian, Rapier); no-collide covers only the joined pair, default split; the usual complaints are frames captured at creation, scale, and chain instability.
- [How are joints modelled in the ECS?](issues/22-joints-in-the-ecs.md): ADR-0013. A `Joint` on a joint entity (any entity, including one of its bodies) names `bodyA` and `bodyB` (body entities only; an empty `bodyB` is the world); the kind is a tagged union; explicit `frameA`/`frameB` local to each body's origin, scaled with it, the rest pose where they coincide; a `FrameFromWorld` helper, never captured frames; `bool enabled`; the joint entity's `Transform` ignored.
- [Which joint kinds are there, and what does each expose?](issues/23-joint-kinds-and-settings.md): six kinds (fixed, ball, distance, hinge, slider, swing-twist); frame X is the joint axis; SI units and radians; shared `JointSpring` (Hz, damping ratio), `JointLimits` (hinge and slider, the rest pose always inside) and `JointMotor` (off, velocity, position); swing-twist has cone limits and one orientation motor for ragdolls; every per-kind field a live edit; solver overrides and priority refused as tuning.
- [What joint state can game code read, and how do joints break?](issues/24-joint-state-and-breaking.md): state by query, `PhysicsWorld::JointState(joint)` (force and torque on `bodyB`, `frameB` relative to `frameA`, one free-axis `position`), from the last step's simulated poses for every kind; `breakForce`/`breakTorque` on `Joint` (default infinity), one step over breaks; a broken joint is `enabled = false`, re-enabling repairs; a `JointBroken` event sorted by joint; checked in a new `PostTick` step 5b.
- [What happens at a joint's edges?](issues/26-joint-edge-cases.md): a joint naming no valid body goes inactive (component kept, no constraint, one warning, back when valid, zeroed state, no event); joints with no dynamic end are valid but inert; motion type changes keep the constraint; teleports don't move the other end (warm start reset); shape changes notify, scale or rebuild recreates; every `Joint` change wakes both bodies; constraints removed before and created after bodies in step 1, diffed after bodies in step 2; solve order from joint entity order via a private priority.
- [How do jointed bodies stop colliding?](issues/25-jointed-bodies-not-colliding.md): `bool collideConnected = false` on `Joint`, so jointed bodies do not collide by default; the joint only removes contact the layer rule allows; only the two named bodies (no chains), any excluding joint between a pair is enough; all solid colliders, never triggers; only while enabled, so a broken joint's bodies collide again; queries unaffected; usual contact events on a toggle; privately one Jolt `GroupFilter` over a pair-count table patched before the step, with room for general collision groups.
- [Spike: a hinged door and a hanging chain through the proposed model](issues/27-spike-hinged-door-and-chain.md): works on `prototype/fenrir-physics-joints-spike` (user-verified in the DemoApp; clang Debug and Release; destroying a link mid-swing gives one warning per joint and no crash); Jolt does not leak; lessons: `PhysicsWorld::JointState` hides its own type, an infinite-`maxForce` motor beats a hard limit, torque is rebuilt from Jolt's private axes, teleports are corrected by position (never break a joint, not violent), solve-order priority proven bit for bit, chains stretch 1–2 cm, hinge sign follows which body is A, `FrameFromWorld` treats only an empty `bodyB` as the world.
- [What does C# get for joints?](issues/28-joints-in-csharp.md): every joint type writable from C#; FenrirScripting prerequisite: `EntityLink` made from an `Entity` (owner filled natively) and `EntityLink.None`; `JointKind` hand-written in `CollisionShape`'s pattern with a generator-compatible surface (generator wanted, trigger: a script union or a third engine union); query renamed `GetJointState` in both languages, returning the struct; native `Joint.FrameFromWorld` with a world overload, a dead body giving a warning and identity frames; `JointBroken` through `EventReader<T>`; foundation no-op rules.
- [What do the joints demo scenes show, and how do several scenes switch?](issues/29-joints-demo-scenes.md): a DemoApp `DemoScenes` switcher with one F-key per feature family stepping through its scenes and back to Default (F4: Joints (C++), Joints (C#)), F2 mode re-applied on switch, `FENRIR_DEMO_SCENE` and `FENRIR_DEMO_KEYS` smoke runs; one `CSharpScene` marker with a scene id; new `DebugDraw::Joints` draws both frames as axes (dimmed disabled, grey inactive); readings in joint entity names; C++ is the spike's door and chain with the edge-case keys (minus P) and a trigger child; C# shows a breakable bridge with a hinge/fixed swap, a slider lift, a distance spring and a swing-twist limb; hand-check list.
- [What does Jolt offer for characters?](issues/30-what-jolt-offers-for-characters.md): `CharacterVirtual` (collide-and-slide, for players) is not a body and is invisible to bodies, queries and triggers without a kinematic inner body; `Character` is a dynamic body kept upright; the host owns gravity and ground velocity; `ExtendedUpdate` adds stairs and stick-to-floor; updates run outside the step on the updating thread; pushing is a clamped impulse; `SetShape` checks room to stand; character order and a process-global ID counter affect determinism.
- [How do other engines expose characters?](issues/31-how-other-engines-expose-characters.md): three API shapes, a field physics applies in its own phase (O3DE, Unreal, Tnua), a one-shot request (bevy_rapier) or a move call (Unity, Avian, Rapier), with Godot's field-plus-call between; ground state from a bare bool to Tnua's entity, normal and velocity with anti-flicker; platforms built in only for Godot, Unreal and Tnua; pushing from game-code callbacks to automatic impulses that launch light bodies; ground flicker, stairs and platforms are the common complaints.
- [How is a character body modelled in the ECS?](issues/32-character-bodies-in-the-ecs.md): ADR-0014. A `CharacterBody` beside the entity's own `Collider` (no compounds), driven by a `velocity` field physics applies in `PostTick` and writes back trimmed by hits (no move call); always seen by bodies, queries and triggers as a kinematic body of its shape (privately `CharacterVirtual` with an inner body); position-only write-back, full world rotation, centred `Transform`, world +Y up; teleports by `Transform`; inactive beside a `RigidBody` or without a usable `Collider`; `bool enabled`; Jolt's construction-only settings private; physics never adds or removes components.
- [How does a character move each tick?](issues/33-how-a-character-moves-each-tick.md): a new `PostTick` step 3b moves characters just before the step, one at a time in entity order, written back in step 5; `velocity` trimmed against end-of-move contacts, never measured; gravity is game code's; live `maxSlope` (45°), `stepHeight` (0.4 m), `floorSnap` (0.5 m), `stopOnSlope`; ground velocity added privately on walkable ground, then kept as **carried velocity** until landing; `CharacterBody::interpolate`, position and rotation blended; only a position change is a teleport; no ADR.
- [What does game code read back from a character, and which events?](issues/34-character-state-and-events.md): a `CharacterState state` struct inside `CharacterBody`, overwritten each write-back (ground state `InAir`/`OnGround`/`OnSteepGround`/`Touching`; ground body, collider, point, normal, velocity and angular velocity; `movedVelocity`, `carriedVelocity`, `onWall`, `onCeiling`), reset when disabled or inactive; `ForEachContact` lists end-of-move contacts; the existing contact events (opt-in, from the move only, merged into step 6) and trigger events name the character's entity; no landing events or coyote time; no ADR.
- [Spike: a character walking a small level through the proposed model](issues/37-spike-character-walking-a-level.md): works on `prototype/fenrir-physics-character-spike` (user-verified in the DemoApp on F5; clang Debug and Release; ten headless checks, two runs bit-identical); Jolt does not leak; lessons: trimming `velocity` along contact normals turns walking into climbing speed, so what is underfoot takes only falling speed; rounded box edges read as steep for 1–3 ticks and make ground state flicker down stairs; Jolt hovers one tick of travel above a descending lift and hops at its turn; sliding needs game code to keep the written-back horizontal velocity; no base-of-shape conversion is needed.
- [How does a character interact with other bodies?](issues/35-characters-and-other-bodies.md): pushing is Jolt's capped impulse through live `pushForce` (100 N) and `mass` (70 kg, weight on the ground), never downward; dynamic bodies never push a character, kinematic ones shove it at their own speed into `velocity` (no crush detection); bodies resting on a character are not carried; characters can't be joint ends; characters block each other through inner bodies in entity order, no pushing, seen moving at their `movedVelocity`; contacts with dynamic bodies are the union of move and inner-body step contacts (amends 34); `CollisionFilter` filters move and inner body, layers suffice, collision groups stay in the fog; `PhysicsMaterial` is what touching bodies feel, never the character's movement; `ignoreBody` takes characters; no ADR.
- [What are the motion-test and sweep queries, and how does a character change shape?](issues/36-motion-tests-and-shape-changes.md): general `PhysicsWorld` queries `MoveCast` (closest hit with a safe distance, private 0.02 m skin, ignoring bodies it starts in), `Penetrations` (normal and depth, deepest first) and `Depenetrate` (resolved offset); `QueryFilter` gains `layers` (0 ignores bodies' masks) to filter like a character; box, sphere, capsule and hull characters, meshes inactive; world scale applies; a shape or scale edit that doesn't fit is kept unapplied and retried each move, reported by `state.shapeBlocked`; on ground the feet stay put, in the air the head; no ADR.
- [What does C# get for characters?](issues/38-characters-in-csharp.md): `CharacterBody` writable from C# with C++'s defaults, its `State` read-only in C# (FenrirScripting prerequisite: the field generator gives read-only fields a `ref readonly` accessor on `Ref<T>`); no native move or state function; `MoveCast`, `Penetrations` and `Depenetrate` as native functions plus `QueryFilter.Layers`, with no filter sugar; the existing events and `ContactsOf` name characters; foundation no-op rules; doc notes on sliding, pushing and crouching; the C# scene's list handed to 39; no ADR.
- [What do the character demo scenes show?](issues/39-character-demo-scenes.md): F5 steps Default → Character (C++) (the spike's level rewritten, plus push masses, seesaw, paddle, ball, a second character, box on the head, crouch tunnel, crouch-jump ledge, scale and mesh keys) → Character (C#) (slide ramp, ice, crouch tunnel, `MoveCast` dash, `Penetrations`/`Depenetrate` push-out, trigger pad, lift, landing counter); a C++ and a C# follow camera both write a demo `DemoCamera` component that one C++ system applies after `CameraController`; readouts in names; new `DebugDraw::Characters` (shape in use, ground normal, `movedVelocity`); demo code steers velocity with an acceleration cap; crouch is a toggle; P autopilots for smoke runs; hand-check list; no ADR.
- [What does Jolt offer for vehicles?](issues/40-what-jolt-offers-for-vehicles.md): `VehicleConstraint` is a one-body constraint and a step listener, needing a dynamic body and a ground probe (ray, sphere, cylinder) the host sets; wheeled, motorcycle (lean, "in development") and tracked controllers; wheels in body space from the origin, wheel count and kind need a rebuild, the drivetrain is live; input is plain stores set before the step; it runs inside the step on job threads, in parallel, bodies locked; probes skip triggers and send no contacts; friction from the ground body or a callback; wheel poses are one collision step stale after the step; input doesn't wake the body; Jolt's vehicle drawing is compiled out, its data is readable.
- [How do other engines expose vehicles?](issues/41-how-other-engines-expose-vehicles.md): a chassis body plus a cast per wheel everywhere; wheels as an array on the vehicle (Unreal, bevy_rapier, PhysX) or an entity or node each (Unity, Godot, Unity ECS); normalised pedals and steering (Unreal, PhysX, Unity ECS) or physical per-wheel values; full drivetrain only in PhysX, Unreal and Unity ECS; state written back in the ECS designs, queried elsewhere; only PhysX maps ground material to grip; no engine keeps a motorcycle up or models entering a vehicle; trailers are plain joints; parked creep is the top complaint.
- [How is a vehicle modelled in the ECS?](issues/42-vehicles-in-the-ecs.md): ADR-0015. A `Vehicle` on the dynamic chassis body's entity (chassis-local +Y up, −Z forward by convention) with a `VehicleKind` union (wheeled, motorcycle, tracked), normalised persistent `VehicleInput` (forward, steer, brake, handbrake; tracked adds track ratios) that physics never writes, and `bool enabled` (disabled is a plain rigid body); one `VehicleWheel` per wheel entity with an explicit `vehicle` link and a chassis-local `position` scaled with the chassis, posed by physics for drawing (its `Transform` output only), entity order as wheel order, wheel set changes rebuilding privately; inactive rules for vehicles and wheels as for joints and characters.
- [Which settings does each vehicle kind expose?](issues/43-vehicle-kinds-and-settings.md): no arrays anywhere (curves as peak/slide shape fields, gears spaced geometrically from first to top with one reverse); SI and radians, RPM for engine speeds; `position` is the wheel centre at full extension; per-wheel `caster`/`camber`/`toe` angles; shared `VehicleEngine`, `VehicleTransmission` (auto or manual, manual gear and clutch in `VehicleInput`), `VehicleTrack`; `VehicleDifferential` and `VehicleAntiRollBar` as their own components naming wheels, all-wheel drive with none; `probe` and `maxTilt` (off) on `Vehicle`; motorcycle lean gains private; every field live, only max lean rebuilds; no ADR.
- [How does a vehicle step each tick, and what does game code read back?](issues/44-how-a-vehicle-steps-and-reports.md): input pushed in step 2, the vehicle run inside step 4 as the backend's step listener (in parallel, private priority from entity order, every probe on every collision step); state written back into a nested `VehicleState state` on `Vehicle` (speed, RPM, engaged gear and clutch, lean, track speeds) and a `VehicleWheelState state` on each wheel (ground, contact, compression, suspension force, slips, spin, steer); wheel poses written after the chassis and interpolated with it; grip is the geometric mean of tyre and ground `PhysicsMaterial` friction; no wheel or vehicle events; any input or vehicle edit wakes the chassis; rebuilds keep RPM, gear and spin; no ADR.
- [How does a vehicle meet other bodies, joints and characters?](issues/45-vehicles-and-other-bodies.md): probes filter as the chassis does and always skip triggers, the chassis and character bodies; wheels push dynamic ground and ride moving ground through grip; a car meets a character with its hull (stated limits: rubble dip, heavy-trailer jitter); getting in and out and righting flipped vehicles are game code, with recipes; a new `TrailerVehicle` kind (no engine) towed by an ordinary joint; no general collision groups for vehicles; chassis edges follow the joints and 44 rules; a differential's dead wheel name counts as empty; no ADR.
- [Spike: a car, a motorcycle and a tank driving a small track through the proposed model](issues/46-spike-vehicles-on-a-track.md): works on `prototype/fenrir-physics-vehicles-spike` (user-verified in the DemoApp on F6; clang Debug and Release; eleven headless checks, runs bit-identical, threaded or not); Jolt does not leak; defaults drive without the ×10 cap, parking sleeps without creep, tanks pivot, live wheel patching and rebuild carry-over work; lessons: Jolt's hard point needs a private margin above the travel or a bottomed wheel lets the chassis sink, Jolt's lean damping diverges below 16.7 kg m² roll inertia (capped privately), the probe default is `Cylinder` for every kind, `JointSpring`'s 1.0 damping leaks into partially initialised suspensions, a chassis must not be scaled to size its look, Manual forward is a pedal, Jolt's default friction combine suffices, an unpowered trailer is a `Vehicle` with no input.

## Not yet specified

- **Feature-family specs still to chart:** ragdolls, soft bodies. (Constraints and joints graduated into tickets 20–29, the character controller into tickets 30–39 and vehicles into tickets 40–48; each later family gets an F-key from F7 and a C++ and a C# scene, per "What do the joints demo scenes show, and how do several scenes switch?".)
  - **Ragdolls:** wait for a skeleton, an animation system and skinned-mesh rendering, none of which the engine has. Without them a ragdoll is only a jointed body, which the joints spec already gives (hinge and swing-twist were chosen for ragdolls). What they need from a renderer is in `.scratch/fenrir-renderer/notes.md`.
  - **Soft bodies:** wait for a renderer that re-uploads a mesh's vertices every frame; the DemoApp draws only rigid meshes. See `.scratch/fenrir-renderer/notes.md`.
- **A separate demo app per area:** not in the joints spec. Splitting the DemoApp today would mean copying its renderer, editor and scene switching, so it waits until those can be shared as a library. Trigger: the DemoApp runs out of family keys (F3–F12), or its start-up time or clutter gets in the way of hand checks ("What do the joints demo scenes show, and how do several scenes switch?").
- **General collision groups** (any set of bodies that ignore each other): not in the joints spec, which only stops jointed bodies colliding. They come with ragdolls (a character and its own ragdoll, excluding a whole chain). Characters and vehicles were checked and need none: layers cover teams, player against enemy and debris ("How does a character interact with other bodies?"); a seated driver is a disabled character, and a trailer or turret is excluded by its joint's `collideConnected` ("How does a vehicle meet other bodies, joints and characters?").
- **A `[TaggedUnion]` generator** (FenrirScripting): **triggered.** `VehicleKind` is the third engine union, the trigger set by "What does C# get for joints?". So the generator is a FenrirScripting prerequisite ticket of the vehicles spec. The author writes the byte tag enum and the private fields; the generator emits the constructor, `Type`, the views, the conversions and the wrong-kind check. `CollisionShape` and `JointKind` move onto it unchanged ("What does C# get for vehicles?"). This entry leaves the map once the vehicles spec is written.
- **Further joint kinds:** not in the joints spec, addable later as new `JointKind` alternatives ("Which joint kinds are there, and what does each expose?"). Cone and six-DOF need only their settings; gear and rack-and-pinion need a way to couple two other joints; pulley needs fixed world points; path needs a shared curve handle like `CollisionMesh`.

## Out of scope

- 2D physics: Jolt has no 2D support.
- A second physics backend: the seam must allow one, but none is built.
- Large worlds (double-precision positions): positions are float; the seam must not assume Jolt's types, so this stays addable later.
- Determinism across platforms or builds.
- An asset pipeline for collision data: callers supply vertex and index data ("How is physics modelled in the ECS?").
- Articulations (multibody, reduced-coordinate joints): Jolt has none, only maximal-coordinate constraints ("What does Jolt offer for constraints?"), and a second backend is out of scope.

# 07: Every package's registration committed and compiled in; `App` owns the registry; each `Install` registers its package

**What to build:** a running engine knows every described type by name. Each package with an API description gains a `[registration]` table, its generated header and source are committed and compiled into the package, which links `FenrirTypes`; `App`'s constructor makes one `TypeRegistry` as an app resource and registers the packages beneath `Install` (FenrirMath, FenrirECS, FenrirScene, FenrirApp); every `X::Install(App&, XConfig)` registers its package's types first (ADR-0074 "fills a run-time type registry in a new package at `Install`"). A headless `App` with assets, physics and animation installed can be asked for `Fenrir::RigidBody`, `Fenrir::Transform` or `Fenrir::Sky` and get their fields.

- **Selections:** every `packages/*/api/*.api.toml` with a description gains `[registration]` naming its header, source, function and includes (the types spec's names: `include/<Package>/Generated/<Package>Types.hpp`, `src/Generated/<Package>Types.cpp`, `Fenrir::Generated::Register<Package>Types`); FenrirScene, FenrirCore, FenrirTime, FenrirScheduler, FenrirLogger and FenrirDebugDraw have no description and register nothing (FenrirScene's resources are reached through FenrirRenderer's and others' descriptions, as today).
- **Build:** each described package calls `fenrir_generate_type_registry` beside its `fenrir_describe_api`, compiles its generated source and links `FenrirTypes` `PUBLIC`; the generated header is public so `Describe<T>` is visible to a game (ADR-0084's `Project::Get<T>`). The generated files are committed as the bindings are.
- **`App`:** constructs a `TypeRegistry` app resource first and calls the four Install-less registrations; `App::GetResource<TypeRegistry>()` is how everything reaches it. FenrirECS's and FenrirScene's registrations run before any scene exists.
- **Each `Install`** (`Assets`, `Physics`, `Animation`, `Skeletons`, `Renderer`, `Window`, `Input`, `DebugDrawing`, `Scripting`) calls its package's registration as its first act, before any resource or system, and an `Install` called twice registers once (the registry's duplicate rule makes the second call a no-op with no diagnostic when the description is the same object).
- **Per-package defaults test:** each package's test suite gains a generated-shape test that the registration's defaults equal `T{}` field by field through the visitor, the shape of the binding's `<Package>DefaultsTests.cpp`; the registry generator emits it as a test source the package's `Tests/CMakeLists.txt` includes, or the test is one template the FenrirTypes tests export and each package instantiates, whichever the implementer finds smaller.
- **Docs:** `README.md`'s API-description paragraph names the registration beside the description and binding; each package's `CMakeLists.txt` header comment says it registers types.

## Comments

- Built in `claude/ser-types-07-every-package-registers`. With the user's approval the ticket grew one tool change. Several descriptions hold the same type, because a binding needs it there: FenrirMath's `Vec3` is in FenrirECS's, FenrirPhysics's, FenrirSkeleton's and FenrirRenderer's; `AABB`, `WindowId`, the asset handles, `PoseState` and `Transform` are each in more than one. Registering each one in every package would have specialised `Describe<T>` twice and been refused by the registry. Now `[registration]` takes `uses`, the selections of the packages whose registrations register those types. The tool skips those types, includes the used headers, points fields at the used description objects (each header now declares them `extern const` in `Fenrir::Generated::<Package>Types`), and runs the used registrations first. The uses: ECS, Physics and Input use Math; Skeleton uses Assets and ECS; Animation uses Assets and Skeleton; Window uses Input; Renderer uses Math, Assets and Input.
- No type is skipped: all eleven described packages register every type their descriptions hold, the tagged unions included.
- Registering once lives in the generated code, not in `TypeRegistry::Register`. Each type registers and goes to its role's hook only when `registry.Find(name)` is not already the same description. A hand-written second `Register` of one description is still a diagnostic. This also keeps ticket 08's hooks from attaching twice.
- `DebugDrawing` is in the ticket's list of Installs, but FenrirDebugDraw has no description, so it registers nothing (as the Selections line says). UI and Painting have none either. `Scripting::Install` registers FenrirScripting's two error enums, as the first statement inside its `try`.
- The defaults test is generated: `[registration] test` names `Tests/Generated/<Package>TypesDefaultsTests.cpp`. Each package's tests compile it and link `FenrirTypesTesting`, whose `FenrirTypesTesting/Defaults.hpp` checks the defaults. `Testing/` would have been ignored by `.gitignore`, hence the name. The registration records no defaults, so the generator writes the description's defaults as expected values: nested structs' own defaults or the members a field's initialiser sets, a tagged union's default kind, array elements, the null entity, empty references, lists and optionals. The checker constructs the type through its description, visits it, and fails on a value that differs, a value it cannot reach, or a value it reaches that has no expectation. A bound type's component that its field's initialiser leaves to glm is expected as `Unchecked`. FenrirScripting's test holds only a `SUCCEED()` until ticket 09 gives it `ScriptingConfig`.
- FenrirApp's tests: `TypeRegistry.cpp` in `FenrirAppTests` covers the registry before any Install. `FenrirAppInstalledTypesTests` (`InstalledTypes.cpp`, its own executable because it links the packages above FenrirApp) installs Assets, Skeletons, Animation, Physics and, when built, the Renderer on its null backend. The second-Install test reinstalls Physics; every Install's guard is the same generated line.
- Also outside the Touches: `tools/generate-type-registry/` (`uses`, `test`, the register-once guard, the README), `packages/FenrirTypes/Tests/` (`FenrirTypesTesting`; the fixture's test of a second registration now expects nothing to be refused) and the regenerated fixture and test-package registrations. The full msvc-x64-debug CTest run with the renderer on passed 153 of 153. In a later run, `FenrirRenderer-GL` once timed out at 300 s under `-j 8` and passed alone.

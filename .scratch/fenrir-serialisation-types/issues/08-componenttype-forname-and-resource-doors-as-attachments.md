# 08: `ComponentType::ForName` and the scene and app resource doors as attachments in FenrirECS, FenrirScene and FenrirApp

**What to build:** code holding a type's name alone can act on an entity or a scene with it: `ComponentType::ForName(registry, "Fenrir::RigidBody")` gives the `ComponentType` that `AddComponent`, `HasComponent`, `GetComponent` and `RemoveComponent` take, and a scene's or the app's resource of a named described type can be found, added and removed without the C++ type in hand. These are the attachments the registry generator's role hooks (ticket 06) hang: FenrirECS attaches a `ComponentType` per `component`-role type, FenrirScene a type-erased find, add and remove over a `Scene&` per `scene-resource`, FenrirApp the same over an `App&` per `app-resource` (ADR-0074 "a component registers its name and `ComponentType`; a scene or app resource a type-erased add, get and remove"). The file reader and writer of the later specs reach components and resources only this way.

- **FenrirECS:** `AttachComponent<T>(TypeRegistry&, const TypeDescription&)` defined in a public header, hanging a `ComponentType` (made as `ComponentType::Native<T>()` is today) under an ECS tag; `ComponentType::ForName(const TypeRegistry&, std::string_view) -> std::optional<ComponentType>` and `ComponentType::NameOf(const TypeRegistry&, ComponentType) -> std::optional<std::string_view>` over the attachments; `EntityList` gains nothing, since its by-`ComponentType` doors already exist. `Transient`-style empty tag types are the scenes spec's; this ticket's `ForName` refuses nothing the registry holds.
- **FenrirScene:** `AttachSceneResource<T>` hangs `{find, add, remove}` function pointers over `Scene&` (`AddResource<T>()` default-constructed, `GetResource<T>()`, `RemoveResource<T>()`) under a scene tag; `Scene::FindResource(const TypeRegistry&, name) -> void*`, `Scene::AddResource(const TypeRegistry&, name) -> void*` and `Scene::RemoveResource(const TypeRegistry&, name)` use them. FenrirScene links `FenrirTypes` for this and nothing else.
- **FenrirApp:** `AttachAppResource<T>` and the same three doors on `App` over its app resources.
- **The generated hooks** from ticket 06 stop being no-ops: a package's generated header includes the three attach functions from FenrirECS, FenrirScene and FenrirApp (through `[registration] includes`), and its registration calls them for each type of the role; a package that describes only shared structs or data assets includes none.
- **The registry generator** needs no change beyond what ticket 06 emitted; if the hook names or signatures move here, the generator and every committed registration move with them in this ticket.

**Blocked by:** 07.

**Touches:** `packages/FenrirECS/` (`include/FenrirECS/ComponentType.hpp`, a new `include/FenrirECS/TypeAttachments.hpp`, `src/`, `Tests/`), `packages/FenrirScene/` (`include/FenrirScene/Scene.hpp`, `CMakeLists.txt`, `Tests/`), `packages/FenrirApp/` (`include/FenrirApp/App.hpp`, `src/App.cpp`, `Tests/`), `tools/generate-type-registry/src/` (the hook calls, if they move), every package's generated `Types.hpp` and `Types.cpp` (regenerated)

**Status:** resolved

- [x] On a headless `App` with physics installed, `ComponentType::ForName(registry, "Fenrir::RigidBody")` gives a `ComponentType` an entity accepts through `AddComponent`, and `NameOf` gives the name back; an unknown name gives an empty optional.
- [x] `Scene::AddResource(registry, "Fenrir::Sky")` on a scene makes a default `Sky` that `GetResource<Sky>()` finds; `FindResource` by name returns it; `RemoveResource` by name removes it; a name that is not a `scene-resource` returns null with no diagnostic.
- [x] The same three doors work on `App` for an `app-resource` type the tests describe.
- [x] Every described package's registration calls the attach functions for its components and resources, regenerated byte-identical by `fenrir-generate-type-registry`.
- [x] FenrirECS's and FenrirScene's existing tests pass unchanged; `PublicHeaders` passes for both.

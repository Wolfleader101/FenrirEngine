# 06: Generated visitors for owning types and base chains, attachments by role, and a FenrirTypes test package through the real tools

**What to build:** the registry generator writes a generated visitor function for every `data-asset` and `settings` type, walking the base's fields first and reaching `string`, `list`, `optional`, `path` and nested values by member rather than by offset (ADR-0074 "a generated per-type visitor so nothing pokes an owning type's bytes", ADR-0075 "the generated visitor walks the base's fields first"), records each `data-asset`'s base so `IsA` answers over the chain, and emits the attachments a role implies as calls the registration makes. A test package under FenrirTypes with its own `.api.toml` and `[registration]` runs describe-api and the registry generator for real under CI's dirty-tree check, so the whole pipeline is exercised on a header that is not an engine package's.

- **Owning visitors:** per `data-asset` and `settings` type a function that visits the base's fields (through the base's own generated visitor), then the type's own, giving each `FieldInfo` a `ValueRef` over the member: a `string`'s text, a `list`'s size, resize and element access, an `optional`'s presence and emplace, a `path`'s text, a nested struct's recursion. A caller sees the same `FieldVisitor` calls as for a table-driven type.
- **Base chains:** the description's `base` becomes `TypeDescription::base`; the registry's `IsA` walks it; registering a `data-asset` whose base is not registered first is a diagnostic naming both, so a package's registration orders bases first and the tool emits them in that order.
- **Attachments by role:** the generated registration calls, for each type, a hook the package supplies per role (`AttachComponent<T>`, `AttachSceneResource<T>`, `AttachAppResource<T>`), declared in the package's `includes` and defined by FenrirECS, FenrirScene and FenrirApp in ticket 08; until then the hooks are inline no-ops in the generated header so a package registers without them. The tool emits no hook for `data-asset`, `settings`, `shared-struct`, `bound-type`, `nested` or `enum`.
- **The test package:** `packages/FenrirTypes/Tests/Package/` with a header holding one of everything (a `data-asset` extending another with owning kinds, a `settings` type, a component with the three fixed-layout kinds, a scene resource, a bound type, an enum, every doc command), its own `.api.toml` with `[registration]`, and both tools run on it through `fenrir_describe_api` and `fenrir_generate_type_registry`, its description and registration committed and covered by CI's dirty-tree check (which gains the registry target in ticket 10; until then the check covers its description alone).
- **Tests** over the test package's registration: a `list` of nested structs resized and filled through the visitor and read back from the struct, an `optional` emplaced and cleared, a `string` and a `path` written, a base's fields visited before the derived type's, `IsA` over the chain, `transient` and `editorOnly` read from the description, every metadata command's value present on its field, and `version` and former names as the header says.

# FenrirRenderer

Label: wayfinder:map

## Destination

A set of specs, one feature directory each (`.scratch/fenrir-renderer-<name>/spec.md`, so each spec's tickets sit beside it), each ready for `/to-tickets`, plus ADRs for the hard-to-reverse calls: where the graphics seam sits and whether the backend is picked at compile time or at runtime, who owns the graphics context and the swapchain or surface, who owns input, and the shader language (and any other call that proves hard to reverse). The first is the **foundation spec**: the graphics seam over OpenGL, FenrirWindow over its windowing library, enough input to drive the demos, the renderer's core components and systems, meshes, materials and shaders (an unlit material and one simple lit material, with one directional light and ambient, no shadows), cameras, the frame and its passes (skybox and background included), debug lines and text, what the renderer offers a UI library drawn over it, the renderer's scripting extension, and the demo apps: a shared demo scaffold, a renderer demo app, the physics scenes rewritten as physics demo apps on the new stack, and the old `examples/DemoApp` deleted. The foundation spec is ticketable as soon as its own decisions close. Then one spec per feature family, each built on the foundation: **animation and skinning** first (skeletons with bind poses, clips and playback, pose blending, skinned meshes drawn from bone transforms, blending an animated pose with a simulated ragdoll pose, and the bone-to-body mapping ragdolls need, as plain data), then whatever else the map turns up.

## Notes

- **FenrirPhysics is the pattern.** Its facade is what these packages copy at a high level: `Install(App&, Config)` returns the owner of the package's process-wide state; game code configures it with plain-data components on entities, named by `Entity`, with no public backend handle; scene-scoped state is a scene resource; C# support is a scripting extension (ADR-0009) in the package, built only when scripting is on. (Its code wants a review and clean-up, which is not this map's work.)
- **Libraries are hidden at compile level.** As ADR-0010: no public header of FenrirRenderer, FenrirWindow, the input package or the animation package names or includes the library underneath (GL and its loader, GLFW or SDL, assimp or whatever imports assets, the shader compiler); each links them `PRIVATE`. The graphics backends are private too, chosen at runtime behind a private graphics device (ADR-0016).
- **The graphics seam must allow D3D, Vulkan or Metal** to replace OpenGL without touching the code that calls the renderer. Only OpenGL is built.
- **Packages stay independent.** Physics produces plain data (debug lines, bone poses, soft-body vertices) that rendering and animation read; physics never depends on them and they never depend on physics. Glue that joins them (a ragdoll's bodies to its skeleton) lives in app or demo code, or in the physics map's ragdoll spec. What other packages need from a renderer: `notes.md` beside this map.
- **The DemoApp is not a reference.** Everything in `examples/DemoApp` about GLFW, OpenGL, events, ImGui, its components and systems is placeholder, written fast; it is neither a model to follow nor something to stay compatible with. It is deleted once the demo apps replace it. `FenrirCamera` may be removed or reshaped to fit the ECS.
- **Demo apps, not one DemoApp.** Each feature area gets its own demo app on a shared scaffold. The ImGui editor is a prototype of its own and out of scope here; ImGui will later be replaced by the user's own GUI library, so the renderer offers a UI library a way to draw over it rather than building ImGui in.
- **Platforms:** Windows (MSVC and clang, Debug and Release) verified; Linux kept buildable but unverified; macOS out of scope until a Metal backend exists.
- **Conventions:** meters, Y-up, right-handed (as glm); single-precision floats, like the rest of the engine. In this map *component*, *system*, *event*, *entity*, *world transform* and *scene resource* carry their meanings from `GLOSSARY.md`.
- Skills: grilling tickets call `grilling` and `domain-modeling`; seam and module-shape questions also use `codebase-design`. Research tickets call `research` and put their findings on a `research/<name>` branch, pushed, never merged.
- Plan, don't do: tickets produce decisions, not code (spikes are throwaway, on `prototype/…` branches).
- Built specs are removed, as on the physics map: the commit that records a spec built deletes its directory.

## Decisions so far

<!-- one line per resolved ticket: [title](issues/NN-slug.md): gist -->

- [What do GLFW 3.4 and SDL3 each offer FenrirWindow?](issues/03-glfw-or-sdl3.md): equal on windowing basics; both fix the graphics API at window creation; SDL3 adds IME, rumble, touch, a header-free `HWND` and a Metal layer, at ~16x GLFW's size and build time; GLFW allows GL calls off the main thread, SDL3 does not; both zlib, both clean as `SYSTEM` includes.
- [How do engines import and own meshes, textures, shaders, skeletons and clips?](issues/06-asset-import-and-ownership.md): assimp reads 40+ formats into its own scene but is heavy and loose with glTF skins and clip timing; cgltf and fastgltf hand back raw glTF, ufbx covers FBX well, stb_image or libktx for textures; glTF carries skins, 4-weight sets, clips in seconds and PBR, and exported files are often wrong; Bevy and Godot both have one asset system with typed handles (ref-counted or generational), deduplicated by path, upload separate from load, procedural meshes in the same storage.
- [How do engines write shaders once for several graphics APIs?](issues/04-shader-languages-and-toolchains.md): GLSL costs nothing now and, written with explicit bindings and no loose uniforms, goes to SPIR-V later unchanged; GLSL → SPIR-V → SPIRV-Cross is the shared multi-backend route (bgfx, Filament, Godot); GL 4.6 SPIR-V loses names, so reflection moves to SPIR-V; HLSL needs DXC (glslang's HLSL front end is deprecated); Slang is strongest on variants but "limited" on GL; variants are `#define` bitmasks everywhere; all tools permissive and linkable `PRIVATE`.
- [How do engines model skeletons, clips, blending, skinning and ragdoll blending?](issues/07-how-engines-model-animation.md): bones as entities (Bevy, Unity) or arrays in one object (Godot, Unreal, ozz, Jolt), named by index or by name (names let clips be shared); blending in local space everywhere, from ozz's one weighted job to full graphs; GPU skinning in a vertex or compute shader, ozz CPU only; ragdolls map one body per bone with a constraint to the nearest mapped ancestor, blended per body (Unreal), per subtree (Godot) or as a graph node (EMotionFX); Jolt has `SkeletonMapper` and drive-to-pose; ozz (MIT) fits behind a seam but leaks SoA math, joint order and its own format.
- [How do engines build and submit a frame?](issues/05-how-engines-build-a-frame.md): render graphs pay off on explicit APIs and big frames; small engines use fixed passes (Godot builds a barrier graph below them); Bevy 0.20 swapped its render graph for ECS schedules; data leaves the ECS by direct reads, a per-frame snapshot or persistent proxies (the last two needed for a render thread); interpolation runs after the tick loop; GL calls come from one thread; 64-bit sort keys; debug draw is an immediate buffer rebuilt each frame; text from a glyph atlas (raster, SDF or MSDF); ImGui and RmlUi need only textures plus scissored textured triangles in an overlay pass.
- [Which OpenGL version and features should the backend target?](issues/02-which-opengl-to-target.md): every current NVIDIA, AMD and Intel driver on Windows and Linux reports GL 4.6 with DSA, clip control and SPIR-V; the explicit-style subset (DSA, immutable storage, persistent mapping, separate programs, samplers, clip control) is all ≤ 4.5; CI's llvmpipe is 4.5 on Ubuntu 24.04's Mesa; bindless is not portable; GL SPIR-V loses names and needs own reflection; glad 2's multi-context mode keeps GL out of public headers; headless CI needs Mesa (EGL surfaceless on Linux, Mesa's `opengl32.dll` on Windows).
- [How do other engines put a seam over graphics APIs?](issues/01-how-other-engines-seam-graphics-apis.md): most put a thin explicit-API-shaped seam (pipelines, binding groups, passes, command lists) right over the API, often with a higher layer above; only sokol selects purely at compile time, the rest at runtime with coarse crossings; GL is dropped (NVRHI, SDL3 GPU, O3DE), emulated under the explicit model (Diligent, wgpu, sokol, Filament), or kept out of the thin seam (Godot, bgfx); handles range from bare indices to generational ids and ref counts, destruction deferred by frame or fence; every library but SDL3 GPU has a native escape hatch; null backends test bookkeeping, golden images test pixels.
- [Where does the graphics seam go, and is the backend picked at compile time or at runtime?](issues/08-where-the-graphics-seam-goes.md): ADR-0016; a public renderer over a private graphics device shaped like the explicit APIs, OpenGL 4.6 (raised from 4.5 by ADR-0018) and an always-built null backend chosen at runtime in `RendererConfig`; commands recorded through per-pass encoders into a plain-data `CommandList` and replayed on `Submit`; typed generational handles, destruction deferred by frame; no escape hatch or tuning settings; UI libraries reach the renderer only through a public overlay that takes their own shaders and vertex layouts.
- [Which library sits behind FenrirWindow, GLFW or SDL3?](issues/09-glfw-or-sdl.md): ADR-0020; SDL3 3.4.x, static and `PRIVATE`, for IME, rumble, sensors, touch and pen that GLFW lacks; video, events, input, gamepad, haptic, hidapi and sensor built, audio, GPU, 2D render, camera, dialogs, tray, process and `SDL_main` off; OpenGL calls stay on the main thread (SDL3's rule), so a render thread waits for an explicit-API backend; switch if a GL render thread or SDL3's build cost forces it.
- [Who owns input: FenrirWindow or a FenrirInput package?](issues/10-who-owns-input.md): ADR-0017. FenrirInput, linking no library, owns input types, app-wide `Keyboard`/`Mouse`/`Gamepads` resources and input events; FenrirWindow feeds it through a public input feed in `PreUpdate`, and tests feed it the same way with no window. Polled state and `EventReader` events, both. Just-pressed edges follow the reading phase (since the last tick in `PreTick`/`Tick`/`PostTick`, since the last frame elsewhere). Events name their window, and mouse units are logical window coordinates. First version: keys (key code and scancode), text, mouse, cursor modes (FenrirWindow's) and gamepads. C# gets the same through an extension.
- [Which shader language do we write, and how is it compiled for each backend?](issues/12-shader-language.md): ADR-0018, amending ADR-0016's GL floor to 4.6; every shader is GLSL 460 with explicit `set`/`binding`/`location` and blocks only, compiled at build time by our own `FenrirShaderCompiler` (glslang, SPIRV-Reflect; never linked into the engine) into one versioned shader container per program; SPIR-V is the device's only shader input, GL 4.6 ingests it, Vulkan will take it unchanged and D3D12 and Metal get it through SPIRV-Cross; layouts declared in C++, checked against build-time reflection in debug builds; `#define` variants all built offline; `#include` against a shared engine directory; no hot reload yet; CI's GL tests need a Mesa newer than Ubuntu 24.04's.
- [How is a frame built and submitted?](issues/13-how-a-frame-is-built.md): ADR-0019; three layers (ECS facade, a renderer core with no ECS dependency, the private graphics device); a new `Render` phase after `PostUpdate` on the main thread reads the active scene into a plain-data draw list with 64-bit sort keys; a render graph compiled each frame, ordered by render stage then dependencies, with culling and pooled transients, designed as if explicit (aliasing, async compute, parallel recording, a render thread listed as waiting); foundation passes Opaque, Background, sorted Transparent, Debug, Output, Overlay into linear RGBA16F scene targets.
- [How are the renderer and window packages tested?](issues/20-how-the-renderer-is-tested.md): no ADR; OpenGL floor raised to 4.6 core (ADR-0016 amended, as ADR-0018 also requires); most tests on the null backend through the public interface and a `RendererProbe` (draw lists, handle lifetimes, deferred destruction), a smaller GL suite reading back small offscreen targets with analytic per-pixel probes and tolerances, no golden images yet; GL debug errors fail tests; the context is made the app's way (ticket 11), under `xvfb-run` if it needs a display; GL tests in Linux CI on llvmpipe 4.6 (newest Ubuntu runner, else a newer-Mesa PPA), skipped elsewhere without 4.6; input tested by feeding neutral window events, FenrirWindow thinly; demo apps get smoke runs on null and on llvmpipe.
- [How are meshes, textures, shaders, skeletons and clips loaded and owned?](issues/15-how-assets-are-loaded-and-owned.md): ADR-0021; a new FenrirAssets package owns plain CPU-side asset data (meshes, images, materials, skeletons, clips, shader containers, models with labelled sub-assets), no GPU code, depended on by renderer and animation; `AssetHandle<T>` is a plain generational id, each load owned by the app or a scene, freed when its last owner ends or on `Unload`, deduplicated by path; synchronous, main thread only, failures as diagnostics, stale handles skipped; assimp and stb_image behind a private compile-time importer seam; procedural meshes through `Add`/`Replace`; the renderer uploads in its own prepare step keyed by handle and revision, CPU copy kept; one asset root in `AssetsConfig`.
- [Who owns the graphics context and the swapchain or surface?](issues/11-who-owns-the-graphics-context.md): ADR-0022; FenrirWindow makes the window and the API's surface SDL creates (the GL context today), the backend owns the swapchain or the use of the context; the core's private abstract `GraphicsSurface`, adapted from FenrirWindow by the ECS facade alone; `Renderer::Install` requests the main window's surface (4.6 core, sRGB colour backbuffer) and fails if it can't be made, otherwise a plain window at the first `PreInit`; the renderer presents last in `Render`, sets vsync (`Off`/`On`/`Adaptive`) and skips minimised windows while FenrirWindow sleeps; one main window keyed by `WindowId`; Window installs first and tears down last; closing the main window stops the app by default.

## Not yet specified

- **The rest of the animation spec:** clips and playback (sampling, looping, events in clips), pose blending (crossfades, layers, masks, and whether a blend tree or graph is in the first spec), skinning (GPU skinning from a bone-matrix buffer, bone limits per vertex), the animated-plus-simulated pose blend (going limp, powered ragdolls driving joint motors towards the animation) and the bone-to-body mapping as plain data, what C# gets, and an animation demo app. Graduates once the animation's home and the foundation's ECS model, assets and frame are decided.
- **Lighting and shadows:** more lights (point, spot, several directional), shadow maps, image-based lighting; extends the foundation's lit material.
- **Post-processing:** HDR and tonemapping, bloom, anti-aliasing; depends on how the frame's passes and render targets are decided.
- **Dynamic meshes:** meshes whose vertices change every frame (soft bodies, procedural geometry), with normals recomputed and stable indices and UVs; see `notes.md`.
- **Richer animation:** state machines or graphs, IK, root motion, morph targets.
- **Instancing and culling at scale.**
- **A render thread:** rendering a frame behind on its own thread, consuming the draw list as a snapshot (ADR-0019); with parallel recording, once the frame is CPU-bound.
- **Particles.**
- **Live redraw while a window is dragged or resized** on Windows, where the event pump blocks (SDL3's exposed event from an event watch); the first version freezes.
- **More input devices:** rumble, IME composition, touch and pen (SDL3 only, per ticket 03); join FenrirInput's types and feed when wanted.
- **Shader hot reload:** development builds run `FenrirShaderCompiler` as a child process on a changed file and reload its shader container (ADR-0018); with or after the foundation.
- **Golden-image tests:** whole-frame comparison with a tolerance metric, for the first feature family that analytic pixel probes cannot pin (shadows, post-processing); see ticket 20.
- **More asset loading:** `LoadAsync` with load states, a public loader registry for game-defined formats, a cgltf path for glTF if assimp's skins or clips prove loose, KTX2 and compressed textures, and a per-asset flag that drops the CPU copy after upload (ADR-0021).
- **Several windows:** the renderer drawing to more than one window (the editor), with one shared GL context made current per window; FenrirWindow's API is already keyed by `WindowId` (ADR-0022).

## Out of scope

- A second graphics backend: the seam must allow D3D, Vulkan or Metal, but none is built.
- macOS: until a Metal backend exists.
- The editor: a prototype of its own, as is ImGui in it; only what the renderer offers a UI library is in scope.
- Input mapping (actions and bindings): as on the physics map.
- 2D and sprites, game UI beyond debug text, terrain, ray tracing, VR, audio.
- An asset database with cooking and hot reload of art.
- The physics side of ragdolls and soft bodies: bodies and joints built from a skeleton, powered ragdolls' motors, soft-body simulation; they stay on the physics map (`.scratch/fenrir-physics/map.md`).

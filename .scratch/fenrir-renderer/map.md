# FenrirRenderer

Label: wayfinder:map

## Destination

A set of specs, one feature directory each (`.scratch/fenrir-renderer-<name>/spec.md`, so each spec's tickets sit beside it), each ready for `/to-tickets`, plus ADRs for the hard-to-reverse calls: where the graphics seam sits and whether the backend is picked at compile time or at runtime, who owns the graphics context and the swapchain or surface, who owns input, and the shader language (and any other call that proves hard to reverse). The first is the **foundation spec**: the graphics seam over OpenGL, FenrirWindow over its windowing library, enough input to drive the demos, the renderer's core components and systems, meshes, materials and shaders (an unlit material and one simple lit material, with one directional light and ambient, no shadows), cameras, the frame and its passes (skybox and background included), debug lines and text, what the renderer offers a UI library drawn over it, the renderer's scripting extension, and the demo apps: a shared demo scaffold, a renderer demo app, the physics scenes rewritten as physics demo apps on the new stack, and the old `examples/DemoApp` deleted. The foundation spec is ticketable as soon as its own decisions close. Then one spec per feature family, each built on the foundation: **animation and skinning** first (skeletons with bind poses, clips and playback, pose blending, skinned meshes drawn from bone transforms, blending an animated pose with a simulated ragdoll pose, as plain data; the bone-to-body mapping is the physics map's ragdoll spec's, per ADR-0028), then whatever else the map turns up.

## Notes

- **FenrirPhysics is the pattern.** Its facade is what these packages copy at a high level: `Install(App&, Config)` returns the owner of the package's process-wide state; game code configures it with plain-data components on entities, named by `Entity`, with no public backend handle; scene-scoped state is a scene resource; C# support is a scripting extension (ADR-0009) in the package, built only when scripting is on. (Its code wants a review and clean-up, which is not this map's work.)
- **Libraries are hidden at compile level.** As ADR-0010: no public header of FenrirRenderer, FenrirWindow, the input package or the animation package names or includes the library underneath (GL and its loader, GLFW or SDL, cgltf and ufbx (ADR-0031), the shader compiler); each links them `PRIVATE`. The graphics backends are private too, chosen at runtime behind a private graphics device (ADR-0016).
- **The graphics seam must allow D3D, Vulkan or Metal** to replace OpenGL without touching the code that calls the renderer. Only OpenGL is built.
- **Packages stay independent.** Physics produces plain data (bone poses, soft-body vertices) that rendering and animation read, and draws its debug output into FenrirDebugDraw (ADR-0025); physics never depends on them and they never depend on physics. Glue that joins them (a ragdoll's bodies to its skeleton) lives in app or demo code, or in the physics map's ragdoll spec. What other packages need from a renderer: `notes.md` beside this map.
- **The DemoApp is not a reference.** Everything in `examples/DemoApp` about GLFW, OpenGL, events, ImGui, its components and systems is placeholder, written fast; it is neither a model to follow nor something to stay compatible with. It is deleted once the demo apps replace it. `FenrirCamera` may be removed or reshaped to fit the ECS.
- **Demo apps, not one DemoApp.** Each feature area gets its own demo app on a shared scaffold. The ImGui editor is a prototype of its own and out of scope here; ImGui will later be replaced by the user's own GUI library, so the renderer offers a UI library a way to draw over it rather than building ImGui in.
- **Platforms:** Windows (MSVC and clang, Debug and Release) verified; Linux kept buildable but unverified; macOS out of scope until a Metal backend exists.
- **Conventions:** meters, Y-up, right-handed (as glm); single-precision floats, like the rest of the engine. In this map *component*, *system*, *event*, *entity*, *world transform* and *scene resource* carry their meanings from `GLOSSARY.md`.
- Skills: grilling tickets call `grilling` and `domain-modeling`; seam and module-shape questions also use `codebase-design`. Research tickets call `research` and put their findings on a `research/<name>` branch, pushed, never merged.
- Plan, don't do: tickets produce decisions, not code (spikes are throwaway, on `prototype/…` branches).
- Built specs are removed, as on the physics map: the commit that records a spec built deletes its directory.

## Decisions so far

<!-- one line per resolved ticket: [title](issues/NN-slug.md): gist -->

- [What do GLFW 3.4 and SDL3 each offer FenrirWindow?](issues/03-glfw-or-sdl3.md): equal on windowing basics; both fix the graphics API at window creation; SDL3 adds IME, rumble, touch, a header-free `HWND` and a Metal layer, at ~16x GLFW's size and build time; GLFW allows GL calls off the main thread, SDL3 does not; both zlib, both clean as `SYSTEM` includes.
- [How do engines import and own meshes, textures, shaders, skeletons and clips?](issues/06-asset-import-and-ownership.md): assimp reads 40+ formats into its own scene but is heavy and loose with glTF skins and clip timing; cgltf and fastgltf hand back raw glTF, ufbx covers FBX well, stb_image or libktx for textures; glTF carries skins, 4-weight sets, clips in seconds and PBR, and exported files are often wrong; Bevy and Godot both have one asset system with typed handles (ref-counted or generational), deduplicated by path, upload separate from load, procedural meshes in the same storage.
- [How do engines write shaders once for several graphics APIs?](issues/04-shader-languages-and-toolchains.md): GLSL costs nothing now and, written with explicit bindings and no loose uniforms, goes to SPIR-V later unchanged; GLSL → SPIR-V → SPIRV-Cross is the shared multi-backend route (bgfx, Filament, Godot); GL 4.6 SPIR-V loses names, so reflection moves to SPIR-V; HLSL needs DXC (glslang's HLSL front end is deprecated); Slang is strongest on variants but "limited" on GL; variants are `#define` bitmasks everywhere; all tools permissive and linkable `PRIVATE`.
- [How do engines model skeletons, clips, blending, skinning and ragdoll blending?](issues/07-how-engines-model-animation.md): bones as entities (Bevy, Unity) or arrays in one object (Godot, Unreal, ozz, Jolt), named by index or by name (names let clips be shared); blending in local space everywhere, from ozz's one weighted job to full graphs; GPU skinning in a vertex or compute shader, ozz CPU only; ragdolls map one body per bone with a constraint to the nearest mapped ancestor, blended per body (Unreal), per subtree (Godot) or as a graph node (EMotionFX); Jolt has `SkeletonMapper` and drive-to-pose; ozz (MIT) fits behind a seam but leaks SoA math, joint order and its own format.
- [How do engines build and submit a frame?](issues/05-how-engines-build-a-frame.md): render graphs pay off on explicit APIs and big frames; small engines use fixed passes (Godot builds a barrier graph below them); Bevy 0.20 swapped its render graph for ECS schedules; data leaves the ECS by direct reads, a per-frame snapshot or persistent proxies (the last two needed for a render thread); interpolation runs after the tick loop; GL calls come from one thread; 64-bit sort keys; debug draw is an immediate buffer rebuilt each frame; text from a glyph atlas (raster, SDF or MSDF); ImGui and RmlUi need only textures plus scissored textured triangles in an overlay pass.
- [Which OpenGL version and features should the backend target?](issues/02-which-opengl-to-target.md): every current NVIDIA, AMD and Intel driver on Windows and Linux reports GL 4.6 with DSA, clip control and SPIR-V; the explicit-style subset (DSA, immutable storage, persistent mapping, separate programs, samplers, clip control) is all ≤ 4.5; CI's llvmpipe is 4.5 on Ubuntu 24.04's Mesa; bindless is not portable; GL SPIR-V loses names and needs own reflection; glad 2's multi-context mode keeps GL out of public headers; headless CI needs Mesa (EGL surfaceless on Linux, Mesa's `opengl32.dll` on Windows).
- [How do other engines put a seam over graphics APIs?](issues/01-how-other-engines-seam-graphics-apis.md): most put a thin explicit-API-shaped seam (pipelines, binding groups, passes, command lists) right over the API, often with a higher layer above; only sokol selects purely at compile time, the rest at runtime with coarse crossings; GL is dropped (NVRHI, SDL3 GPU, O3DE), emulated under the explicit model (Diligent, wgpu, sokol, Filament), or kept out of the thin seam (Godot, bgfx); handles range from bare indices to generational ids and ref counts, destruction deferred by frame or fence; every library but SDL3 GPU has a native escape hatch; null backends test bookkeeping, golden images test pixels.
- [Where does the graphics seam go, and is the backend picked at compile time or at runtime?](issues/08-where-the-graphics-seam-goes.md): ADR-0016; a public renderer over a private graphics device shaped like the explicit APIs, OpenGL 4.6 (raised from 4.5 by ADR-0018) and an always-built null backend chosen at runtime in `RendererConfig`; commands recorded through per-pass encoders into a plain-data `CommandList` and replayed on `Submit`; typed generational handles, destruction deferred by frame; no escape hatch or tuning settings; UI libraries reach the renderer only through a public overlay that takes their own shaders and vertex layouts.
- [Which library sits behind FenrirWindow, GLFW or SDL3?](issues/09-glfw-or-sdl.md): ADR-0020; SDL3 3.4.x, static and `PRIVATE`, for IME, rumble, sensors, touch and pen that GLFW lacks; video, events, input, gamepad, haptic, hidapi and sensor built, audio, GPU, 2D render, camera, dialogs, tray, process and `SDL_main` off; OpenGL calls stay on the main thread (SDL3's rule), so a render thread waits for an explicit-API backend; switch if a GL render thread or SDL3's build cost forces it.
- [Who owns input: FenrirWindow or a FenrirInput package?](issues/10-who-owns-input.md): ADR-0017. FenrirInput, linking no library, owns input types, app-wide `Keyboard`/`Mouse`/`Gamepads` resources and input events; FenrirWindow feeds it through a public input feed in `PreUpdate`, and tests feed it the same way with no window. Polled state and `EventReader` events, both. Just-pressed edges follow the reading phase (since the last tick in `PreTick`/`Tick`/`PostTick`, since the last frame elsewhere). Events name their window, and mouse units are logical window coordinates. First version: keys (key code and scancode), text, mouse, cursor modes (FenrirWindow's) and gamepads. C# gets the same through an extension.
- [Which shader language do we write, and how is it compiled for each backend?](issues/12-shader-language.md): ADR-0018, amending ADR-0016's GL floor to 4.6; every shader is GLSL 460 with explicit `set`/`binding`/`location` and blocks only, compiled at build time by our own `FenrirShaderCompiler` (glslang, SPIRV-Reflect; never linked into the engine) into one versioned shader container per program; SPIR-V is the device's only shader input, GL 4.6 ingests it, Vulkan will take it unchanged and D3D12 and Metal get it through SPIRV-Cross; layouts declared in C++, checked against build-time reflection in debug builds; `#define` variants all built offline; `#include` against a shared engine directory; no hot reload yet; CI's GL tests need a Mesa newer than Ubuntu 24.04's.
- [How is a frame built and submitted?](issues/13-how-a-frame-is-built.md): ADR-0019; three layers (ECS facade, a renderer core with no ECS dependency, the private graphics device); a new `Render` phase after `PostUpdate` on the main thread reads the active scene into a plain-data draw list with 64-bit sort keys; a render graph compiled each frame, ordered by render stage then dependencies, with culling and pooled transients, designed as if explicit (aliasing, async compute, parallel recording, a render thread listed as waiting); foundation passes Opaque, Background, sorted Transparent, Debug, Output, Overlay into linear RGBA16F scene targets.
- [How are the renderer and window packages tested?](issues/20-how-the-renderer-is-tested.md): no ADR; OpenGL floor raised to 4.6 core (ADR-0016 amended, as ADR-0018 also requires); most tests on the null backend through the public interface and a `RendererProbe` (draw lists, handle lifetimes, deferred destruction), a smaller GL suite reading back small offscreen targets with analytic per-pixel probes and tolerances, no golden images yet; GL debug errors fail tests; the context is made the app's way (ticket 11), under `xvfb-run` if it needs a display; GL tests in Linux CI on llvmpipe 4.6 (newest Ubuntu runner, else a newer-Mesa PPA), skipped elsewhere without 4.6; input tested by feeding neutral window events, FenrirWindow thinly; demo apps get smoke runs on null and on llvmpipe.
- [How are meshes, textures, shaders, skeletons and clips loaded and owned?](issues/15-how-assets-are-loaded-and-owned.md): ADR-0021; a new FenrirAssets package owns plain CPU-side asset data (meshes, images, materials, skeletons, clips, shader containers, models with labelled sub-assets), no GPU code, depended on by renderer and animation; `AssetHandle<T>` is a plain generational id, each load owned by the app or a scene, freed when its last owner ends or on `Unload`, deduplicated by path; synchronous, main thread only, failures as diagnostics, stale handles skipped; assimp and stb_image behind a private compile-time importer seam; procedural meshes through `Add`/`Replace`; the renderer uploads in its own prepare step keyed by handle and revision, CPU copy kept; one asset root in `AssetsConfig`.
- [Who owns the graphics context and the swapchain or surface?](issues/11-who-owns-the-graphics-context.md): ADR-0022; FenrirWindow makes the window and the API's surface SDL creates (the GL context today), the backend owns the swapchain or the use of the context; the core's private abstract `GraphicsSurface`, adapted from FenrirWindow by the ECS facade alone; `Renderer::Install` requests the main window's surface (4.6 core, sRGB colour backbuffer) and fails if it can't be made, otherwise a plain window at the first `PreInit`; the renderer presents last in `Render`, sets vsync (`Off`/`On`/`Adaptive`) and skips minimised windows while FenrirWindow sleeps; one main window keyed by `WindowId`; Window installs first and tears down last; closing the main window stops the app by default.
- [How is rendering modelled in the ECS?](issues/14-rendering-in-the-ecs.md): ADR-0023; one `MeshRenderer` (mesh, material, `visible`) per drawn mesh, several materials as child entities, as Bevy and Unity DOTS do; empty or stale meshes skipped, missing materials drawn with a magenta fallback; read directly from the active scene each `Render` with `GetWorldMatrix` per item; no renderer scene resource, GPU resources keyed by asset handle and revision; `Renderer::Install` owns core and device after assets and the window; `GetWorldBounds` and `Stats` read back; `SpawnModel` in the renderer facade.
- [What are materials, and how do they bind shaders and parameters?](issues/17-materials-and-shaders.md): ADR-0024; a material is one shared plain-data `MaterialData` asset (shader, blend mode `Opaque`/`Masked`/`AlphaBlend`/`Additive`, `doubleSided`, named parameters), edited through FenrirAssets with a revision bump, no per-entity overrides; sets 0 frame (lights), 1 view, 2 material, 3 draw, set 2's layout and names reflected from the shader container (narrowing ADR-0018), the rest declared; `builtin:unlit` and `builtin:lit` (metallic-roughness GGX, one `DirectionalLight` component, an `AmbientLight` scene resource, plain-multiplier intensities); the renderer picks variants (`ALPHA_MASK`, `SKINNED` reserved), default textures instead of keys; user shaders are full programs on engine includes; imported materials map to the built-ins; pipelines made lazily and cached.
- [How are debug lines and text drawn?](issues/18-debug-lines-and-text.md): ADR-0025; a new FenrirDebugDraw package (no GPU code, every build) owns a `DebugDraw` scene resource that game code, C# and FenrirPhysics draw into and FenrirRenderer reads; Unreal-sized immediate calls (wire and solid shapes, pixel thickness, depth tested or on top) with durations (once, which in a tick phase means until the next tick; seconds; `Forever`), named groups and an optional `relativeTo` entity; screen text, keyed on-screen messages in the overlay and constant-size world text in the `Debug` stage, from one built-in SDF font (stb_truetype); FenrirDebugDraw tessellates into plain batches, the renderer uploads them; `Fenrir::Colour` (linear floats) joins FenrirMath; physics's span of packed lines is replaced by drawing into its scene's `DebugDraw`.
- [How do the new libraries join the build?](issues/21-how-libraries-join-the-build.md): no ADR; SDL3, assimp, stb, glslang and SPIRV-Reflect as pinned submodules under the package that links them, static and `PRIVATE`, with Jolt's `libs/CMakeLists.txt` pattern (directory flags cleared, `SYSTEM`, dynamic MSVC runtime, Debug and Release, unused parts off); glad 2's GL 4.6 loader generated once and checked in, no Python in the build; root options `FENRIR_ENABLE_ASSETS` and `FENRIR_ENABLE_RENDERER`, both ON, renderer without assets a configure error, FenrirInput always built; `FENRIR_BUILD_EXAMPLES` means the new demo apps and CI turns it on, the old DemoApp moves behind `FENRIR_BUILD_LEGACY_DEMOAPP` (OFF) untouched until deleted; later libraries (animation, fonts, SPIRV-Cross) join by the same rule.
- [How are cameras, viewports and render targets modelled?](issues/16-cameras-viewports-and-render-targets.md): ADR-0026; a `Camera` component oriented by its entity's world transform (−Z forward), perspective (vertical FOV, near, infinite far) or orthographic, drawn with reversed-Z in [0,1]; every enabled camera in the active scene draws one view, ordered by `order`, into a normalised top-left viewport of its target, a window or a pixel-less render-target `AssetHandle<Image>` that materials and the overlay sample; a `Sky` scene resource (colour or cubemap) a camera can override with a colour; `ScreenPointToRay`, `WorldToScreenPoint` and `CameraAt` on `Renderer`, computed on call; screen text once per window, `drawDebug` per camera; `FenrirCamera` deleted with the legacy DemoApp.
- [What does the renderer offer a UI library drawn over it?](issues/19-ui-library-over-the-renderer.md): ADR-0027; three responsibilities: a new plain-data FenrirDraw2D package (target-neutral `DrawList2D`: vertex and index bytes, value-type 2D pipeline descriptions with the UI's own shaders and vertex layouts, commands with image slots, local scissors and parameter bytes, in local logical coordinates), FenrirRenderer's one 2D render feature drawing it into a 2D target, and a future painter or UI framework producing it; only the window overlay is built (`Overlay::Submit(WindowId, layer, list)`, layers in order, debug screen text on top, `builtin:2d`); linear blending by default with separate colour and alpha factors per blend mode and opt-in gamma; FenrirInput's input routers consume events before game state and readers, with per-control ownership, per-window input claims and cancelled releases; FenrirWindow adds cursor shapes, clipboard, focus and claim-driven text input; ImGui is an optional demo-scaffold router.
- [Where does animation live: its own package or inside the renderer?](issues/24-where-animation-lives.md): ADR-0028; bones are arrays, not entities: immutable `SkeletonData`, a per-instance `SkeletonPose` (base and final local poses, model-space matrices, palette) in a new FenrirSkeleton package that owns lookup, pose modifiers' entry points, finalisation and `BoneAttachment`; a new FenrirAnimation (own glm runtime, not ozz) writes only the base pose, clips binding bones by name; the renderer depends on FenrirSkeleton alone and skins from its palette (`SKINNED`, four weights); modifiers aim in local, model or world space, one weighted override first; stages in `PostUpdate` for now; `SpawnNodes` in FenrirAssets' facade under `SpawnModel` (ADR-0023 amended); headless animates; model space relative to the skeleton entity, `GetBoneWorldMatrix` = its world × bone model, skinned meshes drawn with its world matrix, one bind space baked by the importer; the bone-to-body mapping moves to the physics map; graduated into tickets 26–34.
- [How are skeleton instances spawned, owned and read?](issues/26-skeleton-instances.md): ADR-0031; `SkeletonPose` is a plain blittable `{ AssetHandle<SkeletonData> }` naming an instance whose arrays a FenrirSkeleton `SkeletonPoses` scene resource owns, reconciled each frame without hooks, with `Ready`/`Unavailable`/`Missing` states, const spans and `EditBasePose`; cgltf (glTF) and ufbx (FBX, OBJ) replace assimp behind ADR-0021's seam; the `Model` keeps the whole source tree and identities; bones are joints, the nodes between them, animated empty children and FBX `LimbNode`s, everything else an ordinary node attached by `BoneAttachment`; skins grouped by joint identity, merged only through a checked conversion; owners from `skin.skeleton` or the nearest non-bone ancestor, synthetic owners when skeletons collide; one bind space, `v_world = W(owner) × M_model × B × v` with rest and bind kept apart; partial loads fail the smallest unit; `SpawnNodes`, `SpawnSkeletons` and two `SpawnModel` wrappers; clip channels keep source identity and engine name.
- [What does the renderer's scripting extension give C#?](issues/22-renderer-scripting-extension.md): ADR-0029, amending ADR-0009; one extension per package (`Fenrir.Assets`, `Fenrir.Renderer`, `Fenrir.Window`, `Fenrir.Input`, each with a `<Pkg>Scripting` library, built with scripting and its package); a FenrirScripting prerequisite adds native resources (plain-data resources such as `Sky`, `AmbientLight` and `InputClaims` mirrored through `Resources.Get<T>()`, while input devices stay native-function facades with C++'s phase-following edges), the change buffer on the call context (so C# `SpawnModel` works), and a `Fenrir.Math` contract; `MeshRenderer`, `Camera` (three `[TaggedUnion]`s) and `DirectionalLight` are writable mirrors; `AssetHandle<T>` with a phantom type, `Assets.Load` by path with the active scene as default owner, procedural meshes, render-target and pixel images; materials created, cloned and set by name; the renderer's read-backs and `SpawnModel`; window size, scale, cursor, clipboard and events; input events through `EventReader`; physics's no-op rules.
- [How are the demo apps split, and what does each show?](issues/23-demo-apps.md): no ADR; RendererDemo, ScriptingDemo and PhysicsDemo (every physics family as scenes of one app; AnimationDemo from ticket 34) on a demo scaffold: `FenrirDemoScaffold` under `examples/DemoScaffold/`, `fenrir_add_demo_app` and a `Fenrir.Demo` C# assembly, installing the packages with a free-fly camera, an ordered scene list on PageUp/PageDown, F1 help in debug screen text, F3 camera, a scene-click ray and an optional ImGui overlay; smoke runs keep `FENRIR_DEMO_SCENE`/`FENRIR_DEMO_KEYS` and add `FENRIR_DEMO_SMOKE` and `FENRIR_DEMO_BACKEND`, CTest on null and llvmpipe; RendererDemo shows materials, cameras and targets, sky, debug draw and overlay (C# twins of materials and debug draw), each scene added by its foundation ticket; the scripting showcase and the physics scenes ported faithfully with their hand-check lists; the ImGui editor not ported; the legacy DemoApp deleted by the foundation spec's last ticket.
- [Spike: a lit mesh, a camera, a skybox and debug lines through the proposed seam](issues/25-spike-lit-mesh-through-the-seam.md): works on `prototype/fenrir-renderer-spike` (user-verified by eye; clang Debug and Release; GL and null give the same frame; MSVC and Linux unverified); GL and SDL do not leak and the device's shape survives GL; lessons: glslang takes `set` only as Vulkan GLSL, so the compiler rewrites a GL copy (bindings flattened per resource kind as set x 4 + binding, `gl_BaseInstance` instead of `gl_InstanceIndex`); GL's clip origin is set per pass (upper-left for textures, lower-left for the window, winding unchanged); std140 blocks hold no defaults, so ADR-0024's GLSL default goes to ticket 41; FenrirApp needs app-wide resources; main-thread systems must be sequential; `Install` needs a failure shape.

## Not yet specified

- **The animation spec** (`.scratch/fenrir-renderer-animation/spec.md`): graduated into tickets 26–34 by ADR-0028; written once they close.
- **Lighting and shadows:** more lights (point, spot, several directional), shadow maps, image-based lighting; extends the foundation's lit material.
- **Post-processing:** HDR and tonemapping, bloom, anti-aliasing; depends on how the frame's passes and render targets are decided.
- **Dynamic meshes:** meshes whose vertices change every frame (soft bodies, procedural geometry), with normals recomputed and stable indices and UVs; see `notes.md`.
- **Richer animation:** state machines or graphs, IK, root motion, morph targets; ordered pose modifiers beyond the first weighted override, animation in fixed ticks, crowd features (level-of-detail updates, reduced update rates, instanced skinning), ozz or ACL behind a private seam if sampling or clip memory shows in a profile, and the editor's virtual bone hierarchy (ADR-0028).
- **More scripting:** resources defined in C# by script assemblies, and resource system parameters (`Res<T>`) over `Resources.Get` (ADR-0029).
- **Instancing and culling at scale**, and a per-frame memo of ancestor world matrices if `GetWorldMatrix` per item shows in a profile (ADR-0023).
- **A render thread:** rendering a frame behind on its own thread, consuming the draw list as a snapshot (ADR-0019); with parallel recording, once the frame is CPU-bound.
- **Particles.**
- **Live redraw while a window is dragged or resized** on Windows, where the event pump blocks (SDL3's exposed event from an event watch); the first version freezes.
- **More input devices:** rumble, IME composition, touch and pen (SDL3 only, per ticket 03); join FenrirInput's types and feed when wanted; IME composition updates, commit, caret and cancellation have room reserved by ADR-0027.
- **UI and 2D painting:** a FenrirPainter (shapes, paths, text, images, borders, clipping) and a retained UI framework (layout, CSS-like styling, focus) over FenrirDraw2D, C# authoring through the managed host; image targets (UI painted into a render-target image that a material samples: creation, resizing, clearing, graph order, premultiplied storage) and world-space targets (depth and transforms from the target); dynamic images with sub-rectangle updates for atlases; raising the first version's 4 texture slots and 128 parameter bytes (ADR-0027).
- **Shader hot reload:** development builds run `FenrirShaderCompiler` as a child process on a changed file and reload its shader container (ADR-0018); with or after the foundation.
- **Golden-image tests:** whole-frame comparison with a tolerance metric, for the first feature family that analytic pixel probes cannot pin (shadows, post-processing); see ticket 20.
- **More asset loading:** `LoadAsync` with load states, a public loader registry for game-defined formats, import options (an *import as unskinned* fallback, ADR-0031), compatible skeleton reloads that keep the current pose, KTX2 and compressed textures, and a per-asset flag that drops the CPU copy after upload (ADR-0021).
- **Several windows:** the renderer drawing to more than one window (the editor), with one shared GL context made current per window; FenrirWindow's API is already keyed by `WindowId` (ADR-0022).
- **Inherited visibility:** hiding a spawned hierarchy as one; `MeshRenderer::visible` hides only its own entity (ADR-0023).
- **Richer materials:** per-entity material overrides, a surface-function model for user shaders, and physical light units with exposure (ADR-0024); with the lighting and post-processing families.
- **More debug drawing:** drawing a loaded mesh asset (`Mesh(AssetHandle<Mesh>)`, which ties FenrirDebugDraw to FenrirAssets), loaded fonts, and durations in game time once the engine has a pause or time scale (ADR-0025).
- **More camera features:** depth-only layering (a weapon camera over the world camera in one viewport), render scale, culling layers per camera, per-viewport screen text, HDR render targets, and drawing a scene that is not active (an editor's scene view) (ADR-0026).

## Out of scope

- A second graphics backend: the seam must allow D3D, Vulkan or Metal, but none is built.
- macOS: until a Metal backend exists.
- The editor: a prototype of its own, as is ImGui in it; only what the renderer offers a UI library is in scope.
- Input mapping (actions and bindings): as on the physics map.
- 2D and sprites, game UI beyond debug text, terrain, ray tracing, VR, audio.
- An asset database with cooking and hot reload of art.
- The physics side of ragdolls and soft bodies: bodies and joints built from a skeleton, powered ragdolls' motors, soft-body simulation; they stay on the physics map (`.scratch/fenrir-physics/map.md`).

| Godot | Two seams: `RenderingDeviceDriver` thin under `RenderingDevice`; `RendererCompositor` high-level | Runtime, at startup | Yes, but only as a separate high-level renderer | `RID` above, `uint64` driver ids below | `RasterizerDummy` compositor |

## 1. Altitude: what sits above and below the line

Two altitudes recur. **Thin RHIs** expose GPU objects and commands (buffers, textures, pipelines, binding groups, command lists, passes) and leave the renderer above them. **High-level seams** put a whole renderer, or a whole frame of draw submissions, behind the line, with one implementation per API. Several projects have both, one above the other.

### Thin, explicit-API-shaped

- **NVRHI.** Its guide calls the model "mostly a blend between DX11 and DX12, with a flavor of Vulkan": pipeline state objects, graphics state structs, binding layouts and sets ([ProgrammingGuide.md L3–L5](https://github.com/NVIDIA-RTX/NVRHI/blob/6b96fb03e07539f08327aea76c56d55f1de9d906/doc/ProgrammingGuide.md#L3-L5)). `IDevice` creates resources and executes command lists; draw calls live on `ICommandList` ([L19–L40](https://github.com/NVIDIA-RTX/NVRHI/blob/6b96fb03e07539f08327aea76c56d55f1de9d906/doc/ProgrammingGuide.md#L19-L40)). Above it the library tracks resource states and lifetimes for you ([README L9–L19](https://github.com/NVIDIA-RTX/NVRHI/blob/6b96fb03e07539f08327aea76c56d55f1de9d906/README.md#L9-L19)). It does not create the native device; the application does and wraps it ([ProgrammingGuide.md L23–L28](https://github.com/NVIDIA-RTX/NVRHI/blob/6b96fb03e07539f08327aea76c56d55f1de9d906/doc/ProgrammingGuide.md#L23-L28)).
- **Diligent.** A "low-level graphics API" with D3D11, D3D12, OpenGL/GLES, Vulkan and WebGPU backends ([README L3–L4](https://github.com/DiligentGraphics/DiligentCore/blob/4678e4393cd0194f3c56e5d6611221d46497cc95/README.md#L3-L4)). Shaders bind through static, mutable and dynamic variables on a PSO and a shader resource binding (SRB) object ([README L514–L545](https://github.com/DiligentGraphics/DiligentCore/blob/4678e4393cd0194f3c56e5d6611221d46497cc95/README.md#L514-L545)); state transitions are explicit or automatic per call ([DeviceContext.h L248–L273](https://github.com/DiligentGraphics/DiligentCore/blob/4678e4393cd0194f3c56e5d6611221d46497cc95/Graphics/GraphicsEngine/interface/DeviceContext.h#L248-L273)).
- **SDL3 GPU.** "3D graphics and compute support, in the style of Metal, Vulkan, and Direct3D 12": devices, shaders, buffers, textures, samplers, graphics pipelines, command buffers, render and compute passes ([SDL_gpu.h L24–L117](https://github.com/libsdl-org/SDL/blob/829a65d769d935c4852f8159e964312c0957260a/include/SDL3/SDL_gpu.h#L24-L117)). It calls itself "a relatively thin layer over the underlying graphics API" ([L205–L212](https://github.com/libsdl-org/SDL/blob/829a65d769d935c4852f8159e964312c0957260a/include/SDL3/SDL_gpu.h#L205-L212)) and deliberately targets a common feature set so "the app won't have to branch itself by querying feature support" ([L145–L148](https://github.com/libsdl-org/SDL/blob/829a65d769d935c4852f8159e964312c0957260a/include/SDL3/SDL_gpu.h#L145-L148)).
- **sokol_gfx.** Buffers, images, samplers, shaders, pipelines, views and passes, with no exposed command buffers: calls go straight to an implicit per-frame context, and `sg_apply_pipeline`, `sg_apply_bindings` and `sg_draw` must be inside a pass ([sokol_gfx.h L489–L515](https://github.com/floooh/sokol/blob/efeb77603e24daea7d1dd6445b9358bb5d82533b/sokol_gfx.h#L489-L515)). It requires the 3D context or device and the swapchain to be provided from outside ([L116–L135](https://github.com/floooh/sokol/blob/efeb77603e24daea7d1dd6445b9358bb5d82533b/sokol_gfx.h#L116-L135)).
- **wgpu, two layers in one stack.** `wgpu-hal` is "a cross-platform unsafe graphics abstraction" with "no overhead for validation or tracking"; callers record explicit barriers and pass pipeline layouts ([wgpu-hal/src/lib.rs L1–L57](https://github.com/gfx-rs/wgpu/blob/3050396df223f189925c5a7d9d81c0ef219b6117/wgpu-hal/src/lib.rs#L1-L57)). `wgpu-core` sits above it and does exhaustive validation, state and lifetime tracking, because "implementing this separately for each backend is infeasible" ([L151–L181](https://github.com/gfx-rs/wgpu/blob/3050396df223f189925c5a7d9d81c0ef219b6117/wgpu-hal/src/lib.rs#L151-L181)). The public `wgpu` crate is the WebGPU API over `wgpu-core`.
- **Godot `RenderingDeviceDriver`.** The lowest seam: minimal validation, ids of 0 for errors, some enums "follow Vulkan values/layout", and no backwards calls into `RenderingDevice` ([rendering_device_driver.h L33–L46](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/servers/rendering/rendering_device_driver.h#L33-L46)). It has pure virtuals for buffers, uniform sets, pipeline barriers, render passes and pipelines ([L195](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/servers/rendering/rendering_device_driver.h#L195), [L398](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/servers/rendering/rendering_device_driver.h#L398), [L542](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/servers/rendering/rendering_device_driver.h#L542), [L682](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/servers/rendering/rendering_device_driver.h#L682), [L711](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/servers/rendering/rendering_device_driver.h#L711)). `RenderingDevice` sits on top with RIDs, validation and a `RenderingDeviceGraph` that places barriers ([rendering_device.h L1762](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/servers/rendering/rendering_device.h#L1762), [rendering_device_graph.h L49–L137](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/servers/rendering/rendering_device_graph.h#L49-L137)). The docs say it "presents a similar level of abstraction as WebGPU" ([Internal rendering architecture, "RenderingDevice abstraction"](https://docs.godotengine.org/en/stable/engine_details/architecture/internal_rendering_architecture.html)).
- **O3DE Atom RHI.** A `Factory` interface creates buffers, pools, images, devices, fences and also a `FrameGraphCompiler` and `FrameGraphExecuter` per API ([Factory.h L63–L161](https://github.com/o3de/o3de/blob/2462b90ee389939336931a14e234fc4e3b4cd534/Gems/Atom/RHI/Code/Include/Atom/RHI/Factory.h#L63-L161)). Above the objects, the RHI owns a frame graph of scopes and attachments, from which lifetimes and usage chains are derived ([FrameGraph.h L33–L60](https://github.com/o3de/o3de/blob/2462b90ee389939336931a14e234fc4e3b4cd534/Gems/Atom/RHI/Code/Include/Atom/RHI/FrameGraph.h#L33-L60)). Render passes enter it as `ScopeProducer`s that implement `SetupFrameGraphDependencies`, `CompileResources` and `BuildCommandList` ([ScopeProducer.h L17–L23](https://github.com/o3de/o3de/blob/2462b90ee389939336931a14e234fc4e3b4cd534/Gems/Atom/RHI/Code/Include/Atom/RHI/ScopeProducer.h#L17-L23)).
- **Unreal RHI.** `FDynamicRHI` is "the interface which is implemented by the dynamically bound RHI", with methods such as `RHICreateGraphicsPipelineState` and `RHIGetDefaultContext` ([FDynamicRHI docs](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/RHI/FDynamicRHI)). The render thread enqueues "platform-agnostic graphical commands" into an `RHICommandList`; the RHI thread translates them through a per-API `IRHICommandContext` ([Parallel Rendering Overview, "Threading Overview" and "Graphical Commands and the Command List"](https://dev.epicgames.com/documentation/en-us/unreal-engine/parallel-rendering-overview-for-unreal-engine)).

### High-level: a frame, or a whole renderer, per API

- **bgfx.** The public API is draw submission: state flags, views and `submit(view, program)`, with optional `Encoder`s for multithreaded submission ([bgfx.h L4373–L4385](https://github.com/bkaradzic/bgfx/blob/21a5cf8fc00888103f97c9ea87ed8a8b4040fb2f/include/bgfx/bgfx.h#L4373-L4385), `Encoder::setState` and `Encoder::submit` at [L1360](https://github.com/bkaradzic/bgfx/blob/21a5cf8fc00888103f97c9ea87ed8a8b4040fb2f/include/bgfx/bgfx.h#L1360) and [L1833](https://github.com/bkaradzic/bgfx/blob/21a5cf8fc00888103f97c9ea87ed8a8b4040fb2f/include/bgfx/bgfx.h#L1833)). Below the line, each backend implements `RendererContextI`: create and destroy calls per resource type plus one `submit(Frame*, ...)` that renders a whole recorded frame ([bgfx_p.h L5956–L6008](https://github.com/bkaradzic/bgfx/blob/21a5cf8fc00888103f97c9ea87ed8a8b4040fb2f/src/bgfx_p.h#L5956-L6008)). So each backend owns the loop over sorted draws, its own state caching and its own pipeline building.
- **Filament.** The public API (`Engine`, `Renderer`, `View`, `Material`) is a renderer; the backend is private (`include/private/backend`). Its `Driver` interface is generated from one macro list, `DriverAPI.inc` ([L17–L54](https://github.com/google/filament/blob/a84309371cca4cbe20efd79e0033ad19849b3c59/filament/backend/include/private/backend/DriverAPI.inc#L17-L54)). The list is thin and explicit-shaped (programs, descriptor set layouts, `beginRenderPass`, `bindPipeline`, `bindDescriptorSet`, `draw2`) ([L326](https://github.com/google/filament/blob/a84309371cca4cbe20efd79e0033ad19849b3c59/filament/backend/include/private/backend/DriverAPI.inc#L326), [L356](https://github.com/google/filament/blob/a84309371cca4cbe20efd79e0033ad19849b3c59/filament/backend/include/private/backend/DriverAPI.inc#L356), [L576–L590](https://github.com/google/filament/blob/a84309371cca4cbe20efd79e0033ad19849b3c59/filament/backend/include/private/backend/DriverAPI.inc#L576-L590), [L689–L702](https://github.com/google/filament/blob/a84309371cca4cbe20efd79e0033ad19849b3c59/filament/backend/include/private/backend/DriverAPI.inc#L689-L702)). Filament thus has a thin seam, but hides it behind a high-level public one.
- **Godot `RendererCompositor`.** Above `RenderingDevice`, Godot has a second seam: an abstract `RendererCompositor` with scene, mesh-storage and texture-storage interfaces, `begin_frame` and `blit_render_targets_to_screen` ([renderer_compositor.h L52–L82](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/servers/rendering/renderer_compositor.h#L52-L82)). The Forward+ and Mobile renderers implement it on `RenderingDevice`; the OpenGL renderer `RasterizerGLES3` implements it directly ([rasterizer_gles3.h L53](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/drivers/gles3/rasterizer_gles3.h#L53)). See section 3.
- **Bevy.** Bevy's renderer is the layer above wgpu; it runs in a separate `RenderApp` sub-app ([lib.rs L380](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_render/src/lib.rs#L380)), optionally on its own thread one frame behind simulation ([pipelined_rendering.rs L99–L110](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_render/src/pipelined_rendering.rs#L99-L110)). It has no seam of its own under it: wgpu is the seam.

## 2. Selection: compile time or runtime

### Compile time

- **sokol_gfx** is the one pure compile-time design. The implementation file defines exactly one of `SOKOL_GLCORE`, `SOKOL_GLES3`, `SOKOL_D3D11`, `SOKOL_METAL`, `SOKOL_WGPU`, `SOKOL_VULKAN` or `SOKOL_DUMMY_BACKEND` ([sokol_gfx.h L18–L38](https://github.com/floooh/sokol/blob/efeb77603e24daea7d1dd6445b9358bb5d82533b/sokol_gfx.h#L18-L38)), and it is an error to define none ([L6314–L6315](https://github.com/floooh/sokol/blob/efeb77603e24daea7d1dd6445b9358bb5d82533b/sokol_gfx.h#L6314-L6315)). Each public call dispatches through `#if` blocks to `_sg_gl_*`, `_sg_mtl_*` and so on. Cost: no virtual calls and dead backends are not compiled; but one binary runs one API, and shaders must be provided for that API.
- **wgpu-hal** uses "static dispatch": the traits "are not generally object-safe", and a caller picks a concrete `vulkan::Api` or `metal::Api` ([wgpu-hal/src/lib.rs L34–L38](https://github.com/gfx-rs/wgpu/blob/3050396df223f189925c5a7d9d81c0ef219b6117/wgpu-hal/src/lib.rs#L34-L38)). Backends are also cargo features (`dx12`, `metal`, `vulkan`, `gles`, `noop`) ([wgpu/Cargo.toml L50–L98](https://github.com/gfx-rs/wgpu/blob/3050396df223f189925c5a7d9d81c0ef219b6117/wgpu/Cargo.toml#L50-L98)).

### Runtime

- **Function tables in C.** bgfx keeps an array of `{create, destroy, name, supported}` per `RendererType`, filled with each backend's `rendererCreate` or a no-op when the backend is compiled out ([bgfx.cpp L3650–L3669](https://github.com/bkaradzic/bgfx/blob/21a5cf8fc00888103f97c9ea87ed8a8b4040fb2f/src/bgfx.cpp#L3650-L3669)); the user picks with `Init::type`, or `Count` for the platform default ([bgfx.h L789–L790](https://github.com/bkaradzic/bgfx/blob/21a5cf8fc00888103f97c9ea87ed8a8b4040fb2f/include/bgfx/bgfx.h#L789-L790)). SDL's `SDL_GPUDevice` is a struct of function pointers filled by a backend ([SDL_sysgpu.h L666–L672](https://github.com/libsdl-org/SDL/blob/829a65d769d935c4852f8159e964312c0957260a/src/gpu/SDL_sysgpu.h#L666-L672)), chosen from a compiled-in `backends[]` list of `SDL_GPUBootstrap`s ([SDL_gpu.c L314–L328](https://github.com/libsdl-org/SDL/blob/829a65d769d935c4852f8159e964312c0957260a/src/gpu/SDL_gpu.c#L314-L328), [SDL_sysgpu.h L1193–L1198](https://github.com/libsdl-org/SDL/blob/829a65d769d935c4852f8159e964312c0957260a/src/gpu/SDL_sysgpu.h#L1193-L1198)). SDL picks the backend from the shader formats the app says it can provide, or by name ([SDL_gpu.h L119–L130](https://github.com/libsdl-org/SDL/blob/829a65d769d935c4852f8159e964312c0957260a/include/SDL3/SDL_gpu.h#L119-L130), [L2379–L2389](https://github.com/libsdl-org/SDL/blob/829a65d769d935c4852f8159e964312c0957260a/include/SDL3/SDL_gpu.h#L2379-L2389)).
- **Abstract C++ interfaces.**
  - bgfx: `RendererContextI` (above). One virtual call per resource operation and one per frame (`submit`), so the per-draw loop runs inside the backend without virtual calls.
  - Diligent: COM-style interfaces with per-API factories (`GetEngineFactoryD3D12()` and so on). Statically linked or loaded as DLLs with `LoadGraphicsEngineD3D12()` ([README L79–L170](https://github.com/DiligentGraphics/DiligentCore/blob/4678e4393cd0194f3c56e5d6611221d46497cc95/README.md#L79-L170)). Device types are an enum ([GraphicsTypes.h L1609–L1617](https://github.com/DiligentGraphics/DiligentCore/blob/4678e4393cd0194f3c56e5d6611221d46497cc95/Graphics/GraphicsEngine/interface/GraphicsTypes.h#L1609-L1617)).
  - NVRHI: `IDevice`, with one `createDevice` per API in its own header and library (`nvrhi_d3d12`, `nvrhi_vk`) ([README L64–L74](https://github.com/NVIDIA-RTX/NVRHI/blob/6b96fb03e07539f08327aea76c56d55f1de9d906/README.md#L64-L74), [ProgrammingGuide.md L23–L28](https://github.com/NVIDIA-RTX/NVRHI/blob/6b96fb03e07539f08327aea76c56d55f1de9d906/doc/ProgrammingGuide.md#L23-L28)).
  - Godot: virtual `RenderingDeviceDriver` (above), with the driver picked from project settings or `--rendering-driver`; since Godot 4.4 a failed Vulkan falls back to D3D12 and then to the Compatibility (OpenGL) renderer ([Overview of renderers](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html)).
  - O3DE: a backend gem registers its `Factory`; with several available, a priority decides ([Factory.h L53–L69, L111–L112](https://github.com/o3de/o3de/blob/2462b90ee389939336931a14e234fc4e3b4cd534/Gems/Atom/RHI/Code/Include/Atom/RHI/Factory.h#L53-L112)).
  - Filament: `Engine::create(Backend)` with `DEFAULT`, `OPENGL`, `VULKAN`, `METAL`, `WEBGPU` or `NOOP` ([Engine.h L648](https://github.com/google/filament/blob/a84309371cca4cbe20efd79e0033ad19849b3c59/filament/include/filament/Engine.h#L648), [DriverEnums.h L179–L186](https://github.com/google/filament/blob/a84309371cca4cbe20efd79e0033ad19849b3c59/filament/backend/include/backend/DriverEnums.h#L179-L186)). The macro list generates the virtual `Driver` methods and the command-stream marshalling from one source ([DriverAPI.inc L20–L39](https://github.com/google/filament/blob/a84309371cca4cbe20efd79e0033ad19849b3c59/filament/backend/include/private/backend/DriverAPI.inc#L20-L39)).
  - Unreal: `FDynamicRHI` subclasses are created by an `IDynamicRHIModule::CreateRHI` and stored in the global `GDynamicRHI` ([FDynamicRHI docs, `Init`](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/RHI/FDynamicRHI)).
- **wgpu above hal goes dynamic.** `wgpu-core` stores `Box<dyn hal::DynDevice>` ([device/resource.rs L321](https://github.com/gfx-rs/wgpu/blob/3050396df223f189925c5a7d9d81c0ef219b6117/wgpu-core/src/device/resource.rs#L321)) through object-safe `Dyn*` wrappers ([wgpu-hal/src/dynamic/mod.rs L1–L34](https://github.com/gfx-rs/wgpu/blob/3050396df223f189925c5a7d9d81c0ef219b6117/wgpu-hal/src/dynamic/mod.rs#L1-L34)). The `wgpu` crate dispatches between `wgpu-core`, browser WebGPU and custom backends, and states that this "should optimize well if only one backend is compiled in" ([wgpu/src/dispatch.rs L1–L12](https://github.com/gfx-rs/wgpu/blob/3050396df223f189925c5a7d9d81c0ef219b6117/wgpu/src/dispatch.rs#L1-L12)). Bevy chooses among the compiled-in backends at runtime with `WgpuSettings::backends` ([settings.rs L28–L41](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_render/src/settings.rs#L28-L41)).

### What each costs, as the sources show it

- Runtime selection costs a virtual or function-pointer call per crossing. The designs keep crossings coarse: bgfx crosses once per frame for drawing; NVRHI says draws take "more structure filling" and fewer calls so it can cache state ([ProgrammingGuide.md L5](https://github.com/NVIDIA-RTX/NVRHI/blob/6b96fb03e07539f08327aea76c56d55f1de9d906/doc/ProgrammingGuide.md#L5)); Filament records commands into a `CommandStream` and replays them on its driver thread ([CommandStream.h L196–L258](https://github.com/google/filament/blob/a84309371cca4cbe20efd79e0033ad19849b3c59/filament/backend/include/private/backend/CommandStream.h#L196-L258)).
- Runtime selection also means every backend's shaders must ship together, or be generated at runtime (section 5).
- Compile-time selection (sokol) removes the indirection but makes "two backends in one binary" impossible, and makes the backend-specific shader and native-handle functions (`sg_gl_*`, `sg_d3d11_*`) appear or disappear by build.
- Only Diligent, bgfx and Godot keep OpenGL and an explicit API selectable in one binary. Diligent and bgfx do it behind one thin interface; Godot does it with two renderers.

## 3. OpenGL beside explicit APIs

Of the ten, **NVRHI, SDL3 GPU and O3DE Atom have no OpenGL backend**: NVRHI's `GraphicsAPI` is `D3D11`, `D3D12`, `VULKAN` ([nvrhi.h L154–L159](https://github.com/NVIDIA-RTX/NVRHI/blob/6b96fb03e07539f08327aea76c56d55f1de9d906/include/nvrhi/nvrhi.h#L154-L159)); SDL lists Vulkan, D3D12 and Metal ([SDL_gpu.h L214–L267](https://github.com/libsdl-org/SDL/blob/829a65d769d935c4852f8159e964312c0957260a/include/SDL3/SDL_gpu.h#L214-L267), and `src/gpu` holds only `d3d12`, `metal` and `vulkan`); Atom's RHI gems are `DX12`, `Vulkan`, `Metal` and `Null` (tree of `Gems/Atom/RHI` at the pinned commit). The others fit GL in three ways.

### a. The API is shaped like GL, and explicit backends build PSOs from loose state (bgfx)

- bgfx's draw state is a 64-bit flag word plus bindings per draw, not a pipeline object. The GL backend applies only what changed since the last draw (`changedFlags = currentState.m_stateFlags ^ newFlags`) ([renderer_gl.cpp L9435](https://github.com/bkaradzic/bgfx/blob/21a5cf8fc00888103f97c9ea87ed8a8b4040fb2f/src/renderer_gl.cpp#L9435)).
- The Vulkan backend hashes state, layouts and program into a key and looks it up in a `VkPipeline` cache, building on a miss ([renderer_vk.cpp L4835](https://github.com/bkaradzic/bgfx/blob/21a5cf8fc00888103f97c9ea87ed8a8b4040fb2f/src/renderer_vk.cpp#L4835), [L4501](https://github.com/bkaradzic/bgfx/blob/21a5cf8fc00888103f97c9ea87ed8a8b4040fb2f/src/renderer_vk.cpp#L4501)).
- Gives up: explicit APIs pay hashing and possible pipeline-creation hitches at draw time; the user cannot pre-build pipelines.

### b. The API is shaped like the explicit APIs, and GL emulates it (Diligent, wgpu, sokol, Filament)

- **Pipeline objects** become cached GL state applied on bind. Diligent's GL `SetPipelineState` applies rasterizer, depth and blend state from the PSO desc ([DeviceContextGLImpl.cpp L85–L99](https://github.com/DiligentGraphics/DiligentCore/blob/4678e4393cd0194f3c56e5d6611221d46497cc95/Graphics/GraphicsEngineOpenGL/src/DeviceContextGLImpl.cpp#L85-L99)) through a `GLContextState` cache ([GLContextState.hpp L42–L81](https://github.com/DiligentGraphics/DiligentCore/blob/4678e4393cd0194f3c56e5d6611221d46497cc95/Graphics/GraphicsEngineOpenGL/include/GLContextState.hpp#L42-L81)). sokol keeps a `_sg_gl_cache_t` of depth, stencil, blend, bound buffers, program and texture-sampler slots ([sokol_gfx.h L7380–L7409](https://github.com/floooh/sokol/blob/efeb77603e24daea7d1dd6445b9358bb5d82533b/sokol_gfx.h#L7380-L7409)). Filament's `OpenGLDriver` owns an `OpenGLContext` that tracks state ([OpenGLDriver.h L21, L232](https://github.com/google/filament/blob/a84309371cca4cbe20efd79e0033ad19849b3c59/filament/backend/src/opengl/OpenGLDriver.h#L21-L232)), and its driver API has `resetState` "if the driver does any state tracking (e.g. GL)" ([DriverAPI.inc L177–L178](https://github.com/google/filament/blob/a84309371cca4cbe20efd79e0033ad19849b3c59/filament/backend/include/private/backend/DriverAPI.inc#L177-L178)).
- **Descriptor sets and bind groups** become flattened GL binding points. wgpu's GL backend linearises bind group entries per pipeline layout into GL slots; because GL "has sampler objects, but they aren't separately bindable to the shaders", it supports "at most one sampler used with each texture" and remaps on pipeline or bind-group change ([gles/mod.rs L14–L33](https://github.com/gfx-rs/wgpu/blob/3050396df223f189925c5a7d9d81c0ef219b6117/wgpu-hal/src/gles/mod.rs#L14-L33)). Filament emulates descriptor sets with `GLDescriptorSet` and `GLDescriptorSetLayout` ([OpenGLDriver.h L25–L26, L156–L158](https://github.com/google/filament/blob/a84309371cca4cbe20efd79e0033ad19849b3c59/filament/backend/src/opengl/OpenGLDriver.h#L25-L158)). Diligent's SRB commit is recorded and bound lazily before the draw ([DeviceContextGLImpl.cpp L169–L181, L701](https://github.com/DiligentGraphics/DiligentCore/blob/4678e4393cd0194f3c56e5d6611221d46497cc95/Graphics/GraphicsEngineOpenGL/src/DeviceContextGLImpl.cpp#L169-L181)). sokol's GL shaders pair textures with samplers in "texture-sampler" slots ([sokol_gfx.h L7372–L7376](https://github.com/floooh/sokol/blob/efeb77603e24daea7d1dd6445b9358bb5d82533b/sokol_gfx.h#L7372-L7376)).
- **Render passes** become framebuffer binds plus clears. Diligent's GL `BeginSubpass` clears attachments whose load op is `CLEAR` on their first use ([DeviceContextGLImpl.cpp L479–L540](https://github.com/DiligentGraphics/DiligentCore/blob/4678e4393cd0194f3c56e5d6611221d46497cc95/Graphics/GraphicsEngineOpenGL/src/DeviceContextGLImpl.cpp#L479-L540)).
- **Barriers** mostly vanish, because GL synchronises implicitly except for image and buffer stores. Diligent's GL `TransitionResourceStates` and `TransitionShaderResources` only assert they are outside a render pass ([DeviceContextGLImpl.cpp L164–L167, L1996–L1999](https://github.com/DiligentGraphics/DiligentCore/blob/4678e4393cd0194f3c56e5d6611221d46497cc95/Graphics/GraphicsEngineOpenGL/src/DeviceContextGLImpl.cpp#L164-L167)); instead it remembers textures and buffers bound for writing and issues `glMemoryBarrier` bits before their next use ([L778–L798](https://github.com/DiligentGraphics/DiligentCore/blob/4678e4393cd0194f3c56e5d6611221d46497cc95/Graphics/GraphicsEngineOpenGL/src/DeviceContextGLImpl.cpp#L778-L798)). wgpu's GL `transition_buffers` drops every barrier except those from storage writes, noting "GLES only synchronizes storage -> anything explicitly" ([gles/command.rs L280–L298](https://github.com/gfx-rs/wgpu/blob/3050396df223f189925c5a7d9d81c0ef219b6117/wgpu-hal/src/gles/command.rs#L280-L298)), and turns those into `glMemoryBarrier` flags at execution ([gles/queue.rs L1287–L1299](https://github.com/gfx-rs/wgpu/blob/3050396df223f189925c5a7d9d81c0ef219b6117/wgpu-hal/src/gles/queue.rs#L1287-L1299)).
- **Command buffers** are recorded and replayed. wgpu's GL `CommandBuffer` is a `Vec<Command>` ([gles/mod.rs L910, L1107–L1112](https://github.com/gfx-rs/wgpu/blob/3050396df223f189925c5a7d9d81c0ef219b6117/wgpu-hal/src/gles/mod.rs#L910-L1112)) executed on submit. Diligent's GL backend does not support deferred contexts at all: `FinishCommandList` and `ExecuteCommandLists` log "Deferred contexts are not supported in OpenGL mode" ([DeviceContextGLImpl.cpp L1607–L1616](https://github.com/DiligentGraphics/DiligentCore/blob/4678e4393cd0194f3c56e5d6611221d46497cc95/Graphics/GraphicsEngineOpenGL/src/DeviceContextGLImpl.cpp#L1607-L1616)).
- **What GL gives up here:**
  - wgpu ranks GL a "secondary" backend with "a partial implementation", says "the API is generally designed to fit the primary backends better", and reports GL's gaps through `DownlevelCapabilities` ([wgpu-hal/src/lib.rs L75–L106](https://github.com/gfx-rs/wgpu/blob/3050396df223f189925c5a7d9d81c0ef219b6117/wgpu-hal/src/lib.rs#L75-L106), [wgpu-types/src/limits.rs L1113–L1162](https://github.com/gfx-rs/wgpu/blob/3050396df223f189925c5a7d9d81c0ef219b6117/wgpu-types/src/limits.rs#L1113-L1162)). Texture views over a subset of mips or layers cannot be sampled on GL, and `first_instance` is emulated or unsupported for indirect draws depending on GL version ([gles/mod.rs L8–L80](https://github.com/gfx-rs/wgpu/blob/3050396df223f189925c5a7d9d81c0ef219b6117/wgpu-hal/src/gles/mod.rs#L8-L80)).
  - Multithreaded recording (Diligent above).
  - Bevy notes that native GL through wgpu on Windows or macOS needs ANGLE, "because wgpu requires EGL to create a GL context without a window" ([settings.rs L32–L37](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_render/src/settings.rs#L32-L37)).

### c. GL gets its own renderer above the thin seam (Godot)

- Godot's docs: "The OpenGL driver does not use the RenderingDevice abstraction"; only the Compatibility rendering method can use it, and "core shaders are entirely different from the Vulkan renderer" ([Internal rendering architecture, "OpenGL" and "RenderingDevice abstraction"](https://docs.godotengine.org/en/stable/engine_details/architecture/internal_rendering_architecture.html)). In source, `RasterizerGLES3` implements `RendererCompositor` directly (section 1).
- Gives up: two renderers to maintain, with features that differ by renderer (the docs list VoxelGI and SDFGI as Forward+ only, same page). Gains: neither the GL renderer nor the explicit-API renderers bend to the other.

## 4. Handles and lifetimes

### Handle shapes

- **Index only, no generation.** bgfx handles are `struct { uint16_t idx; }` with `UINT16_MAX` invalid ([bgfx.h L22–L26](https://github.com/bkaradzic/bgfx/blob/21a5cf8fc00888103f97c9ea87ed8a8b4040fb2f/include/bgfx/bgfx.h#L22-L26)). O3DE's reflect-level `Handle<T, Namespace>` is an integral index with -1 as null, typed by a namespace tag ([Handle.h L20–L30](https://github.com/o3de/o3de/blob/2462b90ee389939336931a14e234fc4e3b4cd534/Gems/Atom/RHI/Code/Include/Atom/RHI.Reflect/Handle.h#L20-L30)).
- **Index plus generation.** sokol ids are `(generation << 16) | slot_index`; allocating a slot bumps its generation counter ([sokol_gfx.h L7058–L7060, L8546–L8559](https://github.com/floooh/sokol/blob/efeb77603e24daea7d1dd6445b9358bb5d82533b/sokol_gfx.h#L8546-L8559)), and the docs describe invalid, failed and valid resource states for a handle ([L2068–L2110](https://github.com/floooh/sokol/blob/efeb77603e24daea7d1dd6445b9358bb5d82533b/sokol_gfx.h#L2068-L2110)). Filament handles are a 32-bit id ([Handle.h L58–L97](https://github.com/google/filament/blob/a84309371cca4cbe20efd79e0033ad19849b3c59/filament/backend/include/backend/Handle.h#L58-L97)); its allocator stores a 4-bit age before each pool slot, checks it on lookup and on free ("check for double-free"), and increments it on free ([HandleAllocator.h L207–L215, L274–L284](https://github.com/google/filament/blob/a84309371cca4cbe20efd79e0033ad19849b3c59/filament/backend/include/private/backend/HandleAllocator.h#L207-L284)). Its pool sizes differ per backend (`HandleAllocatorGL`, `VK`, `MTL`) ([L47–L52](https://github.com/google/filament/blob/a84309371cca4cbe20efd79e0033ad19849b3c59/filament/backend/include/private/backend/HandleAllocator.h#L47-L52)).
- **Opaque ids backed by pointers.** Godot's driver-level ids are `uint64_t` typed per kind (`BufferID`, `TextureID`, ...), "backed with the native ones or memory addresses" ([rendering_device_driver.h L40, L94–L140](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/servers/rendering/rendering_device_driver.h#L94-L140)); above, `RenderingDevice` hands out `RID`s (for example `uniform_set_create` and `render_pipeline_create` return `RID`) ([rendering_device.h L1199, L1283](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/servers/rendering/rendering_device.h#L1199-L1283)). SDL uses opaque struct pointers (`typedef struct SDL_GPUTexture SDL_GPUTexture`) ([SDL_gpu.h L411, L473](https://github.com/libsdl-org/SDL/blob/829a65d769d935c4852f8159e964312c0957260a/include/SDL3/SDL_gpu.h#L411-L473)).
- **Reference-counted objects.** NVRHI resources are COM-style with `RefCountPtr<T>` handles ([ProgrammingGuide.md L9–L13](https://github.com/NVIDIA-RTX/NVRHI/blob/6b96fb03e07539f08327aea76c56d55f1de9d906/doc/ProgrammingGuide.md#L9-L13)). Diligent: "automatic reference counting", the engine shuts down when the last reference goes ([README L263–L265](https://github.com/DiligentGraphics/DiligentCore/blob/4678e4393cd0194f3c56e5d6611221d46497cc95/README.md#L263-L265)). Unreal `FRHIResource` has `AddRef`, `Release` and `GetRefCount` ([FRHIResource docs](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/RHI/FRHIResource)). wgpu-core uses `Arc`; its ids now exist only for tracing, as `Arc::as_ptr` values ([id.rs L3–L14](https://github.com/gfx-rs/wgpu/blob/3050396df223f189925c5a7d9d81c0ef219b6117/wgpu-core/src/id.rs#L3-L14)), though trackers still index flat arrays by a reused index ([track/mod.rs L1–L23](https://github.com/gfx-rs/wgpu/blob/3050396df223f189925c5a7d9d81c0ef219b6117/wgpu-core/src/track/mod.rs#L1-L23)).

### Deferred destruction across frames in flight

Every design with GPU work in flight defers the real destroy. They differ in what they key on:

- **The frame.**
  - bgfx queues freed handles in the frame being submitted and releases them when frames swap, so a handle is reused only after the render side has consumed that frame ([bgfx_p.h L4054](https://github.com/bkaradzic/bgfx/blob/21a5cf8fc00888103f97c9ea87ed8a8b4040fb2f/src/bgfx_p.h#L4054), [bgfx.cpp L2906, L3332–L3337](https://github.com/bkaradzic/bgfx/blob/21a5cf8fc00888103f97c9ea87ed8a8b4040fb2f/src/bgfx.cpp#L3332-L3337)).
  - sokol's Metal backend puts released objects in a release queue "released N frames later" ([sokol_gfx.h L16455–L16475](https://github.com/floooh/sokol/blob/efeb77603e24daea7d1dd6445b9358bb5d82533b/sokol_gfx.h#L16455-L16475)); its Vulkan backend has a delete queue per in-flight frame slot, next to that slot's fence ([L7908–L7919, L8070–L8078](https://github.com/floooh/sokol/blob/efeb77603e24daea7d1dd6445b9358bb5d82533b/sokol_gfx.h#L8070-L8078)), and logs "too many objects destroyed per frame" when full ([L5185](https://github.com/floooh/sokol/blob/efeb77603e24daea7d1dd6445b9358bb5d82533b/sokol_gfx.h#L5185)).
  - Godot's `RenderingDevice` keeps per-frame `*_to_dispose_of` lists ([rendering_device.h L1802–L1806](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/servers/rendering/rendering_device.h#L1802-L1806)); `free_rid` pushes into the current frame's list ([rendering_device.cpp L7735–L7774](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/servers/rendering/rendering_device.cpp#L7735-L7774)) and `_free_pending_resources(frame)` drains it later ([rendering_device.h L1885](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/servers/rendering/rendering_device.h#L1885)).
  - O3DE's `ObjectCollector` "deferred-releases reference-counted objects at a specific latency", for example at frame end after syncing the oldest GPU frame ([ObjectCollector.h L39–L86](https://github.com/o3de/o3de/blob/2462b90ee389939336931a14e234fc4e3b4cd534/Gems/Atom/RHI/Code/Include/Atom/RHI/ObjectCollector.h#L39-L86)).
- **The submission and its fence.**
  - Diligent's `ResourceReleaseQueue` moves a released object to a stale queue with the next command-list number, then to a release queue with that submission's fence value, and destroys it when the fence signals ([ResourceReleaseQueue.hpp L214–L221](https://github.com/DiligentGraphics/DiligentCore/blob/4678e4393cd0194f3c56e5d6611221d46497cc95/Graphics/GraphicsAccessories/interface/ResourceReleaseQueue.hpp#L214-L221)); `ReleaseStaleResources` and `FinishFrame` are called by `Present` ([RenderDevice.h L397–L402](https://github.com/DiligentGraphics/DiligentCore/blob/4678e4393cd0194f3c56e5d6611221d46497cc95/Graphics/GraphicsEngine/interface/RenderDevice.h#L397-L402), [DeviceContext.h L3478–L3493](https://github.com/DiligentGraphics/DiligentCore/blob/4678e4393cd0194f3c56e5d6611221d46497cc95/Graphics/GraphicsEngine/interface/DeviceContext.h#L3478-L3493)).
  - NVRHI command lists hold internal references until their GPU work finishes; `IDevice::runGarbageCollection()` does the destroys and "is supposed to be called at least once per frame" ([ProgrammingGuide.md L9](https://github.com/NVIDIA-RTX/NVRHI/blob/6b96fb03e07539f08327aea76c56d55f1de9d906/doc/ProgrammingGuide.md#L9)). Long-lived binding sets can opt out of this tracking with `trackLiveness = false` ([L106](https://github.com/NVIDIA-RTX/NVRHI/blob/6b96fb03e07539f08327aea76c56d55f1de9d906/doc/ProgrammingGuide.md#L106)).
  - wgpu-core's `ActiveSubmission` holds what each submission uses until the device fence passes its index ([device/life.rs L17–L56](https://github.com/gfx-rs/wgpu/blob/3050396df223f189925c5a7d9d81c0ef219b6117/wgpu-core/src/device/life.rs#L17-L56)).
  - SDL's `SDL_ReleaseGPUTexture` and friends free "as soon as it is safe to do so" ([SDL_gpu.h L3054–L3124](https://github.com/libsdl-org/SDL/blob/829a65d769d935c4852f8159e964312c0957260a/include/SDL3/SDL_gpu.h#L3054-L3124)); the Vulkan backend parks them in `texturesToDestroy` and destroys each once its reference count from in-flight command buffers is zero ([SDL_gpu_vulkan.c L7061, L10514–L10519](https://github.com/libsdl-org/SDL/blob/829a65d769d935c4852f8159e964312c0957260a/src/gpu/vulkan/SDL_gpu_vulkan.c#L10514-L10519)).
  - Unreal: "RHI resources should only be destructed via the deletion queue", so the destructor is protected ([FRHIResource docs](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/RHI/FRHIResource)).
- **Reuse instead of destroy.** SDL's "cycling": buffers and textures "effectively function as ring buffers on internal resources"; with `cycle = true` a write to a bound resource rotates to an unbound internal copy, so the app needs no manual tracking ([SDL_gpu.h L309–L353](https://github.com/libsdl-org/SDL/blob/829a65d769d935c4852f8159e964312c0957260a/include/SDL3/SDL_gpu.h#L309-L353)). NVRHI versions volatile constant buffers and sub-allocates uploads inside command lists for the same reason ([ProgrammingGuide.md L38](https://github.com/NVIDIA-RTX/NVRHI/blob/6b96fb03e07539f08327aea76c56d55f1de9d906/doc/ProgrammingGuide.md#L38)).

### State tracking goes with lifetime tracking

Libraries that track lifetimes also track usage and place barriers: NVRHI (with three ways to tell a command list a resource's entry state, and an opt-out) ([ProgrammingGuide.md L42–L52](https://github.com/NVIDIA-RTX/NVRHI/blob/6b96fb03e07539f08327aea76c56d55f1de9d906/doc/ProgrammingGuide.md#L42-L52)); wgpu-core ([track/mod.rs L1–L40](https://github.com/gfx-rs/wgpu/blob/3050396df223f189925c5a7d9d81c0ef219b6117/wgpu-core/src/track/mod.rs#L1-L40)); Godot's graph; O3DE's frame graph; SDL's per-resource default usages ([SDL_gpu_vulkan.c L2921–L2991](https://github.com/libsdl-org/SDL/blob/829a65d769d935c4852f8159e964312c0957260a/src/gpu/vulkan/SDL_gpu_vulkan.c#L2921-L2991)); sokol's Vulkan access flags and `vkCmdPipelineBarrier2` ([sokol_gfx.h L7922, L20927](https://github.com/floooh/sokol/blob/efeb77603e24daea7d1dd6445b9358bb5d82533b/sokol_gfx.h#L20927)). Diligent makes it per call: transition, verify, or none ([DeviceContext.h L248–L273](https://github.com/DiligentGraphics/DiligentCore/blob/4678e4393cd0194f3c56e5d6611221d46497cc95/Graphics/GraphicsEngine/interface/DeviceContext.h#L248-L273)). Only `wgpu-hal` and Godot's `RenderingDeviceDriver` put barriers on the caller, and both have a tracking layer directly above them.

## 5. Leaks

### Native escape hatches

Almost every library has one; SDL3 GPU is the exception among those read.

### Shader formats

No library makes one shader binary serve every API. They split three ways:

1. **App provides one format per API, offline.** SDL takes SPIR-V, DXBC, DXIL, MSL or metallib, depending on backend ([SDL_gpu.h L1035–L1041](https://github.com/libsdl-org/SDL/blob/829a65d769d935c4852f8159e964312c0957260a/include/SDL3/SDL_gpu.h#L1035-L1041)), and fixes per-format register and set layouts the shader must follow ([L2606–L2626](https://github.com/libsdl-org/SDL/blob/829a65d769d935c4852f8159e964312c0957260a/include/SDL3/SDL_gpu.h#L2606-L2626)); cross-compiling is a separate project, SDL_shadercross ([L131–L135](https://github.com/libsdl-org/SDL/blob/829a65d769d935c4852f8159e964312c0957260a/include/SDL3/SDL_gpu.h#L131-L135)). NVRHI's `createShader` takes a binary blob ([nvrhi.h L3832](https://github.com/NVIDIA-RTX/NVRHI/blob/6b96fb03e07539f08327aea76c56d55f1de9d906/include/nvrhi/nvrhi.h#L3832)), and Vulkan's lack of separate register namespaces leaks as `VulkanBindingOffsets` ([ProgrammingGuide.md L122–L126](https://github.com/NVIDIA-RTX/NVRHI/blob/6b96fb03e07539f08327aea76c56d55f1de9d906/doc/ProgrammingGuide.md#L122-L126)). bgfx's `shaderc` compiles its GLSL-like language to one binary per renderer, loaded from `dxbc/`, `dxil/`, `glsl/`, `spirv/`, `metal/` and so on ([docs/tools.rst L61–L82](https://github.com/bkaradzic/bgfx/blob/21a5cf8fc00888103f97c9ea87ed8a8b4040fb2f/docs/tools.rst#L61-L82), [examples/common/bgfx_utils.cpp L105–L115](https://github.com/bkaradzic/bgfx/blob/21a5cf8fc00888103f97c9ea87ed8a8b4040fb2f/examples/common/bgfx_utils.cpp#L105-L115)). sokol's `sokol-shdc` generates per-backend code plus reflection into a C header, and `sg_make_shader(myshader_shader_desc(sg_query_backend()))` picks the right one ([sokol_gfx.h L888–L912](https://github.com/floooh/sokol/blob/efeb77603e24daea7d1dd6445b9358bb5d82533b/sokol_gfx.h#L888-L912)).
2. **Library translates at runtime from one source.** wgpu translates WGSL (and other front ends) through naga per backend, with `PASSTHROUGH_SHADERS` as the native escape ([features.rs L1060](https://github.com/gfx-rs/wgpu/blob/3050396df223f189925c5a7d9d81c0ef219b6117/wgpu-types/src/features.rs#L1060)). Diligent converts HLSL to GLSL for GL and to SPIR-V for Vulkan ([README L328–L335](https://github.com/DiligentGraphics/DiligentCore/blob/4678e4393cd0194f3c56e5d6611221d46497cc95/README.md#L328-L335)). 3. **Asset pipeline bakes per-API variants.** O3DE encodes an API index in the shader variant asset's sub-id because "pc" supports DX12 and Vulkan ([Factory.h L117–L130](https://github.com/o3de/o3de/blob/2462b90ee389939336931a14e234fc4e3b4cd534/Gems/Atom/RHI/Code/Include/Atom/RHI/Factory.h#L117-L130)). Filament's driver enums list the shader languages a material may carry (`ESSL1`, `ESSL3`, ...) ([DriverEnums.h L217–L220](https://github.com/google/filament/blob/a84309371cca4cbe20efd79e0033ad19849b3c59/filament/backend/include/backend/DriverEnums.h#L217-L220)).

### Threading shaped by the backend

- GL contexts are bound to a thread, and designs route all GL calls to one: bgfx has an API thread and a render thread, and `getInternalData` is "render thread only" ([bgfx.h L4490–L4509](https://github.com/bkaradzic/bgfx/blob/21a5cf8fc00888103f97c9ea87ed8a8b4040fb2f/include/bgfx/bgfx.h#L4490-L4509), [config.h L288–L290](https://github.com/bkaradzic/bgfx/blob/21a5cf8fc00888103f97c9ea87ed8a8b4040fb2f/src/config.h#L288-L290)); Filament's `CommandStream` is filled on one thread and drained on the driver thread ([CommandStream.h L244](https://github.com/google/filament/blob/a84309371cca4cbe20efd79e0033ad19849b3c59/filament/backend/include/private/backend/CommandStream.h#L244)); Diligent's GL device needs `UpdateCurrentGLContext` if the app uses several contexts ([GraphicsEngineOpenGL/readme.md](https://github.com/DiligentGraphics/DiligentCore/blob/4678e4393cd0194f3c56e5d6611221d46497cc95/Graphics/GraphicsEngineOpenGL/readme.md)) and has no deferred contexts.
- Explicit APIs allow parallel recording, and libraries expose it where the backend has it: Diligent deferred contexts (D3D11, D3D12, Vulkan only; [README L175–L179](https://github.com/DiligentGraphics/DiligentCore/blob/4678e4393cd0194f3c56e5d6611221d46497cc95/README.md#L175-L179)); NVRHI parallel command lists plus a special "immediate" list for D3D11 ([ProgrammingGuide.md L34–L38](https://github.com/NVIDIA-RTX/NVRHI/blob/6b96fb03e07539f08327aea76c56d55f1de9d906/doc/ProgrammingGuide.md#L34-L38)); SDL command buffers per thread ([SDL_gpu.h L3155–L3159](https://github.com/libsdl-org/SDL/blob/829a65d769d935c4852f8159e964312c0957260a/include/SDL3/SDL_gpu.h#L3155-L3159)); Unreal's RHI thread, where "anything generated in parallel on the frontend is translated in parallel on the backend" on "game consoles, DX12, and Vulkan" ([Parallel Rendering Overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/parallel-rendering-overview-for-unreal-engine)).
- Some calls bypass the queue and need flushes: Unreal's `Lock`/`Unlock` either flush the RHI thread or copy data, "differently depending on the operation and the platform" (same page); `RHIGetNativeDevice` is marked "Flush RHI Thread" ([FDynamicRHI docs](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/RHI/FDynamicRHI)).
- Bevy wraps wgpu objects so they are `Send`/`Sync` on web, where they may only be touched on the wgpu thread ([wgpu_wrapper.rs L1–L5](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_render/src/renderer/wgpu_wrapper.rs#L1-L5)).

## Options this suggests for FenrirRenderer's seam

Listed for the grilling ticket, not chosen.

1. **Where the seam sits.**
   - Thin, explicit-API-shaped RHI (pipelines, binding groups, passes, command lists), with GL emulating it as Diligent, wgpu and Filament do. Cost: GL needs state caches, flattened bindings, pass emulation and a recorded command list; multithreaded recording does not exist on GL.
   - Thin, GL-shaped API with explicit backends hashing state into PSOs, as bgfx does. Cost: hashing and possible pipeline-build hitches at draw time on explicit APIs.
   - High-level seam, one renderer per API (Godot's `RendererCompositor`, bgfx's per-frame `submit`). Cost: features re-implemented per backend; Godot's two renderers differ in features.
   - Both: a public high-level renderer over a private thin backend (Filament, Godot, Bevy over wgpu). The public API hides the backend, the private one keeps backends small.
2. **Selection.** Compile time (sokol; matches ADR-0010's physics choice) or runtime interface (everyone else). With only GL built, a runtime interface buys nothing until a second backend ships, and the per-call cost depends on how coarse the crossings are.
3. **Handles.** Index plus generation (sokol, Filament's age bits) gives cheap stale-handle detection without ref counts; ref-counted objects (NVRHI, Diligent, Unreal, wgpu) give automatic lifetime tracking but leak ownership semantics across the seam.
4. **Deferred destruction.** Keyed on frame index (bgfx, sokol, Godot, O3DE) or on submission fence (Diligent, NVRHI, wgpu, SDL). Under GL alone none is needed, but a seam that allows Vulkan later needs the hook.
5. **Barriers and state tracking.** In the backend (most libraries), so callers never see them, or on the caller with a tracking layer above (wgpu-hal, Godot's driver).
6. **Shaders.** One format per API supplied by the app (SDL, NVRHI, bgfx, sokol, via an offline tool) or one source translated by the library (wgpu, Diligent, Godot). This is the shader-language ADR's question.
7. **Escape hatch.** All but SDL expose native handles; ADR-0010 refused one for physics.
8. **Testing.** A null backend tests bookkeeping on any machine (wgpu, sokol, Bevy); pixels need image comparison on a real or software device (Diligent, wgpu, Filament).

# How engines model skeletons, clips, blending, skinning and ragdoll blending

Research for [07-how-engines-model-animation](../issues/07-how-engines-model-animation.md). This file reports how Bevy, Unity, Unreal, Godot 4, O3DE's EMotionFX and ozz-animation model skeletal animation, in the areas that FenrirEngine's animation spec and the physics map's ragdolls depend on. Jolt's own ragdoll and skeleton types are added because FenrirPhysics is built on Jolt. The file chooses nothing for FenrirEngine: each section ends with the options it raises and their trade-offs.

Sources are engine source, pinned to the commit read, plus official docs. Line numbers refer to these versions:

- **Bevy** `main` @ [`2614884`](https://github.com/bevyengine/bevy/tree/2614884437512e310eeb196241828162b6507533) (workspace version `0.20.0-dev`): `bevy_animation`, `bevy_mesh`, and `bevy_pbr`'s skinning.
- **Unity** C# reference source `UnityCsReference` @ [`6c1fc79`](https://github.com/Unity-Technologies/UnityCsReference/tree/6c1fc7919aa64a2698e06922c4516eb1daa91b75). These are the managed bindings only; the native animation and skinning code behind them is closed. Unity docs: the 6000.2 Manual and the Entities Graphics 1.4 manual.
- **Unreal Engine 5.8**: the source needs an Epic account, so this file cites only the official API reference and manual on dev.epicgames.com (all pages read as UE 5.8).
- **Godot** `master` @ [`6790667`](https://github.com/godotengine/godot/tree/679066724352c12673001d692d41dc2dab9314c0) (4.8 beta): `scene/3d`, `scene/3d/physics`, `doc/classes`, and the RenderingDevice skinning shader.
- **O3DE** `development` @ [`2462b90`](https://github.com/o3de/o3de/tree/2462b90ee389939336931a14e234fc4e3b4cd534): the EMotionFX gem (`Gems/EMotionFX/Code`).
- **ozz-animation** `master` @ [`744eb9d`](https://github.com/guillaumeblanc/ozz-animation/tree/744eb9d99f606eda849acb0b1204f7a3dc20bca1) (CMake version 0.17.0, the latest tag).
- **Jolt Physics** tag `v5.6.0` @ [`e77f175`](https://github.com/jrouwe/JoltPhysics/tree/e77f175595e64cb44218cc9d9d56fc365ad0e36a), for `Ragdoll`, `Skeleton`, `SkeletonPose` and `SkeletonMapper`.
- **ACL** (Animation Compression Library), [nfrechette/acl](https://github.com/nfrechette/acl), latest tag `v2.1.0`; its README only.

Every link is a full URL. "Model space" means relative to the skeleton's root or owning object (Unreal calls it component space; Godot calls it the bone's "global pose"); "local space" means relative to the parent bone.

## Summary

| | Skeleton | Clip storage | Blending | Result pose lives in | Skinning | Ragdoll blend |
|---|---|---|---|---|---|---|
| Bevy | one entity per bone; mesh holds `Vec<Entity>` + inverse bind poses asset | curves, uncompressed | DAG of Blend/Add/Clip nodes, 64 mask groups, crossfade helper | bones' local `Transform` | GPU vertex shader, 4 influences, 256 joints per mesh | none built in |
| Unity (GameObjects) | one `Transform` per bone; renderer holds `Transform[]`, mesh holds `bindposes` | keyframe reduction at import (closed) | state machines, blend trees, layers (Override/Additive) with Avatar masks | bones' `Transform`s | GPU, 1/2/4/unlimited influences | user code with Rigidbody + CharacterJoint per bone |
| Unity (Entities) | no shipped animation package; Entities Graphics takes skin matrices from user code | n/a | n/a | n/a | compute shader | n/a |
| Unreal | arrays in a `USkeleton` / reference skeleton; bones are not components | ACL codec by default | AnimGraph: state machines, blend spaces, layered blend per bone | local or component space, converted explicitly | GPU vertex shader or compute skin cache; 4/8, or up to 12 | per-body `PhysicsBlendWeight`, Physical Animation component motors, RigidBody anim node |
| Godot 4 | arrays in one `Skeleton3D` node; `Skin` resource holds bind poses by bone name | `Animation` tracks, optional lossy `compress()` | `AnimationTree`: blend trees, state machines, blend spaces, per-track filters | bone local pose in `Skeleton3D` | compute shader, 4 or 8 influences | `PhysicalBoneSimulator3D` as a skeleton modifier with `influence`; partial by bone subtree |
| EMotionFX | node array in `Skeleton`; actor holds inverse bind poses | uniform or non-uniform keyframes | anim graph: state machines, blend trees, masks, additive | `Pose` with local and model arrays | GPU, dual quaternion by default | ragdoll node in the anim graph; per-joint strength drives powered joints; pose data blends kinematic and simulated |
| ozz | SoA arrays: parents, rest poses, names | quantized keys, hierarchical keyframe reduction offline | `BlendingJob`: weighted layers, per-joint weights, additive layers | local SoA, then `LocalToModelJob` | CPU `SkinningJob` (any influences); GPU left to the app | none |
| Jolt | `Skeleton` of named joints with parent indices | `SkeletalAnimation` (simple) | none | `SkeletonPose` | none | `Ragdoll`: a body and parent constraint per joint; drive to pose by kinematics or motors; `SkeletonMapper` maps ragdoll to animation skeletons |

## Skeleton

### Bones as entities, or an array in one component

**Bones as entities or scene objects.**

- **Bevy:** each joint is an entity with a `Transform`. A skinned mesh names its skeleton as a list of joint entities plus a handle to an asset of inverse bind matrices: `SkinnedMesh { inverse_bindposes: Handle<SkinnedMeshInverseBindposes>, joints: Vec<Entity> }`, and the asset is a `Box<[Mat4]>` ([skinning.rs L14–L34](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_mesh/src/skinning.rs#L14-L34)). The renderer computes each joint matrix as the joint entity's `GlobalTransform` times its inverse bind pose ([skin.rs L399–L412](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_pbr/src/render/skin.rs#L399-L412)).
- **Bevy's clips find bones by a name hash.** `AnimationTargetId` is a UUID that "asset loaders typically use the full path name from the armature to the bone to generate"; a bone named `Chest` under `Hips` gets a different ID from a `Chest` under `Stomach`. Any clip plays on any armature whose bone paths match ([lib.rs L163–L187](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_animation/src/lib.rs#L163-L187)). `AnimatedBy(Entity)` links each animated entity to the entity holding the `AnimationPlayer`, and "each entity can only be animated by one animation player at a time" ([L196–L215](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_animation/src/lib.rs#L196-L215)).
- **Unity (GameObjects):** each bone is a `Transform`. `SkinnedMeshRenderer` holds `Transform[] bones` and a `rootBone` ([GraphicsRenderers.bindings.cs L405–L415](https://github.com/Unity-Technologies/UnityCsReference/blob/6c1fc7919aa64a2698e06922c4516eb1daa91b75/Runtime/Export/Graphics/GraphicsRenderers.bindings.cs#L405-L415)). The bind poses live on the `Mesh`, as `Matrix4x4[] bindposes` ([Mesh.bindings.cs L246](https://github.com/Unity-Technologies/UnityCsReference/blob/6c1fc7919aa64a2698e06922c4516eb1daa91b75/Runtime/Export/Graphics/Mesh.bindings.cs#L246)), one per entry of `bones`.

**Bones as an array inside one object.**

- **Godot:** `Skeleton3D` is one node holding all bones: "an interface for managing a hierarchy of bones, including pose, rest and animation"; its "global pose" is relative to the skeleton, not the world ([Skeleton3D.xml L6–L10](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/doc/classes/Skeleton3D.xml#L6-L10)). Each `Bone` is a struct in an array: name, parent index, child list, `rest`, `global_rest`, and a pose split into `pose_position`, `pose_rotation` (quaternion) and `pose_scale` ([skeleton_3d.h L101–L120](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/scene/3d/skeleton_3d.h#L101-L120)). Bones are not nodes; `BoneAttachment3D` exists to hang nodes off them.
- **Godot's skinned mesh names its skeleton twice:** `MeshInstance3D.skeleton` is a `NodePath` to the `Skeleton3D`, and `skin` is a `Skin` resource ([MeshInstance3D.xml L131–L137](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/doc/classes/MeshInstance3D.xml#L131-L137)). A `Skin` is "a list of bind pose matrices and a list of either bone names if bones are named, or bone indices", where the bind pose is "also called offset matrix or inverse bind matrix" ([Skin.xml L6–L8](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/doc/classes/Skin.xml#L6-L8)). Binding by name lets one mesh be skinned to any skeleton with matching bone names.
- **Unreal:** `USkeleton` is the asset "that links between mesh and animation": the bone hierarchy for animations, the bone and track link-up between mesh and animation, and retargeting ([USkeleton](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/USkeleton)). Each mesh also carries an `FReferenceSkeleton`, with arrays of bone info and reference (bind) poses and `GetParentIndex` ([FReferenceSkeleton](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/FReferenceSkeleton)), and the precomputed inverse bind matrices, `GetRefBasesInvMatrix` ([USkinnedAsset](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/USkinnedAsset)). Bones are not components: the component exposes them as arrays, `GetBoneSpaceTransforms` ([USkeletalMeshComponent](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/USkeletalMeshComponent)).
- **EMotionFX:** `Skeleton` is an array of `Node`s with a bind pose; node IDs are "based on the name. So all nodes (also inside other actors) with the same name will have the same ID" ([Skeleton.h L71–L77](https://github.com/o3de/o3de/blob/2462b90ee389939336931a14e234fc4e3b4cd534/Gems/EMotionFX/Code/EMotionFX/Source/Skeleton.h#L71-L77)). The `Actor` holds the inverse bind pose per node, `GetInverseBindPoseTransforms` ([Actor.h L662–L671](https://github.com/o3de/o3de/blob/2462b90ee389939336931a14e234fc4e3b4cd534/Gems/EMotionFX/Code/EMotionFX/Source/Actor.h#L662-L671)).
- **ozz:** `Skeleton` stores "joint names, rest-poses and hierarchy information ... in separate arrays", the hierarchy as "an array of parent joint indices (16 bits), stored in depth-first order", up to `kMaxJoints = 1024` ([skeleton.h L51–L71](https://github.com/guillaumeblanc/ozz-animation/blob/744eb9d99f606eda849acb0b1204f7a3dc20bca1/include/ozz/animation/runtime/skeleton.h#L51-L71)). Rest poses are SoA transforms, four joints per element ([L104–L113](https://github.com/guillaumeblanc/ozz-animation/blob/744eb9d99f606eda849acb0b1204f7a3dc20bca1/include/ozz/animation/runtime/skeleton.h#L104-L113)). ozz has no mesh type in the library; its samples' mesh carries `inverse_bind_poses` and a `joint_remaps` table from mesh joints to skeleton joints ([samples/framework/mesh.h L40–L81](https://github.com/guillaumeblanc/ozz-animation/blob/744eb9d99f606eda849acb0b1204f7a3dc20bca1/samples/framework/mesh.h#L40-L81)).
- **Jolt:** `Skeleton` is a list of joints, each with a name, a parent name and a parent index ([Skeleton.h L16–L35](https://github.com/jrouwe/JoltPhysics/blob/e77f175595e64cb44218cc9d9d56fc365ad0e36a/Jolt/Skeleton/Skeleton.h#L16-L35)); `SkeletonPose` is "Instance of a skeleton, contains the pose the current skeleton is in" ([SkeletonPose.h L16](https://github.com/jrouwe/JoltPhysics/blob/e77f175595e64cb44218cc9d9d56fc365ad0e36a/Jolt/Skeleton/SkeletonPose.h#L16)).

### Options for FenrirEngine

- **Bones as entities** (Bevy, Unity) reuse the ECS's transform hierarchy, so attaching a sword to a hand is ordinary parenting, and every system that reads world transforms sees bones. The cost is one entity per bone (hundreds per character), and evaluation, blending and skinning must gather scattered transforms, and clips must find each bone's entity (Bevy does this by `AnimationTargetId`).
- **Bones as an array in one component** (Godot, Unreal, EMotionFX, ozz, Jolt) keeps a pose contiguous for sampling, blending and upload, and matches what physics (Jolt's `SkeletonPose`) and ozz expect. Attachments then need a dedicated "follow bone N" component, as Godot's `BoneAttachment3D`.
- **How the mesh names its skeleton** is either by index into one skeleton (Unity, Unreal, ozz with a remap table) or by bone name (Godot `Skin`, Bevy's path-hash IDs, EMotionFX's name IDs). Names let clips and meshes be shared across skeletons; indices are cheaper and need a remap at import.

## Clips and playback

### Sampling and compression

- **ozz** stores one array of keys per channel (translation, rotation, scale) for all joints, "sorted by time, then by track number" for cache coherence ([animation.h L54–L63](https://github.com/guillaumeblanc/ozz-animation/blob/744eb9d99f606eda849acb0b1204f7a3dc20bca1/include/ozz/animation/runtime/animation.h#L54-L63)). Translations and scales are half floats; rotations keep the three smallest quaternion components in 15 bits each and rebuild the largest ([animation_keyframe.h L52–L80](https://github.com/guillaumeblanc/ozz-animation/blob/744eb9d99f606eda849acb0b1204f7a3dc20bca1/src/animation/runtime/animation_keyframe.h#L52-L80)). An offline `AnimationOptimizer` removes keys within a tolerance measured "on its whole child hierarchy", so a shoulder error is judged by its effect at the finger ([animation_optimizer.h L44–L57](https://github.com/guillaumeblanc/ozz-animation/blob/744eb9d99f606eda849acb0b1204f7a3dc20bca1/include/ozz/animation/offline/animation_optimizer.h#L44-L57)). `SamplingJob` takes a time ratio in [0, 1] and outputs a local-space pose; a context caches decompressed keys so forward playback is fast ([sampling_job.h L47–L72](https://github.com/guillaumeblanc/ozz-animation/blob/744eb9d99f606eda849acb0b1204f7a3dc20bca1/include/ozz/animation/runtime/sampling_job.h#L47-L72)).
- **Unreal** compresses through codecs; the docs recommend "the default Anim Compress ACL codec for most projects" ([Animation Compression Library](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-compression-library-in-unreal-engine)). ACL itself is MIT-licensed and "100% headers", and does compression and decompression only ([ACL README](https://github.com/nfrechette/acl)).
- **Godot** clips are `Animation` resources of typed tracks (position, rotation, scale, blend shape, value, method, bezier, audio, animation) ([Animation.xml L702–L728](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/doc/classes/Animation.xml#L702-L728)); `compress()` is lossy and opt-in, and compressed tracks are not editable ([L257–L266](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/doc/classes/Animation.xml#L257-L266)).
- **EMotionFX** has two key stores, `UniformMotionData` and `NonUniformMotionData` ([UniformMotionData.h L28](https://github.com/o3de/o3de/blob/2462b90ee389939336931a14e234fc4e3b4cd534/Gems/EMotionFX/Code/EMotionFX/Source/MotionData/UniformMotionData.h#L28), [NonUniformMotionData.h L30](https://github.com/o3de/o3de/blob/2462b90ee389939336931a14e234fc4e3b4cd534/Gems/EMotionFX/Code/EMotionFX/Source/MotionData/NonUniformMotionData.h#L30)).
- **Bevy** clips are maps from `AnimationTargetId` to curves ([lib.rs L98–L161](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_animation/src/lib.rs#L98-L161)); the glTF curves keep keyframes, including cubic-spline ones ([gltf_curves.rs L47–L133](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_animation/src/gltf_curves.rs#L47-L133)). No compression step was found in `bevy_animation`. A curve can target any reflected property, not only bones.

### Looping, time and speed

- **Bevy:** `RepeatAnimation::{Never, Count(n), Forever}` ([lib.rs L484–L492](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_animation/src/lib.rs#L484-L492)); `ActiveAnimation` has `set_speed`, `seek_to`, `completions` ([L667–L724](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_animation/src/lib.rs#L667-L724)).
- **Godot:** `LOOP_NONE`, `LOOP_LINEAR`, `LOOP_PINGPONG` per clip ([Animation.xml L762–L770](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/doc/classes/Animation.xml#L762-L770)).
- **EMotionFX:** `MotionInstance` has play speed, play mode (forward or backward), max loops, in-place and mirroring ([MotionInstance.h L198–L387](https://github.com/o3de/o3de/blob/2462b90ee389939336931a14e234fc4e3b4cd534/Gems/EMotionFX/Code/EMotionFX/Source/MotionInstance.h#L198-L387)).
- **ozz has no playback state** in the library: jobs take a ratio. Its samples' `PlaybackController` holds time, speed and loop flag and returns how many loops happened ([samples/framework/utils.h L76–L97](https://github.com/guillaumeblanc/ozz-animation/blob/744eb9d99f606eda849acb0b1204f7a3dc20bca1/samples/framework/utils.h#L76-L97)).

### Events in clips

- **Bevy:** `AnimationClip::add_event(time, event)` triggers an ECS event, optionally on a target bone's entity ([lib.rs L320–L351](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_animation/src/lib.rs#L320-L351)).
- **Unity:** `AnimationClip.AddEvent(AnimationEvent)`, which names a function to call ([AnimationClip.bindings.cs L339](https://github.com/Unity-Technologies/UnityCsReference/blob/6c1fc7919aa64a2698e06922c4516eb1daa91b75/Modules/Animation/ScriptBindings/AnimationClip.bindings.cs#L339)).
- **Unreal:** Notifies, "repeatable events synchronized to Animation Sequences", such as footstep sounds or particles; extensible with custom types ([Animation Notifies](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-notifies-in-unreal-engine)).
- **Godot:** method tracks "call functions with given arguments per key" ([Animation.xml L717–L719](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/doc/classes/Animation.xml#L717-L719)).
- **EMotionFX:** `MotionEvent` on motions ([MotionEvent.h L54](https://github.com/o3de/o3de/blob/2462b90ee389939336931a14e234fc4e3b4cd534/Gems/EMotionFX/Code/EMotionFX/Source/MotionEvent.h#L54)).
- **ozz:** no event type; float tracks plus `TrackTriggeringJob`, which reports rising and falling edges as a track crosses a threshold, across loops and backwards ([track_triggering_job.h L39–L64](https://github.com/guillaumeblanc/ozz-animation/blob/744eb9d99f606eda849acb0b1204f7a3dc20bca1/include/ozz/animation/runtime/track_triggering_job.h#L39-L64)).

### Root motion

- **ozz:** offline `MotionExtractor` moves a root joint's motion into separate tracks and bakes it out of the clip; "user code is expected to reapply motion at runtime by moving the character transform" ([motion_extractor.h L43–L53](https://github.com/guillaumeblanc/ozz-animation/blob/744eb9d99f606eda849acb0b1204f7a3dc20bca1/include/ozz/animation/offline/motion_extractor.h#L43-L53)); `MotionBlendingJob` blends the deltas alongside pose blending ([motion_blending_job.h L43–L46](https://github.com/guillaumeblanc/ozz-animation/blob/744eb9d99f606eda849acb0b1204f7a3dc20bca1/include/ozz/animation/runtime/motion_blending_job.h#L43-L46)).
- **Unity:** `Animator.applyRootMotion`, with `deltaPosition` and `deltaRotation` read in `OnAnimatorMove` ([Animator.bindings.cs L1359–L1403](https://github.com/Unity-Technologies/UnityCsReference/blob/6c1fc7919aa64a2698e06922c4516eb1daa91b75/Modules/Animation/ScriptBindings/Animator.bindings.cs#L1359-L1403)).
- **Unreal:** enabled per sequence or montage; the root bone's motion then drags the character's movement component ([Root Motion](https://dev.epicgames.com/documentation/en-us/unreal-engine/root-motion-in-unreal-engine)).
- **Godot:** `root_motion_track` names a bone track whose motion is cancelled visually and returned by `get_root_motion_position` and friends ([AnimationMixer.xml L106–L110, L323–L325](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/doc/classes/AnimationMixer.xml#L323-L325)).
- **EMotionFX:** a motion extraction node per actor, "the node from which to transfer a filtered part of the motion onto the actor instance" ([Actor.h L842](https://github.com/o3de/o3de/blob/2462b90ee389939336931a14e234fc4e3b4cd534/Gems/EMotionFX/Code/EMotionFX/Source/Actor.h#L842)).
- **Bevy:** none found.

### Options for FenrirEngine

- **Clip format:** raw keyframes per bone (simple, editable, larger), or quantized keys with keyframe reduction (ozz; or ACL as a compression-only library). Quantization can come later behind the same sampler, as Godot's opt-in `compress()` shows.
- **Clip targets:** bone tracks only (ozz, EMotionFX), or any property (Bevy, Godot, Unity). Bones-only keeps the sampler simple; property tracks overlap with a general tweening system.
- **Events:** time-stamped events fired as the playhead crosses them (every engine), delivered through the engine's event mechanism, against threshold tracks (ozz). Crossing detection needs the previous and current time and loop count, which the playback state must keep.
- **Root motion** is listed as "richer animation" in the map; every engine but Bevy has it, and ozz shows it can be an offline extraction plus a delta, added later without changing the pose model.

## Blending

### Crossfades, layers, masks

- **Bevy** blends through an `AnimationGraph`, a DAG of three node kinds: `Clip`, `Blend` (children's weights normalised) and `Add` (weights not normalised, added in order) ([graph.rs L214–L238](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_animation/src/graph.rs#L214-L238)). Each node can carry a mask, a bitfield of mask groups; a set bit disables the targets in that group ([L82–L102](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_animation/src/graph.rs#L82-L102)); the mask type is `u64`, so 64 groups ([L490](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_animation/src/graph.rs#L490)). Crossfades are a separate component, `AnimationTransitions`, that fades weights of the outgoing animation ([transition.rs L17–L33](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_animation/src/transition.rs#L17-L33)). There is no state machine.
- **Unity** Animator layers blend as Override ("replacing the animation on previous layers") or Additive ("on top of the animation from previous layers"), each optionally restricted by an Avatar Mask; synced layers reuse another layer's state machine ([Animation Layers](https://docs.unity3d.com/6000.2/Documentation/Manual/AnimationLayers.html)). Script controls include `SetLayerWeight` and `CrossFade` ([Animator.bindings.cs L1961, L2404](https://github.com/Unity-Technologies/UnityCsReference/blob/6c1fc7919aa64a2698e06922c4516eb1daa91b75/Modules/Animation/ScriptBindings/Animator.bindings.cs#L2404)).
- **Unreal** has state machines in the AnimGraph ([State Machines](https://dev.epicgames.com/documentation/en-us/unreal-engine/state-machines-in-unreal-engine)), blend spaces and additive blends, and "Layered blend per bone", which applies one pose from a named bone down with a blend depth, optionally blending rotation in mesh space ([Using Layered Animations](https://dev.epicgames.com/documentation/en-us/unreal-engine/using-layered-animations-in-unreal-engine)).
- **Godot** `AnimationTree` composes `AnimationNodeBlendTree`, `AnimationNodeStateMachine`, blend spaces, `Add2`, `OneShot` ([AnimationTree.xml](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/doc/classes/AnimationTree.xml), [AnimationNodeAdd2.xml](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/doc/classes/AnimationNodeAdd2.xml)); masks are per-node filters on track paths ([AnimationNode.xml L182–L210](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/doc/classes/AnimationNode.xml#L182-L210)). `AnimationMixer.deterministic` chooses between normalising the total weight to 1 and accumulating over a `RESET` pose so that zero weight gives the rest pose ([AnimationMixer.xml L308–L312](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/doc/classes/AnimationMixer.xml#L308-L312)).
- **EMotionFX** has state machines, blend trees with Blend2, BlendN, additive Blend2, pose subtract, pose mask by joint names, 1D and 2D blend spaces, and IK nodes ([BlendTreeMaskNode.h L80](https://github.com/o3de/o3de/blob/2462b90ee389939336931a14e234fc4e3b4cd534/Gems/EMotionFX/Code/EMotionFX/Source/BlendTreeMaskNode.h#L80), [AnimGraphStateMachine.h L25](https://github.com/o3de/o3de/blob/2462b90ee389939336931a14e234fc4e3b4cd534/Gems/EMotionFX/Code/EMotionFX/Source/AnimGraphStateMachine.h#L25), [BlendTreeBlend2AdditiveNode.h](https://github.com/o3de/o3de/blob/2462b90ee389939336931a14e234fc4e3b4cd534/Gems/EMotionFX/Code/EMotionFX/Source/BlendTreeBlend2AdditiveNode.h)).
- **ozz** has one job, `BlendingJob`: weighted layers of local-space poses, each with optional per-joint weights for partial blending, normalised; plus additive layers ([blending_job.h L44–L115](https://github.com/guillaumeblanc/ozz-animation/blob/744eb9d99f606eda849acb0b1204f7a3dc20bca1/include/ozz/animation/runtime/blending_job.h#L44-L115)). When the accumulated weight is under `threshold` (default 0.1) it blends in the rest pose ([L104–L107](https://github.com/guillaumeblanc/ozz-animation/blob/744eb9d99f606eda849acb0b1204f7a3dc20bca1/include/ozz/animation/runtime/blending_job.h#L104-L107)). Additive clips are built offline as deltas from the first frame or a given reference pose ([additive_animation_builder.h L47–L66](https://github.com/guillaumeblanc/ozz-animation/blob/744eb9d99f606eda849acb0b1204f7a3dc20bca1/include/ozz/animation/offline/additive_animation_builder.h#L47-L66)). Crossfades, graphs and state machines are left to the user.

### Where the result pose lives

- **Local space is where every engine blends clips.** ozz samples and blends local SoA transforms, then `LocalToModelJob` produces model-space matrices, optionally for a sub-range of the hierarchy and with a root matrix to get world space directly ([local_to_model_job.h L51–L106](https://github.com/guillaumeblanc/ozz-animation/blob/744eb9d99f606eda849acb0b1204f7a3dc20bca1/include/ozz/animation/runtime/local_to_model_job.h#L51-L106)).
- **Unreal makes the space explicit in the graph:** "most nodes will operate within Local Space", while "certain blend nodes and all skeletal controls nodes" (IK, physics) work in component space, with conversion nodes between them, and each conversion costs ([Space Conversion Nodes](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-blueprint-component-space-conversion-in-unreal-engine)).
- **EMotionFX's `Pose`** holds both arrays, local and model space, with lazy model-space updates and setters for local, model or world transforms ([Pose.h L58–L107](https://github.com/o3de/o3de/blob/2462b90ee389939336931a14e234fc4e3b4cd534/Gems/EMotionFX/Code/EMotionFX/Source/Pose.h#L58-L107)).
- **Godot** writes into each bone's local pose; `SkeletonModifier3D`s (IK, physics) then run "after playback process of the AnimationMixer" ([SkeletonModifier3D.xml L6–L10](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/doc/classes/SkeletonModifier3D.xml#L6-L10)).
- **Bevy** writes directly into each bone entity's local `Transform`, in `PostUpdate` before transform propagation ([lib.rs L1322–L1340](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_animation/src/lib.rs#L1322-L1340)).

### Options for FenrirEngine

- **Fixed layers versus a graph:** a fixed stack (base clip, crossfade, optional additive and masked layers, as ozz's one job or Unity's layers) covers the map's first spec and needs no asset format. A node graph (Bevy's three-node DAG is the smallest shown) or a state machine is what the map files under "richer animation".
- **Masks:** per-bone weights (ozz, Unreal's blend depth) allow soft edges; bitmask groups (Bevy) are cheap but binary; name filters (Godot, EMotionFX) are editor-friendly and need resolving to indices.
- **Pose type:** a local-space array per skeleton, converted to model space once per frame for skinning, physics and attachments (ozz, EMotionFX), versus writing straight into ECS transforms (Bevy). A pose type that carries both arrays, as EMotionFX's, suits a later ragdoll stage that works in model or world space.

## Skinning

### CPU or GPU, and the bone-matrix buffer

- **Bevy:** vertex shader skinning from a buffer of `mat4` joint matrices, a storage buffer with a per-mesh offset where supported and a uniform buffer otherwise ([skinning.wesl L4–L38](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_pbr/src/render/skinning.wesl#L4-L38)). The joint matrices are world-space (joint `GlobalTransform` × inverse bind pose), so the skin matrix replaces the mesh's model matrix ([mesh.wesl L45–L48](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_pbr/src/render/mesh.wesl#L45-L48)). The previous frame's matrices are kept for motion vectors ([skinning.wesl L9–L18](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_pbr/src/render/skinning.wesl#L9-L18)). `MAX_JOINTS = 256` per mesh ([skin.rs L28](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_pbr/src/render/skin.rs#L28)).
- **Godot:** a compute shader reads source vertices, bone indices and weights (packed 16-bit) and 3×4 bone matrices, and writes a destination vertex buffer that is then drawn like any mesh ([skeleton.glsl L9–L37, L251–L282](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/servers/rendering/renderer_rd/shaders/skeleton.glsl#L251-L282)).
- **Unreal:** three paths: the GPU skin vertex factory (vertex shader), the Skin Cache (compute shader, results cached in vertex buffers), and mesh deformers ([Skeletal Mesh Rendering Paths](https://dev.epicgames.com/documentation/en-us/unreal-engine/skeletal-mesh-rendering-paths-in-unreal-engine)). Sections with too many bones are split into chunks, one draw each; mobile caps sections at 75 bones.
- **Unity Entities Graphics:** "Mesh deformations are compute shader based by default"; skinning is driven by writing `SkinMatrix` components, and the vertex-shader path "will not be supported in the future" ([Mesh deformations](https://docs.unity3d.com/Packages/com.unity.entities.graphics@1.4/manual/mesh_deformations.html)). The same page says OpenGLCore is not supported on desktop.
- **ozz:** the library ships a CPU `SkinningJob` that skins positions, normals and tangents with "any number of joints influences per vertex"; matrices "must be pre-multiplied with the inverse of the skeleton bind-pose matrices", and an optional inverse-transpose set handles non-uniform scale ([skinning_job.h L41–L74](https://github.com/guillaumeblanc/ozz-animation/blob/744eb9d99f606eda849acb0b1204f7a3dc20bca1/include/ozz/geometry/runtime/skinning_job.h#L41-L74)). GPU skinning is the application's job.

### Bone limits per vertex

- **Bevy:** 4 (`JOINT_INDEX` as `Uint16x4`, `JOINT_WEIGHT` as `Float32x4`) ([mesh.rs L416–L423](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_mesh/src/mesh.rs#L416-L423)).
- **Godot:** 4 or 8, by the `ARRAY_FLAG_USE_8_BONE_WEIGHTS` flag ([Mesh.xml L253–L256](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/doc/classes/Mesh.xml#L253-L256)).
- **Unity:** quality setting `SkinWeights` of 1, 2, 4 or Unlimited ([GraphicsEnums.cs L244–L251](https://github.com/Unity-Technologies/UnityCsReference/blob/6c1fc7919aa64a2698e06922c4516eb1daa91b75/Runtime/Export/Graphics/GraphicsEnums.cs#L244-L251)); meshes store variable counts as `bonesPerVertex` plus a flat `BoneWeight1` array ([Mesh.bindings.cs L207–L226](https://github.com/Unity-Technologies/UnityCsReference/blob/6c1fc7919aa64a2698e06922c4516eb1daa91b75/Runtime/Export/Graphics/Mesh.bindings.cs#L207-L226)).
- **Unreal:** 4 or 8 by platform, fixed slots with zero weights filling the rest; "Unlimited Bone Influences" stores an offset and count per vertex into a separate buffer, capped at 12 in practice ([Skeletal Mesh Rendering Paths](https://dev.epicgames.com/documentation/en-us/unreal-engine/skeletal-mesh-rendering-paths-in-unreal-engine)).
- **ozz:** any; the samples split meshes into parts by influence count, since the job's loop is specialised per count ([skinning_job.h L62–L66](https://github.com/guillaumeblanc/ozz-animation/blob/744eb9d99f606eda849acb0b1204f7a3dc20bca1/include/ozz/geometry/runtime/skinning_job.h#L62-L66)).

### Dual quaternions

- **EMotionFX's renderer integration defaults to dual-quaternion skinning**: `SkinningMethod m_skinningMethod = SkinningMethod::DualQuat` ([RenderActorInstance.h L65](https://github.com/o3de/o3de/blob/2462b90ee389939336931a14e234fc4e3b4cd534/Gems/EMotionFX/Code/Source/Integration/Rendering/RenderActorInstance.h#L65)).
- The Bevy and Godot shaders read are linear blend skinning only; the Unreal and Unity pages read do not mention dual quaternions; ozz's job is linear.

### Options for FenrirEngine

- **GPU vertex shader from a bone-matrix buffer** (Bevy, Unreal's default path): least plumbing, but every pass that draws the mesh (each shadow map later) skins again, and each skinned draw needs its buffer bound.
- **Compute pre-pass into a vertex buffer** (Godot, Unreal's skin cache, Unity Entities): skin once per frame, then draw as a static mesh in every pass; the same "vertices change every frame" path that soft bodies need (`notes.md`). It needs compute shaders, which OpenGL has from 4.3 and which the graphics seam would have to expose; Unity's note that OpenGLCore is unsupported for this path is a warning about how backends differ.
- **CPU skinning** (ozz's job) needs no shader work and suits a first demo, but costs bandwidth every frame.
- **Buffer layout:** world-space skin matrices (Bevy) fold the model matrix in, which suits per-instance buffers; model-space matrices (ozz) let several instances share one buffer and keep the usual model matrix. A storage buffer with offsets avoids uniform-size limits (Bevy's 256-joint cap comes from the uniform path).
- **Influences:** 4 per vertex is the common floor; 8 doubles the attribute size; variable counts need an indirection buffer.

## Ragdolls

### Mapping bones to bodies and joints

- **Unreal:** a skeletal mesh has one `UPhysicsAsset`, "a set of rigid bodies and constraints that make up a single ragdoll", holding `SkeletalBodySetups` and `ConstraintSetup` arrays, a collision-disable table between body pairs, and named physical-animation and constraint profiles ([UPhysicsAsset](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/UPhysicsAsset)). Each body names its bone (`BoneName`: "Associates this Body with Bone in a skeletal mesh") ([UBodySetupCore](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/PhysicsCore/UBodySetupCore)); each constraint names two bones, `ConstraintBone1` and `ConstraintBone2` ([FConstraintInstance](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/FConstraintInstance)). Bones without a body follow the nearest controlling body, `FindControllingBodyIndex`.
- **Godot:** one `PhysicalBone3D` node per simulated bone under a `PhysicalBoneSimulator3D`; it names its bone by `bone_name`, resolved to an index ([physical_bone_3d.cpp L1184–L1186, L1304–L1312](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/scene/3d/physics/physical_bone_3d.cpp#L1304-L1312)). Each has a `body_offset` from the bone, a `joint_offset`, and a joint type (none, pin, cone, hinge, slider, 6DOF) ([physical_bone_3d.h L48–L53](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/scene/3d/physics/physical_bone_3d.h#L48-L53)). The joint's other body is the nearest ancestor bone that has a physical bone ([physical_bone_simulator_3d.cpp L177–L192](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/scene/3d/physics/physical_bone_simulator_3d.cpp#L177-L192)).
- **Unity:** the Ragdoll Wizard adds colliders, Rigidbodies and Character Joints to the limbs you drag in ([Create a ragdoll](https://docs.unity3d.com/6000.2/Documentation/Manual/wizard-RagdollWizard.html)); there is no ragdoll asset, the components sit on the bone GameObjects.
- **EMotionFX:** the actor's `PhysicsSetup` holds a `RagdollConfiguration` ([PhysicsSetup.h L38–L56](https://github.com/o3de/o3de/blob/2462b90ee389939336931a14e234fc4e3b4cd534/Gems/EMotionFX/Code/EMotionFX/Source/PhysicsSetup.h#L38-L56)); `RagdollInstance` keeps two-way index maps between skeleton joints and ragdoll nodes ([RagdollInstance.h L52–L62](https://github.com/o3de/o3de/blob/2462b90ee389939336931a14e234fc4e3b4cd534/Gems/EMotionFX/Code/EMotionFX/Source/RagdollInstance.h#L52-L62)).
- **Jolt:** `RagdollSettings` has its own `Skeleton` and one `Part` per joint, each a `BodyCreationSettings` plus `mToParent` constraint settings, "1-on-1 with mSkeleton.GetJoints()", plus additional non-parent constraints ([Ragdoll.h L89–L125](https://github.com/jrouwe/JoltPhysics/blob/e77f175595e64cb44218cc9d9d56fc365ad0e36a/Jolt/Physics/Ragdoll/Ragdoll.h#L89-L125)). It can build a collision filter that disables collisions between parent and child joints, and between joints overlapping in a given pose ([L35–L43](https://github.com/jrouwe/JoltPhysics/blob/e77f175595e64cb44218cc9d9d56fc365ad0e36a/Jolt/Physics/Ragdoll/Ragdoll.h#L35-L43)). `SkeletonMapper` maps "a low detail (ragdoll) skeleton to a high detail (animation) skeleton and vice versa", with 1-on-1 joints, chains between mapped joints, and unmapped joints ([SkeletonMapper.h L12–L60](https://github.com/jrouwe/JoltPhysics/blob/e77f175595e64cb44218cc9d9d56fc365ad0e36a/Jolt/Skeleton/SkeletonMapper.h#L12-L60)).

### Going limp and partial ragdolls

- **Unreal:** per body, `PhysicsBlendWeight` is the "Influence of rigid body physics (blending) on the mesh's pose (0.0 == use only animation, 1.0 == use only physics)" ([FBodyInstance](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/FBodyInstance)). The component sets subtrees: `SetAllBodiesBelowSimulatePhysics`, `SetAllBodiesBelowPhysicsBlendWeight`, `AccumulateAllBodiesBelowPhysicsBlendWeight`; `KinematicBonesUpdateType` chooses whether non-simulated bodies follow the animation ([USkeletalMeshComponent](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/USkeletalMeshComponent)). Inside the AnimGraph, the RigidBody node runs a light simulation of the physics asset as a graph node, typically for secondary parts such as ponytails, with the rest kinematic ([RigidBody](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-blueprint-rigid-body-in-unreal-engine)).
- **Godot:** `physical_bones_start_simulation(bones)` simulates the named bones and their descendants, or the whole body if none are named ([PhysicalBoneSimulator3D.xml L34–L41](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/doc/classes/PhysicalBoneSimulator3D.xml#L34-L41), [physical_bone_simulator_3d.cpp L279–L300](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/scene/3d/physics/physical_bone_simulator_3d.cpp#L279-L300)). Each simulated body writes its pose back as the bone's skeleton-space pose ([physical_bone_3d.cpp L823–L835](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/scene/3d/physics/physical_bone_3d.cpp#L823-L835)); non-simulated ones are reset to follow the bone ([physical_bone_simulator_3d.cpp L370–L388](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/scene/3d/physics/physical_bone_simulator_3d.cpp#L370-L388)). The simulator is a `SkeletonModifier3D`, so its whole result is blended with the animated pose by one `influence` value, interpolating each bone's local pose ([skeleton_3d.cpp L1239–L1270](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/scene/3d/skeleton_3d.cpp#L1239-L1270); [SkeletonModifier3D.xml L57–L60](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/doc/classes/SkeletonModifier3D.xml#L57-L60)). Godot has no motors driving bones to the animation.
- **EMotionFX:** the ragdoll is a node in the anim graph. Its input is a target pose; for joints it simulates, it copies the ragdoll's world transforms in and recomputes local transforms, and other joints come from the target pose ([BlendTreeRagdollNode.cpp L188–L301](https://github.com/o3de/o3de/blob/2462b90ee389939336931a14e234fc4e3b4cd534/Gems/EMotionFX/Code/EMotionFX/Source/BlendTreeRagdollNode.cpp#L188-L301)). Because a ragdoll state rides along with every pose, ordinary blend nodes blend it: blending kinematic to simulated starts at maximum joint strength and lerps to the target strength, and the reverse lerps back to maximum before switching to kinematic, to avoid pops ([PoseDataRagdoll.cpp L87–L127](https://github.com/o3de/o3de/blob/2462b90ee389939336931a14e234fc4e3b4cd534/Gems/EMotionFX/Code/EMotionFX/Source/PoseDataRagdoll.cpp#L87-L127)).
- **Jolt:** `SetPose` teleports the bodies, `GetPose` reads world-space joint matrices back from the bodies ([Ragdoll.h L165–L178](https://github.com/jrouwe/JoltPhysics/blob/e77f175595e64cb44218cc9d9d56fc365ad0e36a/Jolt/Physics/Ragdoll/Ragdoll.h#L165-L178)). Going limp is stopping the drive; blending the read-back pose with an animated pose is left to the caller.

### Powered ragdolls

- **Unreal:** `UPhysicalAnimationComponent` drives bodies towards the animated pose with constraint motors; per body, `FPhysicalAnimationData` sets orientation, angular velocity, position and velocity strengths, max linear and angular force, and whether targets are local (relative to the parent body) or world ([FPhysicalAnimationData](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/FPhysicalAnimationData)). Profiles are applied to a body and all below it, and `StrengthMultiplyer` scales every motor, "can blend from 0-1 for example" ([UPhysicalAnimationComponent](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/UPhysicalAnimationComponent)). The component is marked `Experimental`. The skeletal mesh also has `bUpdateJointsFromAnimation`, which passes joint targets to "motorized joints to drive the ragdoll based on the animation" ([USkeletalMeshComponent](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/USkeletalMeshComponent)).
- **EMotionFX:** joint strength and damping ratio are per-joint pose data, set or multiplied by a "Ragdoll Strength Modifier" node ([BlendTreeRagdollStrengthModifierNode.h L39–L49](https://github.com/o3de/o3de/blob/2462b90ee389939336931a14e234fc4e3b4cd534/Gems/EMotionFX/Code/EMotionFX/Source/BlendTreeRagdollStrengthModifierNode.h#L39-L49)); after the graph runs, kinematic ragdoll nodes are moved to the final pose and the target state is queued to physics ([RagdollInstance.cpp L160–L174](https://github.com/o3de/o3de/blob/2462b90ee389939336931a14e234fc4e3b4cd534/Gems/EMotionFX/Code/EMotionFX/Source/RagdollInstance.cpp#L160-L174)).
- **Jolt:** `DriveToPoseUsingMotors(pose)` activates each constraint's motor towards the pose, and an overload takes the previous pose and a time step to drive velocity as well; `DriveToPoseUsingKinematics` sets body velocities so they reach the pose in one step ([Ragdoll.h L180–L193](https://github.com/jrouwe/JoltPhysics/blob/e77f175595e64cb44218cc9d9d56fc365ad0e36a/Jolt/Physics/Ragdoll/Ragdoll.h#L180-L193)).
- **Godot, Unity, Bevy:** no built-in powered ragdoll.

### Options for FenrirEngine

The map keeps physics and animation independent: physics writes bone transforms as plain data, glue lives in app code or the physics map's ragdoll spec. Within that:

- **Bone-to-body mapping as plain data:** a list of entries, each a bone (index or name), a body shape and offset, and a constraint to the parent body (Unreal's physics asset, Godot's physical bones, Jolt's `Part`s). Jolt's ragdoll needs its own `Skeleton` with one part per joint, so either the ragdoll skeleton is a reduced copy of the animation skeleton plus an index map (what `SkeletonMapper` provides), or every animation bone gets a part. Unmapped bones follow the nearest mapped ancestor in all engines read.
- **Where the blend happens:**
  - a per-bone weight between animated and simulated pose, applied after animation (Unreal's `PhysicsBlendWeight`), which handles going limp, partial ragdolls (weight on a subtree) and fading back;
  - one influence value for the whole simulator (Godot), simpler but all-or-nothing per ragdoll;
  - a ragdoll node inside the blend graph whose state blends like a pose (EMotionFX), the most flexible and tied to having a graph.
- **Space:** physics gives world-space body transforms; the blend needs them back in the skeleton's model or local space (Godot inverts the skeleton's global transform; EMotionFX recomputes local transforms). Blending in local space keeps children attached; blending in model space keeps simulated limbs where physics put them.
- **Powered ragdolls** need the animated pose sent to physics each step (Jolt's `DriveToPoseUsingMotors` takes a `SkeletonPose`), plus per-body strengths (Unreal's profile, EMotionFX's per-joint strength). On the map these motors are physics's side; the animation side needs only to publish the target pose as plain data, and to accept the simulated pose back.

## Libraries: ozz-animation, and what it would leak

### What ozz offers

- **Runtime:** `Skeleton`, `Animation`, sampling, blending (with per-joint and additive layers), local-to-model, float and vector tracks with edge triggering, two-bone and aim IK, motion blending ([include/ozz/animation/runtime](https://github.com/guillaumeblanc/ozz-animation/tree/744eb9d99f606eda849acb0b1204f7a3dc20bca1/include/ozz/animation/runtime)), and CPU skinning ([include/ozz/geometry/runtime/skinning_job.h](https://github.com/guillaumeblanc/ozz-animation/blob/744eb9d99f606eda849acb0b1204f7a3dc20bca1/include/ozz/geometry/runtime/skinning_job.h)).
- **Offline:** raw skeleton and animation types, builders, the optimizer, additive builder, motion extractor, and glTF and FBX importers ([src/animation/offline](https://github.com/guillaumeblanc/ozz-animation/tree/744eb9d99f606eda849acb0b1204f7a3dc20bca1/src/animation/offline)). The FBX pipeline requires the Autodesk FBX SDK; glTF needs nothing extra ([CMakeLists.txt L16–L26](https://github.com/guillaumeblanc/ozz-animation/blob/744eb9d99f606eda849acb0b1204f7a3dc20bca1/CMakeLists.txt#L16-L26)). Samples cover playback, blend, partial blend, additive, attach, skinning, IK, motion extraction and multithreading ([samples](https://github.com/guillaumeblanc/ozz-animation/tree/744eb9d99f606eda849acb0b1204f7a3dc20bca1/samples)).
- **Not offered:** playback state, crossfade timing, graphs or state machines, events beyond threshold tracks, GPU skinning, ragdolls.
- **Licence:** MIT ([LICENSE.md](https://github.com/guillaumeblanc/ozz-animation/blob/744eb9d99f606eda849acb0b1204f7a3dc20bca1/LICENSE.md)). Jobs do not own their input or output buffers; the caller allocates them, and the multithread sample runs jobs on worker threads ([sampling_job.h L54–L55](https://github.com/guillaumeblanc/ozz-animation/blob/744eb9d99f606eda849acb0b1204f7a3dc20bca1/include/ozz/animation/runtime/sampling_job.h#L54-L55)).

### What it would leak through a seam

- **Math types:** poses are `ozz::math::SoaTransform` (four joints per element) and model-space output is `ozz::math::Float4x4` ([local_to_model_job.h L51–L59](https://github.com/guillaumeblanc/ozz-animation/blob/744eb9d99f606eda849acb0b1204f7a3dc20bca1/include/ozz/animation/runtime/local_to_model_job.h#L51-L59)). Exposing poses as glm types means converting at the seam each frame, or exposing poses only as opaque handles and copying out model-space matrices for skinning and physics.
- **Joint order and limits:** the skeleton reorders joints depth-first and caps them at 1024 ([skeleton.h L51–L71](https://github.com/guillaumeblanc/ozz-animation/blob/744eb9d99f606eda849acb0b1204f7a3dc20bca1/include/ozz/animation/runtime/skeleton.h#L51-L71)), so meshes and ragdoll mappings must use ozz's indices, or a remap (as the samples' `joint_remaps`).
- **Asset format:** runtime skeletons and clips are ozz's own binary archives built offline; importing at runtime means running the builders.
- **Time as a ratio:** sampling takes a normalised ratio, so seconds, speed and looping sit in FenrirEngine's own playback state.
- **ADR-0010:** keeping ozz `PRIVATE` is plausible because its outputs are plain arrays; what must not appear in public headers is `SoaTransform`, `ozz::span` and its archive types.

### Alternatives

- **Write it in-house:** the runtime core (sample keys, blend local poses, local-to-model, upload matrices) is small; ozz's value is the compression, the SoA speed, the optimizer and the importers.
- **ACL** for compression only, MIT and header-only, used by Unreal as its default codec ([ACL README](https://github.com/nfrechette/acl); [Animation Compression Library](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-compression-library-in-unreal-engine)).
- **Jolt** already in FenrirPhysics has a skeleton, pose and a simple `SkeletalAnimation` ([SkeletalAnimation.h](https://github.com/jrouwe/JoltPhysics/blob/e77f175595e64cb44218cc9d9d56fc365ad0e36a/Jolt/Skeleton/SkeletalAnimation.h)), but using it from the animation package would make animation depend on the physics backend, against the map's "packages stay independent".

## Gaps

- Unreal's and Unity's native implementation was not read (closed or account-gated); their claims rest on the official API reference and manual.
- Unity's ECS animation: no shipped Entities animation package was found. Unity's Q1 2025 roadmap post targeted a new animation system "during the Unity 6 release lifecycle" without a version ([Animation Status Update (Q1 2025)](https://discussions.unity.com/t/animation-status-update-q1-2025-gdc-roadmap/1614718)), a forum source, not docs.
- O3DE's Atom skinning shaders (and their influence limits) were not read; only EMotionFX's default skinning method is cited.
- Godot's motors: none found in `PhysicalBone3D`; a future version may differ.

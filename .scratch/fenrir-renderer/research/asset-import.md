# How engines import and own meshes, textures, shaders, skeletons and clips

Research for [06-asset-import-and-ownership](../issues/06-asset-import-and-ownership.md). This file reports what the candidate importers do, what glTF 2.0 carries and where exported files go wrong, and how Bevy and Godot name, share, load and unload assets. It does not choose anything for FenrirRenderer or the animation package.

Sources are library and engine source on GitHub, pinned to the commit read, plus the libraries' own docs and the glTF specification. Line numbers refer to those commits:

### assimp

- **Formats and model.** "More than 40 file formats for import" into "a shared, in-memory format", with post-processing steps such as normal and tangent generation, triangulation and vertex-cache optimisation ([README](https://github.com/assimp/assimp/blob/c3f68d29c4237435652ec242e00928d5dd2b3011/README.md); [Fileformats.md](https://github.com/assimp/assimp/blob/c3f68d29c4237435652ec242e00928d5dd2b3011/doc/Fileformats.md)). Its glTF 2.0 importer lists only four extensions: `KHR_lights_punctual`, `KHR_materials_pbrSpecularGlossiness`, `KHR_materials_unlit`, and `KHR_texture_transform` "under test" (same file).
- **Licence:** BSD-style, three clauses ([LICENSE](https://github.com/assimp/assimp/blob/c3f68d29c4237435652ec242e00928d5dd2b3011/LICENSE)).
- **Build cost.** Every importer and exporter is on by default (`ASSIMP_BUILD_ALL_IMPORTERS_BY_DEFAULT` and `..._EXPORTERS_...` default `TRUE`; [code/CMakeLists.txt L249–L285](https://github.com/assimp/assimp/blob/c3f68d29c4237435652ec242e00928d5dd2b3011/code/CMakeLists.txt#L249-L285)), so a lean build switches them off and re-enables the few wanted, as DemoApp does. The tree vendors zlib, draco, pugixml, rapidjson, poly2tri, clipper, earcut, openddlparser, utf8cpp, unzip/zip, tinyusdz and stb under `contrib/` ([contrib](https://github.com/assimp/assimp/tree/c3f68d29c4237435652ec242e00928d5dd2b3011/contrib)). On Windows the draco sources have paths long enough that a plain `git clone` failed to check out here without `core.longpaths`.
- **Skins: bones live on the mesh, joined to the hierarchy by name.** `aiMesh` holds `mBones` ([mesh.h L762–L770](https://github.com/assimp/assimp/blob/c3f68d29c4237435652ec242e00928d5dd2b3011/include/assimp/mesh.h#L762-L770)). An `aiBone` has a name "by which it can be found in the frame hierarchy", per-vertex weights, and `mOffsetMatrix`, "mesh space to bone space in bind pose ... sometimes called an inverse-bind matrix" ([mesh.h L257–L308](https://github.com/assimp/assimp/blob/c3f68d29c4237435652ec242e00928d5dd2b3011/include/assimp/mesh.h#L257-L308)). Pointers from a bone to its node and armature root (`mNode`, `mArmature`) are filled only with `aiProcess_PopulateArmatureData` ([mesh.h L277–L290](https://github.com/assimp/assimp/blob/c3f68d29c4237435652ec242e00928d5dd2b3011/include/assimp/mesh.h#L277-L290); [postprocess.h L330–L339](https://github.com/assimp/assimp/blob/c3f68d29c4237435652ec242e00928d5dd2b3011/include/assimp/postprocess.h#L330-L339)). A separate `aiSkeleton` that decouples bones from meshes is "experimental" (`AI_CONFIG_FBX_USE_SKELETON_BONE_CONTAINER`, [config.h.in L690–L698](https://github.com/assimp/assimp/blob/c3f68d29c4237435652ec242e00928d5dd2b3011/include/assimp/config.h.in#L690-L698); [mesh.h L1140](https://github.com/assimp/assimp/blob/c3f68d29c4237435652ec242e00928d5dd2b3011/include/assimp/mesh.h#L1140)). So a skeleton has to be rebuilt by matching bone names against `aiNode` names.
- **Weights per vertex.** No limit by default (`AI_MAX_BONE_WEIGHTS` is `0x7fffffff`, [mesh.h L83–L85](https://github.com/assimp/assimp/blob/c3f68d29c4237435652ec242e00928d5dd2b3011/include/assimp/mesh.h#L83-L85)); `aiProcess_LimitBoneWeights` cuts to 4 (configurable) and renormalises ([postprocess.h L234–L248](https://github.com/assimp/assimp/blob/c3f68d29c4237435652ec242e00928d5dd2b3011/include/assimp/postprocess.h#L234-L248); [config.h.in L324–L329](https://github.com/assimp/assimp/blob/c3f68d29c4237435652ec242e00928d5dd2b3011/include/assimp/config.h.in#L324-L329)). `aiProcess_Debone` removes bones that exporters add to static meshes ([postprocess.h L544–L556](https://github.com/assimp/assimp/blob/c3f68d29c4237435652ec242e00928d5dd2b3011/include/assimp/postprocess.h#L544-L556)).
- **Clips: keyed by node name, absolute keys, time in ticks.** An `aiNodeAnim` names the node it drives; keys "replace the node's original transformation ... all keys are absolute and not relative to the bone default pose", applied scale, rotation, translation ([anim.h L278–L293](https://github.com/assimp/assimp/blob/c3f68d29c4237435652ec242e00928d5dd2b3011/include/assimp/anim.h#L278-L293)). `aiAnimation::mDuration` is in ticks and `mTicksPerSecond` is "0 if not specified in the imported file" ([anim.h L424–L450](https://github.com/assimp/assimp/blob/c3f68d29c4237435652ec242e00928d5dd2b3011/include/assimp/anim.h#L424-L450)). Morph targets come as `aiAnimMesh` plus mesh channels ([mesh.h L801–L811](https://github.com/assimp/assimp/blob/c3f68d29c4237435652ec242e00928d5dd2b3011/include/assimp/mesh.h#L801-L811)).
- **Hierarchy and scale.** Output is right-handed, Y-up by default; `aiProcess_MakeLeftHanded` flips it ([postprocess.h L100–L114](https://github.com/assimp/assimp/blob/c3f68d29c4237435652ec242e00928d5dd2b3011/include/assimp/postprocess.h#L100-L114)). The FBX importer keeps pivots as extra nodes by default (`AI_CONFIG_IMPORT_FBX_PRESERVE_PIVOTS`, default true, [config.h.in L634–L641](https://github.com/assimp/assimp/blob/c3f68d29c4237435652ec242e00928d5dd2b3011/include/assimp/config.h.in#L634-L641)), and centimetre-to-metre conversion is an opt-in (`AI_CONFIG_FBX_CONVERT_TO_M`, [L668–L676](https://github.com/assimp/assimp/blob/c3f68d29c4237435652ec242e00928d5dd2b3011/include/assimp/config.h.in#L668-L676)). `aiProcess_GlobalScale` applies a scale factor the caller supplies ([postprocess.h L561–L570](https://github.com/assimp/assimp/blob/c3f68d29c4237435652ec242e00928d5dd2b3011/include/assimp/postprocess.h#L561-L570)). `aiProcess_PreTransformVertices` flattens the hierarchy and drops animations; `aiProcess_OptimizeGraph` merges nodes ([postprocess.h L218–L232, L488–L500](https://github.com/assimp/assimp/blob/c3f68d29c4237435652ec242e00928d5dd2b3011/include/assimp/postprocess.h#L218-L232)), both of which break skeletons if used carelessly.

### cgltf

- **Scope.** "Single-file/stb-style C glTF loader and writer"; core glTF 2.0 including skins, animations, morph targets, and a long list of extensions including `EXT_meshopt_compression`, `KHR_texture_basisu` and Draco (with an external decoder) ([README](https://github.com/jkuhlmann/cgltf/blob/85cd62382dfea638278962690cf515023f33ed00/README.md)). Used in bgfx, Filament, gltfpack and raylib (same).
- **Licence:** MIT ([cgltf.h L1–L4](https://github.com/jkuhlmann/cgltf/blob/85cd62382dfea638278962690cf515023f33ed00/cgltf.h#L1-L4)).
- **What it does and does not do.** `cgltf_parse` reads the JSON; external buffers and images are not loaded unless you call `cgltf_load_buffers`, and image data is never decoded ([README](https://github.com/jkuhlmann/cgltf/blob/85cd62382dfea638278962690cf515023f33ed00/README.md)). `cgltf_validate` performs extra checks on request ([cgltf.h L52–L53](https://github.com/jkuhlmann/cgltf/blob/85cd62382dfea638278962690cf515023f33ed00/cgltf.h#L52-L53)). Memory and file callbacks can be supplied ([L134–L146](https://github.com/jkuhlmann/cgltf/blob/85cd62382dfea638278962690cf515023f33ed00/cgltf.h#L134-L146)).
- **Skins, hierarchy, clips.** The data is the glTF document with indices turned into pointers: `cgltf_skin` holds `joints` (node pointers), `skeleton`, and the `inverse_bind_matrices` accessor ([L638–L646](https://github.com/jkuhlmann/cgltf/blob/85cd62382dfea638278962690cf515023f33ed00/cgltf.h#L638-L646)); animation samplers and channels mirror the spec ([L725–L740](https://github.com/jkuhlmann/cgltf/blob/85cd62382dfea638278962690cf515023f33ed00/cgltf.h#L725-L740)). Helpers compute a node's world matrix and read or unpack accessors as floats ([L867–L886](https://github.com/jkuhlmann/cgltf/blob/85cd62382dfea638278962690cf515023f33ed00/cgltf.h#L867-L886)). Everything glTF-specific (units, skinning rules, clamping) is left to the caller, which section 2 describes.

### fastgltf

- **Scope.** C++20 glTF 2.0 library, "the entirety of glTF 2.0 specification, including many extensions", SIMD-accelerated; C++17 users must stay on 0.9.x, and the README says to use a tagged release, not `main` ([README](https://github.com/spnda/fastgltf/blob/cd30d761672f222265d13214b32042ca3621c919/README.md)).
- **Licence:** MIT; embeds simdjson and simdutf, both MIT (same). By default CMake downloads simdjson and simdutf if not found (`FASTGLTF_DOWNLOAD_SIMDJSON`, `..._SIMDUTF` default ON, [CMakeLists.txt L15–L16](https://github.com/spnda/fastgltf/blob/cd30d761672f222265d13214b32042ca3621c919/CMakeLists.txt#L15-L16)), which matters for offline or submodule-only builds.
- **Speed (author's figures).** On the 2CylinderEngine sample (1.7 MB base64 buffer), 24.56× faster than tinygltf and 7.4× faster than cgltf; on Bistro's 148k-line JSON, 1.4× and 5× ([docs/overview.rst L228–L245](https://github.com/spnda/fastgltf/blob/cd30d761672f222265d13214b32042ca3621c919/docs/overview.rst#L228-L245)). Those compare JSON parsing with images and buffers off.
- **Does the minimum by default.** "Without specifying any options, fastgltf will only parse the glTF JSON"; it does not decode images and has no built-in Draco ([overview.rst L25–L100](https://github.com/spnda/fastgltf/blob/cd30d761672f222265d13214b32042ca3621c919/docs/overview.rst#L25-L100)). Options load external buffers and images, generate missing indices, and `DecomposeNodeMatrices` turns `matrix` nodes into TRS, "which should simplify working with nodes, especially with animations" ([parser.hpp L186–L233](https://github.com/spnda/fastgltf/blob/cd30d761672f222265d13214b32042ca3621c919/include/fastgltf/parser.hpp#L186-L233)).
- **Skins, hierarchy, accessors.** `Skin` is `inverseBindMatrices`, `skeleton` and `joints` as indices ([types.hpp L912–L918](https://github.com/spnda/fastgltf/blob/cd30d761672f222265d13214b32042ca3621c919/include/fastgltf/types.hpp#L912-L918)). Tools iterate accessors (sparse and normalised included), copy them into caller memory, compute node transforms and walk a scene's nodes with world matrices ([tools.hpp L640–L744, L874–L885](https://github.com/spnda/fastgltf/blob/cd30d761672f222265d13214b32042ca3621c919/include/fastgltf/tools.hpp#L640-L744)). The docs show copying straight into a mapped GL buffer ([docs/tools.rst L162–L166](https://github.com/spnda/fastgltf/blob/cd30d761672f222265d13214b32042ca3621c919/docs/tools.rst#L162-L166)).

### ufbx

- **Scope.** "Single source file FBX file loader" aiming at parity with the FBX SDK: binary and ASCII FBX from version 3000, meshes, skinning, blend shapes, a unified PBR material, animation evaluation and layer blending, CPU skinning, and OBJ files too ([README](https://github.com/ufbx/ufbx/blob/5955c5c0b042ac2dc6f32955ab206aaec0620cfc/README.md)). Copy `ufbx.c` and `ufbx.h` into a project; C99 or C++11 (same).
- **Safety.** Invalid files and out-of-memory are handled; loaded scenes are sanitised; fuzzed; 95% branch coverage; tested against a 33.6 GB private corpus (same).
- **Licence:** MIT or public domain (Unlicense), your choice ([LICENSE L1–L22](https://github.com/ufbx/ufbx/blob/5955c5c0b042ac2dc6f32955ab206aaec0620cfc/LICENSE)). `0.Y.Z` minor releases may break the API (README "Versioning").
- **Skins and bind poses.** A `ufbx_skin_deformer` binds a mesh to a set of `ufbx_skin_cluster`s, one per bone; each cluster has the bone node and `geometry_to_bone` ("binding matrix from local mesh vertices to the bone", the inverse-bind matrix), plus `bind_to_world`, which it says is "not generally needed for skinning" ([ufbx.h L1979–L2045](https://github.com/ufbx/ufbx/blob/5955c5c0b042ac2dc6f32955ab206aaec0620cfc/ufbx.h#L1979-L2045)). It reports `max_weights_per_vertex` and dual-quaternion blend weights (same). Separate `ufbx_pose` objects can be marked `is_bind_pose`; FBX stores only world matrices, so the bone-to-parent matrix "is approximated from the parent world transform" ([L3444–L3470](https://github.com/ufbx/ufbx/blob/5955c5c0b042ac2dc6f32955ab206aaec0620cfc/ufbx.h#L3444-L3470)).
- **Hierarchy and scale: the FBX quirks are options.** `target_axes` and `target_unit_meters` normalise axes and units, applied either on the root node, as adjust transforms, or by modifying geometry ([L3618–L3643](https://github.com/ufbx/ufbx/blob/5955c5c0b042ac2dc6f32955ab206aaec0620cfc/ufbx.h#L3618-L3643), [L4811–L4845](https://github.com/ufbx/ufbx/blob/5955c5c0b042ac2dc6f32955ab206aaec0620cfc/ufbx.h#L4811-L4845)). FBX "geometry transforms" that move a mesh but not its children can be kept, turned into helper nodes, or baked into the mesh; non-standard scale inheritance can be kept, turned into helper nodes, compensated, or ignored ([L3645–L3709](https://github.com/ufbx/ufbx/blob/5955c5c0b042ac2dc6f32955ab206aaec0620cfc/ufbx.h#L3645-L3709)).
- **Clips.** FBX animation is stacks, layers and curves; `ufbx_bake_anim` "bakes" one to linearly interpolated keyframes and "composites the FBX transformation chain into quaternion rotations" ([L5510–L5514](https://github.com/ufbx/ufbx/blob/5955c5c0b042ac2dc6f32955ab206aaec0620cfc/ufbx.h#L5510-L5514)).

### stb_image

- JPEG (baseline and progressive), PNG 1–16 bit, TGA, BMP, PSD (composited), GIF, Radiance HDR, PIC, PNM; SIMD on SSE2 and NEON; decode from memory, `FILE`, or callbacks ([stb_image.h L1–L40](https://github.com/nothings/stb/blob/a7d4c2175630e1ea5b6f8dd00ab96fed0b97b96d/stb_image.h#L1-L40)). MIT or public domain ([L7950–L7990](https://github.com/nothings/stb/blob/a7d4c2175630e1ea5b6f8dd00ab96fed0b97b96d/stb_image.h#L7950-L7990)).
- It says it is for people "who can avoid problematic images" (L19–L21). `STBI_MAX_DIMENSIONS` defaults to 2^24 to bound memory on untrusted data, "but that's still very big" ([L361–L368](https://github.com/nothings/stb/blob/a7d4c2175630e1ea5b6f8dd00ab96fed0b97b96d/stb_image.h#L361-L368)).
- Vertical flip is a global setting with per-thread variants when the compiler has thread-locals ([L518–L525](https://github.com/nothings/stb/blob/a7d4c2175630e1ea5b6f8dd00ab96fed0b97b96d/stb_image.h#L518-L525)); a loader running on worker threads should use the thread-local versions or not flip.
- It decodes to raw pixels only: no mipmaps, no block compression. glTF's core image formats are exactly PNG and JPEG ([Specification.adoc L2313](https://github.com/KhronosGroup/glTF/blob/7cee0fcddd5730e90d488bfb5aa2e52171483dde/specification/2.0/Specification.adoc#L2313)), so stb_image covers core glTF textures.

### KTX and Basis Universal (libktx)

- KTX is "a lightweight container for textures for OpenGL, Vulkan and other GPU APIs", holding mip levels, arrays and cubemaps, in Basis Universal (ETC1S or UASTC, "quickly transcoded to any GPU-supported format"), any GL/Vulkan block-compressed format, or uncompressed ([README](https://github.com/KhronosGroup/KTX-Software/blob/2e690dd27c7ffaee0fc88966367df47e022e1b5e/README.md)).
- libktx can create the GL texture itself (`ktxTexture_GLUpload`) and transcode Basis data (`ktxTexture2_NeedsTranscoding`, `ktxTexture2_TranscodeBasis`) ([lib/include/ktx.h L1008, L1208, L1831](https://github.com/KhronosGroup/KTX-Software/blob/2e690dd27c7ffaee0fc88966367df47e022e1b5e/lib/include/ktx.h#L1008)). GL upload, Vulkan upload, KTX1 and ETC unpack are CMake options, and a read-only library can be built (`LIBKTX_VERSION_READ_ONLY`) ([lib/CMakeLists.txt L50–L58](https://github.com/KhronosGroup/KTX-Software/blob/2e690dd27c7ffaee0fc88966367df47e022e1b5e/lib/CMakeLists.txt#L50-L58); [BUILDING.md L44–L46](https://github.com/KhronosGroup/KTX-Software/blob/2e690dd27c7ffaee0fc88966367df47e022e1b5e/BUILDING.md#L44-L46)). A GL upload helper inside the decoder means the decoder has to see the graphics API, which is a seam question.
- **Licence:** Apache-2.0 for its own files, but "many other licenses" from incorporated projects, all believed compatible; `reuse spdx` gives the bill ([LICENSE.md](https://github.com/KhronosGroup/KTX-Software/blob/2e690dd27c7ffaee0fc88966367df47e022e1b5e/LICENSE.md)).
- glTF reaches KTX through `KHR_texture_basisu`: a texture's extension points at a KTX v2 image with Basis supercompression, with an optional PNG/JPEG fallback ([KHR_texture_basisu README L30–L106](https://github.com/KhronosGroup/glTF/blob/7cee0fcddd5730e90d488bfb5aa2e52171483dde/extensions/2.0/Khronos/KHR_texture_basisu/README.md#L30-L106)).

## 2. glTF 2.0 as the interchange format

All citations in this section are to [Specification.adoc](https://github.com/KhronosGroup/glTF/blob/7cee0fcddd5730e90d488bfb5aa2e52171483dde/specification/2.0/Specification.adoc) at the pinned commit, unless another file is named.

### What it carries

- **Space.** Right-handed, +Y up, front faces +Z, units metres (L692–L701). That matches the map's conventions (metres, Y-up, right-handed).
- **Hierarchy.** Nodes form "disjoint strict trees" (L759); each node has either a `matrix` or TRS, rotation a unit quaternion in XYZW (L815).
- **Skins.** A skin lists `joints` (node indices) and optionally `inverseBindMatrices`; absent, they are identity (L2038–L2042). IBMs are float `MAT4`, finite, last row `0 0 0 1` (L2064). `skeleton`, if present, must be the joints' common root (L2072). A node is not marked as a joint; "client implementations that care ... may need to traverse the `skins` array first, marking each joint node", and a joint may carry an unskinned subtree, such as a sword on a hand (L2085–L2100).
- **Skinning rule.** A skinned primitive ignores the global transform of the node that instantiates it; each vertex uses Σ Wᵢ · M(Jᵢ) · B(Jᵢ), joint world matrix times IBM (L2176–L2212). A vertex with all-zero weights therefore has no transform (same).
- **Joints and weights per vertex.** `JOINTS_n`/`WEIGHTS_n` come in VEC4 pairs, so 8 influences means two sets; clients SHOULD support at least `JOINTS_0`/`WEIGHTS_0` (L1637, L1961–L1968). Weights are non-negative; joint indices with non-zero weight unique per vertex; unorm8/16 weights MUST sum to exactly 1, float weights SHOULD be within 2·10⁻⁷ per non-zero weight of 1 (L1971–L2018).
- **Animation.** Only node TRS and morph weights are animated in core (L2999–L3010); `KHR_animation_pointer` extends this ([extensions list](https://github.com/KhronosGroup/glTF/tree/7cee0fcddd5730e90d488bfb5aa2e52171483dde/extensions/2.0/Khronos)). A channel names a node and a path; a node with `matrix` cannot have its TRS animated; each target at most once per animation (L3166–L3182). Sampler input is time in seconds from the animation's start; outside the range, values clamp (L3186–L3192). Interpolation is `STEP`, `LINEAR` or `CUBICSPLINE`; rotations interpolate as slerp, and cubic rotations must be renormalised (L3909–L4016). So a glTF "animation" is a set of node-targeted channels, not a clip bound to a skeleton; retargeting by name or index is the engine's job.
- **Morph targets.** Per-primitive `targets` of attribute deltas, default `weights` on the mesh, node `weights` override; clients SHOULD support POSITION, NORMAL, TANGENT and at least eight morphed attributes (L1773–L1950, L2147–L2149).
- **Materials.** Metallic-roughness PBR: base colour (sRGB texture × linear factor), metallic and roughness packed in G and B of a linear texture, normal, occlusion (R), emissive (sRGB) (L2560–L2790). Extensions add unlit, clearcoat, transmission, and so on (extension list). An unlit and a simple lit material, as the foundation spec plans, can be fed from `KHR_materials_unlit` and the core model.
- **Textures.** Core images are PNG or JPEG only (L2313); KTX2 via `KHR_texture_basisu` (above). `KHR_mesh_quantization` allows quantised attributes and, for skinned meshes, folds the dequantisation into the IBMs ([KHR_mesh_quantization README L78–L80](https://github.com/KhronosGroup/glTF/blob/7cee0fcddd5730e90d488bfb5aa2e52171483dde/extensions/2.0/Khronos/KHR_mesh_quantization/README.md#L78-L80)).

### What is commonly missing or wrong

The validator's issue list names the failure modes it checks, which is the best primary record of what exporters get wrong; the engines' importer code records the ones they work around.

- **Weights not normalised.** Validator error `ACCESSOR_WEIGHTS_NON_NORMALIZED` ([ISSUES.md L159](https://github.com/KhronosGroup/glTF-Validator/blob/602c54043ba66856b2e68c40fdf2bced975cdb8a/ISSUES.md#L159)). Godot renormalises every vertex on import, with the comment "glTF does not seem to normalize the weights for some reason" ([gltf_document.cpp L1686–L1705](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/modules/gltf/gltf_document.cpp#L1686-L1705)).
- **Joint index noise.** Non-zero joint indices on zero weights (`ACCESSOR_JOINTS_USED_ZERO_WEIGHT`, warning), duplicates and out-of-range indices (L149–L151).
- **Transforms on skinned-mesh nodes and their parents**, which glTF ignores but authors expect to apply: `NODE_SKINNED_MESH_LOCAL_TRANSFORMS`, `NODE_SKINNED_MESH_PARENT_TRANSFORMS`, `NODE_SKINNED_MESH_NON_ROOT`, and `ANIMATION_CHANNEL_TARGET_NODE_SKIN` ("Animated TRS properties will not affect a skinned mesh") (L32, L68–L70).
- **Bad quaternions.** `ROTATION_NON_UNIT` and non-unit quaternions in animation output (L75, L140).
- **Skeleton shape.** `SKIN_NO_COMMON_ROOT`, `SKIN_SKELETON_INVALID` (L76–L77). Godot's skin tool merges skins that are branches of one skeleton and reparents non-joint nodes found between joints, calling both "another unclear issue caused by the current glTF specification" ([skin_tool.cpp L314–L316, L465–L467](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/modules/gltf/skin_tool.cpp#L314-L316)). It also handles a node parented to a bone, which "happens when a node in Blender has Relations -> Parent set to a bone" ([gltf_document.cpp L4735–L4737](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/modules/gltf/gltf_document.cpp#L4735-L4737)).
- **Missing tangents.** `MESH_PRIMITIVE_NO_TANGENT_SPACE` and `MESH_PRIMITIVE_GENERATED_TANGENT_SPACE` ("runtime-generated tangent space may be non-portable") (L109–L115). Godot generates tangents on request (`force_generate_tangents`, [gltf_document.cpp L1784–L1825](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/modules/gltf/gltf_document.cpp#L1784-L1825)).
- **More than four influences.** Legal (two VEC4 sets) but not universal: Godot accepts 4 or 8 ([gltf_document.cpp L1686–L1755](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/modules/gltf/gltf_document.cpp#L1686-L1755)); Bevy caps a skinned mesh at 256 joints (`MAX_JOINTS`, [bevy_pbr/src/render/skin.rs L28](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_pbr/src/render/skin.rs#L28)).
- **Forward axis.** glTF's front is +Z; Bevy treats −Z as forward, so Bevy offers an experimental conversion that negates X and Z ([convert_coordinates.rs L1–L40](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_gltf/src/convert_coordinates.rs#L1-L40)).
- **Hierarchy cycles** are rejected by Bevy (`CircularChildren`), and animations with a missing sampler (`MissingAnimationSampler`) ([bevy_gltf loader/mod.rs L127–L139](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_gltf/src/loader/mod.rs#L127-L139)).

## 3. Ownership: naming, sharing, unloading, loading

### Bevy

- **Storage per type, handles into it.** Assets of type `A` live in an `Assets<A>` resource; a `Handle` is "an id-based reference to entries in the Assets collection" ([bevy_asset lib.rs L12–L16](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_asset/src/lib.rs#L12-L16)). A mesh entity carries `Mesh3d(pub Handle<Mesh>)` ([bevy_mesh components.rs L103](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_mesh/src/components.rs#L103)); many entities sharing one mesh share one handle.
- **Generation counters.** The runtime id is `AssetIndex { generation: u32, index: u32 }`, "a generational runtime-only identifier", not stable across runs ([assets.rs L21–L25](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_asset/src/assets.rs#L21-L25)). `AssetId` is that index or a UUID for assets registered under a constant id; it "can point to an Asset that no longer exists" ([id.rs L15–L44](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_asset/src/id.rs#L15-L44)).
- **Strong handles are reference counts.** `Handle::Strong(Arc<StrongHandle>)` keeps the asset alive; `Handle::Uuid` does not ([handle.rs L98–L121](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_asset/src/handle.rs#L98-L121)). When the last strong handle drops, `StrongHandle::drop` sends a drop event and the asset is freed ([L78–L96](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_asset/src/handle.rs#L78-L96)). There is no `Weak` variant any more; the weak-or-not distinction is now `Handle` versus `AssetId` (the crate docs still mention "weak handles", [lib.rs L102](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_asset/src/lib.rs#L102)).
- **The documented trade-off.** Ref counting is "simple, largely automatic", but the two failure modes are never dropping a handle (a persistent manifest keeps everything loaded) and dropping it too early (models vanish while entities remain) ([lib.rs L75–L103](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_asset/src/lib.rs#L75-L103)).
- **Asynchronous, deduplicated by path.** `AssetServer::load` "will not block"; it returns a strong handle at once and the asset appears in `Assets` when `LoadState::Loaded`; loading a path already loaded returns the existing handle ([server/mod.rs L319–L364](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_asset/src/server/mod.rs#L319-L364)). `LoadState` is `NotLoaded`, `Loading`, `Loaded`, `Failed` ([L2114–L2128](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_asset/src/server/mod.rs#L2114-L2128)); `is_loaded_with_dependencies` covers dependent assets ([lib.rs L27–L33](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_asset/src/lib.rs#L27-L33)). `AssetEvent` reports `Added`, `Modified`, `Removed` ([event.rs L50–L56](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_asset/src/event.rs#L50-L56)).
- **One file, many typed sub-assets.** A glTF yields labelled sub-assets: `Scene{}`, `Node{}`, `Mesh{}`, `Mesh{}/Primitive{}` (a Bevy `Mesh`), `Texture{}`, `Material{}`, `Animation{}` (an `AnimationClip`), `Skin{}`, `Skin{}/InverseBindMatrices` ([bevy_gltf label.rs L34–L65](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_gltf/src/label.rs#L34-L65)), addressed as `file.gltf#Label`.
- **Skeletons are entities; bind poses are an asset.** `SkinnedMesh { inverse_bindposes: Handle<SkinnedMeshInverseBindposes>, joints: Vec<Entity> }` ([bevy_mesh skinning.rs L14–L21](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_mesh/src/skinning.rs#L14-L21)). The IBMs are shared; the joints are per-instance entities with ordinary transforms. A clip is an asset keyed by `AnimationTargetId`, a UUID made from the bone's full name path, so "any animation is playable on any armature as long as the bone names match" ([bevy_animation lib.rs L160–L187](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_animation/src/lib.rs#L160-L187)); an entity says which player drives it with `AnimatedBy(Entity)` ([L215](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_animation/src/lib.rs#L215)).
- **GPU upload is a separate step.** A `RenderAsset` is extracted from the main world in `ExtractSchedule` and turned into its GPU form in `PrepareAssets` ([bevy_render render_asset.rs L40–L47](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_render/src/render_asset.rs#L40-L47)), stored in `RenderAssets<A>` keyed by the same `AssetId` ([L220](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_render/src/render_asset.rs#L220)), with an optional bytes-per-frame upload limit ([L509–L525](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_render/src/render_asset.rs#L509-L525)). `RenderAssetUsages` says whether the CPU copy stays (`MAIN_WORLD`), is freed after upload (`RENDER_WORLD` only), or never reaches the GPU; the default keeps both ([bevy_asset render_asset.rs L4–L50](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_asset/src/render_asset.rs#L4-L50)).

### Godot

- **Resources are ref-counted objects, cached by path.** `Resource` derives from `RefCounted`; "resources are reference-counted and freed when no longer in use"; a global cache keyed by path returns the cached reference for later loads and drops it when all references go ([Resource.xml L7–L9](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/doc/classes/Resource.xml#L7-L9); [resource.h L52, L197](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/core/io/resource.h#L52)). Sharing one mesh between many `MeshInstance3D` nodes is sharing one `Ref<Mesh>`.
- **Sync and async load.** `ResourceLoader::load` is synchronous; `load_threaded_request`, `load_threaded_get_status` and `load_threaded_get` load on threads, optionally with sub-threads, and a cache mode chooses reuse, replace or ignore ([resource_loader.h L249–L259](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/core/io/resource_loader.h#L249-L259); [ResourceLoader.xml L142–L144](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/doc/classes/ResourceLoader.xml#L142-L144)).
- **GPU objects are RIDs owned by servers.** A `Mesh` resource holds an RID from the `RenderingServer`; RIDs are opaque, session-only ids "used by the low-level server classes" and may correspond to a high-level `Resource` ([RID.xml L7–L9](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/doc/classes/RID.xml#L7-L9)). `RID_Alloc` packs a slot index in the low 32 bits and a validator in the high 32 bits and checks it on every lookup, the same idea as a generation counter ([rid_owner.h L157–L163, L191–L245](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/core/templates/rid_owner.h#L157-L163)). Upload happens when the surface is added: `ArrayMesh::add_surface_from_arrays` builds surface data and calls `RenderingServer::mesh_add_surface` ([mesh.cpp L1810–L1853](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/scene/resources/mesh.cpp#L1810-L1853)).
- **Import is an editor step.** Source files are imported into `res://.godot/imported/` with settings in a `.import` file beside each source; at runtime code loads through `ResourceLoader`, which finds the imported files, and reading the source with `FileAccess` "will break in the exported project" ([Import process](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/import_process.html)). Runtime glTF loading also exists through `GLTFDocument` and `GLTFState` ([GLTFDocument.xml L6–L12](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/modules/gltf/doc_classes/GLTFDocument.xml#L6-L12)).
- **Skeleton and skin split.** A `Skin` resource holds bind-pose (inverse bind) matrices and bone names or indices ([Skin.xml L7](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/doc/classes/Skin.xml#L7)); the skeleton is a `Skeleton3D` node. Godot's importer builds skeletons from glTF skins and removes duplicate skins ([skin_tool.cpp L298–L316, L756–L780](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/modules/gltf/skin_tool.cpp#L298-L316)).

### Patterns side by side

| | Bevy | Godot |
|---|---|---|
| Name for an asset | `Handle<T>` (strong, ref-counted) or `AssetId<T>` (generational index or UUID, non-owning) | `Ref<T>` (ref-counted object); RID (index + validator) for server-side data |
| Shared between entities | clone the handle | share the `Ref` |
| Deduplication | by path in `AssetServer` | by path in `ResourceCache` |
| Unload | last strong handle dropped | last reference dropped |
| Load | async only through the server; poll `LoadState` | sync `load`, or threaded request plus poll |
| GPU upload | separate, render-world prepare step; CPU copy optional | at surface creation through `RenderingServer` |
| Skeleton | joint entities + shared IBM asset | `Skeleton3D` node + `Skin` resource |
| Clip binding | by bone name path (UUID) | by node path in the animation track |

## 4. Where assets live, and procedural meshes

- **A dedicated asset package.** Bevy's `bevy_asset` is its own crate: `AssetServer`, `Assets<T>`, loaders registered per type with `register_asset_loader`, dependency tracking, hot reload behind a feature, plus an optional asset processor ([lib.rs L18–L137](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_asset/src/lib.rs#L18-L137); [processor/](https://github.com/bevyengine/bevy/tree/2614884437512e310eeb196241828162b6507533/crates/bevy_asset/src/processor)). Consumers own their types: `bevy_mesh` defines `Mesh`, `bevy_animation` defines `AnimationClip`, `bevy_gltf` is a loader that produces all of them. Godot's equivalent is `core/io` (`ResourceLoader`, `ResourceCache`), with format loaders registered into it and resource types defined where they belong (`scene/resources/mesh.cpp`).
- **Each consumer loading its own.** Neither engine does this. The cost of the alternative shows in the importers above: one glTF holds meshes, textures, materials, skins and clips together, so a renderer-only loader would have to hand skins and clips to the animation package, or both would parse the file. Bevy's single glTF loader emitting typed sub-assets is one answer; Godot's import step that splits a file into resources is another.
- **Procedural meshes use the same handles.** Bevy: "after creating an item of a type that implements Asset, you can add it to the Assets collection using `Assets::add`", and from then on it is "like any other asset"; there is no deduplication for these, so adding one per entity copies it per entity ([lib.rs L65–L73](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_asset/src/lib.rs#L65-L73); `Assets::add` [assets.rs L401](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_asset/src/assets.rs#L401)). Godot: code builds an `ArrayMesh` with `add_surface_from_arrays`, the same `Mesh` type an import produces ([mesh.cpp L1847](https://github.com/godotengine/godot/blob/679066724352c12673001d692d41dc2dab9314c0/scene/resources/mesh.cpp#L1847)). Mesh data from physics would enter the same way, through app or glue code (the map keeps physics independent of rendering).
- **Changing mesh data.** Bevy mutates the asset in `Assets<T>`, which re-extracts it, and the docs warn this changes it "for all entities using this handle" ([lib.rs L35–L53](https://github.com/bevyengine/bevy/blob/2614884437512e310eeb196241828162b6507533/crates/bevy_asset/src/lib.rs#L35-L53)). Per-frame dynamic meshes are on the map's "not yet specified" list.

## Options this leaves for FenrirRenderer and the animation package

Not a choice; the trade-offs the sources show.

**Importer**

1. **assimp only.** One dependency for glTF, FBX and OBJ, already used by DemoApp. Costs: large build unless importers are trimmed, BSD licence notice, its own converted scene where skeletons must be rebuilt from bone names, ticks rather than seconds, and few glTF extensions.
2. **cgltf or fastgltf for glTF, plus ufbx for FBX (and OBJ).** Small, permissive, close to the source formats; the engine writes the glTF rules (skinning, weights, quaternions) itself. cgltf is C, single header, no downloads; fastgltf is C++20 and faster by its own benchmarks but fetches simdjson and simdutf by default, and `main` is ahead of the last release.
3. **glTF only (cgltf or fastgltf), FBX converted offline.** Smallest runtime; artists export glTF from Blender or convert.
4. **Textures:** stb_image covers core glTF (PNG, JPEG) and HDR skyboxes but gives no mips or compression; libktx adds GPU-ready compressed textures and `KHR_texture_basisu` at the cost of a bigger dependency with mixed licences and its own GL upload path that would sit behind the graphics seam.

**Ownership**

1. **Ref-counted strong handles plus non-owning generational ids** (Bevy): automatic unload, path deduplication, both failure modes the Bevy docs list.
2. **Generational ids only, explicit unload** (like Godot's RID layer by itself): no ref counting cost or surprise unloads, but someone must call unload and stale ids must be checked.
3. **CPU asset and GPU resource as separate stages** (Bevy's extract/prepare, optional CPU copy) versus **upload at creation** (Godot's `add_surface`). The first keeps the graphics backend out of loading and fits async loading; the second is simpler.
4. **Synchronous first, async later**, or async from the start with a load state to poll.

**Where assets live**

1. **A dedicated asset package** (storage, handles, loader registry), with mesh, texture, skeleton and clip types defined by the renderer and animation packages and one glTF loader producing all of them.
2. **Each package loads its own**, with the glTF file parsed by whichever package needs it, or a shared importer library that produces plain data for both.
3. In either case, **procedural meshes are added to the same storage** and get the same handle type; skeleton instances are entities or per-instance data, with bind poses and clips shared.

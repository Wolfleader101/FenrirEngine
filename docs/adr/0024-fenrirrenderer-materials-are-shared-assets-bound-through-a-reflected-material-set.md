# FenrirRenderer's materials are shared assets, bound through a reflected material set

A material says which shader draws a mesh, with which parameters and render state. FenrirAssets already holds a `MaterialData` per imported material (ADR-0021), and every shader is GLSL compiled at build time into a shader container with reflection beside its SPIR-V (ADR-0018). The foundation needs an unlit and one lit material, a user's own shaders, and parameters set by name from C++ and C#, all through one path the lighting spec can extend.

## The decision

- **A material is one shared, plain-data asset.** `MaterialData` in FenrirAssets is the renderer's material, generalised from what a file says: a shader (an `AssetHandle<Shader>`, built-in ones under `builtin:` names), a blend mode, a `doubleSided` flag and a table of named parameters. Components hold an `AssetHandle<Material>`, so many entities share one material. *Amended 2026-10-22 (renderer foundation ticket 05):* handles are typed by the short asset name, as C#'s are: `AssetHandle<Material>`, `AssetHandle<Image>` and `AssetHandle<Shader>` resolve to `MaterialData`, `ImageData` and `ShaderData`. There are no per-entity overrides; a variation is another material made with `Add`.
- **Parameters are a name → value table.** Values are `float`, `vec2`, `vec3`, `vec4`, colour, or a texture (an `AssetHandle<Image>` with its sampler description). They are edited through FenrirAssets (`Replace`, or a narrow edit call on the handle), and each edit bumps the material's revision, so the renderer's prepare step re-uploads its block. An unknown name or a wrong type is logged once per material and ignored; a parameter the material leaves unset takes the shader's GLSL default, or zero. C# sets them by name the same way. *Amended 2026-10-21 (ticket 41):* a std140 block holds no initialisers and SPIR-V reflection carries no values, so a parameter the material leaves unset takes the default its shader declares with `#pragma fenrir default(name, values…)`, or zero (a texture: `white`, `black` or `normal`, else white). `FenrirShaderCompiler` reads the pragmas from each variant's preprocessed source, checks them against that variant's reflection, and stores the defaults and a default block image (the `MaterialParams` bytes at their std140 offsets) in the container. The material's table holds only its overrides; reads return the override or the default, and the overrides and the shader's defaults can each be read on their own (see "Parameter defaults" below).
- **A fixed binding-set convention for every material shader.** Set 0 is the frame (time, the directional light, ambient); set 1 the view (camera matrices, viewport); set 2 the material (a `MaterialParams` uniform block at binding 0, then its textures); set 3 the draw (a storage buffer of per-item world and normal matrices, indexed by base instance or `gl_DrawID`). Engine include files (`Fenrir/Frame.glsl`, `View.glsl`, `Draw.glsl`, `Vertex.glsl`) declare sets 0, 1 and 3 and the standard vertex locations.
- **The material set is reflected; the fixed sets stay declared.** This narrows ADR-0018's "layouts are declared, not reflected": the renderer core builds set 2's binding-group layout and its parameter name map (offsets, types, texture bindings) from the build-time reflection in the shader container. Sets 0, 1 and 3 are declared in C++ as ADR-0018 says, and debug builds still check them against the reflection. The reflection is written by `FenrirShaderCompiler` from GLSL source, so the names GL's SPIR-V path loses are kept and no driver reflection is involved.
- **Render state is a blend mode and a cull flag.** `Opaque`, `Masked` (with an alpha cutoff), `AlphaBlend` or `Additive`; the blend mode picks the render stage (ADR-0019: `Opaque` and `Masked` draw in `Opaque`, the blended ones in `Transparent`). Depth test is always on; depth write only for `Opaque` and `Masked`. `doubleSided` turns culling off. No stencil, depth-function or colour-mask settings.
- **Two built-in programs.** `builtin:unlit` is base colour × base-colour texture × vertex colour. `builtin:lit` is metallic-roughness with GGX specular, lit by one directional light and a constant ambient, with no image-based lighting or shadows. Their parameters are `baseColour`, `baseColourTexture`, `metallic`, `roughness`, `metallicRoughnessTexture`, `normalTexture`, `emissive` and `emissiveTexture`.
- **Lights.** A `DirectionalLight` component (colour, intensity) shines along its entity's forward axis (−Z of its world transform). The foundation uses one per active scene: the first found, with a warning logged once if there are more. Ambient is an `AmbientLight` scene resource (colour, intensity), a dim grey by default. Intensities are plain multipliers on colour; shading writes linear HDR into the scene colour target.
- **The renderer picks variants, never the user.** Keys come from the material and mesh: `ALPHA_MASK` from `Masked`, and `SKINNED` (reserved for animation) from a mesh with joints and weights. A missing texture binds a default (white for colour, flat for normals, black for emissive) instead of adding a key. *Amended 2026-10-21 (ticket 41):* which default a texture binds is its shader's `#pragma fenrir default`, white without one; the built-ins declare theirs that way. A user's shader declares its own keys in `fenrir_add_shaders`; the renderer sets the ones it knows and leaves the rest off.
- **A user's shader is a full program.** Vertex and fragment stages on the engine includes, its own `MaterialParams` block and textures in set 2, built by `fenrir_add_shaders`, loaded as a `ShaderData` asset and named by a material. The lights are in set 0, so lighting is up to the shader. No surface-function model yet.
- **Imported materials map onto the built-ins.** The importer turns a file's material into `builtin:unlit` if the file marks it unlit and `builtin:lit` otherwise, with the standard parameter names, alpha mode to blend mode, and double-sidedness kept. glTF's occlusion is dropped until the lighting spec. A texture's colour space follows its use (base colour and emissive sRGB, the rest linear), set by the first material that uses the image; a conflicting later use is warned.
- **Samplers come with the texture.** Each texture parameter carries its sampler (wrap, filter, anisotropy; from the file, else repeat, trilinear, anisotropy 8), and the renderer core deduplicates samplers by description. Mipmaps are made at upload (ADR-0021).
- **Pipelines are created lazily and cached.** A pipeline is keyed by program and variant, render state, vertex layout, and target formats and MSAA count. It is made in the prepare step the first time a draw needs it and kept while its shader asset lives. A vertex attribute the shader reads but the mesh lacks gets a constant default (normal +Y, UV 0, colour white), logged once.

## Parameter defaults

*Added 2026-10-21 (ticket 41).*

- **Declared in the shader.** `#pragma fenrir default(baseColour, 1.0, 1.0, 1.0, 1.0)` beside the `MaterialParams` block or a sampler. A pragma, not a comment, so it survives preprocessing and follows `#include`s and variant `#define`s. A member with no pragma is zero, without a warning.
- **Checked at build time, per variant.** The compiler reads the pragmas from each variant's preprocessed source, so a pragma inside an `#ifdef` applies only to the variants that define it, and each variant's reflection carries its own defaults. Against that variant's final reflection it checks type and component count. A build error stops an unknown name, a malformed pragma, a value count that does not match, two pragmas for one name in a stage, stages that disagree, and a default on a member that is not a material parameter type (an array, struct or matrix).
- **A default block image.** The container stores each default, and the whole `MaterialParams` block packed with its defaults at the reflected std140 offsets and strides. The prepare step copies the image, then writes the material's overrides over it.
- **Default textures are `white`, `black` or `normal`.** The renderer owns one shared 1×1 texture of each. `normal` is the flat tangent-space normal (0.5, 0.5, 1) in linear, in the convention `normalTexture` uses. White and black are exact in either colour space. Each is sampled with the parameter's default sampler.
- **The built-ins use the same path.** `builtin:lit` and `builtin:unlit` declare `baseColour` white, `emissive` black, `metallic` 0 and `roughness` 0.5, and their textures' defaults, by pragma. Nothing is seeded in C++. The importer keeps writing every factor a file gives, or that format's own default, so an imported glTF material keeps glTF's look (metallic 1, roughness 1).
- **A material stores only overrides.** An *override* is a value the material sets. Unset parameters are not copied in, so when a shader's default changes (a rebuild, later hot reload), unset parameters follow it and overrides stay. An override whose name or type the new shader lacks is kept, logged once and ignored.
- **Reads, the same in C++ and C#:** `TryGet…` returns the effective value (the override, else the shader's default) and fails only for a name the shader lacks or a wrong type. `TryGetOverride…` returns only an override. `IsSet(name)` says whether one exists. `Reset(name)` removes it, so the default applies again. Reads never bump the revision, and `Reset` bumps it only when it removed something. `Clone` copies overrides, not resolved defaults. A shader's reflected parameters (name, type, default) can be read from its `ShaderData` apart from any material, so an editor can show an inherited value as the shader's default and offer reset to it.

## Consequences

- The first frame to draw a new material can hitch while its pipeline is made; the foundation loads materials at start-up, and persistent pipeline caches stay on ADR-0019's waiting list.
- Light intensities are not physical units. When post-processing adds exposure and tonemapping, they become physical (lux for directional light) and existing values change meaning.
- ADR-0021's `MaterialData` is no longer only what a file says: it is the renderer's material, and the importer maps files onto it.

## Considered options

- **A renderer `Material` asset beside an import-shaped `MaterialData`.** Rejected: two types for one thing, and the renderer would need to register an asset type before FenrirAssets has a public registry.
- **Materials as component values.** Rejected: nothing is shared, and every entity copies its parameters.
- **Per-entity overrides from the start.** Deferred: a second material is cheap, and overrides can come later without changing the shared asset.
- **Lambert and Blinn-Phong for the lit material.** Rejected: imported glTF and FBX materials describe metallic-roughness and would look wrong, and the lighting spec would rewrite it.
- **Every shader's material layout declared in C++,** as ADR-0018 does for the device. Rejected: a user's shader, and C#, would need a second declaration of what the GLSL already says.
- **"Has texture" variant keys.** Rejected: default textures cost a bind, not a doubling of variants.
- **Surface functions** (the user writes only a `Surface()`, the engine the rest). Deferred to the lighting spec, when more than one light model needs them.

## When to revisit

If per-entity variation turns out to be common (add overrides), if the lighting spec needs a surface-function model, or if pipeline creation hitches during play.

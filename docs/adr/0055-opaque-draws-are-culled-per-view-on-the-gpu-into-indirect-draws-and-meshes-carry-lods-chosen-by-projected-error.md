# Opaque draws are culled per view on the GPU into indirect draws, and meshes carry LODs chosen by projected error

ADR-0051 left instancing unculled: "No per-instance culling yet. Revisit with GPU culling, through indirect draws." It showed up in a frame. LightingDemo's asteroid ring drew 100k full-detail rocks (3.3k to 6.8k triangles each) at 136 ms a frame in Release on an RTX 5080, the GPU fully busy and the CPU idle; every copy, on screen or not, goes through `DepthPrepass` and `Opaque`, and the shadow passes (ADR-0050) will each draw them again. The demo now simplifies its rock meshes by hand at spawn, at about 9 ms. Culling and levels of detail are the structural answers, done on the GPU as Unreal's Nanite and GPU Scene, Unity's GPU Resident Drawer and Bevy's GPU preprocessing do. This amends ADR-0051, and ADR-0021 (what a mesh holds).

## Where the line is

**The renderer decides, each frame, about what it was given; the game decides what to give it.** What follows from "there is a camera, some meshes and a GPU" is the renderer's, because it is the same in every game and no game can do it better: not drawing what is outside a view or behind something, not drawing more triangles than pixels, not issuing a draw per copy, not shading with lights that cannot reach a pixel. What depends on the shape of the world or on gameplay is the game's: what exists right now (streaming), how the world is cut up (a grid, a quadtree, an octree, cells and portals), what a far-off forest is replaced with (proxies, impostors), what is loaded at what resolution. An arena shooter has no answer to those because it has no such question; a voxel engine's answer is a grid of chunks; an interior's is rooms. An engine that picks one picks the game. So the renderer keeps no spatial structure of its own and no notion of a level, and gives the game the pieces instead: an entity's world bounds, the frustum maths it culls with (public, in FenrirMath), `visible`, asset revisions, and tools in FenrirAssets such as `GenerateLods`, which are optional. Its opinions are about how to draw, and each can be switched off.

Culling is two levels for this reason. The CPU culls entities by their world bounds, which a chunked world gets for free by making its chunks or cells entities, at whatever size suits it; the GPU culls copies, over a flat list, because a compute pass over a million spheres is cheap and a tree is what the GPU does worst.

## Culling

- **Every opaque and masked draw is culled on the GPU, per view**, after a coarse cull on the CPU: a lone item, a merged run or an instance list whose world bounds (a list's are the union of its copies', computed when it is uploaded) are outside the view is left out of that view's candidates. A run of merged items, an instance list's copies, and a lone item (a run of one) all go through one compute pass per view that tests each candidate's bounding sphere against the view's frustum planes and writes the survivors. Transparent items stay direct draws, culled on the CPU by their world bounds, which keeps ADR-0019's back-to-front sort.
- **A view is what a pass draws from:** a camera, each cascade of the sun, each shadowed spot light, and each shadowed point light, which culls against its range sphere and draws all six faces from one result. `DepthPrepass` and `Opaque` share their camera's result, so they draw exactly the same copies at the same detail, which `Opaque`'s equality depth test needs (ADR-0049). Each shadow ticket that lands after this one gives its views their own cull. The passes run in a new `Cull` stage, first in ADR-0049's stage list.
- **Bounds are spheres.** Each record of the draw buffer gains one: a lone or merged item's in world space, computed on the CPU (from its skinned bounds for a skinned item, ADR-0035), and an instance list's in its mesh's local space, which the pass moves by the entity's world matrix and each copy's transform, scaling the radius by the largest axis scale. A sphere test is one dot product per plane, and it may keep a copy that is off screen but never drops one that is on it.
- **The survivors reach the shader through an indirection buffer.** Set 3 binding 3 holds one entry per drawn instance: the record it reads and, for an instance list, the copy. `CurrentDraw()` in `Fenrir/Draw.glsl` reads the entry at the draw's base instance plus its instance index, which `FenrirDrawIndex()` already computes per backend, and composes as before. User shaders that read only `CurrentDraw()` need no change. The palette keeps binding 2, so it stays the third storage block GL numbers.
- **Each run draws through indirect commands.** The renderer writes a template per run and level of detail (index count, first index, base vertex, and the base instance where its survivors start, with no instances) and copies it over the view's command buffer before the cull; the pass counts survivors into it with atomics. Work groups never straddle runs: a group table, written with the templates, maps each group to its run, so one dispatch culls a whole view. Each run is then one multi-draw of one command per level of detail.
- **The graphics device gains indirect draws** (ADR-0016): an `Indirect` buffer usage, an `IndirectRead` resource usage that backends derive barriers from, and `CmdDrawIndexedIndirect { buffer, offset, drawCount, stride }`, which the GL backend replays with `glMultiDrawElementsIndirect` and the null backend records and checks. Vulkan's `vkCmdDrawIndexedIndirect` has the same command layout.
- **`RendererConfig::gpuCulling` turns culling off for comparison**, as `automaticInstancing` turns merging off: the pass still runs and still writes the indirection, but accepts every candidate at full detail, so there is one drawing path. `RendererStats::instances` stays the candidates submitted, which the CPU knows; a new count of what the GPU drew is read back once its frame has left flight, a few frames late.

## Levels of detail

- **A mesh carries its levels of detail as extra index lists over its own vertices.** `MeshData` gains `lods`: each a list of indices into the same streams and its simplification error, in the mesh's local units, coarser and with a larger error each. They share the vertex buffer, so a run's levels are commands into one index buffer and differ only in their first index and count, with no rebinding. A skinned mesh's levels share its skin.
- **The pass picks one level per surviving copy by projected error:** the coarsest level whose error, projected at the copy's distance from the camera, is below `RendererConfig::lodErrorPixels` (one pixel by default). This is a projected size test that needs no hand-set distances, and it is the same for every mesh. Shadow views choose by the camera, not the light, so a copy casts with the detail it is seen at and does not shadow itself.
- **A copy smaller than `RendererConfig::minProjectedPixels` is not drawn at all**: a level past the last, chosen by the same projection of the copy's radius. Off by default (0), since what is too small to matter depends on the game.
- **Levels are generated by meshoptimizer** (MIT), a submodule of FenrirAssets: `GenerateLods` simplifies a mesh into a chain, keeping attribute seams, with the error meshoptimizer reports scaled to local units. The engine imports glTF and FBX at load and has no cooked asset format, so levels are made at load, by the app or an import that asks for them; a build-time tool waits for a cooked format. A mesh made by hand may carry its own levels.

## Not yet

- **Occlusion culling.** The cull can later test against a hierarchical depth pyramid built from the depth prepass, in two phases: what was visible last frame draws first, the pyramid is built from it, and the rest is tested against it and drawn if it shows. It waits for a scene where hidden copies cost a frame.
- **Cluster or meshlet culling and continuous LOD** (Nanite's approach), mesh shaders, GPU-written draw lists of whole items (the CPU still resolves materials and pipelines), and LOD cross-fading.

## Considered

- **CPU culling of copies.** 100k copies a view, and as many again per shadow view, is the CPU work this ADR moves off it, and it would need the copies' transforms back on the CPU every frame. Lone items are culled on the CPU as entities, then go down the GPU path with everything else, which keeps one way to draw.
- **An octree or BVH in the renderer.** It would help only the CPU side, which culls entities, and how many entities there are and how they are grouped is the game's choice; the game that needs a tree over its chunks writes one over `Renderer::GetWorldBounds`, shaped for its world.
- **One mesh asset per level.** It leaves the renderer to pair meshes it cannot tell belong together, and costs a vertex buffer bind per level.
- **Distance thresholds per mesh.** They depend on the mesh's size and the field of view, and have to be set by hand; projected error does not.

# generate-type-registry

Writes a package's **type registration** (ADR-0074) from its API description: the generated C++ that gives FenrirTypes' run-time type registry the package's described types, so a file reader, writer or inspector can find a type by the name a file spells and walk its fields without the C++ type in hand. The package's headers stay the one place a type is written by hand and `<Package>.api.json` (`tools/describe-api`) the one record of it; this tool only turns that record into static data.

It is a .NET console program, as describe-api is, and reads only the description and the selection: never the headers.

## What it reads

The package's selection, `<Package>.api.toml`, for its `[registration]` table (describe-api accepts the table and leaves it alone), and the description `<Package>.api.json` beside it:

```toml
[registration]
header = "../include/MyPackage/Generated/MyPackageTypes.hpp"   # The generated public header.
source = "../src/Generated/MyPackageTypes.cpp"                # The generated source.
function = "Fenrir::Generated::RegisterMyPackageTypes"        # The registration function's qualified name.
includes = ["MyPackage/Components.hpp", "MyPackage/Events.hpp"] # The headers declaring the described types.
```

`header` and `source` are relative to the selection. `includes` are spelled as a source includes them, from the package's include directories. A selection without the table has no registration: the tool writes nothing for it. A missing or malformed key, or any other key, fails the tool, saying which.

## What it writes

Two files, each only when its content changes, so an unchanged registration keeps its timestamps. They are the same bytes on every platform: LF line ends, a final newline, and only ASCII (other text, a doc comment's included, is written as octal escapes in its string literals). Each starts `// Generated by tools/generate-type-registry from <Package>.api.json. Do not edit.`, then `// clang-format off`.

- **The header**, public, so code that has a described type's C++ type reaches its description through `Describe<T>` without a registry (ADR-0084): it includes `includes`, declares the registration function, and specialises `Fenrir::Describe<T>` for every described type.
- **The source**: per type a `static_assert` that its size and alignment are the description's, then its `TypeDescription` as `constexpr` data in an anonymous namespace: name, package, role, version, former names, `transient` and `editorOnly`, size and alignment from the compiler, `Construct` (value-initialisation in place) and `Destroy` (the destructor), its doc text, and
  - for a `struct` of a fixed-layout role (`component`, `event`, `scene-resource`, `app-resource`, `shared-struct`, `nested`), its fields with the offsets the description records, their kinds and element or target types, former names, doc and metadata: the table `TypeDescription::Visit` walks;
  - for a `bound-type`, its scalar components as its fields (none when the description records none);
  - for an `enum`, its enumerators and underlying kind.

  Then each `Describe<T>::Description()`, returning that object, and the registration function, which adds every description to a `TypeRegistry` in the description's order (a type after every type its fields name) and returns whether every one was added; the registry reports each it refused.

The package compiles the generated source and links `FenrirTypes`.

A description holding a category, role or kind the tool does not know fails it, naming the type (and the field). So do, for now, the types it cannot write yet, each naming the type: a `data-asset` or `settings` type and any struct holding an owning kind, which are visited by member through a generated function ticket 06 of the types spec adds; and a `tagged-union`, which FenrirTypes does not describe yet. `--skip-unsupported` leaves those out, with every type holding one, instead of failing.

## Running

From a configured build directory:

```sh
cmake --build <build-dir> --target fenrir-generate-type-registry
```

That rebuilds the tool and regenerates every registration from the committed descriptions. The ordinary build never runs it. After changing a described type's header, run `fenrir-describe-api` first, then this target, and commit both. A package joins the target in its `CMakeLists.txt` (`cmake/FenrirGenerateTypeRegistry.cmake`):

```cmake
fenrir_generate_type_registry(MyPackage api/MyPackage.api.toml)
```

`SKIP_UNSUPPORTED` after the selection passes `--skip-unsupported`. A game registers its own types the same way, from its own selection. By hand: `dotnet run --project tools/generate-type-registry/src -- <selection> [--skip-unsupported]`.

## Tests

`tests/` (xunit) generates describe-api's fixture's registration (`tools/describe-api/tests/Fixture/Fixture.api.toml`, with `--skip-unsupported`) and compares it with the committed `packages/FenrirTypes/Tests/Generated/FixtureTypes.hpp` and `.cpp` byte for byte, checks a second run rewrites nothing and a selection without `[registration]` writes nothing, and expects each failure's diagnostic: an unknown kind, element kind, role or category, an owning kind in a fixed-layout type, a data asset or settings type, and a malformed `[registration]`. CTest runs them as `GenerateTypeRegistryTests` when tests are built; by hand, `dotnet test tools/generate-type-registry/tests`. The FenrirTypes tests (`packages/FenrirTypes/Tests/GeneratedFixture.cpp`) compile the fixture's registration against the fixture header and exercise it through the registry. The fixture is also generated by `fenrir-generate-type-registry`, so regenerate it with that target after changing the tool or the fixture.

# generate-type-registry

Writes a package's **type registration** (ADR-0074) from its API description: the generated C++ that gives FenrirTypes' run-time type registry the package's described types, so a file reader, writer or inspector can find a type by the name a file spells and walk its fields without the C++ type in hand. The package's headers stay the one place a type is written by hand and `<Package>.api.json` (`tools/describe-api`) the one record of it; this tool only turns that record into static data.

It is a .NET console program, as describe-api is, and reads only the description and the selection: never the headers.

## What it reads

The package's selection, `<Package>.api.toml`, for its `[registration]` table (describe-api accepts the table and leaves it alone), and the description `<Package>.api.json` beside it:

```toml
[registration]
header = "../include/MyPackage/Generated/MyPackageTypes.hpp"   # The generated public header.
source = "../src/Generated/MyPackageTypes.cpp"                # The generated source.
function = "Fenrir::Generated::RegisterMyPackageTypes"        # The registration function's qualified name.
includes = ["MyPackage/Components.hpp", "MyPackage/Events.hpp"] # The headers declaring the described types.
uses = ["../../FenrirMath/api/FenrirMath.api.toml"]          # Optional: registrations whose types it holds.
test = "../Tests/Generated/MyPackageTypesDefaultsTests.cpp"   # Optional: the generated defaults test.
```

`header`, `source`, `test` and `uses` are relative to the selection. `includes` are spelled as a source includes them, from the package's include directories. A selection without the table has no registration: the tool writes nothing for it. A missing or malformed key, or any other key, fails the tool, saying which.

**Types another package registers.** A package's description holds the other packages' types its own hold (FenrirECS's holds FenrirMath's `Vec3`, since `Transform` does), because a binding needs them there. Each type is registered by one package only: `uses` names the selections of the packages whose registrations register them, and the tool reads their descriptions (and, through their own `uses`, theirs), skips every type they register, includes their generated headers, points its fields at their description objects, and has its registration function run theirs first. Describing such a type again would specialise its `Describe<T>` twice and register a second description under its name, which the registry refuses. A used selection with no `[registration]`, a cycle of uses, two used registrations that both register one type, and a used header under no `include` directory (a header includes it by its path below one) each fail the tool, naming them.

## What it writes

Two files, each only when its content changes, so an unchanged registration keeps its timestamps. They are the same bytes on every platform: LF line ends, a final newline, and only ASCII (other text, a doc comment's included, is written as octal escapes in its string literals). Each starts `// Generated by tools/generate-type-registry from <Package>.api.json. Do not edit.`, then `// clang-format off`.

- **The header**, public, so code that has a described type's C++ type reaches its description through `Describe<T>` without a registry (ADR-0084): it includes `includes` and the used registrations' headers, declares the registration function and each description object (`extern const Fenrir::TypeDescription`, in `<function's namespace>::<Package>Types`, where a registration using this one finds it), and specialises `Fenrir::Describe<T>` for every type it registers.
- **The source**: per type whose description records a layout a `static_assert` that its size and alignment are the description's, then its `TypeDescription` as `constexpr` data in the namespace the header declares it in: name, package, role, version, former names, `transient` and `editorOnly`, size and alignment from the compiler, `Construct` (value-initialisation in place) and `Destroy` (the destructor), a data asset's `base`, its doc text, and
  - for a `struct` of a fixed-layout role (`component`, `event`, `scene-resource`, `app-resource`, `shared-struct`, `nested`), its fields with the offsets the description records, their kinds and element or target types, former names, doc and metadata: the table `TypeDescription::Visit` walks;
  - for a `struct` visited by member, one whose description records no size (a `data-asset`, a `settings` type, a `nested` struct holding an owning kind; describe-api's `SCHEMA.md` "Owning kinds"), its fields without offsets and a generated visit function as its `visit`: it pushes the base's fields first, through the base's own visit function (ADR-0075), then each of the type's own, reached by member. A `list` or `optional` reaches its elements through `ListOperationsOf` or `OptionalOperationsOf` over the member's own type (`decltype(T::member)::value_type`), so the tool never spells a standard library type. A data asset's base must be described before it;
  - for a `bound-type`, its scalar components as its fields (none when the description records none);
  - for an `enum`, its enumerators and underlying kind;
  - for a `tagged-union`, its tag as a field whose type refuses writes through a value reference (`unionTag`), the union's offset, its alternatives (each the tag value its `tag` enumerator has, and its member as a field at the union's offset) and the index among them of the alternative its `defaultKind` names, which `Construct`, the default constructor, holds. `TypeDescription::Visit` pushes the tag, then the live alternative alone, and `SelectAlternative` switches it. The tag's enum must be described before it, each alternative's tag must name one of its enumerators, and an alternative is fixed-layout.

  Then each `Describe<T>::Description()`, returning that object, and the registration function, which runs the used registrations first, then adds every description to a `TypeRegistry` in the description's order (a type after every type its fields name and the data asset it extends) and returns whether every one was added; the registry reports each it refused. A type the registry already holds as the same description is left alone, so running a registration twice (an `Install` called twice, or two packages using one registration) registers nothing the second time and reports nothing.
- **The defaults test**, when `test` names one: a Catch2 source the package's tests compile, which for every described struct and tagged union checks that an instance default-constructed through the registered description and visited through it holds the defaults the description records, field by field: a nested struct's own defaults or the members its field's initialiser sets, a tagged union's default kind, every element of an array, the null entity and empty reference, empty lists and optionals. Every value the visit reaches has an expectation, and a value it reaches that has none fails the test. A bound type's own defaults are its library's, so a component its field's initialiser does not spell is expected as `Unchecked`: reached, not compared. A pointer is opaque. A field (not a tagged union's alternative) recording no default fails the tool, naming it. `FenrirTypesTesting/Defaults.hpp` (FenrirTypes' tests' `FenrirTypesTesting`, which the test links) walks the instance.

**Role hooks.** Once a `component`, `scene-resource` or `app-resource` type registers, the registration hands it to its role's hook, `Fenrir::AttachComponent<T>`, `AttachSceneResource<T>` or `AttachAppResource<T>` (`FenrirTypes/RoleHooks.hpp`, which declares them), so the package that knows the role hangs its attachments: a `ComponentType`, a resource's doors (ADR-0074). No other role has one. A package defining a hook (FenrirECS, FenrirScene and FenrirApp, from ticket 08 of the types spec) does so in a header that also defines the hook's macro, `FENRIR_TYPES_ATTACH_COMPONENT_DEFINED` and so on, and a registration calling the hook lists that header in `includes`. The generated header, after its includes, defines each hook its registration calls whose macro is still undefined as a no-op returning true, and defines the macro, so a package registers before the defining package exists and several registrations' headers compile together. A hook returning false makes the registration function return false.

The package compiles the generated source and links `FenrirTypes`.

A description holding a category, role or kind the tool does not know fails it, naming the type (and the field).

## Running

From a configured build directory:

```sh
cmake --build <build-dir> --target fenrir-generate-type-registry
```

That rebuilds the tool and regenerates every registration from the committed descriptions. The ordinary build never runs it. After changing a described type's header, run `fenrir-describe-api` first, then this target, and commit both. A package joins the target in its `CMakeLists.txt` (`cmake/FenrirGenerateTypeRegistry.cmake`):

```cmake
fenrir_generate_type_registry(MyPackage api/MyPackage.api.toml)
```

A game registers its own types the same way, from its own selection. By hand: `dotnet run --project tools/generate-type-registry/src -- <selection>`.

## Tests

`tests/` (xunit) also checks what `uses` writes (a used type pointed at and not described again, the used registration run first, a used registration's own uses followed) and its failures, the register-once guard, the declared description objects, and the defaults test's expectations. It generates describe-api's fixture's registration (`tools/describe-api/tests/Fixture/Fixture.api.toml`) and FenrirTypes' test package's (`packages/FenrirTypes/Tests/Package/TestPackage.api.toml`) and compares each with its committed header and source byte for byte, checks a second run rewrites nothing and a selection without `[registration]` writes nothing, and expects each failure's diagnostic: an unknown kind, element kind, role or category, an owning kind in a fixed-layout type, a data asset whose base is not described before it, a tagged union whose tag is no enum (or one not described before it), whose alternative's tag is none of its enumerators or whose default kind is none of its alternatives, an owning or unknown kind in an alternative, and a malformed `[registration]`. CTest runs them as `GenerateTypeRegistryTests` when tests are built; by hand, `dotnet test tools/generate-type-registry/tests`. They also check what it writes for a type visited by member (its visit function, its base first, its lists' and optionals' operations), what it writes for a tagged union (its tag, alternatives and default) and for a type holding one, and the role hooks each role calls. The FenrirTypes tests compile both registrations against their headers and exercise them through the registry (`packages/FenrirTypes/Tests/GeneratedFixture.cpp` and `PackageRegistration.cpp`). Both are also generated by `fenrir-generate-type-registry`, and the test package described by `fenrir-describe-api`, so regenerate them with those targets after changing a tool, the fixture or the test package's header.

# FenrirSkeleton

Skeleton poses as arrays, with no animation, renderer or physics (ADR-0028, ADR-0031, ADR-0033, ADR-0037, ADR-0041): skeleton instances and their reads in local, model and world space, the pose pipeline and its stages, pose modifiers through `PoseEdit`, bone attachments, the pose generation and the lazy skinning palette, the skinning source, and spawning. It depends on FenrirAssets, FenrirECS, FenrirScene, FenrirApp, FenrirMath and FenrirTime, links no library, and is built with `FENRIR_ENABLE_ASSETS`, with no option of its own. FenrirRenderer and FenrirPhysics link nothing from it: the renderer reaches poses only through FenrirAssets' `SkinningSource`.

## Install

`Skeletons::Install(App&)` returns the move-only `Skeletons` owner, the package's facade. It registers FenrirSkeleton's skinning source as the `SkinningSourceRegistration` app resource and adds the pose pipeline's systems: the frame pass in `PostUpdate` and the tick pass in `PreTick`. Without FenrirAssets installed, or with a skinning source already registered (a second install), it logs one error and returns an owner whose `IsValid()` is false, having added nothing. Destroying the owner removes the source and every scene's instances; the systems then do nothing.

## Skeleton instances

`SkeletonPose { AssetHandle<Skeleton> skeleton; PoseTiming timing = PoseTiming::Frame; }` is plain data on the skeleton entity, one per entity. The instance it names (base and final locals, model matrices, the cached palette) lives in a private scene resource.

- **Reconcile**, the pipeline's first step, makes an instance for a new component, rebuilds it at the rest pose when its handle or the asset's revision changes, and drops it when the entity or component is gone. `Ensure(scene, entity)` does that at once for one entity.
- **`GetPoseState`** is `Ready`, `Unavailable` (an empty or stale handle: every read empty, logged once each time it becomes so) or `Missing` (no instance yet, or none at all). On recovery the instance rebuilds.
- **Reads** are static, taking the scene and the skeleton entity: `FindBone` (by engine name), the spans `GetLocals`, `GetBaseLocals` and `GetModelMatrices`, per bone `GetLocal`, `GetModel`, `GetBaseLocal` and `GetBaseModel` (computed on first read and cached until the base pose changes), and `GetBoneWorldMatrix`, `GetWorldMatrix(entity) × M_model[bone]`. A span is valid until the end of the current system or the next change to the scene's instances.
- **`PoseKind`** is `Render` (the default) or `Simulation`, taken by `GetBaseLocals`, `GetBaseLocal`, `GetBaseModel` and `GetBoneWorldMatrix`. On a frame-posed skeleton both read the render pose. On a tick-posed one `Simulation` reads the last tick's simulation pose (below), and a world read applies the skeleton entity's world matrix as it is when read. No read changes meaning with the phase it runs in.
- **`EditBasePose(scene, entity)`** gives the base pose's locals to write and marks the instance pose-dirty, even if no value changes. Written before the pipeline, the change is this frame's; after it, the next frame's. It is refused (an empty span, logged once per call site) during `Modify` and `Late`, and during `Animate` on an instance of the other timing. On a tick-posed skeleton it gives the simulation pose, which the next tick evaluates from.
- **Three kinds of change stay apart:** a pose change dirties the model matrices and the palette; a move of the skeleton entity changes only world reads; an asset or revision change rebuilds the instance.
- **`GetPoseGeneration`** is advanced when finalisation changes the final pose and when the instance is rebuilt, from one counter per scene, so a recycled entity never repeats one. A move never advances it.
- **`GetPalette`**, main thread only, is `M_model × inverse bind` per bone, built on first read for the current generation and cached with it.

## The pose pipeline

One sequential `PostUpdate` system runs it on the active scene: reconcile, `Animate`, prepare (final pose from base pose), `Modify`, finalise (model matrices left, parents first), attach (bone attachments placed) and `Late`. Inactive scenes pause, and resume without catching up.

- **Stages:** `AddAnimate`, `AddModifier` and `AddLate` add work at an `int` order, ties in the order added, and return a `PoseStageHandle` that `Remove` takes outside the pipeline (inside it, `Remove` is refused with an error). FenrirSkeleton's own modifiers use constants: `ModifierOrder::Override` is 1000. Nothing is promised against other `PostUpdate` systems.
- **`Animate`** items get an `AnimateContext`: the pass's `Timing()` (`Frame`, or `Tick` in a tick pass), its `Step()` (`Time::deltaTime`, or `Time::tickRate`), and the `Ready` `Instances()` of that timing, the only ones they may write. Every item runs in the frame pass and in each tick pass.
- **`Modify`:** a modifier runs every frame, chooses its instances, and opens `PoseEdit edit = context.Edit(entity)`, valid only during that call and empty for an instance that is not `Ready`. It offers `Base()`, `Local(bone)`, `Model(bone)` and `Write(bone, Target)`.
- **`Target { space, trs, channels, weight }`** resolves when written: a `World` target through the inverse of the skeleton entity's world matrix (read at the instance's first edit of the frame, before any modifier may have moved it), a `Model` target through the inverse of the parent's current model matrix, then decomposed into TRS (shear dropped) and blended into the local by `weight` (clamped to [0, 1]) for the masked `Channels`: translation and scale lerp, rotation nlerps along the shortest arc. Writes compose in order; model matrices below a write are recomputed when read. A missing inverse skips the target, with a warning naming the entity and bone, at most once every 300 frames.
- **`Late`** items get a `LateContext` and read this frame's final poses; they may write ordinary ECS state, never a pose.
- **Cost:** an instance whose base pose is clean and that no modifier edited this frame or the last skips prepare and finalise, and keeps its generation.

## Tick-posed skeletons (ADR-0040)

`SkeletonPose::timing = PoseTiming::Tick` makes a skeleton's base pose evaluate once per fixed tick, at tick time, for bodies that follow its bones with no lag and the right velocity. Switching is a field edit, taking effect at the next pass's reconcile.

- **The tick pass** runs in `PreTick` of each fixed tick, on the active scene, only while it has a tick-posed skeleton: reconcile, `Animate` (the `Tick` pass, stepping by `Time::tickRate`, listing the tick-posed instances), then the base pose's model matrices. That is the **simulation pose**: the base pose at tick time, with no modifiers. The tick before it is kept beside it. Several ticks run the pass once each; a frame with no tick evaluates nothing.
- **Writes:** a base-pose write before a `PreTick` is seen by that tick, one in `Tick` by the next, one in `Update` by the next frame's first tick.
- **The frame pass:** a tick-posed instance skips `Animate`. Its base pose is the last two ticks' blended at `Time::accumulator / Time::tickRate`, read from FenrirTime (translation and scale lerp, rotation slerps, as physics interpolates bodies), then prepare, `Modify`, finalise, attach and `Late` give the **render pose**. Modifiers are render-only, and the palette and attachments use the render pose.
- **Seeding:** when the instance is built, and when it switches from `Frame` to `Tick`, both tick poses are its current base pose, so nothing jumps. Switching back runs frame `Animate` again, which resumes from where the tick clock stopped.
- **Bodies that follow bones go through glue**, not `BoneAttachment`: in `Tick`, glue computes `GetBoneWorldMatrix(scene, skeleton, bone, PoseKind::Simulation) × offset`, takes it into the body entity's parent space and writes the entity's `Transform`, and physics's `PostTick` moves the kinematic body there. Each tick gets its own target. Powered ragdolls read motor targets in `Tick` with `PoseKind::Simulation`.

## The pose override (ADR-0033, ADR-0038)

- **`PoseOverride`** is FenrirSkeleton's own modifier, added by `Install` at `ModifierOrder::Override` (1000): the first modifier, not the contract, so modifiers at higher orders, or added later at 1000, see its results. Each instance holds a persistent entry per bone, set with `SetOverride(scene, entity, bone, Target)`, read with `GetOverride` and removed with `ClearOverride` or `ClearOverrides`. Each frame it writes the entries in bone order, parents first, skipping bones with no entry, so a `World` target resolves through its parent's current model matrix, after any override of an ancestor. A bone with no entry keeps its animated local, and the bones below an overridden bone follow it. The last `SetOverride` on a bone wins, whoever made it.
- **Override weights:** one per bone, default 1, gameplay's. An entry is written at `clamp(Target.weight × overrideWeight[bone], 0, 1)` and skipped at 0. `SetOverrideWeight(scene, entity, bone, weight, OverrideScope::Bone | BoneSubtree)` writes the bone's value, or each bone's in its subtree (latest assignment wins, nothing multiplied); `GetOverrideWeight` reads it, and `ClearOverrideWeight` sets it back to 1. Weights survive every entry update and clear. There are no fades: game code ramps the weights.
- **Rebuilds:** entries and weights are both dropped when the instance is destroyed or rebuilt (a handle or asset revision change).
- The calls work on a `Ready` instance and do nothing on anything else.

**The ragdoll handover contract**, for the physics map's ragdoll spec: bone names, indices and parents (`SkeletonData`, `FindBone`) and the subtree query (`GetSubtree`); glue writes world targets through `SetOverride` in `Update`; gameplay sets override weights; base-pose reads (`GetBaseLocal`, `GetBaseModel`) never see overrides and are valid from `Animate` to the next `Animate`, so on frame-posed skeletons glue reads them a frame late; on tick-posed ones, glue reads them at tick time in `Tick` with `PoseKind::Simulation`. Overrides apply in `Modify` to the render pose, whatever the timing. Bones with no entry keep their animated locals, and unmapped children follow their nearest mapped ancestor because model matrices are built parents first. While bodies simulate, glue writes every mapped bone each frame; blending back, it writes the live poses or nothing (the held last pose); once the weight is 0 it clears its entries.

## Bone attachments (ADR-0037)

`BoneAttachment { Entity skeleton; BoneName bone; Transform offset; }` is plain data placing its entity at `GetBoneWorldMatrix(skeleton, bone) × offset` every frame, in the pipeline's attach step, under any ECS parent. The full bone transform is inherited.

- **`BoneName`** is a fixed 256-byte UTF-8 buffer holding at most 255 bytes. `Set(name, logger)` refuses a longer name (or one holding a zero byte) with an error and leaves the field unchanged: it never truncates, since a truncated name could match another bone. A buffer written raw with no terminator is malformed: `Get` gives nothing, and the attachment is `BoneNotFound`, never resolved as a partial name.
- **Resolution** is FenrirSkeleton's, cached per attached entity, never in the component: the bone index and what it was resolved against (the skeleton entity, the name, the instance's build). Any change resolves it again by engine name before the next placement; a name that did not resolve is tried again only when one of those changes.
- **Placement:** under the skeleton entity, the entity's local `Transform` is `M_model[bone] × offset`. Under any other parent it is the target world matrix taken through the inverse of the parent's world matrix and decomposed into TRS, so shear is dropped: under non-uniform scale with rotation, the placed world matrix can differ from the target.
- **Order:** an attachment comes after any attachment that is its skeleton entity or parent, or an ancestor of either, so a scope attached to a rifle attached to a hand, or a skeleton parented under an attached entity, is placed in one pass. Ties go by entity index. The order is cached and rebuilt when an attachment, its skeleton entity or the hierarchy above either changes. An attachment in a cycle (a skeleton parented under an entity attached to it) is `Unplaceable`; what depends on it is still placed.
- **`Skeletons::GetAttachmentState(scene, entity)`**: `Attached`, `SkeletonMissing` (the skeleton entity is dead or has no `SkeletonPose`), `SkeletonUnavailable`, `BoneNotFound`, `TransformMissing` or `Unplaceable` (a cycle, or a parent whose world matrix has no inverse), and `NotAttached` for an entity with no `BoneAttachment` or none placed yet. It is never a component field.
- **Failure:** the entity keeps its last `Transform`, the state says why, a warning is logged once per cause, and it recovers by itself. Attach makes no structural change.
- **Ownership:** while attached, FenrirSkeleton owns the entity's local `Transform`, and gameplay moves the object through `offset`; a direct write to the `Transform` is overwritten at the next attach.
- **`Skeletons::Detach(scene, entity, DetachMode, newParent = {})`:** `KeepLocal` removes the component only. `KeepWorld` reparents the entity under `newParent` (to the top of the scene when null) with the local `Transform` that keeps its world transform as it is now. It is transactional: it checks the new parent (alive, and not the entity or a descendant), that the parent's world matrix inverts and that the result is representable as TRS, and on any failure changes nothing and returns the failure. Detaching is structural, refused inside the pipeline.
- **Physics:** a dynamic body on an attached entity is unsupported, since attach runs in `PostUpdate` and overwrites what the physics step wrote. A kinematic body on an entity attached to a frame-posed skeleton lags a frame: the next tick reads a `Transform` placed after the previous frame's ticks. Tick-posed skeletons, with glue writing the body's `Transform` in `Tick`, remove the lag (ADR-0040).

## Spawning

`SpawnSkeletons(scene, model, spawned)` adds a `SkeletonPose` to each skeleton's owner (`Model::skeletonOwners`, an ordinary node or a synthetic owner) whose skeleton loaded, and `Ensure`s it. An owner that already has one keeps it, with a warning. `SpawnModel(scene, model, parent)` is `SpawnNodes` then `SpawnSkeletons`, for apps with no renderer. Then every ordinary node whose parent node is a bone gets a `BoneAttachment` to that bone, with its rest transform relative to the bone as the offset, so it follows the bone from the first frame. There is no socket concept: a named attachment point is such a node, and a sword hung on it is parented under its entity with no attachment of its own.

## The skinning source

FenrirSkeleton's `SkinningSource` answers the renderer per scene and entity: `GetPoseState`, `GetSkeleton`, `GetPoseGeneration`, `GetPalette`, `GetModelMatrices` and `SpawnSkeletons`, from the same reads. The renderer finds it with `app.TryGetResource<SkinningSourceRegistration>()`, whenever it needs it, so install order does not matter.

## C# (ADR-0039)

`Skeletons::ScriptingExtension()`, in `FenrirSkeletonScripting` (`Scripting/`, built with `FENRIR_ENABLE_SCRIPTING`), gives C# the `Fenrir.Skeleton` contract (`Managed/Fenrir.Skeleton/`): the `SkeletonPose`, `BoneAttachment`, `BoneName` (whose `Set` refuses a name over 255 bytes) and `Target` mirrors with their enums; `Skeletons` for the per-bone reads (an optional `PoseKind`), the copies into a caller's span (`ReadLocals`, `ReadBaseLocals`, `ReadModel`), base-pose writes, overrides and weights, `GetAttachmentState`, and `Detach` and a headless `SpawnModel`, both recorded through the change buffer and run when the calling system (or, from a stage system, the pass) returns; `SkeletonData` for the asset's bones by handle; and `PoseStages`. Bones are `int`, −1 for none, and nothing spans FenrirSkeleton's memory.

The extension declares the stages `Fenrir.Skeleton.Animate`, `.Modify` and `.Late`. When a script loads, each `(stage, order)` group of its `[StageSystem]`s is placed as **hosted work** through the App (`Skeletons::HostAnimate`, `HostModifier`, `HostLate`), after C++ work of an equal order whenever that was added, and one `HostPassEnd` item plays the groups' structural changes back when each pass returns. Inside `Animate`, `PoseStages.Timing` and `Step` name the pass (the tick passes included); inside `Modify`, `Skeletons.Edit(entity)` opens a `PoseEdit` whose edit token is good for that group's call only. Install FenrirSkeleton before Scripting, or the stages never run (logged once). The rules (`Scripting/src/SkeletonScriptingState.hpp`): an entity that is not a Ready skeleton entity, a bone out of range, a stale handle or a stage native outside its stage does nothing, returns `false`, 0, −1 or the default, and warns once per call site in a debug build.

## Tests

`FenrirSkeletonTests` (with `FENRIR_BUILD_TESTS`) is the spec's seam 8: instances, generations and the palette, the pipeline, modifiers, the pose override and ADR-0038's ragdoll handover with plain entities as bodies (`PoseOverride.cpp`), bone attachments (`Attachments.cpp`), tick-posed skeletons with a test glue placing a plain entity on the simulation bone (`TickPosed.cpp`), spawning and install, on skeletons and models built in code, driven by `App::RunFrame`. `PublicHeaders.cpp` fails the build if a header reaches the renderer, physics, a window or a graphics API, and configuring fails if FenrirRenderer or FenrirPhysics links the package. `FenrirSkeletonScriptingTests` (seam 7) drives the C# side through a fixture script: a C# `Modify` system between two C++ modifiers, a stale edit, a `Late` system reading this frame's bone, `PoseStages` in both passes, `Simulation` reads, the reads and copies against C++, attachments, `Detach` and `SpawnModel`; `FenrirSkeletonScriptingRulesTests` checks each native's rule and warning with no .NET.

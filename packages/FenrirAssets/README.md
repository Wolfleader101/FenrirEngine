# FenrirAssets

Plain CPU-side assets behind generational handles, owned by the app or a scene (ADR-0021): meshes, images, materials, shader containers, skeletons, clips, bone masks, instance lists, models and fonts (TrueType or OpenType bytes, which FenrirText reads), loaded from files or added from code. It has no GPU code; FenrirRenderer and the animation packages each turn its data into their own form. Its importers sit behind a private seam: cgltf reads glTF and GLB, ufbx reads FBX and OBJ (ADR-0031), stb_image reads PNG, JPEG and HDR, and meshoptimizer simplifies meshes into levels of detail (ADR-0057). Each is a submodule under `libs/`, built static and linked `PRIVATE`, so no public header names one.

`Assets::Install(App&, AssetsConfig)` returns the move-only owner of the `AssetStore`. The store's `Load<T>(path, owner)`, `Add<T>(data, owner)`, `Replace(handle, data)` and `Unload(handle)` are the whole interface, with, for data assets (game-defined structs in `.asset.json5` envelopes, ADR-0075), a named `Add<T>(data, owner, name)`, `Edit<T>(handle, action)`, `PathOf(handle)` and `Save<T>(handle)` or `Save<T>(handle, path)`, which writes the asset and its file's sub-assets back atomically, the same data as the same bytes with the file's comments kept, and with `UpdateImage(image, region, pixels)`, which writes a rectangle of an image in place, and `ImageUpdatesSince(image, revision)`, which names the rectangles written since a revision, so a holder of a copy (the renderer's texture of a glyph atlas) updates just them; every `Add` and `Replace` checks the data and refuses what is malformed with one logged error saying why.

Hot reload (ADR-0081): with `AssetsConfig::hotReload` on, its default, `Install` adds one sequential system at `SchedulePriority::PreUpdate` that looks at each file the store loaded (data asset envelopes, model files, images, `.cubemap` files, fonts and `.fshader` shader containers), every `reloadInterval` milliseconds (250), and reloads one that changed and stayed unchanged for `reloadDebounce` (400), between frames on the main thread. A data asset file is read whole into new instances, and an imported file is imported again through its importer; either is swapped in under the handles it already gave, each sub-asset under its own label, with revisions bumped, and `AssetStore::Reloaded()` lists this frame's swaps as `ReloadedAsset` records (asset path, kind, slot, and `Is(handle)`), cleared at the next poll. A reference the new file adds loads for every owner of the asset. A file that fails to read or import, or reads any value or imports any unit only in part, keeps everything it loaded and logs why once per change; a sub-asset the new file no longer has keeps its data, with one warning; a deleted file keeps its data with one warning and reloads when it comes back. A save to the asset's own file is no change to reload. A pointer `TryGet` gave before a reload no longer points at the asset.

`Assets::Move(root, from, to, registry, dryRun)` needs no running store: it moves or renames one file under the asset root, refusing a destination that exists, and rewrites every reference to it and to its sub-assets (`from#name`) across the root's `.json5` envelopes, the moved file's own included, finding them through the registry's `reference` fields and writing each changed file back from its own tree, so only those strings change. Its `MoveResult` lists each file changed and each left unscanned (one that does not parse, or names a type the registry lacks); a dry run writes nothing and lists the same. From a shell, `tools/move-asset` runs it (its README says how a game builds its own copy).

## Levels of detail

A mesh carries its levels of detail as `MeshData::lods`, a vector of `MeshLod { indices, error }`: each a coarser triangle list over the mesh's own vertex streams, with the greatest distance, in local units, by which it departs from full detail. Level 0 is the mesh's own `indices`, with error 0, and is not in the vector. The store refuses a level whose index count is not whole triangles, whose index reaches past the positions or whose error is not greater than the previous level's, and refuses levels on a mesh with more than one submesh.

`Load` takes no import options, so an app that wants levels makes them after loading and replaces the mesh:

```cpp
Fenrir::AssetHandle<Fenrir::Mesh> mesh = store.Load<Fenrir::Mesh>("rock.glb#Rock", owner).handle;
if (const Fenrir::MeshData* data = store.TryGet(mesh))
{
    store.Replace(mesh, Fenrir::GenerateLods(*data));
}
```

`GenerateLods(const MeshData&, const LodSettings&)` returns the mesh with its chain of levels. Each level aims at `LodSettings::ratio` (0.5) of the previous level's triangles, and the chain stops at `maxLevels` (4), when a level would start at or below `minTriangles` (32), or when simplifying saves less than a tenth of the triangles; a cube gets no levels. Where the mesh has normals or `uv0` they weigh in the simplifier's error (`meshopt_simplifyWithAttributes`), and a seam, a position several vertices share, may collapse along its length (meshoptimizer still moves a seam's two sides together, so no crack opens); a mesh with neither goes through `meshopt_simplify`. That is the default because a mesh of many small UV islands, such as a scanned rock, has a seam vertex every few triangles: with every seam vertex locked it stalls at a few hundred triangles, and free it goes on to a few dozen, which LightingDemo's asteroid ring measured as faster with no visible loss. `lockSeams` on locks every seam vertex where it is, so hard edges and UV islands stay exactly where they were, for a mesh whose seams must not move. Each level is simplified from the one before, and its `error` is the sum of each step's error (meshoptimizer's relative error times `meshopt_simplifyScale`), so it is in the mesh's units, bounds the level's departure from full detail and grows strictly. The full-detail indices and each level come back reordered for the GPU's vertex cache; streams, submeshes, bounds and skin are untouched, so a skinned mesh's levels share its skin. A mesh built in code gets its levels the same way before `Add`.

From C# (`Fenrir.Assets`, ADR-0029), a mesh's levels are made and read by handle, since C# never holds a `MeshData` (it adds a mesh as spans, `Assets.AddMesh`): `Assets.GenerateLods(mesh, settings)` replaces the mesh's data with `GenerateLods`' result, `settings` a `LodSettings` mirror whose `new` is C++'s default (`Ratio`, `MaxLevels`, `MinTriangles`, `LockSeams`), and `Assets.GenerateLods(mesh)` uses that default; `Assets.AddMeshLod(mesh, indices, error)` appends a level built by hand under the store's rules (a refused level is logged and changes nothing), and `Assets.ReplaceMesh` drops every level; `Assets.GetMeshLodErrors(mesh, errors)` gives how many levels the mesh has and copies each level's error, and `Assets.GetMeshLodIndices(mesh, level, indices)` a level's triangles, level 0 the mesh's own, as many as fit. `MeshLod` itself has no C# mirror: a level is read as its error and its indices.
